## Vòng đời cluster và version skew {#cluster-lifecycle-and-version-skew}

Theo curriculum CKA hiện hành, **Troubleshooting chiếm 30%** trọng số, còn **Cluster Architecture, Installation & Configuration chiếm 25%**. Chương này gom hai nhóm đó lại: vòng đời cluster (upgrade, backup etcd, node maintenance), RBAC, scheduling và các kỹ năng chẩn đoán sự cố mà một DevOps/SRE phải dùng hàng ngày.

Cluster Kubernetes không phải "cài xong là hết". Bạn phải trả lời được những câu hỏi như: nâng cấp cluster lên minor mới thế nào cho an toàn? Được phép để kubelet cũ hơn API server bao nhiêu version? Backup etcd ra sao và restore khi thảm họa xảy ra? Khi node cần bảo trì thì đưa node ra khỏi vòng phục vụ thế nào? Đây đều là nội dung thi CKA và cũng là công việc vận hành thực tế.

### Version skew policy {#version-skew-policy}

Kubernetes không yêu cầu mọi component chạy cùng version, nhưng giới hạn khoảng cách giữa chúng. Quy tắc hiện hành (áp dụng từ v1.28 trở đi):

- **kubelet** không được mới hơn kube-apiserver, và được phép cũ hơn tối đa **3 minor version**. Ví dụ apiserver v1.33 thì kubelet v1.33, v1.32, v1.31, v1.30 đều hợp lệ; kubelet v1.29 hoặc v1.34 là không hợp lệ.
- **kube-controller-manager, kube-scheduler, cloud-controller-manager** không được mới hơn apiserver; được phép cũ hơn **1 minor** (để phục vụ live upgrade trên cluster HA).
- **kubectl** được phép lệch **±1 minor** so với apiserver. Đây là lý do bạn có thể dùng kubectl v1.33 với cluster v1.32 mà vẫn ổn.
- Trong cluster HA, các instance **kube-apiserver** mới nhất và cũ nhất chỉ được lệch 1 minor.
- **kube-proxy** không được mới hơn apiserver, được phép cũ hơn 3 minor và lệch ±3 minor so với kubelet trên cùng node.
- Dự án Kubernetes chỉ duy trì release branch cho **3 minor gần nhất** (mỗi minor có khoảng 1 năm patch support).

Có một cảnh báo thực tế rất quan trọng: nếu kubelet bị bỏ quên quá lâu (3 minor sau apiserver), bạn **buộc phải upgrade kubelet trước khi upgrade control plane**. Vì vậy hãy đặt lịch upgrade đều đặn mỗi minor thay vì nhảy nhiều minor một lúc.

Một hệ quả nữa của version skew: **upgrade phải đi từng minor một**, không nhảy cóc. kube-apiserver không cho phép bỏ qua minor khi nâng cấp; nếu đang ở v1.31 và muốn lên v1.33, bạn phải lên v1.32 trước rồi mới lên v1.33.

### Quy trình upgrade với kubeadm {#kubeadm-upgrade-workflow}

Thứ tự bắt buộc khi nâng cấp cluster kubeadm: **control plane node đầu tiên → các control plane node còn lại → worker node**, và trên mỗi node là **drain → nâng kubeadm/kubelet → uncordon**. Bảng sau tóm tắt các bước:

| Bước | Node | Việc cần làm |
|---|---|---|
| 1 | Control plane đầu tiên | Nâng package `kubeadm`, chạy `kubeadm upgrade plan` và `kubeadm upgrade apply` |
| 2 | Control plane đầu tiên | Drain node, nâng `kubelet` + `kubectl`, restart kubelet, uncordon |
| 3 | Các control plane khác | Drain, nâng `kubeadm`, chạy `kubeadm upgrade node`, nâng kubelet, uncordon |
| 4 | Từng worker node | Drain, nâng `kubeadm` + `kubelet`, chạy `kubeadm upgrade node`, restart kubelet, uncordon |
| 5 | Sau cùng | Upgrade CNI/addon (Cilium, Calico...) và kiểm tra workload |

Dưới đây là chuỗi lệnh đầy đủ cho **control plane node đầu tiên** (ví dụ nâng v1.32 lên v1.33 trên Ubuntu):

```bash
# 0. Trước khi làm bất cứ điều gì: đọc release notes và backup etcd (xem phần sau)
etcdctl snapshot save /var/backups/etcd-truoc-upgrade.db   # chạy trên control plane

# 1. Nâng package kubeadm (tạm bỏ hold để apt cho phép nâng version)
sudo apt-mark unhold kubeadm
sudo apt-get update && sudo apt-get install -y kubeadm='1.33.*'
sudo apt-mark hold kubeadm
kubeadm version

# 2. Kiểm tra kế hoạch nâng cấp (cần internet để tra bản patch mới nhất)
sudo kubeadm upgrade plan

# 3. Nâng control plane; lệnh này cũng nâng etcd static pod nếu dùng stacked etcd
sudo kubeadm upgrade apply v1.33.1

# 4. Drain node trước khi thay binary kubelet
kubectl drain ch05-control-plane --ignore-daemonsets

# 5. Nâng kubelet và kubectl
sudo apt-mark unhold kubelet kubectl
sudo apt-get install -y kubelet='1.33.*' kubectl='1.33.*'
sudo apt-mark hold kubelet kubectl
sudo systemctl daemon-reload && sudo systemctl restart kubelet

# 6. Đưa node trở lại phục vụ
kubectl uncordon ch05-control-plane
```

Với **các control plane node còn lại** và **worker node**, thay bước 2–3 bằng:

```bash
# Trên control plane khác (sau khi node đầu tiên đã xong)
sudo kubeadm upgrade node

# Trên worker node (không cần kubeadm upgrade plan/apply)
kubectl drain ch05-worker --ignore-daemonsets
sudo apt-mark unhold kubeadm && sudo apt-get install -y kubeadm='1.33.*'
sudo kubeadm upgrade node
sudo apt-mark unhold kubelet && sudo apt-get install -y kubelet='1.33.*'
sudo systemctl daemon-reload && sudo systemctl restart kubelet
kubectl uncordon ch05-worker
```

### Upgrade worker node và lưu ý thực tế {#upgrade-notes}

Một vài điểm cần nhớ để không "tự bắn vào chân" khi upgrade:

- **Backup etcd trước khi upgrade** là bắt buộc trong production. Nếu upgrade hỏng và control plane không lên được, snapshot là đường lui duy nhất.
- **Trước khi upgrade một minor**, hãy nâng lên patch mới nhất của minor hiện tại, sau đó nâng lên patch mới nhất của minor đích. Tránh nhảy trực tiếp giữa các patch cũ.
- **Kiểm tra API bị deprecated** (ví dụ bằng `kubectl api-resources` hoặc `kube-no-trouble`) vì minor mới có thể bỏ API cũ (`extensions/v1beta1` ngày trước, `flowcontrol.apiserver.k8s.io/v1beta2`...).
- kubeadm **ghi backup** các manifest cũ vào `/etc/kubernetes/tmp/kubeadm-backup-*`; nếu upgrade lỗi giữa chừng, có thể chạy lại `kubeadm upgrade apply --force` (idempotent) để hoàn tất.
- kubeadm **không có lệnh rollback**. Muốn quay lui, bạn phải restore etcd từ snapshot, hoặc hạ package và chạy lại kubeadm với version cũ (không được khuyến nghị).
- Từ v1.28, addon (CoreDNS, kube-proxy) chỉ được upgrade **sau khi tất cả control plane node** đã nâng xong; vì vậy đừng hoảng nếu thấy CoreDNS vẫn ở version cũ giữa chừng.
- Sau khi upgrade xong, kiểm tra lại: `kubectl get nodes`, `kubectl -n kube-system get pods`, `kubectl get --raw='/readyz?verbose'`.
- Với **external etcd** (etcd chạy ngoài control plane), kubeadm không nâng etcd giúp bạn; phải nâng từng member theo hướng dẫn riêng của etcd.

## Node maintenance: cordon, drain, uncordon {#node-maintenance}

Mỗi khi bảo trì node (nâng cấp kernel, thay ổ đĩa, upgrade kubelet...), bạn phải đưa node ra khỏi vòng phục vụ một cách "lịch sự" để không làm sập workload. Ba lệnh liên quan là `cordon`, `drain`, `uncordon`.

### Cordon và uncordon {#cordon-and-uncordon}

`kubectl cordon` đánh dấu node **unschedulable**: không pod mới nào được schedule lên node, nhưng pod đang chạy vẫn tiếp tục chạy.

```bash
kubectl cordon ch05-worker
kubectl get nodes
# NAME                STATUS                     ROLES    AGE   VERSION
# ch05-worker         Ready,SchedulingDisabled   <none>   10m   v1.33.1
```

Bên dưới, cordon đặt `spec.unschedulable: true` và thêm taint `node.kubernetes.io/unschedulable:NoSchedule`. Muốn đưa node trở lại:

```bash
kubectl uncordon ch05-worker
```

### Drain và eviction {#drain-and-eviction}

`kubectl drain` = cordon + **evict toàn bộ pod** ra khỏi node. Eviction được thực hiện qua Eviction API nên **tôn trọng PodDisruptionBudget**. Các flag quan trọng:

| Flag | Ý nghĩa |
|---|---|
| `--ignore-daemonsets` | Bỏ qua pod do DaemonSet quản lý (drain không xóa và cũng không báo lỗi) |
| `--delete-emptydir-data` | Cho phép xóa pod đang dùng `emptyDir` (chấp nhận mất dữ liệu tạm) |
| `--force` | Xóa cả pod "mồ côi" không do controller nào quản lý |
| `--grace-period=<giây>` | Thời gian chờ container dừng êm trước khi kill |
| `--timeout=120s` | Thời gian tối đa cho toàn bộ thao tác drain |
| `--disable-eviction` | Bỏ qua Eviction API, xóa pod trực tiếp (phá luôn PDB — chỉ dùng khi khẩn cấp và có `--force`) |

Ví dụ thực tế:

```bash
# Drain một worker có DaemonSet (kindnet) và pod dùng emptyDir
kubectl drain ch05-worker --ignore-daemonsets --delete-emptydir-data

# Node sẽ ở trạng thái SchedulingDisabled cho tới khi bạn uncordon
kubectl get pods -o wide    # các pod đã được tái tạo trên node khác
kubectl uncordon ch05-worker
```

Nếu gặp lỗi khi drain, thường là một trong các trường hợp sau:

- `cannot delete DaemonSet-managed Pods` — thêm `--ignore-daemonsets`.
- `cannot delete Pods with local storage` — thêm `--delete-emptydir-data` nếu chấp nhận mất dữ liệu emptyDir.
- `cannot delete Pods not managed by ReplicationController, ...` — pod tạo trực tiếp (bare pod), phải thêm `--force` hoặc chuyển nó vào controller.
- `Cannot evict pod as it would violate the pod's disruption budget` — PDB đang chặn; xem phần tiếp theo.

### PodDisruptionBudget {#poddisruptionbudget}

PodDisruptionBudget (PDB) là object `policy/v1` đảm bảo số pod tối thiểu luôn sẵn sàng trong các thao tác **voluntary disruption** như drain node:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-pdb
spec:
  minAvailable: 2        # luôn giữ ít nhất 2 pod Ready
  selector:
    matchLabels:
      app: web
```

Khi drain, nếu việc evict sẽ khiến số pod Ready tụt dưới `minAvailable` (hoặc vượt quá `maxUnavailable`), Eviction API trả lỗi và `kubectl drain` sẽ thoát với thông báo vi phạm PDB. Trong tình huống khẩn cấp (node hỏng phần cứng), bạn có thể dùng `--disable-eviction --force`, nhưng hãy hiểu rõ đánh đổi: pod bị xóa thẳng, không đảm bảo availability.

## etcd: backup, restore và quorum {#etcd-backup-restore-quorum}

etcd là "trái tim" của cluster: toàn bộ trạng thái Kubernetes (pod, service, secret, RBAC, CRD...) nằm trong etcd. Mất etcd mà không có backup nghĩa là mất cluster. Đây là chủ đề xuất hiện thường xuyên trong đề CKA.

### Kiến trúc etcd trong cluster kubeadm {#etcd-topology}

kubeadm hỗ trợ hai kiểu triển khai:

- **Stacked etcd**: etcd chạy như **static pod** ngay trên từng control plane node. Đây là kiểu mặc định, phổ biến nhất.
- **External etcd**: etcd chạy trên máy riêng (hoặc cluster etcd quản lý độc lập), control plane kết nối tới.

Với stacked etcd, bạn tìm mọi thứ cần cho backup trong manifest static pod:

```bash
kubectl -n kube-system get pod etcd-ch05-control-plane -o wide
kubectl -n kube-system describe pod etcd-ch05-control-plane | grep -E "cert-file|key-file|trusted-ca|data-dir|listen-client"
```

Các đường dẫn chuẩn trên cluster kubeadm:

| Thành phần | Đường dẫn |
|---|---|
| CA certificate | `/etc/kubernetes/pki/etcd/ca.crt` |
| Server certificate / key | `/etc/kubernetes/pki/etcd/server.crt`, `server.key` |
| Peer certificate / key | `/etc/kubernetes/pki/etcd/peer.crt`, `peer.key` |
| Data directory | `/var/lib/etcd` |
| Endpoint | `https://127.0.0.1:2379` |

### Snapshot với etcdctl {#etcd-snapshot}

etcd hỗ trợ **built-in snapshot**: tạo bản sao nhất quán (point-in-time) của toàn bộ keyspace ngay khi etcd đang chạy. Lệnh cơ bản:

```bash
ETCDCTL_API=3 etcdctl snapshot save /var/backups/etcd-snapshot.db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key
```

Giải thích nhanh các tham số:

- `--endpoints`: địa chỉ client của etcd member; đứng trên control plane thì dùng `https://127.0.0.1:2379`.
- `--cacert`, `--cert`, `--key`: etcd dùng mTLS, thiếu cert sẽ gặp lỗi `context deadline exceeded` hoặc lỗi TLS.
- `ETCDCTL_API=3`: etcd 3.4+ mặc định là API v3 nên biến này không còn bắt buộc, nhưng nhiều tài liệu vẫn ghi để tường minh. Trên etcd 3.6+, API v2 đã bị bỏ hoàn toàn.

Kiểm tra snapshot (nên làm ngay sau khi backup):

```bash
# etcd 3.5: etcdctl snapshot status vẫn dùng được; từ 3.6 hãy dùng etcdutl
etcdutl snapshot status /var/backups/etcd-snapshot.db --write-out=table
```

Kết quả cho biết `hash`, `revision`, `total keys`, `total size` — hãy ghi lại revision để đối chiếu khi restore. Vài lưu ý vận hành:

- Snapshot chứa **secret và toàn bộ dữ liệu nhạy cảm**: phải mã hóa file backup và lưu **ngoài cluster** (S3, object storage, máy backup riêng).
- Nên chạy backup định kỳ (ví dụ mỗi 6 giờ), giữ nhiều bản theo rotation, và **thử restore định kỳ** trên môi trường lab.
- Không copy trực tiếp thư mục `/var/lib/etcd` khi etcd đang chạy; hãy dùng `snapshot save`.

### Restore snapshot {#etcd-restore}

Nguyên tắc quan trọng nhất: **restore ra một data directory MỚI**, sau đó trỏ etcd static pod sang thư mục đó. Quy trình trên cluster kubeadm (stacked etcd):

```bash
# 1. Restore snapshot ra thư mục mới (etcd 3.5 dùng etcdctl, 3.6+ dùng etcdutl)
etcdctl snapshot restore /var/backups/etcd-snapshot.db \
  --data-dir=/var/lib/etcd-restore \
  --name=ch05-control-plane \
  --initial-cluster=ch05-control-plane=https://127.0.0.1:2380 \
  --initial-advertise-peer-urls=https://127.0.0.1:2380 \
  --initial-cluster-token=etcd-cluster-restore-1

# 2. Dừng etcd + kube-apiserver (chuyển manifest ra khỏi /etc/kubernetes/manifests)
sudo mv /etc/kubernetes/manifests/etcd.yaml /etc/kubernetes/manifests/kube-apiserver.yaml /root/

# 3. Sửa hostPath của volume etcd-data trong etcd.yaml sang /var/lib/etcd-restore
#    (giữ nguyên --data-dir=/var/lib/etcd trong command của container),
#    rồi chuyển các manifest trở lại để kubelet tạo lại static pod
sudo mv /root/etcd.yaml /root/kube-apiserver.yaml /etc/kubernetes/manifests/
```

Hai cái bẫy kinh điển khiến restore "thành công mà cluster vẫn rỗng":

- Đổi `--data-dir` trong command của container nhưng **không đổi `hostPath`** — container vẫn tạo database mới trong volume cũ, dữ liệu restore nằm chơ vơ trên host.
- Restore **đè trực tiếp** lên `/var/lib/etcd` khi etcd còn giữ file — dễ hỏng cả dữ liệu cũ lẫn mới.

Sau khi etcd lên lại, kiểm tra bằng `kubectl get --raw='/readyz?verbose'` và `etcdctl endpoint health` (dùng cert như phần snapshot).

Với cluster **HA nhiều etcd member**, đừng restore một member cũ vào giữa cụm đang khỏe — member đó sẽ không khớp lịch sử với quorum. Cách đúng là dừng toàn bộ control plane, restore từ cùng một snapshot cho tất cả member (mỗi member một data dir mới, `--name` và peer URL đúng của nó), rồi mới start lại như một cluster mới.

### Quorum và chiến lược backup định kỳ {#etcd-quorum-and-scheduled-backup}

etcd dùng thuật toán **Raft** nên cần **quorum** (đa số) để ghi dữ liệu và bầu leader:

| Số member | Quorum | Chịu được lỗi |
|---|---|---|
| 1 | 1 | 0 |
| 3 | 2 | 1 |
| 5 | 3 | 2 |
| 4 | 3 | 1 (không hơn cluster 3 member) |
| 6 | 4 | 2 (không hơn cluster 5 member) |

Hai kết luận thực tế:

- **Số member lẻ luôn tốt hơn số chẵn** vì chẵn không tăng khả năng chịu lỗi mà lại tăng chi phí replication. 3 hoặc 5 member là lựa chọn thông dụng.
- Mất quorum (ví dụ cụm 3 member chết 2) thì etcd **ngừng phục vụ ghi**, kube-apiserver không hoạt động được dù các process còn sống. Cách xử lý là khôi phục member chết, hoặc restore snapshot và dựng lại cụm.

Kiểm tra trạng thái và quorum: `etcdctl member list` và `etcdctl endpoint status --write-out=table` (dùng cert như phần snapshot) sẽ cho biết leader, term, db size và raft index.

Backup định kỳ: trên production, bạn có thể chạy snapshot bằng CronJob ngay trong cluster. Lưu ý phải có `hostNetwork: true`, nodeSelector control-plane và tolerations vì control plane thường có taint:

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: etcd-snapshot
  namespace: kube-system
spec:
  schedule: "0 */6 * * *"                  # 4 lần/ngày
  jobTemplate:
    spec:
      template:
        spec:
          hostNetwork: true                # để gọi được 127.0.0.1:2379
          nodeSelector:
            node-role.kubernetes.io/control-plane: ""
          tolerations:
            - key: node-role.kubernetes.io/control-plane
              effect: NoSchedule
          restartPolicy: OnFailure
          containers:
            - name: etcd-snapshot
              image: registry.k8s.io/etcd:3.5.16-0
              command: ["etcdctl"]         # image etcd không có shell nên khai báo command trực tiếp
              args:
                - --endpoints=https://127.0.0.1:2379
                - --cacert=/etc/kubernetes/pki/etcd/ca.crt
                - --cert=/etc/kubernetes/pki/etcd/server.crt
                - --key=/etc/kubernetes/pki/etcd/server.key
                - snapshot
                - save
                - /backup/etcd-snapshot.db
              volumeMounts:
                - { name: etcd-certs, mountPath: /etc/kubernetes/pki/etcd, readOnly: true }
                - { name: backup, mountPath: /backup }
          volumes:
            - name: etcd-certs
              hostPath: { path: /etc/kubernetes/pki/etcd, type: Directory }
            - name: backup
              hostPath: { path: /var/backups/etcd, type: DirectoryOrCreate }
```

CronJob chỉ tạo file trên node, nên cần thêm bước đồng bộ ra ngoài cluster và rotation để không đầy đĩa. Snapshot chứa secret nên hãy coi file backup là tài sản nhạy cảm: mã hóa, phân quyền chặt, định kỳ thử restore.

## RBAC chi tiết {#rbac-in-depth}

RBAC (Role-Based Access Control) là cơ chế phân quyền chính của Kubernetes, thuộc API group `rbac.authorization.k8s.io/v1`. Mọi request tới kube-apiserver đều đi qua **authentication → authorization → admission**; RBAC nằm ở bước authorization. Trong đề CKA, bạn sẽ gặp các task kiểu "tạo Role/ClusterRole, bind cho user/service account và verify quyền". Trong CKS, RBAC còn quan trọng hơn nữa vì phải đảm bảo **least privilege** — chương 7 (Cluster Hardening) sẽ đào sâu phần này.

### Bốn API object của RBAC {#rbac-api-objects}

| Object | Phạm vi | Dùng cho |
|---|---|---|
| **Role** | 1 namespace | Cấp quyền trong namespace |
| **ClusterRole** | Toàn cluster | Cấp quyền cluster-scoped (nodes, PV...) hoặc template quyền dùng lại ở nhiều namespace |
| **RoleBinding** | 1 namespace | Gán Role/ClusterRole cho subject, hiệu lực trong namespace |
| **ClusterRoleBinding** | Toàn cluster | Gán ClusterRole cho subject, hiệu lực mọi namespace + cluster-scoped |

Một Role đọc pod trong namespace `team-a`:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: team-a
rules:
  - apiGroups: [""]                 # "" là core API group (pod, service, configmap...)
    resources: ["pods", "pods/log"]
    verbs: ["get", "list", "watch"]
```

RoleBinding gán Role đó cho user và service account:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: team-a
subjects:
  - kind: User
    name: dev-user
    apiGroup: rbac.authorization.k8s.io
  - kind: ServiceAccount
    name: reader-sa
    namespace: team-a
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

Tạo nhanh bằng imperative command (rất hữu ích trong phòng thi):

```bash
kubectl -n team-a create role pod-reader --verb=get,list,watch --resource=pods
kubectl -n team-a create rolebinding read-pods --role=pod-reader --user=dev-user
kubectl create clusterrole node-reader --verb=get,list,watch --resource=nodes
kubectl create clusterrolebinding dev-read-nodes --clusterrole=node-reader --user=dev-user
kubectl auth can-i list pods -n team-a --as=dev-user
kubectl auth can-i list nodes --as=dev-user
```

### verbs, resources và nonResourceURLs {#rbac-rules}

Mỗi rule gồm ba trục chính: `apiGroups`, `resources`, `verbs`, có thể thêm `resourceNames` và `nonResourceURLs`.

| Trục | Ví dụ | Ghi chú |
|---|---|---|
| `apiGroups` | `""`, `apps`, `batch`, `rbac.authorization.k8s.io` | Một số resource nằm ở nhiều group (deployment: `apps`) |
| `resources` | `pods`, `deployments`, `nodes`, `pods/log` | Subresource tách bằng `/`: `pods/log`, `pods/exec`, `pods/portforward` |
| `verbs` | `get`, `list`, `watch`, `create`, `update`, `patch`, `delete`, `deletecollection` | `get` không bao gồm `list`; `list` không bao gồm `get` |
| `resourceNames` | `["my-configmap"]` | Giới hạn theo tên object; chỉ hợp lệ với một số verb |
| `nonResourceURLs` | `/healthz`, `/metrics` | Chỉ dùng trong ClusterRole (URL không thuộc namespace) |

Rule cluster-scoped chỉ cho đọc node có dạng `resources: ["nodes"]` trong một **ClusterRole** (không dùng Role vì node không thuộc namespace nào).

Một số mẹo thực chiến:

- `kubectl auth can-i --list --as=system:serviceaccount:team-a:reader-sa -n team-a` liệt kê mọi quyền của một subject — dùng để audit.
- Tránh wildcard (`resources: ["*"]`, `verbs: ["*"]`) trong production; đó là dấu hiệu phân quyền quá rộng.
- Kubernetes có sẵn các ClusterRole mặc định: `view`, `edit`, `admin`, `cluster-admin`; `cluster-admin` tương đương `*` trên mọi thứ nên chỉ dành cho break-glass account.

### RoleBinding với ClusterRole và ClusterRoleBinding {#rbac-bindings}

Đây là chỗ dễ nhầm nhất khi học RBAC:

- **RoleBinding có thể trỏ tới ClusterRole**. Khi đó, quyền của ClusterRole chỉ có hiệu lực **trong namespace của RoleBinding**. Đây là cách tái sử dụng một ClusterRole (ví dụ `view`) cho nhiều namespace mà không cần copy Role.
- **ClusterRoleBinding chỉ trỏ tới ClusterRole** và cấp quyền **toàn cluster** (mọi namespace + cluster-scoped resource). Không thể bind một Role trong ClusterRoleBinding.
- Khi một subject có nhiều binding (Role + ClusterRole, nhiều namespace...), quyền được **hợp (union)** lại, không có quy tắc "cấm" nào trong RBAC — muốn chặn phải dùng admission controller (chương 9).

Ví dụ RoleBinding trỏ ClusterRole:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: view-team-a
  namespace: team-a
subjects:
  - kind: Group
    name: developers
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole       # vẫn có thể là ClusterRole!
  name: view
  apiGroup: rbac.authorization.k8s.io
```

Phân biệt subject:

| kind | Ý nghĩa | Ví dụ |
|---|---|---|
| `User` | User bên ngoài (thường qua x509 cert hoặc OIDC) | `CN=dev-user` trong cert → name `dev-user` |
| `Group` | Group bên ngoài (O trong cert, claim trong OIDC) | `O=developers` → group `developers` |
| `ServiceAccount` | Tài khoản cho workload | `system:serviceaccount:team-a:reader-sa` |

Các group đặc biệt cần biết: `system:masters` (thường được bind `cluster-admin`, là group của admin cert), `system:authenticated`, `system:unauthenticated`, `system:serviceaccounts` (mọi service account).

### Aggregated ClusterRole {#aggregated-clusterrole}

ClusterRole có thể được **tổng hợp** từ các ClusterRole khác nhờ `aggregationRule`. Kubernetes sẽ tự động điền `rules` từ mọi ClusterRole khớp label selector — cơ chế này được dùng cho các role mặc định như `admin`/`edit`/`view`:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: monitoring-endpoints
aggregationRule:
  clusterRoleSelectors:
    - matchLabels:
        rbac.example.com/aggregate-to-monitoring: "true"
rules: []   # controller tự điền; đừng sửa tay
```

Khi bạn tạo một ClusterRole mới có label `rbac.example.com/aggregate-to-monitoring: "true"`, rule của nó ngay lập tức xuất hiện trong `monitoring-endpoints`. Đây là pattern mở rộng quyền cho operator/CRD mà không phải sửa role gốc.

### ServiceAccount và bound token {#serviceaccount-and-token}

ServiceAccount (SA) là danh tính cho **process chạy trong pod**. Mọi namespace đều có SA `default`. Khi pod được tạo mà không chỉ định `serviceAccountName`, nó dùng SA `default` của namespace.

```bash
kubectl -n team-a create serviceaccount reader-sa
kubectl -n team-a get serviceaccount
kubectl -n team-a describe serviceaccount reader-sa
```

Những điểm cần nhớ ở version hiện hành:

- Từ Kubernetes v1.24, tạo SA **không còn tự động sinh Secret token vĩnh viễn**. Thay vào đó, kubelet xin **bound token** qua TokenRequest API, có thời hạn và gắn với pod/SA cụ thể.
- Token được mount vào pod qua projected volume tại `/var/run/secrets/kubernetes.io/serviceaccount/token` (JWT), kèm `ca.crt` và `namespace`.
- `kubectl create token reader-sa -n team-a` tạo bound token có thời hạn mặc định **1 giờ** (có thể chỉnh `--duration`, bị giới hạn bởi cấu hình apiserver), dùng để test API nhanh.
- Bound token bị vô hiệu khi SA bị xóa hoặc khi pod gắn với nó bị xóa — khác với legacy token Secret không thể thu hồi.
- Pod nào không cần gọi API server thì nên tắt mount token: đặt `automountServiceAccountToken: false` ở pod spec hoặc ở SA. Đây là một khuyến nghị hardening quan trọng (sẽ gặp lại ở chương 7 và 9).

### Least privilege và kiểm tra quyền {#rbac-least-privilege}

Nguyên tắc least privilege trong RBAC được cụ thể hóa như sau:

1. **Bắt đầu từ quyền tối thiểu**, thêm dần khi có yêu cầu rõ ràng; không cấp sẵn `edit`/`admin` cho cả team.
2. **Ưu tiên namespace-scoped**: Role + RoleBinding thay vì ClusterRole + ClusterRoleBinding. Chỉ dùng ClusterRoleBinding khi thật sự cần quyền toàn cluster (đọc node, PV...).
3. **Không dùng wildcard** cho resource/verb. Nếu cần `pods/exec`, hãy cấp đúng `pods/exec` chứ không cấp `*`.
4. **Không dùng `cluster-admin` cho CI/CD pipeline**. Pipeline chỉ cần apply manifest → cấp Role theo namespace; nếu cần tạo namespace, cần ClusterRole riêng cho `namespaces` (namespace là cluster-scoped).
5. **Mỗi workload một SA riêng**, không dùng chung `default`; xóa/tắt `automountServiceAccountToken` khi không cần.
6. **Audit định kỳ**: tìm binding trỏ tới `cluster-admin`, subject lạ, quyền thừa.

Một số lệnh hay dùng để kiểm tra:

```bash
# Liệt kê quyền hiện có của subject
kubectl auth can-i --list --as=system:serviceaccount:team-a:reader-sa -n team-a

# Kiểm tra một quyền cụ thể
kubectl auth can-i delete secrets -n team-a --as=dev-user

# Ai đang có quyền gì (cần quyền đọc rbac)
kubectl get clusterrolebindings -o wide
kubectl get rolebindings -A -o wide

# Xem mình là ai (từ v1.27)
kubectl auth whoami
```

Liên hệ với **chương 7 (Cluster Hardening)**: ngoài việc tạo đúng Role/Binding, chương sau còn nói về cách giới hạn service account mặc định, tắt automount token, siết quyền cho các SA hệ thống, và kết hợp với audit log để phát hiện abuse. Ở chương này, hãy nắm chắc "bộ tứ" Role/ClusterRole/RoleBinding/ClusterRoleBinding và cách verify bằng `kubectl auth can-i`.

## Kiểm tra cấu hình component theo CIS Benchmark {#cis-benchmark-checks}

CIS Kubernetes Benchmark là bộ khuyến nghị cấu hình bảo mật cho cluster, được xây dựng dựa trên kinh nghiệm vận hành thực tế. CKA chỉ yêu cầu bạn biết **cách kiểm tra**; CKS (chương 6) sẽ yêu cầu **sửa cấu hình theo khuyến nghị**. Trước hết hãy biết mỗi component được cấu hình ở đâu:

| Component | Nơi cấu hình trên cluster kubeadm | Check quan trọng của CIS |
|---|---|---|
| kube-apiserver | `/etc/kubernetes/manifests/kube-apiserver.yaml` | `--anonymous-auth=false`, `--authorization-mode=Node,RBAC`, `--profiling=false`, audit log |
| kubelet | `/var/lib/kubelet/config.yaml` + `/var/lib/kubelet/kubeadm-flags.env` | `authentication.anonymous.enabled=false`, `authorization.mode=Webhook`, `readOnlyPort=0`, `protectKernelDefaults=true`, rotate certificate |
| etcd | `/etc/kubernetes/manifests/etcd.yaml` | `--client-cert-auth=true`, `--peer-client-cert-auth=true`, TLS cert/key đúng, `--auto-tls=false` |
| kube-scheduler | `/etc/kubernetes/manifests/kube-scheduler.yaml` | `--profiling=false`, bind address an toàn |
| kube-controller-manager | `/etc/kubernetes/manifests/kube-controller-manager.yaml` | `--profiling=false`, `--use-service-account-credentials=true` |

Vì control plane chạy dưới dạng static pod, cách kiểm tra nhanh là đọc command line của pod:

```bash
# Xem flag của kube-apiserver đang chạy
kubectl -n kube-system get pod kube-apiserver-ch05-control-plane \
  -o jsonpath='{.spec.containers[0].command}' | tr ',' '\n'

# Trên node, đọc trực tiếp manifest
sudo grep -E "anonymous-auth|authorization-mode|profiling" /etc/kubernetes/manifests/kube-apiserver.yaml
```

Với kubelet, hãy nhớ nó **không phải pod**: cấu hình nằm trong `/var/lib/kubelet/config.yaml` (KubeletConfiguration do kubeadm sinh ra, gồm `authentication.anonymous.enabled`, `authorization.mode`, `evictionHard`...) và các flag command line trong `/var/lib/kubelet/kubeadm-flags.env`. Chỉ cần `sudo cat` hai file này để đối chiếu với CIS:

Công cụ phổ biến nhất để chạy checklist CIS là **kube-bench** của Aqua Security. Nó tự phát hiện version cluster, chạy các check và in bảng PASS/FAIL/WARN:

```bash
# Chạy kube-bench như một Job trên control plane node
kubectl apply -f https://raw.githubusercontent.com/aquasecurity/kube-bench/main/job.yaml
kubectl logs job/kube-bench | head -n 60
```

kube-bench cần đọc được file cấu hình của host nên job chính thức mount `/var/lib/kubelet`, `/etc/kubernetes`, `/etc/systemd` và chạy với `hostPID: true`. Trong môi trường thật, bạn nên chạy kube-bench định kỳ (CI/CD hoặc scan tự động) thay vì chỉ chạy tay một lần.

Một điểm quan trọng về tư duy: **CIS Benchmark là baseline, không phải chân lý tuyệt đối**. Vài check có thể không phù hợp (ví dụ yêu cầu flag mà kubeadm đã đặt mặc định an toàn, hoặc check dành cho phiên bản cũ). Hãy đọc kỹ lý do của từng check trước khi "sửa cho xanh", vì sửa sai cấu hình control plane có thể làm cluster không lên được.

## Scheduling nâng cao {#scheduling-advanced}

kube-scheduler quyết định pod chạy trên node nào qua hai pha: **filter** (loại node không phù hợp) và **score** (chọn node điểm cao nhất). Phần này điểm lại các cơ chế điều khiển scheduling mà bạn cần cho cả thi và công việc: nodeSelector, affinity, taint/toleration, topology spread và priority.

### nodeName, nodeSelector và node affinity {#node-selector-and-affinity}

**nodeName** là cách "nhảy cóc" qua scheduler: pod được gán thẳng vào node, không qua filter/score.

```yaml
spec:
  nodeName: ch05-worker2   # bỏ qua scheduler; thường chỉ dùng cho debug
```

**nodeSelector** là cách đơn giản nhất để ràng buộc theo label (chỉ hỗ trợ equality):

```bash
kubectl label node ch05-worker2 disktype=ssd
kubectl run pod-ssd --image=nginx:1.27 --restart=Never \
  --overrides='{"spec":{"nodeSelector":{"disktype":"ssd"}}}'
```

**node affinity** mạnh hơn nodeSelector: hỗ trợ nhiều operator (`In`, `NotIn`, `Exists`, `DoesNotExist`, `Gt`, `Lt`), có mức **required** (bắt buộc) và **preferred** (ưu tiên):

```yaml
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: disktype
                operator: In
                values: ["ssd"]
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 100
          preference:
            matchExpressions:
              - key: topology.kubernetes.io/zone
                operator: In
                values: ["zone-a"]
```

Hai điểm cần hiểu đúng:

- `IgnoredDuringExecution` nghĩa là nếu label node thay đổi **sau khi pod đã chạy**, pod **không bị đuổi**. Muốn đuổi phải có cơ chế khác (taint + NoExecute).
- "Node anti-affinity" chỉ là cách viết node affinity với `NotIn`/`DoesNotExist`; còn `podAntiAffinity` là cơ chế khác, ràng buộc giữa các pod (ví dụ không cho 2 replica cùng `app=web` nằm trên cùng node, dùng `topologyKey: kubernetes.io/hostname`).

### Taint và toleration {#taints-and-tolerations}

Taint là "vết bẩn" gắn lên node để **đẩy pod ra**; toleration gắn lên pod để "chịu được" taint đó. Có ba effect:

| Effect | Hành vi |
|---|---|
| `NoSchedule` | Pod mới không có toleration sẽ không được schedule lên node; pod đang chạy không bị đuổi |
| `PreferNoSchedule` | Scheduler hạn chế nhưng không cấm (soft) |
| `NoExecute` | Pod không tolerate **bị đuổi khỏi node** (sau `tolerationSeconds` nếu có) |

```bash
# Gắn taint và bỏ taint (chú ý dấu - ở cuối để gỡ)
kubectl taint node ch05-worker dedicated=gpu:NoSchedule
kubectl taint node ch05-worker dedicated=gpu:NoSchedule-
```

Toleration tương ứng:

```yaml
spec:
  tolerations:
    - key: dedicated
      operator: Equal
      value: gpu
      effect: NoSchedule
```

Toleration không "hút" pod vào node — nó chỉ mở khóa. Muốn pod **chỉ** chạy trên node đó, hãy kết hợp toleration với nodeSelector/node affinity.

Vài loại taint có sẵn bạn sẽ luôn gặp:

- `node.kubernetes.io/not-ready:NoExecute` và `node.kubernetes.io/unreachable:NoExecute` — node lifecycle controller gắn khi node không sẵn sàng, pod mặc định có `tolerationSeconds: 300` trước khi bị evict.
- `node.kubernetes.io/disk-pressure`, `node.kubernetes.io/memory-pressure`, `node.kubernetes.io/pid-pressure` — kubelet gắn khi node bị áp lực tài nguyên.
- `node.kubernetes.io/unschedulable:NoSchedule` — chính là taint mà `kubectl cordon` tạo ra.
- Taint `node-role.kubernetes.io/control-plane:NoSchedule` (kubeadm) — vì sao workload thường không chạy trên control plane.

### Topology spread constraints {#topology-spread-constraints}

Topology spread constraints chia pod theo một **topology key** (zone, hostname...) sao cho độ lệch số pod giữa các domain không vượt `maxSkew`:

```yaml
spec:
  topologySpreadConstraints:
    - maxSkew: 1
      topologyKey: kubernetes.io/hostname
      whenUnsatisfiable: DoNotSchedule     # hoặc ScheduleAnyway
      labelSelector:
        matchLabels:
          app: web
```

- `maxSkew: 1` + `topologyKey: kubernetes.io/hostname`: các node không chênh nhau quá 1 pod cùng label.
- `whenUnsatisfiable: DoNotSchedule`: hard constraint (pod sẽ Pending nếu không thỏa); `ScheduleAnyway`: soft, scheduler chỉ ưu tiên cân bằng.
- Đây là công cụ chuẩn để chạy 3 replica trải đều trên 3 zone, kèm `nodeAffinity` giới hạn zone nếu cần.

### PriorityClass và preemption {#priorityclass-and-preemption}

Pod có **PriorityClass** sẽ được scheduler ưu tiên; khi một pod priority cao không đủ chỗ, scheduler có thể **preempt** (đuổi) pod priority thấp hơn trên node để lấy chỗ — preemption không tôn trọng PodDisruptionBudget:

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: high-priority
value: 1000000
globalDefault: false
```

Gắn vào pod bằng `spec.priorityClassName: high-priority`. Kubernetes tự tạo sẵn hai PriorityClass hệ thống rất cao cho control plane/addon: `system-cluster-critical` và `system-node-critical`. Lưu ý: pod bị preempt vẫn là gián đoạn dịch vụ, nên hãy dùng cẩn thận và tránh lạm dụng.

## Phương pháp troubleshooting {#troubleshooting-methodology}

Troubleshooting chiếm **30% điểm CKA**, nhiều nhất trong các domain. Bí quyết không phải là nhớ hết lỗi, mà là có một **quy trình kiểm tra có hệ thống** và biết đọc đúng chỗ.

### Trình tự kiểm tra {#troubleshooting-order}

Khi nhận báo lỗi, tôi đi theo thứ tự "từ ngoài vào trong, từ trên xuống dưới":

1. **kubectl có kết nối được API server không?** — `kubectl cluster-info`, `kubectl get nodes`. Nếu timeout, vấn đề nằm ở kubeconfig, certificate hết hạn, control plane hoặc etcd chứ chưa phải workload.
2. **Node có Ready không?** — `kubectl get nodes -o wide`, chú ý cột STATUS và VERSION. Node NotReady kéo theo nhiều lỗi workload "từ trên trời rơi xuống".
3. **Control plane và addon có khỏe không?** — `kubectl -n kube-system get pods -o wide` (apiserver, etcd, controller-manager, scheduler, coredns, kube-proxy, CNI).
4. **Workload đang ở trạng thái gì?** — `kubectl get pods -o wide`, `kubectl describe pod`, `kubectl logs`, `kubectl get events --sort-by=.lastTimestamp`.
5. **Service/network có đúng không?** — `kubectl get svc`, `kubectl get endpointslices`, thử DNS và curl từ trong pod.
6. **Tầng host/container runtime** (khi cần) — `systemctl status kubelet`, `journalctl -u kubelet`, `systemctl status containerd`, `crictl ps -a`.

Một lời khuyên nhỏ nhưng hiệu quả: **đọc Events trước khi đọc log**. 80% lỗi scheduling, image, probe, volume đều đã được ghi thẳng vào Events của pod/node/namespace.

### Static pod và systemd unit của kubelet {#static-pods-and-kubelet-systemd}

Static pod là pod do **kubelet trực tiếp quản lý** từ các file YAML đặt trong `/etc/kubernetes/manifests` (đường dẫn này nằm trong `staticPodPath` của kubelet config). Toàn bộ control plane của cluster kubeadm chạy theo cách này.

Đặc điểm cần nhớ:

- Thêm/sửa/xóa file trong thư mục manifest → kubelet tự tạo lại pod tương ứng; **không cần** `kubectl apply`.
- kubelet mirror static pod lên API server dưới dạng **mirror pod**, tên có hậu tố node (ví dụ `etcd-ch05-control-plane`); xóa mirror pod bằng kubectl không xóa file manifest, kubelet sẽ tạo lại.
- Khi apiserver không truy cập được, static pod **vẫn có thể chạy** và kubelet vẫn restart chúng — đây là lý do bạn có thể dùng node để gỡ rối control plane.

kubelet chạy dưới dạng **systemd unit**, không phải pod:

```bash
systemctl status kubelet                 # trạng thái tổng quan
journalctl -u kubelet -f                 # theo dõi log trực tiếp
journalctl -u kubelet --since "10 min ago" | tail -n 50
sudo systemctl daemon-reload && sudo systemctl restart kubelet   # sau khi sửa config/unit
```

Các file quan trọng của kubelet trên cluster kubeadm:

| File | Nội dung |
|---|---|
| `/var/lib/kubelet/config.yaml` | KubeletConfiguration (auth, cgroup driver, eviction...) |
| `/var/lib/kubelet/kubeadm-flags.env` | Flag command line do kubeadm sinh |
| `/etc/kubernetes/kubelet.conf` | kubeconfig để kubelet xác thực với apiserver |
| `/etc/kubernetes/manifests/` | Manifest của static pod control plane |
| `/var/log/pods/`, `/var/log/containers/` | Log container trên node |

### Logs control plane {#control-plane-logs}

Bình thường bạn đọc log control plane qua kubectl:

```bash
kubectl -n kube-system logs kube-apiserver-ch05-control-plane
kubectl -n kube-system logs etcd-ch05-control-plane --tail=100
kubectl -n kube-system logs kube-controller-manager-ch05-control-plane
kubectl -n kube-system logs kube-scheduler-ch05-control-plane
```

Khi API server chết, kubectl không dùng được nữa; hãy lên node và dùng container runtime:

```bash
# Trên node: liệt kê container đang chạy (kể cả pod lỗi)
sudo crictl ps -a
sudo crictl logs <container-id>

# Với cluster kind: node là container Docker, nên từ máy host có thể lấy log
docker exec ch05-control-plane crictl ps -a
docker exec ch05-control-plane crictl logs <container-id>
docker exec ch05-control-plane journalctl -u kubelet --no-pager | tail -n 50
```

Với cluster dựng bằng kubeadm, log kubelet cũng là nguồn tin quan trọng vì nó ghi lại lý do static pod không start (thiếu image, sai manifest, lỗi mount...).

### Bảng lệnh chẩn đoán theo triệu chứng {#diagnostic-commands}

| Triệu chứng | Kiểm tra nhanh | Bước tiếp theo |
|---|---|---|
| `kubectl` không kết nối được cluster | `kubectl config current-context`, `openssl s_client -connect <apiserver>:6443` | Kiểm tra cert/kubeconfig, apiserver static pod, etcd, firewall |
| Node NotReady | `kubectl describe node <node>`, `systemctl status kubelet` | Xem Conditions, log kubelet, runtime, CNI |
| Node DiskPressure | `kubectl describe node`, `df -h`, `sudo crictl images` | Dọn image/container cũ, tăng dung lượng, dọn log |
| Node MemoryPressure | `kubectl describe node`, `free -h`, `kubectl top pods` | Tìm pod ăn RAM, chỉnh request/limit, thêm node |
| Pod Pending | `kubectl describe pod`, `kubectl get events --sort-by=.lastTimestamp` | Đọc message của scheduler: thiếu CPU/RAM, taint, affinity, PVC, quota |
| Pod CrashLoopBackOff | `kubectl logs <pod> --previous`, `kubectl describe pod` | Xem exit code, command/args, config/secret, probe |
| Pod ImagePullBackOff | `kubectl describe pod` (Events), `kubectl get secret` | Kiểm tra tên/tag image, registry private, imagePullSecrets, network |
| Pod OOMKilled | `kubectl describe pod` (Last State), `kubectl top pod` | Tăng memory limit, sửa memory leak, chỉnh QoS |
| Service không kết nối được | `kubectl get svc`, `kubectl get endpointslices`, `kubectl describe svc` | Kiểm tra selector, targetPort, readiness, kube-proxy/CNI |
| DNS trong pod lỗi | `kubectl exec <pod> -- nslookup kubernetes.default` | Kiểm tra CoreDNS, NetworkPolicy, resolv.conf |
| `kubectl top` lỗi | `kubectl get apiservice v1beta1.metrics.k8s.io` | Kiểm tra metric-server pod, flag `--kubelet-insecure-tls` |
| Cụm etcd chậm/quorum | `etcdctl endpoint status --write-out=table`, `etcdctl endpoint health` | Kiểm tra disk I/O, latency mạng, số member, defrag |
| Cert sắp hết hạn | `kubeadm certs check-expiration` | `kubeadm certs renew all`, restart static pod |
| Drain treo | `kubectl get pdb -A`, `kubectl describe pdb <name>` | Xử lý PDB, evict thủ công hoặc `--disable-eviction` có cân nhắc |

### metric-server và resource monitoring {#metrics-server-and-monitoring}

`kubectl top` không đọc dữ liệu từ kubelet trực tiếp mà đi qua **metrics API** do **metric-server** phục vụ (đăng ký qua aggregated API `v1beta1.metrics.k8s.io`). HPA cũng lấy số liệu từ đây.

```bash
kubectl top nodes
kubectl top pods -A --sort-by=memory
kubectl get apiservice v1beta1.metrics.k8s.io    # phải Available=True
kubectl -n kube-system logs deploy/metrics-server
```

Trên cluster kind, kubelet dùng serving certificate tự ký nên metric-server mặc định không xác thực được; đây là lỗi "kinh điển" của mọi lab:

```bash
# Lỗi: error: Metrics API not available / unable to fully collect metrics
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml
kubectl -n kube-system patch deployment metrics-server --type=json \
  -p '[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]'
kubectl -n kube-system rollout status deploy/metrics-server
kubectl top nodes
```

Ngoài `kubectl top`, bạn có thể xem mức tài nguyên đã cấp phát trên node bằng `kubectl describe node` (mục Allocated resources) và đối chiếu với Capacity/Allocatable — kỹ năng rất hữu ích khi điều tra pod Pending do thiếu tài nguyên.

## Troubleshooting node {#node-troubleshooting}

### Node NotReady {#node-notready}

Node chuyển NotReady khi kubelet không còn gửi heartbeat hoặc điều kiện Ready = False. Quy trình kiểm tra của tôi:

1. `kubectl describe node <node>` — đọc Conditions (`Ready`, `MemoryPressure`, `DiskPressure`, `PIDPressure`) và Events gần nhất.
2. `kubectl get node <node> -o wide` — xem version kubelet và runtime để phát hiện lệch version.
3. Lên node: `systemctl status kubelet` và `journalctl -u kubelet --since "10 min ago"`.
4. Kiểm tra container runtime: `systemctl status containerd`, `crictl ps`; runtime chết thì kubelet cũng NotReady.
5. Kiểm tra CNI: `ls /etc/cni/net.d/`, log của pod CNI (nếu CNI chưa ready, một số kubelet version vẫn Ready nhưng pod không có network).
6. Kiểm tra tài nguyên: hết disk (`df -h`), hết inode (`df -i`), cgroup, swap bật ngoài mong muốn.
7. Kiểm tra đồng hồ hệ thống (`timedatectl`) — lệch giờ làm TLS/cert fail hàng loạt.
8. Nếu kubelet không start được: đọc kỹ log, kiểm tra `/etc/kubernetes/kubelet.conf`, certificate.

Các nguyên nhân thường gặp trong thực tế: kubelet bị stop/không start sau reboot; certificate kubelet hết hạn; disk đầy khiến kubelet không ghi được; apiserver quá tải khiến heartbeat fail; node mất mạng tới control plane; container runtime bị treo.

Lưu ý về **node lease**: từ v1.14, heartbeat của node dùng object `Lease` trong namespace `kube-node-lease` (`kubectl -n kube-node-lease get lease`). Nếu bạn từng thấy node NotReady sau khi `kubectl get leases` lỗi, hãy kiểm tra quyền của node và tình trạng etcd.

### DiskPressure và MemoryPressure {#node-pressure}

kubelet liên tục giám sát tài nguyên và gắn taint/condition khi vượt ngưỡng **eviction** (mặc định hard eviction: `memory.available<100Mi`, `nodefs.available<10%`, `imagefs.available<15%`...). Khi đó:

- Node hiển thị `MemoryPressure`/`DiskPressure: True`, kubelet gắn taint tương ứng và **evict pod** theo thứ tự QoS: BestEffort → Burstable vượt request → Guaranteed.
- Pod bị evict có STATUS `Failed` với reason `Evicted`; `kubectl describe pod` hiển thị lý do.
- Hệ quả dây chuyền: pod bị đuổi → deployment tạo pod mới → pod mới Pending/không schedule được → dịch vụ suy giảm.

Điều tra nhanh:

```bash
kubectl describe node ch05-worker | grep -A5 -E "Conditions|Eviction"
kubectl get pods -A --field-selector status.phase=Failed
kubectl get events -A --field-selector reason=Evicted --sort-by=.lastTimestamp
```

Trên node:

```bash
df -h                          # nodefs
du -sh /var/lib/containerd /var/log   # chỗ ăn disk thường là image, container log
sudo crictl rmi --prune        # dọn image không dùng (cẩn thận: sẽ pull lại khi cần)
journalctl -u kubelet | grep -i -E "evict|pressure" | tail -n 30
```

Cách xử lý căn cơ: đặt request/limit đúng cho workload, giới hạn log container (`containerLogMaxSize`), dọn image định kỳ, tách phân vùng cho `/var/lib/containerd`, và mở rộng node trước khi chạm ngưỡng.

## Troubleshooting workload {#workload-troubleshooting}

### Pod Pending {#pod-pending}

Pod Pending nghĩa là **chưa được gán vào node nào** (khác với pod đang chạy nhưng lỗi). Hãy đọc message trong Events — scheduler luôn nói lý do:

```bash
kubectl describe pod <pod> | tail -n 20
kubectl get events --field-selector involvedObject.name=<pod> --sort-by=.lastTimestamp
```

Các message thường gặp:

| Message | Nguyên nhân | Cách xử lý |
|---|---|---|
| `Insufficient cpu` / `Insufficient memory` | Node không đủ tài nguyên theo `requests` | Giảm request, thêm node, hoặc xóa pod thừa |
| `node(s) had untolerated taint` | Node có taint (control-plane, dedicated...) | Thêm toleration hoặc bỏ taint |
| `node(s) didn't match node selector/affinity` | Label không khớp | Sửa label/affinity |
| `pod has unbound immediate PersistentVolumeClaims` | PVC chưa bind | Kiểm tra StorageClass, PV, provisioner |
| `exceeded quota` | ResourceQuota của namespace | Tăng quota hoặc giảm request |
| `too many pods` | Chạm giới hạn pod của node | Thêm node/giảm replica |
| `0/N nodes are available` | Tổng hợp mọi lý do | Đọc kỹ phần liệt kê trong message |

### CrashLoopBackOff {#crashloopbackoff}

Container start lên rồi **thoát lặp đi lặp lại**; kubelet tăng dần thời gian chờ (backoff 10s, 20s, 40s... tối đa 5 phút) — trạng thái hiển thị `CrashLoopBackOff`. Quy trình chẩn đoán:

```bash
kubectl get pod <pod>                       # xem RESTARTS
kubectl describe pod <pod> | grep -A5 "Last State"
kubectl logs <pod> --previous               # log của lần chạy trước khi crash
kubectl get pod <pod> -o jsonpath='{.spec.containers[0].command}{"\n"}{.spec.containers[0].args}'
```

Các nguyên nhân phổ biến:

- **command/args sai** — ghi đè ENTRYPOINT/CMD của image bằng một lệnh không tồn tại hoặc thoát ngay (ví dụ `args: ["exit", "1"]`). Đây là lỗi bạn sẽ tự tạo trong lab.
- **Thiếu config** — app require ConfigMap/Secret/env mà chưa có; log thường ghi rõ file không tồn tại.
- **Lỗi kết nối** — app không kết nối được database, DNS sai, quyền network bị NetworkPolicy chặn.
- **Probe giết sớm** — liveness probe timeout thấp hơn thời gian khởi động → container bị restart liên tục (xem phần dưới).
- **OOMKilled** — xem exit code 137.

Cách đọc exit code: `0` là thoát bình thường (app thoát xong nhưng không phải job), `1` lỗi ứng dụng, `137` bị SIGKILL (OOM hoặc kill), `143` SIGTERM (thường do liveness probe).

### ImagePullBackOff {#imagepullbackoff}

`ErrImagePull` là trạng thái tạm khi kéo image thất bại lần đầu; kubelet thử lại và chuyển sang `ImagePullBackOff` khi tiếp tục thất bại. Kiểm tra:

```bash
kubectl describe pod <pod> | grep -A3 "Failed"
# Failed to pull image "nginx:1.27-khong-ton-tai": ... not found
```

Checklist:

1. Tên/tag image đúng chưa (lỗi gõ, tag `latest` bị xóa...)? — thử `crictl pull` trên node hoặc `docker pull` trên máy local.
2. Registry private cần `imagePullSecrets`? — tạo secret `regcred` và khai báo `spec.imagePullSecrets: [{name: regcred}]` trong pod spec.
3. Node có ra được internet/registry không? — kiểm tra proxy, firewall, NetworkPolicy (nếu registry nằm trong cluster).
4. Registry rate limit (Docker Hub)? — dùng registry mirror hoặc private registry.

### OOMKilled và lỗi probe {#oomkilled-and-probe-failures}

**OOMKilled**: container bị kernel kill vì vượt memory limit. Dấu hiệu:

```bash
kubectl describe pod <pod> | grep -A3 "Last State"
# Last State: Terminated
#   Reason: OOMKilled
#   Exit Code: 137
```

Cách xử lý: tăng `resources.limits.memory` nếu limit quá chặt; sửa memory leak nếu app tăng RAM vô hạn; chú ý **limit < request là cấu hình vô lệ**. Nhớ rằng nếu container vượt **request** nhưng chưa vượt limit, nó có thể bị **evict** khi node MemoryPressure — chứ không phải OOMKilled.

**Lỗi probe** có ba loại với hệ quả khác nhau:

| Probe | Thất bại nghĩa là | Hậu quả |
|---|---|---|
| `livenessProbe` | Container "chết" về mặt logic | Bị restart → có thể vào CrashLoopBackOff |
| `readinessProbe` | Chưa sẵn sàng nhận traffic | Bị rút khỏi EndpointSlice → service không route tới |
| `startupProbe` | App chưa khởi động xong | Các probe khác tạm hoãn; thất bại mãi → kill |

Dấu hiệu trong Events: `Liveness probe failed: ...`, `Readiness probe failed: ...`. Các lỗi thường gặp: sai port, sai path (`/healthz` vs `/health`), `initialDelaySeconds` quá ngắn, `timeoutSeconds` quá thấp, exec probe chạy lệnh không tồn tại trong image (nhất là image distroless không có shell).

## DNS và service connectivity {#dns-and-service-connectivity}

### CoreDNS {#coredns}

Cluster cài DNS addon (mặc định là **CoreDNS**) để pod phân giải tên service. Trong namespace `kube-system` bạn sẽ thấy:

- Deployment `coredns` (thường 2 replica) và Service `kube-dns` (ClusterIP, ví dụ `10.96.0.10`).
- ConfigMap `coredns` chứa file `Corefile`.

```bash
kubectl -n kube-system get deploy,svc,pods -l k8s-app=kube-dns
kubectl -n kube-system get configmap coredns -o yaml
kubectl -n kube-system logs -l k8s-app=kube-dns --tail=50
```

Một pod khi hỏi DNS sẽ dùng tên dạng `<service>.<namespace>.svc.cluster.local`; `/etc/resolv.conf` trong pod trỏ nameserver về ClusterIP của `kube-dns` với `search` domain và `ndots:5`.

```bash
# Tạo pod debug và kiểm tra DNS
kubectl run netdebug --image=busybox:1.36 --command -- sleep 3600
kubectl exec netdebug -- cat /etc/resolv.conf
kubectl exec netdebug -- nslookup kubernetes.default
kubectl exec netdebug -- nslookup web.default.svc.cluster.local
```

Checklist khi DNS lỗi:

1. Pod `coredns` có Running/Ready không? Nếu CrashLoopBackOff: xem log (thường do ConfigMap sai hoặc không có quyền).
2. Service `kube-dns` có EndpointSlice không? CoreDNS chết mà không có replica → DNS toàn cluster tê liệt.
3. Pod có NetworkPolicy chặn UDP/TCP 53 không? — kiểm tra policy trong namespace.
4. Node có đang bị lỗi CNI không? — CoreDNS chạy trên node lỗi sẽ không phục vụ được.
5. `ndots` và search domain có bị thiếu trong resolv.conf? — trường hợp hiếm nhưng hay gặp khi chỉnh `dnsPolicy`/`dnsConfig`.

### Service, EndpointSlice và CNI {#service-endpointslices-cni}

Service chỉ là abstraction; đường đi thật sự là: **Service → EndpointSlice → pod IP**, do kube-proxy (iptables/IPVS/nftables) lập trình trên mỗi node. Khi service không kết nối được, hãy kiểm tra theo thứ tự:

```bash
kubectl get svc web-svc -o wide
kubectl describe svc web-svc
kubectl get endpointslices -l kubernetes.io/service-name=web-svc -o wide
kubectl get pod -l app=web -o wide     # pod có Ready chưa?
```

Ba lỗi phổ biến nhất:

1. **Selector không khớp** — service không tìm thấy pod nào → EndpointSlice rỗng (`<none>`).
   ```bash
   # Sửa selector cho đúng
   kubectl patch svc web-svc -p '{"spec":{"selector":{"app":"web"}}}'
   ```
2. **Pod chưa Ready** — readiness probe fail → pod bị loại khỏi EndpointSlice; service vẫn có IP nhưng không route tới.
3. **targetPort sai** — service port 80 nhưng targetPort trỏ 8080 trong khi app nghe 80 → connection refused.

Ngoài ra, nếu EndpointSlice cũng bình thường mà vẫn không kết nối được, khả năng cao là **CNI/kube-proxy**:

```bash
kubectl -n kube-system get pods -l k8s-app=kube-proxy -o wide
kubectl -n kube-system logs <kube-proxy-pod>
kubectl -n kube-system get pods -l k8s-app=kindnet   # CNI của kind
# Trên node
sudo ls -l /etc/cni/net.d/
```

Một điểm về version: `Endpoints` (core/v1) đã bị **deprecated từ v1.33**; API mới là `discovery.k8s.io/v1 EndpointSlice`. Trong đề thi hiện hành, hãy dùng `kubectl get endpointslices` và `kubectl get endpoints` vẫn hoạt động trên các bản cũ, nhưng tư duy "EndpointSlice là nguồn sự thật" sẽ đúng dài hạn.

## Lab thực hành {#hands-on-lab}

Lab này dùng **kind** để dựng cluster 3 node (1 control plane + 2 worker) trên máy local, luyện toàn bộ kỹ năng của chương: cordon/drain, mô phỏng upgrade, snapshot etcd (kèm restore), RBAC cho service account và user giả, scheduling, và các tình huống troubleshooting kinh điển.

**Môi trường cần có:**

- Docker (Docker Desktop hoặc Docker Engine) đang chạy.
- `kind` (v0.24 trở lên), `kubectl` (v1.33), `openssl`.
- Kubernetes **v1.33** trên kind; thời gian làm lab khoảng 45–60 phút.

### Bước 0: Dựng cluster kind 3 node {#lab-setup}

```bash
# Kiểm tra version công cụ trước khi bắt đầu
kind version
kubectl version --client

# Cluster 1 control plane + 2 worker
cat <<'EOF' > kind-ch05.yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
name: ch05
nodes:
  - role: control-plane
  - role: worker
  - role: worker
EOF

kind create cluster --config kind-ch05.yaml

# Verify: 3 node Ready và control plane/addon khỏe
kubectl get nodes -o wide
kubectl -n kube-system get pods -o wide
```

Trong output, bạn sẽ thấy `ch05-control-plane`, `ch05-worker`, `ch05-worker2` cùng các pod hệ thống: `etcd`, `kube-apiserver`, `kube-controller-manager`, `kube-scheduler`, 2 `coredns`, `kindnet` và `kube-proxy`.

### Bước 1: Cordon và drain node {#lab-drain}

```bash
# Tạo workload để thấy pod được evict/tái tạo
kubectl create deployment web --image=nginx:1.27
kubectl scale deployment web --replicas=4
kubectl wait --for=condition=available deployment/web --timeout=120s
kubectl get pods -o wide

# Đưa worker khỏi vòng schedule
kubectl cordon ch05-worker
kubectl get nodes

# Drain: evict pod (DaemonSet kindnet bị bỏ qua, emptyDir được phép xóa)
kubectl drain ch05-worker --ignore-daemonsets --delete-emptydir-data

# Verify: pod cũ biến mất, pod mới chạy trên node khác; node không nhận pod mới
kubectl get pods -o wide
kubectl get node ch05-worker -o jsonpath='{.spec.unschedulable}{"\n"}'

# Trả node về phục vụ
kubectl uncordon ch05-worker
```

### Bước 2: Mô phỏng upgrade cluster {#lab-upgrade-drill}

Trên kind, "upgrade" thực chất là tạo cluster mới với node image version mới, nhưng các bước kiểm tra và lệnh kubeadm thì giống hệt cluster thật. Hãy chạy để quen tay:

```bash
# Xem version của từng thành phần (chú ý cột KUBELET)
kubectl get nodes -o custom-columns='NAME:.metadata.name,KUBELET:.status.nodeInfo.kubeletVersion,RUNTIME:.status.nodeInfo.containerRuntimeVersion'
docker exec ch05-control-plane kubeadm version -o short

# Kế hoạch upgrade (cần internet; nếu môi trường offline, bỏ qua bước này)
docker exec ch05-control-plane kubeadm upgrade plan || true

# Nơi kubeadm upgrade sẽ thay đổi image control plane
docker exec ch05-control-plane ls -l /etc/kubernetes/manifests/
```

Với cluster thật (VM/kubeadm), ghi nhớ thứ tự: **nâng kubeadm package → `kubeadm upgrade plan` → `kubeadm upgrade apply` (control plane đầu tiên) → drain + nâng kubelet/kubectl → `kubeadm upgrade node` (các node còn lại)**. Nếu có VM dựng bằng kubeadm, hãy làm thử toàn bộ chuỗi lệnh ở phần lý thuyết.

### Bước 3: Backup etcd bằng snapshot {#lab-etcd-snapshot}

etcd chạy như static pod trong node control plane. Cách đúng kiểu "từ ngoài node" là dùng `docker exec` vào node rồi `crictl exec` vào container etcd:

```bash
# Lấy container ID của etcd, đặt sẵn bộ option dùng lại cho các lệnh sau
ETCD_ID=$(docker exec ch05-control-plane crictl ps -q --name etcd)
ETCD_OPTS="--endpoints=https://127.0.0.1:2379 \
--cacert=/etc/kubernetes/pki/etcd/ca.crt \
--cert=/etc/kubernetes/pki/etcd/server.crt \
--key=/etc/kubernetes/pki/etcd/server.key"

# Tạo snapshot (ghi vào /var/lib/etcd - chính là hostPath trên node kind)
docker exec ch05-control-plane crictl exec "$ETCD_ID" etcdctl $ETCD_OPTS \
  snapshot save /var/lib/etcd/truoc-upgrade.db

# Verify: file tồn tại trên node, status có revision và số key
docker exec ch05-control-plane ls -lh /var/lib/etcd/truoc-upgrade.db
docker exec ch05-control-plane crictl exec "$ETCD_ID" etcdctl $ETCD_OPTS \
  snapshot status /var/lib/etcd/truoc-upgrade.db --write-out=table

# Copy snapshot ra máy host để lưu trữ ngoài cluster
docker cp ch05-control-plane:/var/lib/etcd/truoc-upgrade.db ./truoc-upgrade.db
```

Cách khác tiện hơn khi bạn chỉ có kubectl: `kubectl -n kube-system exec etcd-ch05-control-plane -- etcdctl <ETCD_OPTS> snapshot save /var/lib/etcd/truoc-upgrade.db`. Trong output `snapshot status`, hãy ghi lại `revision` và `total keys` — đó là bằng chứng snapshot hợp lệ.

### Bước 4: Restore snapshot (bài tập mở rộng) {#lab-etcd-restore}

Các bước dưới đây sẽ **phá hủy và khôi phục lại control plane**, chỉ làm trong môi trường lab. Mục tiêu: xóa deployment `web`, restore lại từ snapshot và thấy nó "sống dậy".

```bash
# 1. Tạo "thảm họa": xóa deployment web
kubectl delete deployment web

# 2. Restore offline ra thư mục mới bằng container etcd cùng version
ETCD_IMAGE=$(kubectl -n kube-system get pod etcd-ch05-control-plane -o jsonpath='{.spec.containers[0].image}')
docker run --rm -v "$PWD:/work" -w /work "$ETCD_IMAGE" \
  etcdctl snapshot restore /work/truoc-upgrade.db \
  --data-dir=/work/etcd-restore \
  --name=ch05-control-plane \
  --initial-cluster=ch05-control-plane=https://127.0.0.1:2380 \
  --initial-advertise-peer-urls=https://127.0.0.1:2380 \
  --initial-cluster-token=etcd-cluster-restore-1

# 3. Dừng static pod control plane (chuyển manifest ra chỗ khác), đợi etcd/apiserver dừng hẳn
docker exec ch05-control-plane bash -c 'mkdir -p /root/manifests-backup && mv /etc/kubernetes/manifests/* /root/manifests-backup/'
docker exec ch05-control-plane crictl ps | grep -E "etcd|kube-apiserver" || echo "control plane đã dừng"

# 4. Giữ data dir cũ lại, đưa dữ liệu restore vào đúng chỗ, rồi chạy lại control plane
docker exec ch05-control-plane bash -c 'mv /var/lib/etcd /var/lib/etcd.bak'
docker cp ./etcd-restore/. ch05-control-plane:/var/lib/etcd
docker exec ch05-control-plane bash -c 'mv /root/manifests-backup/* /etc/kubernetes/manifests/'

# 5. Verify: deployment web "sống lại" từ snapshot
kubectl get deploy web
kubectl get nodes
```

Lưu ý: sau khi restore, `kubectl` có thể mất vài chục giây mới kết nối lại được (apiserver và etcd khởi động lại). Khi mọi thứ ổn, có thể xóa `/var/lib/etcd.bak` trên node.

### Bước 5: RBAC với ServiceAccount {#lab-rbac-serviceaccount}

```bash
kubectl create namespace rbac-lab
kubectl -n rbac-lab create serviceaccount reader-sa
kubectl -n rbac-lab create role pod-reader --verb=get,list,watch --resource=pods
kubectl -n rbac-lab create rolebinding reader-pods --role=pod-reader --serviceaccount=rbac-lab:reader-sa

# Kiểm tra "khô" quyền của SA
```

### Bước 6: RBAC cho user giả bằng certificate {#lab-rbac-user-cert}

Tạo user `dev-user` (group `developers`) bằng cách ký CSR qua API, rồi tự tạo kubeconfig cho user đó:

```bash
mkdir -p ~/ch05-lab && cd ~/ch05-lab

# 1. Sinh private key + CSR (CN = username, O = group)
openssl genrsa -out dev.key 2048
openssl req -new -key dev.key -out dev.csr -subj "/CN=dev-user/O=developers"

# 2. Gửi CSR lên cluster (signerName dành cho client cert)
cat <<EOF > dev-csr.yaml
apiVersion: certificates.k8s.io/v1
kind: CertificateSigningRequest
metadata:
  name: dev-user
spec:
  request: $(cat dev.csr | base64 | tr -d '\n')
  signerName: kubernetes.io/kube-apiserver-client
  usages:
    - client auth
EOF

kubectl apply -f dev-csr.yaml
kubectl certificate approve dev-user
kubectl get csr dev-user
kubectl get csr dev-user -o jsonpath='{.status.certificate}' | base64 -d > dev.crt
```

Tự dựng kubeconfig cho user (lấy CA và server endpoint từ kubeconfig admin):

```bash
docker cp ch05-control-plane:/etc/kubernetes/pki/ca.crt ./ca.crt
SERVER=$(kubectl config view --minify -o jsonpath='{.clusters[0].cluster.server}')

kubectl config set-cluster ch05 --server="$SERVER" --certificate-authority=ca.crt \
  --embed-certs=true --kubeconfig=dev.kubeconfig
kubectl config set-credentials dev-user --client-certificate=dev.crt --client-key=dev.key \
  --embed-certs=true --kubeconfig=dev.kubeconfig
kubectl config set-context dev-user@ch05 --cluster=ch05 --user=dev-user \
  --namespace=rbac-lab --kubeconfig=dev.kubeconfig
kubectl config use-context dev-user@ch05 --kubeconfig=dev.kubeconfig
```

Verify trước và sau khi bind quyền:

```bash
# Chưa có binding nào -> Forbidden
KUBECONFIG=$PWD/dev.kubeconfig kubectl get pods -n rbac-lab

# Bind Role pod-reader cho user giả
kubectl -n rbac-lab create rolebinding dev-user-read-pods --role=pod-reader --user=dev-user

# Bây giờ đọc được pod trong rbac-lab...
KUBECONFIG=$PWD/dev.kubeconfig kubectl get pods -n rbac-lab

# ...nhưng không đọc được ở namespace khác (RoleBinding chỉ có hiệu lực 1 namespace)
KUBECONFIG=$PWD/dev.kubeconfig kubectl get pods -n default
```

## Câu hỏi phỏng vấn thường gặp {#interview-questions}

**1. Version skew giữa kubelet và kube-apiserver được quy định như thế nào?**

kubelet không được **mới hơn** kube-apiserver và được phép **cũ hơn tối đa 3 minor version** (từ v1.28; trước đó là 2). Các component như kube-controller-manager, kube-scheduler, cloud-controller-manager chỉ được cũ hơn apiserver 1 minor, còn kubectl được lệch ±1 minor. Trong cluster HA, các apiserver instance cũng chỉ được lệch nhau 1 minor. Điểm thực hành quan trọng: nếu kubelet bị bỏ quên 3 minor, bạn **phải** upgrade kubelet trước khi upgrade control plane.

**2. Thứ tự nâng cấp cluster kubeadm là gì và vì sao?**

Control plane node đầu tiên trước (nâng kubeadm → `kubeadm upgrade plan` → `kubeadm upgrade apply`), rồi đến các control plane node khác (`kubeadm upgrade node`), sau cùng là worker node. Trên mỗi node, drain trước khi thay binary kubelet, sau đó uncordon. Lý do: kubelet không được mới hơn apiserver, nên control plane phải đi trước; drain để pod di tản êm, không gián đoạn dịch vụ.

**3. `kubectl cordon` khác `kubectl drain` ở điểm nào?**

`cordon` chỉ đánh dấu node unschedulable (không nhận pod mới) nhưng pod đang chạy vẫn tiếp tục chạy. `drain` = cordon + evict toàn bộ pod (trừ khi dùng flag phù hợp), nên node thực sự rỗng trước khi bảo trì. Drain dùng Eviction API nên tôn trọng PodDisruptionBudget; `cordon` thì không đụng đến pod.

**4. Khi drain node thường gặp lỗi gì và cách xử lý?**

Lỗi phổ biến:
- `cannot delete DaemonSet-managed Pods` → thêm `--ignore-daemonsets`.
- `cannot delete Pods with local storage` → thêm `--delete-emptydir-data` nếu chấp nhận mất dữ liệu emptyDir.
- Pod không do controller quản lý → thêm `--force`.
- `Cannot evict pod as it would violate the pod's disruption budget` → PDB đang giữ availability; chờ app ổn định, hoặc chấp nhận `--disable-eviction --force` trong tình huống khẩn cấp.

**5. Vì sao phải backup etcd và nên backup như thế nào?**

etcd giữ toàn bộ trạng thái của cluster; không có backup nghĩa là không thể phục hồi nếu mất control plane hoặc dữ liệu hỏng. Cách chuẩn là `etcdctl snapshot save` (built-in snapshot) chạy định kỳ với cert mTLS, kiểm tra bằng `etcdutl snapshot status`, lưu file **ngoài cluster** và mã hóa vì snapshot chứa secret. Nên định kỳ thử restore trên lab để chắc chắn quy trình hoạt động.

**6. Cụm etcd 3 member mất 1 member thì điều gì xảy ra?**

Cluster vẫn hoạt động vì còn **2/3 member = quorum**, nhưng mất khả năng chịu lỗi thêm: nếu chết thêm 1 member nữa thì mất quorum và etcd ngừng phục vụ ghi, kéo theo apiserver không hoạt động đúng. Việc cần làm là khôi phục member chết (sửa node, start lại etcd, hoặc thay member mới vào cùng peer URL) càng sớm càng tốt — không chờ đến khi sự cố thứ hai xảy ra.

**7. RoleBinding trỏ tới ClusterRole khác gì ClusterRoleBinding?**

RoleBinding trỏ ClusterRole sẽ cấp quyền của ClusterRole đó **chỉ trong namespace của binding** — dùng để tái sử dụng một ClusterRole (ví dụ `view`) cho nhiều namespace. ClusterRoleBinding luôn cấp quyền **toàn cluster**, gồm mọi namespace và cluster-scoped resource. Ngoài ra ClusterRoleBinding chỉ nhận `roleRef.kind: ClusterRole`, không thể trỏ vào Role.

**8. Vì sao không nên cấp `cluster-admin` cho CI/CD, và làm sao để least privilege?**

Vì pipeline thường là mục tiêu tấn công (supply chain, credential rò rỉ): một token `cluster-admin` bị lộ đồng nghĩa toàn bộ cluster bị chiếm. Cách làm đúng: tạo ServiceAccount riêng cho pipeline, bind Role theo namespace với đúng resource/verb cần thiết, chỉ thêm ClusterRole khi thật sự cần quyền cluster-scoped, tắt automount token khi không cần, dùng bound token ngắn hạn, và audit định kỳ các binding. Chương 7 sẽ đi sâu hơn vào chủ đề này.

**9. Node chuyển NotReady, bạn kiểm tra theo thứ tự nào?**

Đầu tiên `kubectl describe node` để xem Conditions (Ready, MemoryPressure, DiskPressure, PIDPressure) và Events; sau đó `systemctl status kubelet` + `journalctl -u kubelet` trên node; kiểm tra container runtime (`containerd`), CNI, dung lượng disk/inode, và tình trạng mạng tới control plane. Nếu mới reboot, nhớ kiểm tra kubelet có tự start không và certificate còn hiệu lực không. Trong cluster lớn, còn phải kiểm tra node lease và tải của apiserver/etcd vì chúng có thể khiến heartbeat bị bỏ lỡ.

**10. Pod Pending, bạn debug thế nào?**

Pod Pending nghĩa là chưa được gán node, nên đọc **scheduler events** là quan trọng nhất: `kubectl describe pod` và `kubectl get events`. Các nhóm nguyên nhân: thiếu tài nguyên (Insufficient cpu/memory), taint không tolerate, node selector/affinity không khớp, PVC chưa bind, quota namespace, hoặc chạm giới hạn pod mỗi node. Sau khi tìm ra message, xử lý đúng nhóm tương ứng (giảm request, thêm toleration, sửa label, sửa StorageClass...).

**11. CrashLoopBackOff khác ImagePullBackOff như thế nào?**

CrashLoopBackOff: kubelet **kéo được image và start container**, nhưng container thoát lặp lại (lỗi app, command sai, thiếu config, probe kill, OOM), kèm backoff tăng dần. ImagePullBackOff: kubelet **không kéo được image** (sai tên/tag, private registry thiếu imagePullSecrets, rate limit, lỗi mạng) nên container còn chưa được tạo. Cả hai đều được mô tả rõ trong Events; CrashLoopBackOff cần `kubectl logs --previous` và đọc exit code, còn ImagePullBackOff cần sửa image/secret.

**12. Tại sao apiserver chết nhưng pod trên node vẫn chạy? Static pod liên quan gì?**

Vì kubelet là "người quản lý node" độc lập: nó đọc manifest static pod trong `/etc/kubernetes/manifests` và tự duy trì các container đó, không cần apiserver. Pod do controller quản lý vẫn tiếp tục chạy theo spec đã có trên node; chỉ khi cần thay đổi (scale, update, evict...) mới phụ thuộc apiserver. Đây là lý do bạn có thể lên node, sửa manifest để khôi phục control plane khi apiserver không truy cập được qua kubectl.

## Các điểm chính {#key-points}

- **Version skew**: kubelet không mới hơn apiserver và được cũ hơn tối đa 3 minor; kubectl lệch ±1 minor; control plane phải upgrade trước kubelet.
- **Upgrade kubeadm** đi theo thứ tự: control plane đầu tiên (`kubeadm upgrade apply`) → control plane khác (`kubeadm upgrade node`) → worker; trên mỗi node là drain → thay binary → restart kubelet → uncordon.
- **Backup etcd là bắt buộc**: dùng `etcdctl snapshot save` với cert mTLS, kiểm tra bằng `etcdutl snapshot status`, lưu ngoài cluster và định kỳ diễn tập restore.
- **Restore etcd** phải restore ra data dir mới rồi sửa `hostPath` (không sửa `--data-dir` trong container); đừng restore một member cũ vào giữa cụm đang khỏe.
- **Quorum etcd**: N member cần đa số; 3 member chịu 1 lỗi, 5 member chịu 2 lỗi; số chẵn không tăng khả năng chịu lỗi.
- **cordon** chỉ chặn schedule; **drain** evict pod và tôn trọng PDB; nhớ `--ignore-daemonsets` và `--delete-emptydir-data` khi cần.
- **RBAC** gồm bốn object: Role/ClusterRole (định nghĩa quyền) và RoleBinding/ClusterRoleBinding (gán quyền cho subject); RoleBinding có thể trỏ ClusterRole nhưng chỉ có hiệu lực trong namespace.
- **ServiceAccount** hiện dùng **bound token** qua TokenRequest API (thời hạn, thu hồi được); pod không cần gọi API server nên đặt `automountServiceAccountToken: false`.
- **Scheduling**: nodeSelector là equality; node affinity hỗ trợ required/preferred; toleration chỉ "mở khóa" chứ không hút pod vào node; taint `NoExecute` mới evict pod đang chạy.
- **Topology spread** giữ độ lệch pod giữa các domain (zone/hostname) trong ngưỡng `maxSkew`; PriorityClass quyết định preemption nhưng không tôn trọng PDB.
- **kubelet là systemd unit**, còn control plane là static pod trong `/etc/kubernetes/manifests` — static pod vẫn chạy khi apiserver down, đây là chìa khóa để cứu cluster.
- **Node NotReady/áp lực tài nguyên**: kiểm tra Conditions → kubelet → runtime → CNI → tài nguyên (disk/inode/memory) → thời gian hệ thống; DiskPressure/MemoryPressure evict theo thứ tự QoS BestEffort → Burstable → Guaranteed (reason `Evicted`).
- **Pod lỗi thường gặp**: Pending (scheduler events), CrashLoopBackOff (command/args, config, exit code), ImagePullBackOff (tag/registry/secret), OOMKilled (exit 137, memory limit), probe sai (liveness restart, readiness rớt khỏi endpoints).
- **Service connectivity**: luôn kiểm tra Service → EndpointSlice → pod Ready → targetPort trước khi nghi ngờ kube-proxy/CNI; DNS lỗi thì kiểm tra CoreDNS, NetworkPolicy và resolv.conf.
- **`kubectl top`** phụ thuộc metric-server và aggregated API `v1beta1.metrics.k8s.io`; trên kind thường phải thêm `--kubelet-insecure-tls`.
