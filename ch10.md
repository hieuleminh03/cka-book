## Supply Chain Security trong kỳ thi CKS {#supply-chain-security-trong-ky-thi-cks}

Supply Chain Security là domain chiếm **20%** điểm CKS — cùng mức với Microservice Vulnerabilities, cao hơn System Hardening (10%). Đây cũng là domain "mới" nhất về mặt tư duy: thay vì bảo vệ cluster đang chạy, bạn bảo vệ **thứ được đưa vào cluster**.

Các domain khác trả lời câu hỏi "kẻ tấn công làm được gì khi đã vào trong?", còn domain này trả lời: "làm sao để image, manifest và pipeline bạn tin tưởng thực sự đáng tin?". Trong thực tế, đây là nơi nhiều vụ breach bắt đầu: một dependency bị chiếm quyền, một base image bị đầu độc, một tag bị ghi đè trong registry nội bộ.

### Vị trí domain trong đề thi {#vi-tri-domain-trong-de-thi}

CKS là kỳ thi performance-based, 15–20 task trong 2 giờ, điểm đạt 67%. Với trọng số 20%, Supply Chain Security thường xuất hiện 3–4 task. Các dạng task điển hình:

| Dạng task | Kỹ năng đề thi kiểm tra |
|---|---|
| Quét image/manifest bằng Trivy, lọc theo severity, xử lý kết quả | Đọc output, phân biệt `vuln`, `misconfig`, `secret`; biết flag `--severity`, `--scanners`, `--ignore-unfixed` |
| Viết Dockerfile nhiều stage, chọn base image nhỏ | Hiểu vì sao multi-stage giảm footprint; biết distroless/alpine/slim |
| Sinh SBOM cho image hoặc filesystem | Nhận diện định dạng SPDX/CycloneDX, công cụ syft/trivy |
| Ký image bằng cosign (keypair), verify chữ ký | `cosign generate-key-pair`, `cosign sign`, `cosign verify`, hiểu digest vs tag |
| Viết policy admission verify chữ ký | Thường là Kyverno `verifyImages` với `imageReferences` + `attestors`, đôi khi là Gatekeeper |
| Kiểm tra manifest bằng kubesec/kube-linter và sửa lỗi | Đọc score/check, sửa `securityContext`, `resources`, `hostNetwork`... |

Điểm khác biệt lớn nhất so với các domain khác: **bạn phải thao tác với registry và chữ ký số**, không chỉ với API Kubernetes. Vì vậy hãy chuẩn bị sẵn một cluster lab có registry nội bộ — chi tiết ở [phần lab](#hands-on-lab).

## Minimize base image footprint {#minimize-base-image-footprint}

### Vì sao kích thước image quan trọng {#vi-sao-kich-thuoc-image-quan-trong}

Một image nhỏ không chỉ "đẹp" trong dashboard của registry. Nó thay đổi trực tiếp bề mặt tấn công của cluster:

- **Ít package hơn thì ít CVE hơn và ít CVE "mới xuất hiện" hơn.** Mỗi gói cài thêm là một dòng trong SBOM, một dependency có thể bị khai thác, và một dòng phải theo dõi khi có CVE mới.
- **Ít binary hơn thì kẻ tấn công có ít shell, ít interpreter, ít công cụ để pivot.** Image không có `sh`, `curl`, `wget` thì việc chạy payload tải từ Internet khó hơn hẳn — đây là lý do distroless rất hiệu quả trong thực tế.
- **Pull nhanh hơn thì thời gian khởi động pod ngắn, node ít cạn disk, autoscaling mượt.** Trên cluster hàng trăm node, image 1GB so với 20MB là khác biệt về tiền và về reliability.
- **Cache layer hiệu quả hơn, CI/CD nhanh hơn**, registry/artifact repository ít tốn dung lượng lưu trữ.

Cần nói rõ để tránh ngộ nhận: **image nhỏ hơn không tự động đồng nghĩa với ít CVE hơn tại mọi thời điểm**. Có giai đoạn `alpine` bị nhiều CVE hơn `debian:slim`; có giai đoạn một CVE nghiêm trọng nằm đúng trong distroless. Điều luôn đúng là: ít thành phần hơn thì bề mặt nhỏ hơn và **khả năng một CVE ảnh hưởng tới bạn thấp hơn**. Hãy đánh giá dựa trên scan thực tế, đừng dựa trên định kiến "nhỏ là sạch".

### Base image: full, slim, alpine, distroless {#base-image-full-slim-alpine-distroless}

Bốn nhóm base image bạn cần phân biệt:

**Full (ubuntu, debian, node:22, python:3.12...)** chứa đầy đủ package manager, shell và thư viện hệ thống. Ưu điểm: quen thuộc, debug dễ, tương thích tốt. Nhược điểm: vài trăm MB đến hơn 1GB, hàng trăm package, nhiều CVE tiềm năng.

```dockerfile
# Ví dụ base "full": tiện nhưng nặng
FROM python:3.12
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
CMD ["python", "app.py"]
```

**Slim (debian-slim, python:3.12-slim, node:22-slim)** là các biến thể đã lược bớt tài liệu, compiler và nhiều gói không cần thiết, nhưng vẫn giữ package manager và shell. Đây thường là lựa chọn cân bằng tốt nhất cho ứng dụng cần debug trong production.

**Alpine** dựa trên musl libc và busybox, kích thước rất nhỏ (khoảng 5–7MB cho base). Lưu ý thực chiến: một số ứng dụng/ngôn ngữ không chạy tốt với musl (đặc biệt khi có native extension), và Alpine từng có giai đoạn CVE nhiều hơn debian-slim. Với ứng dụng Go/Rust build tĩnh thì Alpine chỉ còn là chuyện của build stage.

**Distroless (gcr.io/distroless/...)** chứa ứng dụng, các thư viện runtime cần thiết và **không có** shell, package manager hay bất kỳ công cụ tương tác nào. Đây là lựa chọn mặc định tôi khuyên cho workload mới khi đội có cách debug không cần shell (ephemeral container — xem chương 9). Các biến thể chính:

| Image distroless | Dùng khi |
|---|---|
| `gcr.io/distroless/static-debian12` | Binary tĩnh (Go, Rust musl), không cần libc động |
| `gcr.io/distroless/base-debian12` | Cần glibc, `libssl`, NSS... |
| `gcr.io/distroless/cc-debian12` | Cần libstdc++/libgcc (C++, Rust glibc) |
| `gcr.io/distroless/java21-debian12` | Ứng dụng Java/JVM |
| `gcr.io/distroless/nodejs22-debian12` | Ứng dụng Node.js |
| Hậu tố `:nonroot` | Chạy sẵn với UID 65532, không cần `USER` |

### Bảng so sánh base image {#bang-so-sanh-base-image}

Bảng dưới ghi **giá trị định hướng**, không phải số liệu cố định — size và CVE thay đổi theo thời điểm và theo tag cụ thể. Hãy coi nó là bản đồ để chọn chỗ bắt đầu.

| Base | Size (định hướng) | Shell / package manager | Số package | Điểm mạnh | Điểm yếu |
|---|---|---|---|---|---|
| `ubuntu:24.04` | ~78MB | Có | ~100 | Quen thuộc, hỗ trợ rộng | Bề mặt lớn, debug thoải mái thì tấn công cũng thoải mái |
| `debian:12-slim` | ~75MB | Có | ~90 | Ổn định, dễ debug | Vẫn khá nhiều gói |
| `python:3.12` | hơn 1GB | Có | hơn 500 | Đầy đủ toolchain | Rất nặng, nhiều CVE |
| `python:3.12-slim` | ~120MB | Có | ~120 | Cân bằng tốt cho app Python | Vẫn cần dọn cache pip |
| `alpine:3.20` | ~8MB | busybox | ~15 | Rất nhỏ | musl, một số app không tương thích; CVE tùy thời điểm |
| `nginx:1.27-alpine` | ~45MB | Có (busybox) | ~40 | Nhỏ gọn, có sẵn web server | Vẫn có shell |
| `gcr.io/distroless/static-debian12:nonroot` | ~2–7MB | Không | ~5–10 | Bề mặt tối thiểu, non-root sẵn | Không shell, debug cần cách khác |
| `gcr.io/distroless/base-debian12:nonroot` | ~20MB | Không | ~20 | Có glibc/libssl | Không có package manager |

Quy tắc chọn của tôi, theo thứ tự ưu tiên:

1. Nếu build ra **binary tĩnh** (Go, Rust musl): dùng `distroless/static:nonroot`.
2. Nếu cần glibc/runtime của ngôn ngữ: distroless theo ngôn ngữ, hoặc biến thể `-slim`/`-alpine` chính chủ của language image (ví dụ `node:22-slim`).
3. Nếu base cần nhiều thứ hơn: bắt đầu bằng `debian:12-slim` chứ đừng bắt đầu bằng bản full.
4. Luôn ghim **digest** cho base image trong Dockerfile production, không chỉ tag.

```dockerfile
# Ghim digest: tag có thể bị ghi đè, digest thì không
FROM gcr.io/distroless/static-debian12:nonroot@sha256:6ec5aa99dc335666e79dc64e4a6c8b89c33a543a1967f20d360922a80dd21f02
```

### Multi-stage build {#multi-stage-build}

Multi-stage build là kỹ thuật quan trọng nhất để giảm footprint và đã được trình bày ở chương 3. Nhắc lại ngắn gọn vì trong CKS đây là "vũ khí mặc định": mỗi `FROM` bắt đầu một stage mới, và **chỉ những gì bạn `COPY --from=` vào stage cuối mới tồn tại trong image cuối**.

```dockerfile
# Stage 1: build — chứa compiler, toolchain, source
FROM golang:1.24-alpine AS builder
WORKDIR /src
COPY main.go .
# CGO_ENABLED=0 + GOOS=linux để có binary tĩnh chạy được trên distroless
RUN go mod init demo.local/app && CGO_ENABLED=0 GOOS=linux go build -trimpath -ldflags="-s -w" -o /out/app .

# Stage 2: runtime — chỉ chứa binary, không có Go, không có shell
FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=builder /out/app /app
USER nonroot:nonroot
ENTRYPOINT ["/app"]
```

Ba lỗi thường gặp khi dùng multi-stage:

- `COPY . .` ở stage runtime kéo cả source code, `.env`, `node_modules` vào image cuối.
- Quên `-trimpath`/`-ldflags="-s -w"` khiến binary chứa đường dẫn build và debug symbol (vừa nặng vừa lộ thông tin nội bộ).
- Cài `ca-certificates` hay `tzdata` "cho chắc" trong khi ứng dụng không gọi TLS ra ngoài — hãy cài cái thật sự cần.

### Chỉ cài package cần thiết {#chi-cai-package-can-thiet}

Với những trường hợp buộc phải dùng base có package manager, đây là checklist:

```dockerfile
FROM debian:12-slim

# 1. --no-install-recommends: không kéo theo gói "gợi ý"
# 2. Gộp update + install + dọn cache trong CÙNG một RUN để không lưu layer rác
# 3. Ghim version của gói quan trọng khi cần tái lập chính xác
RUN apt-get update && apt-get install -y --no-install-recommends ca-certificates libssl3 && rm -rf /var/lib/apt/lists/*

# 4. Không dùng root
RUN groupadd -r app && useradd -r -g app -u 10001 app
USER 10001:10001
```

Các nguyên tắc bổ sung:

- Không cài `curl`, `wget`, `netcat`, `vim`, `bash` vào runtime image chỉ để "tiện debug". Nếu cần debug, dùng `kubectl debug` với ephemeral container (chương 9) hoặc image `:debug`.
- Không chạy `apt-get upgrade` trong Dockerfile: kết quả không tái lập được và dễ tạo ra image "khác nhau giữa các lần build". Hãy nâng base tag/digest thay vì upgrade tại chỗ.
- Với image distroless thiếu CA certificate, copy từ stage build: `COPY --from=builder /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/`.
- `USER` phải được set ở cuối stage runtime, và nên là UID số (không phụ thuộc `/etc/passwd` của base image).

### Kiểm tra footprint {#kiem-tra-footprint}

Bộ lệnh tôi dùng để kiểm tra nhanh một image trước khi cho vào pipeline:

```bash
# 1. Kích thước từng image
docker image ls

# 2. Số layer và lệnh nào tạo ra layer nặng nhất
docker history --no-trunc secure-app/app:full

# 3. Số package trong image (cần syft hoặc trivy)
syft docker:secure-app/app:full -o json | jq '.artifacts | length'
```

`dive` (công cụ ngoài, cài miễn phí) cho phép soi từng layer và ước lượng "wasted space" — hữu ích khi tối ưu image lớn, nhưng không cần thiết trong phòng thi. Trong phòng thi, hai lệnh đủ dùng là `docker image ls` (hoặc `crictl images` trên node) và `trivy image`.

## Hiểu supply chain {#hieu-supply-chain}

### Supply chain là gì {#supply-chain-la-gi}

Supply chain (chuỗi cung ứng phần mềm) là toàn bộ đường đi từ **mã nguồn** đến **container đang chạy trong cluster**:

```text
  source code -----> dependencies -----> build (CI) -----> artifact/image
       |                  |                  |                   |
   git, review      npm/pypi/go mod     runner, builder      registry
       |                  |                  |                   |
       +------------------+------------------+-------------------+
                                    |
                          admission / deploy --> runtime trong cluster
```

Mỗi mắt xích đều có thể bị tấn công. Một số lớp tấn công thực tế:

| Mắt xích | Kiểu tấn công | Ví dụ |
|---|---|---|
| Dependency | Dependency confusion, typosquatting, package bị chiếm quyền | Package nội bộ bị "kéo" từ public registry; tên gần giống package thật |
| Build | CI runner bị chiếm, script build bị chèn | Token CI bị đọc từ log; action của bên thứ ba bị đổi version |
| Artifact | Base image bị đầu độc, tag bị ghi đè | Image `:latest` trên registry nội bộ bị thay bằng image có backdoor |
| Registry | Quyền push quá rộng, thiếu audit | Một tài khoản CI có quyền push mọi repo, không có log |
| Deploy | Deploy nhầm artifact, thiếu verify | Manifest trỏ tới image không phải do pipeline của bạn build |

Điểm chung của các lớp phòng thủ là **không tin tưởng mặc định** và **kiểm chứng bằng bằng chứng mật mã** (chữ ký, digest, provenance) thay vì bằng niềm tin (tag, tên repo, "chắc là ổn").

### SBOM với syft: SPDX và CycloneDX {#sbom-voi-syft}

**SBOM (Software Bill of Materials)** là "bảng kê nguyên vật liệu" của một artifact: liệt kê mọi package/thành phần bên trong, kèm version, nguồn và thường cả license. Hai định dạng chuẩn bạn cần biết:

| Định dạng | Đặc điểm | Media type thường gặp |
|---|---|---|
| **SPDX** (ISO/IEC 5962) | Chuẩn mở, nhiều metadata license, phổ biến trong compliance | `application/spdx+json` |
| **CycloneDX** (OWASP) | Sinh ra cho bảo mật, hỗ trợ VEX, cấu trúc component/dependency | `application/vnd.cyclonedx+json` |

SBOM **không phải** là kết quả scan CVE — đây là điểm rất hay bị hỏi. SBOM trả lời câu hỏi "trong image này có gì?", còn scanner trả lời "thành phần đó có CVE nào đang biết không?". Giá trị lớn nhất của SBOM nằm ở thời điểm **sau khi release**: khi CVE mới được công bố (kiểu Log4Shell), bạn tra trong SBOM đã lưu của mọi image từng ship để biết image nào bị ảnh hưởng trong vài phút, thay vì scan lại toàn bộ hoặc ngồi hỏi từng team.

Công cụ phổ biến:

```bash
# Sinh SBOM cho image đang có trong Docker daemon
syft docker:secure-app/app:distroless -o spdx-json=sbom.spdx.json

# Định dạng khác: CycloneDX
syft docker:secure-app/app:distroless -o cyclonedx-json=sbom.cdx.json

# Sinh SBOM cho cả filesystem/repo
syft dir:. -o spdx-json=repo-sbom.spdx.json

# Trivy cũng có thể sinh SBOM
trivy image --format spdx-json -o sbom-trivy.spdx.json secure-app/app:distroless

# Scan lại một SBOM để tìm CVE (rất hữu ích với artifact cũ)
trivy sbom --scanners vuln --severity HIGH,CRITICAL sbom.spdx.json
```

Trong quy trình chuyên nghiệp, SBOM được:

1. Sinh tự động trong CI cho **mọi** image.
2. Lưu cùng artifact (attest vào chính image bằng `cosign attest`) và/hoặc lưu vào artifact repository.
3. Dùng làm đầu vào cho scanner khi có CVE mới, và cho các công cụ policy (ví dụ policy yêu cầu mọi image phải có SBOM attestation).

Định dạng đính kèm SBOM vào image bằng cosign (chạy sau khi đã học phần cosign bên dưới):

```bash
cosign attest --yes --key cosign.key --predicate sbom.cdx.json --type cyclonedx kind-registry:5000/secure-app/app:distroless
```

### Artifact repository và provenance {#artifact-repository-va-provenance}

**Artifact repository** là nơi lưu artifact có kiểm soát: container registry (Harbor, ECR, Artifact Registry, ACR, Nexus, Artifactory) và repository cho dependency (npm, PyPI, Maven proxy). Với CKS và phỏng vấn, bạn cần nắm các năng lực sau của một registry "nghiêm túc":

- **Access control và RBAC theo repository/project**: team A không push được vào repo của team B; CI có quyền push nhưng không có quyền xóa.
- **Immutable tag** (không cho ghi đè tag đã tồn tại) và **retention policy** (giữ bao lâu, xóa image nào).
- **Scan tích hợp** (Harbor có Trivy sẵn) và **policy** (chặn pull image có CVE mức critical).
- **Replication** giữa các site, và **audit log** cho mọi push/pull/delete.
- **Hỗ trợ lưu chữ ký/attestation OCI**: chữ ký cosign, SBOM, provenance nằm cạnh image dưới dạng OCI artifact.
- **Proxy/mirror dependency** để không phải gọi trực tiếp ra Internet, kèm allowlist package nội bộ để chống dependency confusion.

**Provenance** (nguồn gốc) trả lời câu hỏi khó hơn SBOM: artifact này **được build từ commit nào, bởi pipeline nào, bằng lệnh gì, trên runner nào**. Provenance được ký và đính kèm artifact dưới dạng attestation theo format **in-toto**:

```bash
# Provenance tối giản, ví dụ minh họa cách đính kèm attestation
cat > provenance.json <<'EOF'
{
  "buildType": "https://example.com/cicd/github-actions",
  "builder": { "id": "https://github.com/my-org/my-repo/actions/runs/123456" },
  "invocation": { "configSource": { "uri": "git+https://github.com/my-org/my-repo@refs/heads/main" } },
  "metadata": { "buildStartedOn": "2026-01-01T00:00:00Z", "completeness": { "parameters": true, "environment": true, "materials": true } }
}
EOF

cosign attest --yes --key cosign.key --predicate provenance.json --type slsaprovenance kind-registry:5000/secure-app/app:distroless

# Kiểm tra attestation
cosign verify-attestation --key cosign.pub --type slsaprovenance kind-registry:5000/secure-app/app:distroless
```

Provenance là lớp phòng thủ mà **chữ ký đơn thuần không có**: chữ ký chỉ chứng minh "image này được ký bởi key X", provenance còn chứng minh "image này là kết quả của pipeline Y chạy trên commit Z". Nếu kẻ tấn công có được private key nhưng không kiểm soát được pipeline, provenance vẫn có thể phát hiện bất thường.

### SLSA: các cấp độ {#slsa}

**SLSA (Supply-chain Levels for Software Artifacts)** là khung phân cấp độ "trưởng thành" của supply chain, hiện hành là SLSA v1.0 với hai track: **source** và **build**. Phần build được hỏi nhiều nhất:

| Cấp | Yêu cầu cốt lõi | Ý nghĩa thực tế |
|---|---|---|
| **Build L1** | Có provenance (chưa cần ký) | Bạn biết artifact được build từ đâu; hữu ích nhưng chưa chống giả mạo |
| **Build L2** | Build trên nền tảng hosted, provenance được ký bởi builder | Kẻ tấn công không dễ tự tạo provenance giả; CI sinh provenance tự động |
| **Build L3** | Build cô lập, khó giả mạo, provenance không thể sửa từ bên trong build | Chống luôn cả kịch bản kẻ tấn công có quyền trong pipeline |

Trong phòng thi CKS bạn **không** phải triển khai SLSA L3; objective chỉ yêu cầu "hiểu supply chain". Nhưng trong phỏng vấn middle/senior, bạn nên trả lời được: SLSA là thước đo để chọn mức đầu tư, L1/L2 đạt được khá dễ với các CI hiện đại (ví dụ GitHub Actions + provenance attestation), và L3 là mục tiêu cho artifact quan trọng. Công cụ liên quan: `slsa-github-generator`, `slsa-verifier`, attestation predicate type `slsaprovenance`.

## Bảo vệ supply chain {#bao-ve-supply-chain}

### Các bước bảo vệ supply chain {#cac-buoc-bao-ve-supply-chain}

Đây là "bản đồ" tôi thường dùng khi review một hệ thống — hoặc khi làm task CKS. Mỗi lớp giảm một loại rủi ro khác nhau, và các lớp bổ trợ chứ không thay thế nhau.

| Bước | Việc cần làm | Cơ chế / công cụ |
|---|---|---|
| 1. Thu hẹp đầu vào | Base image tối thiểu, multi-stage, không thừa package | distroless/alpine/slim, Dockerfile sạch |
| 2. Kiểm soát dependency | Ghim version, dùng lockfile, proxy/mirror nội bộ, allowlist | lockfile, Renovate/Dependabot, Nexus/Artifactory |
| 3. Scan artifact | Scan CVE + secret + misconfig trước khi push | Trivy, Grype, Kubesec, KubeLinter |
| 4. Ký artifact | Ký image/SBOM/provenance và lưu cạnh artifact | cosign (keypair hoặc keyless), Notary/notation |
| 5. Registry tin cậy | Private registry, RBAC chặt, immutable tag, audit, scan tự động | Harbor/ECR/Artifact Registry/ACR |
| 6. Ghim và deploy | Deploy theo digest, không dùng `latest`, chỉ kéo image từ nguồn tin cậy | image digest trong manifest, `imagePullPolicy` phù hợp |
| 7. Xác thực tại admission | Bắt buộc chữ ký/attestation trước khi pod được tạo | Kyverno `verifyImages`, Gatekeeper + external data, ValidatingAdmissionPolicy |
| 8. Theo dõi và phản ứng | Lưu SBOM, audit log registry, rebuild định kỳ, VEX cho false positive | SBOM store, log tập trung, lịch rebuild, quy trình remediation |

### Private registry và immutable tag {#private-registry-va-immutable-tag}

**Vì sao cần private registry?** Nếu cluster pull image từ public registry, bạn phụ thuộc vào một bên thứ ba có thể bị chiếm quyền, hoặc image có thể biến mất. Private registry cho phép bạn kiểm soát ai push/pull, scan trên đường vào, ký trước khi mọi người sử dụng, và chặn pull từ Internet nhờ NetworkPolicy/egress rule (trừ registry của bạn).

**Immutable tag** là tính năng bắt buộc phải bật với các repo quan trọng: khi tag `v1.2.3` đã tồn tại, registry từ chối push đè. Không có nó, "tag" chỉ là con trỏ có thể bị ghi đè, nghĩa là mọi kiểm soát dựa trên tag đều có lỗ hổng TOCTOU (thời điểm bạn verify khác thời điểm node pull).

```bash
# Ví dụ với ECR: bật tag immutability khi tạo repository
aws ecr create-repository --repository-name secure-app/app --image-tag-mutability IMMUTABLE --image-scanning-configuration scanOnPush=true

# Kiểm tra repository đã bật scan-on-push chưa
aws ecr describe-repositories --repository-names secure-app/app --query 'repositories[0].imageScanningConfiguration'
```

Với registry tự dựng (Harbor, Nexus, registry:3), hãy bật đồng thời: immutable tag, scan on push, retention policy (ví dụ giữ 30 phiên bản gần nhất) và audit log. Đây là những mục xuất hiện trong các câu hỏi phỏng vấn về "registry tin cậy là gì".

### Tag, digest và imagePullPolicy {#tag-digest-va-imagepullpolicy}

Trong CKS và trong sự cố production, đây là chủ đề gây đau đầu nhiều nhất:

- **Tag là con trỏ có thể thay đổi.** `app:1.0.0` hôm nay và mai có thể là hai image khác nhau nếu ai đó push đè. Tag `latest` còn tệ hơn: nó gần như không chỉ định gì cả.
- **Digest là định danh nội dung.** `sha256:...` được tính từ nội dung manifest; đổi một byte trong image là digest đổi. Digest ghim đúng một artifact, không thể bị ghi đè.

```bash
# Xem digest của image trong daemon (sau khi đã pull/push)
{% raw %}
docker image inspect kind-registry:5000/secure-app/app:distroless --format '{{index .RepoDigests 0}}'
# kind-registry:5000/secure-app/app@sha256:9f2c...e1

# Liệt kê image kèm digest trên node
crictl images --digests | grep secure-app
{% endraw %}
```

Quy tắc thực hành:

1. Trong CI: build, push theo **tag** dễ đọc cho người (`v1.2.3`, `sha-abc1234`), rồi lấy digest từ output của push.
2. Trong **manifest deploy**: dùng `image: registry/app@sha256:...`. Đây là yêu cầu nên được enforce bằng policy ở cổng admission.
3. Trong **policy verify chữ ký**: bật `mutateDigest: true` để Kyverno tự chuyển tag thành digest sau khi verify — nghĩa là artifact được verify chính là artifact sẽ chạy.

`imagePullPolicy` tương tác với tag/digest theo bảng sau (kubelet mặc định `IfNotPresent` khi image có tag cụ thể, và `Always` khi image dùng `:latest` hoặc không ghi tag):

| Manifest ghi | `imagePullPolicy` | Kubelet làm gì |
|---|---|---|
| `app:1.0.0` | `IfNotPresent` (mặc định) | Dùng image đã có trên node; chỉ pull khi chưa có |
| `app:1.0.0` | `Always` | Luôn pull lại mỗi lần tạo pod (chậm hơn nhưng "thấy" tag mới) |
| `app@sha256:...` | `IfNotPresent` | Chỉ pull khi digest chưa có trên node; an toàn và hiệu quả nhất |
| `app:latest` | `Always` (mặc định) | Luôn pull lại; vẫn không đảm bảo image giống lần trước |

Lưu ý quan trọng: `imagePullPolicy: Always` **không** phải là biện pháp bảo mật — nó chỉ giúp bạn "thấy" tag mới, và cũng giúp kẻ tấn công ghi đè tag đến được node của bạn. Cách đúng là ghim digest (hoặc tag immutable); `Always` chỉ nên là giải pháp tạm cho tag mutable.

### Image policy: allowlist registry, chặn latest {#image-policy}

Trước khi đi vào ký và verify, hãy chặn những thứ đơn giản nhưng nguy hiểm bằng policy: image phải đến từ registry của bạn, không dùng tag mutable, không bật `privileged`. Kyverno là lựa chọn phổ biến nhất vì viết policy bằng YAML:

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: restrict-image-registries
spec:
  validationFailureAction: Enforce
  background: true
  rules:
    - name: validate-registries
      match:
        any:
          - resources:
              kinds:
                - Pod
      validate:
        message: "Chỉ cho phép image từ registry nội bộ."
        pattern:
          spec:
            containers:
              - image: "kind-registry:5000/* | registry.example.com/*"
```

Với Gatekeeper (OPA), bạn dùng `ConstraintTemplate` + `Constraint`; với các bản Kubernetes mới, **ValidatingAdmissionPolicy** (CEL) là lựa chọn native không cần controller bên thứ ba. Điểm cần nhớ cho phỏng vấn: policy kiểu này **không** chứng minh nguồn gốc image — nó chỉ giới hạn hình dạng tham chiếu. Muốn chứng minh nguồn gốc phải có chữ ký.

### Cosign: ký và xác thực image {#cosign-ky-va-xac-thuc-image}

**cosign** (Sigstore) là công cụ ký và verify container image phổ biến nhất. Luồng cơ bản với keypair:

```bash
# 1. Sinh cặp khóa. cosign.key là private (phải bảo vệ), cosign.pub là public
export COSIGN_PASSWORD="mat-khau-manh-trong-that"   # trong CI, lấy từ secret manager
cosign generate-key-pair
# -> cosign.key, cosign.pub

# 2. Ký image. Chữ ký được lưu ngay trong registry, cùng repo với image
cosign sign --yes --key cosign.key kind-registry:5000/secure-app/app@sha256:<digest>

# 3. Verify bằng public key
cosign verify --key cosign.pub kind-registry:5000/secure-app/app@sha256:<digest>

# 4. Xem các artifact gắn với image (chữ ký, attestation, SBOM)
cosign tree kind-registry:5000/secure-app/app:distroless
```

Những điểm kỹ thuật phải nắm:

- **Ký theo digest, không theo tag.** `cosign sign app:v1` thực chất resolve `v1` thành digest rồi ký digest đó; nhưng nếu bạn ký tag và ai đó ghi đè tag trước khi verify, bạn verify một image khác. Trong pipeline, hãy lấy digest từ bước push và ký `@sha256:...`.
- **Chữ ký nằm trong registry**, không nằm trong image. Với layout legacy, cosign tạo một artifact `sha256-<digest>.sig` trong cùng repository; với OCI 1.1 referrers, chữ ký được tham chiếu qua Referrers API. Đây là lý do **chữ ký không tự "đi theo" image** khi bạn copy image sang registry khác bằng công cụ không hỗ trợ ký — phải copy cả chữ ký (`cosign copy`).
- **Bất kỳ thay đổi nào cũng phá chữ ký.** Sửa một layer, đổi base, thêm ENV đều tạo digest mới, chữ ký cũ không còn áp dụng. Điều này tốt: nó buộc rebuild và ký lại khi image thay đổi.
- **Private key phải được bảo vệ nghiêm ngặt.** Trong production, dùng KMS (`--key awskms://...`, `gcpkms://...`, `azurekms://...`) hoặc keyless; không để `cosign.key` nằm trong repo hay trong biến môi trường CI có thể bị đọc từ log.
- **Nếu kẻ tấn công có private key?** Họ ký được image độc hại "hợp lệ". Đây là lý do cần thêm provenance (attestation mô tả pipeline/commit) và luân chuyển khóa. Cũng là lý do **transparency log (Rekor)** hữu ích: mọi lần ký đều được ghi lại, bất thường có thể bị phát hiện kể cả khi chữ ký "đúng".

Về `--tlog-upload` và `--insecure-ignore-tlog`: khi ký, cosign mặc định đẩy bản ghi lên Rekor (`--tlog-upload=true`). Với môi trường không có Internet, bạn có thể ký với `--tlog-upload=false` và verify với `--insecure-ignore-tlog`; khi đó policy Kyverno cũng phải đặt `rekor.ignoreTlog: true`. Hãy nhớ: tắt tlog là giảm bảo đảm (mất tính transparency), chỉ nên làm khi thật sự cần.

Về version: chương này dùng **cosign v2.x** (ví dụ v2.6.5). Cosign v3 đã ra đời và mặc định dùng bundle format mới, nhưng nhiều hệ sinh thái (bao gồm policy `verifyImages` phổ biến trong CKS) ổn định nhất với v2 — đây là ví dụ rất thật về việc version của công cụ ký **cũng là** một phần của supply chain: hãy ghim version trong CI và nâng cấp có test.

### Keyless với Fulcio và Rekor {#cosign-keyless}

**Keyless signing** giải quyết vấn đề "không muốn quản lý private key" bằng cách dùng danh tính OIDC (identity của CI job, của user Google/GitHub...):

1. cosign lấy một **OIDC token** (ví dụ `id-token` của GitHub Actions, hoặc đăng nhập tương tác).
2. Token được đổi lấy một **certificate ngắn hạn** từ **Fulcio** — certificate gắn với identity, thường chỉ sống vài phút.
3. cosign dùng certificate đó để ký và ghi signature + certificate vào **Rekor** (transparency log).
4. Khi verify, bạn không đưa public key, mà đưa **identity + issuer** chấp nhận:

```bash
# Ký keyless (trong CI, identity là GitHub Actions workflow)
cosign sign --yes kind-registry:5000/secure-app/app@sha256:<digest>

# Verify: chỉ chấp nhận đúng workflow, đúng issuer
cosign verify kind-registry:5000/secure-app/app@sha256:<digest> --certificate-identity "https://github.com/my-org/my-repo/.github/workflows/release.yaml@refs/heads/main" --certificate-oidc-issuer "https://token.actions.githubusercontent.com"
```

So sánh nhanh để trả lời phỏng vấn:

| Tiêu chí | Keypair | Keyless |
|---|---|---|
| Bí mật cần bảo vệ | Private key (rotate, KMS) | Không có; nhưng phải tin Fulcio/Rekor và OIDC |
| Ai ký được | Ai giữ key | Ai có identity OIDC hợp lệ theo policy |
| Phụ thuộc mạng | Có thể chạy offline | Cần Fulcio + Rekor (hoặc hạ tầng tương đương nội bộ) |
| Kiểm tra khi verify | `--key cosign.pub` | `--certificate-identity` + `--certificate-oidc-issuer` |
| Điểm yếu chính | Key bị lộ/rò rỉ | Identity bị chiếm, policy quá rộng (regex `.*`) |

Trong phỏng vấn, đừng chỉ nói "keyless an toàn hơn". Câu trả lời tốt: keyless giảm rủi ro quản lý khóa và tăng khả năng truy vết (certificate + Rekor), nhưng bạn phải **ghim identity thật chặt** — chấp nhận `subject: "https://github.com/*"` thì gần như vô hiệu hóa bảo vệ.

### Notary và các lựa chọn khác {#notary}

Bên cạnh cosign, hai cái tên bạn cần biết:

- **Notary v1 / Docker Content Trust (DCT)**: cơ chế cũ của Docker dựa trên TUF, ký tag bằng key trong `~/.docker/trust`. Ngày nay hầu như không dùng cho Kubernetes mới; nếu gặp cluster cũ hoặc tài liệu cũ, hãy biết nó là "ký theo tag" và đã lỗi thời.
- **Notary Project (notation)**: dự án CNCF, chuẩn hóa việc ký OCI artifact với định dạng chữ ký COSE, có CLI `notation` và hỗ trợ trong các policy engine (Kyverno có attestor `type: Notary`).

```bash
# Ví dụ minh họa với notation (nếu bạn dùng hệ sinh thái Notary Project)
notation cert generate-test --default "my-signer"
notation sign --signature-format cose kind-registry:5000/secure-app/app@sha256:<digest>
notation verify kind-registry:5000/secure-app/app@sha256:<digest>
```

Trong CKS, **cosign là chuẩn thực tế** — hầu hết tài liệu và policy mẫu dùng cosign. Bạn chỉ cần biết Notary tồn tại và biết rằng về nguyên lý ba thứ đều giống nhau: ký artifact, lưu chữ ký cạnh artifact, verify bằng danh tính tin cậy.

### Admission verification với Kyverno và Gatekeeper {#admission-verification}

Ký mà không có ai kiểm tra thì chữ ký chỉ là trang trí. Việc **verify tại thời điểm admission** được thực hiện bởi webhook (Kyverno, Gatekeeper + external data/ratify, hoặc Sigstore Policy Controller). Luồng hoạt động:

```text
kubectl apply pod --> kube-apiserver --> admission webhook (Kyverno)
                                              |
                          1. thấy image trong pod spec
                          2. resolve tag -> digest, gọi registry tải chữ ký
                          3. verify chữ ký với public key/identity
                          4. allow (có thể mutate tag -> digest) hoặc deny
```

Policy Kyverno `verifyImages` tối thiểu trông như sau (đây cũng là policy bạn viết trong lab):

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: verify-supply-chain-images
spec:
  background: false
  validationFailureAction: Enforce
  webhookConfiguration:
    failurePolicy: Fail
    timeoutSeconds: 30
  rules:
    - name: verify-cosign-signature
      match:
        any:
          - resources:
              kinds:
                - Pod
              namespaces:
                - secure-app
      verifyImages:
        - imageReferences:
            - "kind-registry:5000/secure-app/*"
          mutateDigest: true
          verifyDigest: false
          required: true
          imageRegistryCredentials:
            allowInsecureRegistry: true     # lab dùng registry HTTP; production dùng TLS
          attestors:
            - entries:
                - keys:
                    publicKeys: |
                      -----BEGIN PUBLIC KEY-----
                      <nội dung cosign.pub>
                      -----END PUBLIC KEY-----
```

Các trường quan trọng và ý nghĩa:

| Trường | Ý nghĩa |
|---|---|
| `imageReferences` | Danh sách pattern image bị policy quản lý (hỗ trợ wildcard) |
| `attestors.entries[].keys.publicKeys` | Public key dùng để verify (có thể tham chiếu Secret qua `k8s://kyverno/cosign-pub`) |
| `attestors.entries[].keyless` | Verify keyless: khai báo `subject`/`issuer` (hỗ trợ regex) |
| `attestations` | Yêu cầu attestation (SBOM, provenance, vuln) thay vì chỉ chữ ký |
| `mutateDigest: true` | Sau khi verify, ghi lại image theo digest trong pod spec |
| `verifyDigest: true` | Yêu cầu manifest đầu vào đã dùng digest (chặt hơn) |
| `required: true` | Mọi image khớp pattern đều phải verify, không được bỏ qua |
| `imageRegistryCredentials.allowInsecureRegistry` | Cho phép Kyverno gọi registry HTTP/self-signed; chỉ dùng cho lab/nội bộ |
| `failurePolicy: Fail` | Webhook lỗi thì chặn (fail closed) — an toàn hơn nhưng có thể "sập" deploy |

Vài "bẫy" thực tế mà phỏng vấn senior rất hay hỏi:

- **Kyverno phải tự truy cập được registry.** Node pull được image không có nghĩa là controller verify được: DNS của pod khác DNS của node, TLS trust khác, credential khác. Trong cluster có NetworkPolicy chặt, bạn phải mở đường cho namespace của Kyverno tới registry.
- **`failurePolicy: Fail` + registry không truy cập được = sập deploy diện rộng.** Hãy khoanh vùng `match` theo namespace (đừng quên `kube-system`), đặt timeout hợp lý và có alert cho webhook.
- **Bật `mutateDigest` để tránh TOCTOU.** Không có nó, policy verify tag `v1`, nhưng pod có thể được schedule sau khi tag bị ghi đè.
- **Verify chữ ký không kèm policy danh tính thì vô nghĩa.** Với keyless, phải ghim `subject`/`issuer`; với keypair, phải luân chuyển key và bảo vệ public key trong policy (dùng Secret + RBAC).
- **Gatekeeper** làm việc tương tự nhưng cần external data provider (ví dụ `ratify`, `cosign` provider) để gọi verify — cấu hình nặng hơn, nhưng phù hợp nếu tổ chức đã chuẩn hóa OPA/Rego.

### Từ verifyImages sang ImageValidatingPolicy {#tu-verifyimages-sang-imagevalidatingpolicy}

Một thay đổi lớn của hệ sinh thái Kyverno trong 2026: **ClusterPolicy (và rule `verifyImages`) đã bị đánh dấu deprecated từ Kyverno v1.17 và dự kiến bị loại bỏ ở v1.20**. Kiểu policy mới là **ImageValidatingPolicy** (API `policies.kyverno.io/v1`), viết theo CEL, chỉ làm đúng một việc: verify image.

```yaml
apiVersion: policies.kyverno.io/v1
kind: ImageValidatingPolicy
metadata:
  name: verify-cosign-key
spec:
  webhookConfiguration:
    timeoutSeconds: 30
  evaluation:
    background:
      enabled: false
  validationActions: [Deny]
  matchConstraints:
    resourceRules:
      - apiGroups: [""]
        apiVersions: ["v1"]
        operations: ["CREATE", "UPDATE"]
        resources: ["pods"]
  matchImageReferences:
    - glob: "kind-registry:5000/secure-app/*"
  validationConfigurations:
    required: true
    mutateDigest: true
    verifyDigest: false
  attestors:
    - name: cosign
      cosign:
        key:
          data: |
            -----BEGIN PUBLIC KEY-----
            <nội dung cosign.pub>
            -----END PUBLIC KEY-----
  validations:
    - expression: >-
        images.containers.map(image, verifyImageSignatures(image, [attestors.cosign])).all(e, e > 0)
      message: "Image phải có chữ ký cosign hợp lệ."
```

Bạn cần nhớ ba điều cho kỳ thi và phỏng vấn:

1. **Khái niệm không đổi**: vẫn là "webhook đọc image reference, tải chữ ký từ registry, verify với attestor (key/keyless), deny hoặc mutate". Chỉ cú pháp YAML thay đổi.
2. **ClusterPolicy vẫn còn phổ biến trong cluster thật** (và trong tài liệu CKS hiện hành). Đề thi có thể dùng cả hai dạng; hãy đọc kỹ đề bài cho dạng policy nào.
3. **Đừng ghim nhầm công cụ theo "mốt"**: nếu cluster của bạn dùng Kyverno v1.17 và policy `verifyImages` đang chạy tốt, việc nâng lên v1.19 rồi bị cảnh báo deprecation là vấn đề vận hành có kế hoạch, không phải sự cố. Hãy test policy bằng `kyverno test`/CLI trước khi áp vào cluster.

## Static analysis workload và container image {#static-analysis-workload-va-image}

Static analysis là phân tích **tĩnh** — không cần chạy workload. Với container image, "tĩnh" nghĩa là đọc filesystem/package trong image; với manifest, nghĩa là đọc YAML. Đây là lớp phòng thủ rẻ nhất và sớm nhất, nên là thứ đầu tiên nên có trong pipeline.

### Trivy: image, manifest và secret {#trivy}

**Trivy** (Aqua Security) là công cụ "một cửa" phổ biến nhất: scan CVE trong image/filesystem, misconfiguration trong IaC/manifest, và secret bị lộ. Các chế độ bạn cần nhớ:

```bash
# 1. Scan CVE trong image (image đang có trong daemon hoặc từ registry)
trivy image secure-app/app:full
trivy image --scanners vuln --severity HIGH,CRITICAL secure-app/app:full
trivy image --scanners vuln --ignore-unfixed --exit-code 1 secure-app/app:full

# 2. Scan manifest/IaC (k8s YAML, Helm chart, Dockerfile, Terraform...)
trivy config manifests/
trivy config --severity HIGH,CRITICAL manifests/weak-deployment.yaml
trivy fs --scanners vuln,misconfig,secret .

# 3. Scan secret (có thể bật lẫn trong image/fs/repo)
trivy image --scanners secret secure-app/app:full

# 4. Scan một SBOM đã lưu
trivy sbom --scanners vuln --severity HIGH,CRITICAL sbom.spdx.json
```

Mẹo sử dụng trong CI và trong phòng thi:

- `--exit-code 1` để pipeline fail khi có phát hiện, kết hợp `--severity` để chỉ fail ở mức cần chặn.
- `--ignore-unfixed` loại CVE chưa có bản vá; dùng khi bạn muốn tập trung vào những gì sửa được ngay (và vẫn phải theo dõi phần bị loại).
- `.trivyignore` cho các false positive đã được review; đừng lạm dụng nó để "làm xanh" pipeline.
- `--format sarif -o trivy.sarif` để upload lên GitHub code scanning hoặc DefectDojo.
- Trivy có subcommand `trivy k8s` để scan cả cluster (cần quyền đọc) — hữu ích cho audit, không cần cho CKS.

### Kubesec {#kubesec}

**Kubesec** (ControlPlane) chấm điểm một manifest YAML: rule nguy hiểm cho **điểm âm**, cấu hình tốt cho điểm dương. Nó tập trung vào lỗi cấu hình bảo mật cấp pod/container, không scan CVE.

```bash
# Scan một hoặc nhiều document YAML trong cùng file
kubesec scan manifests/weak-deployment.yaml

# Bảng cho người đọc, và JSON cho máy
kubesec scan manifests/weak-deployment.yaml --format table
kubesec scan manifests/weak-deployment.yaml --format json

# In toàn bộ rule kèm điểm để hiểu nó chấm gì
kubesec print-rules --format table

# Nhận YAML từ stdin (dùng được với helm template, kustomize build)
kustomize build overlays/prod | kubesec scan /dev/stdin
```

Output có cấu trúc dễ đọc bằng máy:

```json
[
  {
    "object": "Deployment/weak-web.secure-app",
    "valid": true,
    "message": "Failed with a score of -69 points",
    "score": -69,
    "scoring": {
      "critical": [
        { "id": "Privileged", "reason": "Privileged containers can allow almost completely unrestricted host access", "points": -30 },
        { "id": "CapSysAdmin", "reason": "CAP_SYS_ADMIN is the most privileged capability and should always be avoided", "points": -30 },
        { "id": "HostNetwork", "reason": "Sharing the host's network namespace permits processes in the pod to communicate with processes bound to the host's loopback adapter", "points": -9 }
      ],
      "advise": [
        { "id": "RunAsNonRoot", "reason": "Force the running image to run as a non-root user to ensure least privilege", "points": 1 },
        { "id": "ReadOnlyRootFilesystem", "reason": "Immutable root filesystems increase attack cost", "points": 1 }
      ]
    }
  }
]
```

Cách dùng trong CI: **đừng chỉ gate theo tổng score** (một lỗi critical có thể bị "cân bằng" bởi nhiều điểm dương). Hãy gate theo `scoring.critical`:

```bash
kubesec scan manifests/weak-deployment.yaml --format json --exit-code 0 > kubesec.json

# Fail nếu còn bất kỳ critical finding nào
jq --exit-status 'all(.[]; ((.scoring.critical // []) | length) == 0)' kubesec.json
```

Hai lưu ý: kubesec mặc định trả **exit code 2** khi score nhỏ hơn hoặc bằng 0 (đổi bằng `--exit-code`), và có bản chạy dạng server + API hosted tại `v2.kubesec.io`. **Không gửi manifest chứa Secret lên API hosted của bên thứ ba** — dùng binary local hoặc server nội bộ.

### KubeLinter {#kubelinter}

**KubeLinter** (StackRox/Red Hat) là "linter" cho manifest và Helm chart: kiểm tra cấu hình theo **best practice** (securityContext, resources, probe, label, selector...) và trả về danh sách lỗi kèm remediation. KubeLinter không cần cluster.

```bash
# Lint một file hoặc cả thư mục
kube-linter lint manifests/
kube-linter lint manifests/weak-deployment.yaml --format json

# Liệt kê checks có sẵn để chọn/bỏ
kube-linter checks list

# Cấu hình bằng .kube-linter.yaml (tự đọc trong thư mục hiện tại)
kube-linter lint manifests/ --config .kube-linter.yaml
```

File cấu hình mẫu hay dùng trong repo:

```yaml
# .kube-linter.yaml
checks:
  addAllBuiltIn: true
  # Bỏ những check không phù hợp với môi trường của bạn (có chủ đích, có ghi chú)
  exclude:
    - "unset-cpu-requirements"
    - "unset-memory-requirements"
```

Output dạng text (rút gọn) trông như sau, và exit code khác 0 khi có lỗi:

```text
manifests/weak-deployment.yaml: (object: secure-app/weak-web apps/v1, Kind=Deployment) container "web" does not have a read-only root file system (check: no-read-only-root-fs, remediation: Set securityContext.readOnlyRootFilesystem to true in the container specification.)
manifests/weak-deployment.yaml: (object: secure-app/weak-web apps/v1, Kind=Deployment) container "web" is not set to runAsNonRoot (check: run-as-non-root, remediation: ...)
manifests/weak-deployment.yaml: (object: secure-app/weak-web apps/v1, Kind=Deployment) container "web" is using the 'latest' tag (check: latest-tag, remediation: ...)
manifests/weak-deployment.yaml: (object: secure-app/weak-web apps/v1, Kind=Deployment) pod "weak-web" is using hostNetwork (check: non-isolated-pod, remediation: ...)

Error: found 9 lint errors
```

Ba điều cần nói khi phỏng vấn về KubeLinter: (1) nó là linter **tĩnh**, chạy được ngay trên laptop và trong CI, không cần cluster; (2) có thể bật toàn bộ check mặc định bằng `addAllBuiltIn` rồi loại trừ dần; (3) nó **không** biết ý định của bạn — một số cảnh báo là chấp nhận được với workload cụ thể, nên cấu hình exclude phải được review như code.

### Checklist static analysis {#checklist-static-analysis}

Bảng dưới là checklist tôi dùng để quyết định dùng công cụ nào ở đâu. Nhớ nguyên tắc "shift left": càng gần laptop dev càng rẻ.

| Mục tiêu | Công cụ | Lệnh tiêu biểu | Chạy ở đâu |
|---|---|---|---|
| CVE trong OS package của image | Trivy, Grype | `trivy image --severity HIGH,CRITICAL <image>` | CI (sau build), trước push |
| CVE trong dependency ngôn ngữ | Trivy, Grype, `npm audit`, `pip-audit` | `trivy fs --scanners vuln .` | CI, mỗi PR |
| Secret bị lộ trong image/repo | Trivy (`--scanners secret`), gitleaks | `trivy fs --scanners secret .` | Pre-commit, CI |
| Misconfiguration trong manifest | Trivy (`trivy config`), KubeLinter | `trivy config manifests/` | CI, pre-commit |
| Điểm rủi ro cấu hình pod/container | Kubesec | `kubesec scan <file>` | CI, local |
| Best practice manifest (resources, probe, label...) | KubeLinter | `kube-linter lint manifests/` | CI, local |
| Cấu hình Dockerfile (base lạ, chạy root, thừa gói) | Trivy config, hadolint | `trivy config Dockerfile.full` | CI, local |
| Cấu hình cluster (CIS Benchmark) | kube-bench | xem chương 6 | Định kỳ, audit |
| Chữ ký/attestation của artifact | cosign | `cosign verify`, `cosign verify-attestation` | Admission, CI |

Một "sự thật phũ phàng" cần nhớ: **các công cụ này không thay thế nhau và đôi khi kết quả không khớp**. Trivy và Grype có thể đếm CVE khác nhau cho cùng một image vì khác nguồn dữ liệu (NVD, GHSA, vendor advisory) và khác cách map package. Đừng biến việc "hai scanner báo khác nhau" thành tranh cãi; hãy chọn một scanner làm nguồn chính cho policy gate, và dùng scanner còn lại để đối chiếu khi điều tra.

### Tích hợp vào CI {#tich-hop-vao-ci}

Trong pipeline chuẩn (chi tiết ở chương 12), thứ tự tôi khuyên dùng là: **lint manifest, build, scan image, sinh SBOM, push, ký, verify trong cùng pipeline**. Nếu bước scan fail, không có gì được push; nếu push được, nó đã được ký.

```yaml
# Trích pipeline (GitHub Actions) — bản đầy đủ ở chương 12
name: secure-image
on: [push]

jobs:
  build-scan-sign:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Build image
        run: docker build -f Dockerfile.distroless -t $IMAGE .
      - name: Lint manifest tĩnh
        run: kube-linter lint manifests/ --config .kube-linter.yaml
      - name: Scan image
        run: trivy image --scanners vuln,secret --severity HIGH,CRITICAL --exit-code 1 $IMAGE
      - name: Generate SBOM
        run: syft docker:$IMAGE -o spdx-json=sbom.spdx.json
      - name: Push và lấy digest
        run: docker push $REGISTRY/$IMAGE
      - name: Sign theo digest
        run: cosign sign --yes --key env://COSIGN_PRIVATE_KEY $REGISTRY/$IMAGE@$DIGEST
      - name: Verify lại ngay trong pipeline
        run: cosign verify --key cosign.pub $REGISTRY/$IMAGE@$DIGEST
```

Ba lưu ý về gating để không biến pipeline thành "cửa quay":

1. **Fail ở mức CRITICAL/HIGH có bản fix** là mức thực tế nhất; đừng bật fail cho mọi LOW, team sẽ tìm cách bypass.
2. **Luôn lưu report** (artifact/SARIF) kể cả khi pass, để có dữ liệu so sánh giữa các lần chạy.
3. **Verify ngay trong pipeline** (bước cuối) để chắc chắn chữ ký thực sự attach — nhiều sự cố xảy ra vì ký thất bại nhưng pipeline vẫn xanh do không ai kiểm tra.

## Quản lý lỗ hổng image {#quan-ly-lo-hong-image}

### Đọc kết quả scan {#doc-ket-qua-scan}

Output của Trivy/Grype không phải là "danh sách việc cần làm ngay". Hãy phân loại trước khi hành động:

- **Có bản fix hay không**: CVE có cột `Fixed Version` là loại sửa được (nâng package/base). CVE không có bản fix chỉ có thể giảm thiểu (không dùng package đó, cấu hình lại, chuyển base).
- **Package thuộc đâu**: CVE trong OS package của base image khác với CVE trong dependency ứng dụng. Loại thứ nhất nâng base là xong; loại thứ hai cần sửa lockfile/dependency.
- **Có bị khai thác thực tế không**: mức severity (CVSS) khác với "có exploit ngoài đời" (EPSS, danh sách CISA KEV). Một CVE HIGH nhưng chỉ khai thác được khi bật cấu hình bạn không dùng có thể hạ ưu tiên; một CVE có exploit công khai, khai thác không cần xác thực thì phải xử lý ngay dù chỉ MEDIUM.
- **False positive**: scanner có thể thấy package nhưng thực tế code path không dùng. Đây là chỗ **VEX** (Vulnerability Exploitability eXchange) xuất hiện: bạn phát hành statement "not affected" kèm lý do, để compliance nhìn thấy lý do thay vì tưởng bạn bỏ qua.

### Remediation flow {#remediation-flow}

Một quy trình remediation thực tế, theo thứ tự hiệu quả từ cao xuống thấp:

1. **Nâng base image** (đổi tag/digest distroless/slim mới) rồi rebuild — giải quyết phần lớn CVE OS package với chi phí thấp nhất.
2. **Nâng dependency trực tiếp** gây CVE; sau đó chạy lại test để chắc không phá API.
3. **Rebuild để loại bỏ toolchain khỏi runtime** — nhiều CVE nằm ở build tool vẫn bị mang vào image cuối vì Dockerfile cẩu thả.
4. **Giảm thành phần**: bỏ package không cần, chuyển sang base nhỏ hơn, tắt tính năng không dùng.
5. **Giảm thiểu (mitigate) khi không có bản fix**: NetworkPolicy chặn khai thác từ xa, seccomp/AppArmor, chạy non-root, read-only rootfs, tách workload.
6. **Chấp nhận có ghi nhận**: ghi vào VEX/risk register, đặt ngày review, không im lặng bỏ qua.

Với mỗi mức severity, hãy có SLA rõ ràng. Ví dụ tôi dùng (con số tùy tổ chức):

| Mức | Có bản fix | Không có bản fix |
|---|---|---|
| CRITICAL | 24–72 giờ | Mitigation ngay, review hàng tuần |
| HIGH | 7 ngày | Mitigation + review 2 tuần/lần |
| MEDIUM | 30 ngày | Đưa vào backlog, review định kỳ |
| LOW | Theo lịch rebuild định kỳ | Ghi nhận |

### Grype và các scanner khác {#grype}

**Grype** (Anchore) là scanner CVE thường đi cùng **syft**: syft sinh SBOM, Grype scan SBOM/image đó tìm lỗ hổng. Grype có `--fail-on` để gate pipeline và hỗ trợ scan image trực tiếp:

```bash
syft docker:secure-app/app:distroless -o json | grype
grype secure-app/app:full --fail-on high
grype sbom:./sbom.spdx.json --fail-on critical
```

Ngoài ra còn có **Snyk**, **Aqua**, **Prisma Cloud**, **Wiz** (thương mại) và **Clair**, **Trivy** (mã nguồn mở). Điểm cần nhớ: các scanner khác nhau về cơ sở dữ liệu và cách map package, nên hãy thống nhất một scanner cho gate và ghi lại version + DB timestamp trong report — đây là chi tiết audit rất đáng giá.

### Ghim version và rebuild định kỳ {#ghim-version-va-rebuild-dinh-ky}

Tư duy "build một lần, chạy mãi" là tư duy của supply chain yếu. Base image và dependency **cũ đi mỗi ngày** dù bạn không đổi code: CVE mới được công bố, bản vá mới ra. Vì vậy hãy lên lịch rebuild:

- **Rebuild định kỳ** (hàng tuần hoặc hàng tháng) với base digest mới nhất; rebuild cũng là lúc chạy scan lại.
- **Rebuild khi base image có bản vá bảo mật** — có thể tự động hóa bằng Renovate/Dependabot tạo PR "nâng base digest", pipeline lo phần scan + ký.
- **Ghim chính xác những gì cần tái lập** (base digest, version dependency qua lockfile) nhưng **không ghim cứng những gì cần cập nhật** (base tag cũ, package EOL).
- **Giữ SBOM theo từng release** — đây là thứ cho phép bạn trả lời "image nào đang chạy trong production bị ảnh hưởng?" trong vài phút khi có CVE lớn.

### Bước 2: Cluster kind và registry nội bộ {#lab-buoc-2}

kind mặc định không có registry. Ta dựng một registry nhỏ (image `registry:3`) làm registry "nội bộ" của lab, publish trên host port **5000** và đặt tên DNS là `kind-registry` để cả host, node và pod cùng dùng một tham chiếu image thống nhất. Đây cũng là bài học thực tế: **một registry phải phân giải được từ ba nơi** — máy build (push), containerd trên node (pull), và controller admission (verify).

```bash
# 1. Registry container, publish ở 127.0.0.1:5000, tên kind-registry
docker run -d --restart=always -p "127.0.0.1:5000:5000" --name kind-registry registry:3

# 2. Cluster kind (1 node control-plane là đủ cho lab)
cat > ch10-kind.yaml <<'EOF'
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
name: ch10-lab
nodes:
  - role: control-plane
EOF

kind create cluster --config ch10-kind.yaml --image kindest/node:v1.33.1
kubectl get nodes
```

Nối registry vào network của kind và cho containerd biết registry này chạy **HTTP** (không TLS) — mặc định containerd sẽ thử HTTPS trước:

```bash
# Nối registry container vào network 'kind' để node resolve được tên kind-registry
docker network connect kind kind-registry 2>/dev/null || true

# kind v0.27+ đã bật sẵn config_path=/etc/containerd/certs.d trong node image,
# nên chỉ cần thả file hosts.toml cho registry host nội bộ
REG_DIR="/etc/containerd/certs.d/kind-registry:5000"
for node in $(kind get nodes --name ch10-lab); do
  docker exec "${node}" mkdir -p "${REG_DIR}"
  echo 'server = "http://kind-registry:5000"' | docker exec -i "${node}" cp /dev/stdin "${REG_DIR}/hosts.toml"
done

# Kiểm tra file đã được đặt đúng trong node
docker exec ch10-lab-control-plane cat /etc/containerd/certs.d/kind-registry:5000/hosts.toml
# server = "http://kind-registry:5000"
```

Cấu hình phía **máy host** để `docker push` dùng được tên `kind-registry`:

```bash

echo "127.0.0.1 kind-registry" | sudo tee -a /etc/hosts

# Docker Desktop (Windows/WSL2): Settings -> Docker Engine, thêm vào JSON:
# {
#   "insecure-registries": ["kind-registry:5000"]
# }
# rồi bấm Apply & Restart.
```

### Bước 3: Build hai image: full và distroless {#lab-buoc-3}

Ứng dụng demo là một HTTP server Go tối giản (không dependency ngoài, build ra binary tĩnh).

`app/main.go`:

```go
package main

import (
    "fmt"
    "log"
    "net/http"
    "os"
)

func main() {
    version := os.Getenv("APP_VERSION")
    if version == "" {
        version = "dev"
    }

    // Endpoint health check dùng cho probe và smoke test
    http.HandleFunc("/healthz", func(w http.ResponseWriter, r *http.Request) {
        fmt.Fprintln(w, "ok", version)
    })
    http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
        fmt.Fprintln(w, "supply chain demo", version)
    })

    log.Println("listening on :8080")
    log.Fatal(http.ListenAndServe(":8080", nil))
}
```

`Dockerfile.full` — runtime dùng base "full" để thấy rõ cái giá của vài chục MB và hàng trăm package:

```dockerfile
# Stage build: toolchain, compiler, source
FROM golang:1.24-alpine AS builder
WORKDIR /src
COPY app/main.go .
RUN go mod init demo.local/app && CGO_ENABLED=0 GOOS=linux go build -trimpath -ldflags="-s -w" -o /out/app .

# Stage runtime: base full (ubuntu) — quen thuộc nhưng nặng
FROM ubuntu:24.04
RUN apt-get update && apt-get install -y --no-install-recommends ca-certificates curl bash && rm -rf /var/lib/apt/lists/*
COPY --from=builder /out/app /app
EXPOSE 8080
CMD ["/app"]
```

`Dockerfile.distroless` — cùng ứng dụng, runtime chỉ có binary:

```dockerfile
# Stage build giống hệt Dockerfile.full
FROM golang:1.24-alpine AS builder
WORKDIR /src
COPY app/main.go .
RUN go mod init demo.local/app && CGO_ENABLED=0 GOOS=linux go build -trimpath -ldflags="-s -w" -o /out/app .

# Stage runtime: distroless static, chạy sẵn non-root, không shell, không package manager
FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=builder /out/app /app
USER nonroot:nonroot
EXPOSE 8080
ENTRYPOINT ["/app"]
```

### Bước 6: Push image và ký bằng cosign {#lab-buoc-6}

Push cả hai image, trong đó image **full** được để **chưa ký** làm "vật thí nghiệm" cho bước 7:

```bash
cd ~/ch10-lab

docker tag secure-app/app:full        kind-registry:5000/secure-app/app:full
docker tag secure-app/app:distroless  kind-registry:5000/secure-app/app:distroless

docker push kind-registry:5000/secure-app/app:full
docker push kind-registry:5000/secure-app/app:distroless

# Kiểm chứng registry đã nhận đủ 2 tag
curl -s http://127.0.0.1:5000/v2/secure-app/app/tags/list
# {"name":"secure-app/app","tags":["distroless","full"]}
```

Sinh cặp khóa và ký image distroless:

```bash
cd cosign

# COSIGN_PASSWORD tránh prompt; trong production hãy lấy từ secret manager
export COSIGN_PASSWORD="mat-khau-lab-101"
cosign generate-key-pair
# cosign.key (private — KHÔNG commit, KHÔNG copy vào CI ở dạng plain text)
# cosign.pub (public — chia sẻ rộng rãi, dùng trong policy)

cd ..

# Ký theo tag cho gọn; cosign resolve ra digest và gắn chữ ký vào digest đó
cosign sign --yes --key cosign/cosign.key --allow-http-registry kind-registry:5000/secure-app/app:distroless

# Verify bằng public key
cosign verify --key cosign/cosign.pub --allow-http-registry kind-registry:5000/secure-app/app:distroless | jq .
```

Output verify có các trường `Critical.Identity.docker-reference` và `Critical.Image.docker-manifest-digest` — hãy đọc chúng để thấy chữ ký gắn với **digest**, không phải với tag.

Kiểm tra chữ ký được lưu như thế nào:

```bash
# Xem các artifact gắn với image (chữ ký, attestation)
cosign tree kind-registry:5000/secure-app/app:distroless

# Danh sách tag trong repo: bạn sẽ thấy thêm tag dạng sha256-<digest>.sig
curl -s http://127.0.0.1:5000/v2/secure-app/app/tags/list | jq .
```

Thử "tấn công" để thấy giá trị của việc ký: image chưa ký (full) không thể vượt qua `cosign verify` dù tag trông hoàn toàn bình thường:

```bash
cosign verify --key cosign/cosign.pub --allow-http-registry kind-registry:5000/secure-app/app:full
# Error: no matching signatures: ...
```

Đính kèm SBOM đã tạo ở bước 5 vào image bằng attestation (tùy chọn nhưng rất đáng làm):

```bash
cosign attest --yes --key cosign/cosign.key --allow-http-registry --predicate sbom-distroless.cdx.json --type cyclonedx kind-registry:5000/secure-app/app:distroless

cosign verify-attestation --key cosign/cosign.pub --allow-http-registry --type cyclonedx kind-registry:5000/secure-app/app:distroless | jq -r '.[].payload' | base64 -d | jq '.predicate.bomFormat'
# "CycloneDX"
```

Ghi chú về transparency log: các lệnh trên dùng mặc định (có đẩy bản ghi lên Rekor), nên cần Internet. Trong môi trường air-gapped, ký với `--tlog-upload=false` và verify với `--insecure-ignore-tlog`; khi đó policy Kyverno phải có `rekor.ignoreTlog: true`.

### Bước 7: Kyverno verifyImages và test image đã ký/chưa ký {#lab-buoc-7}

Cài Kyverno v1.17.2 (bản còn hỗ trợ đầy đủ ClusterPolicy `verifyImages`):

```bash
kubectl apply -f https://github.com/kyverno/kyverno/releases/download/v1.17.2/install.yaml
kubectl -n kyverno rollout status deployment/kyverno-admission-controller --timeout=300s
kubectl -n kyverno get pods
```

Kyverno phải truy cập được registry HTTP của lab **từ trong cluster**. Node resolve `kind-registry` nhờ Docker DNS, nhưng pod thì không — vì vậy ta lấy IP registry trong network `kind` và gắn vào pod Kyverno bằng `hostAliases`, đồng thời bật cờ cho phép registry insecure:

```bash
cd ~/ch10-lab

# Lấy IP của registry trong network kind
REG_IP=$(docker inspect kind-registry | jq -r '.[0].NetworkSettings.Networks.kind.IPAddress')
echo "registry IP: $REG_IP"

# 1) Cho Kyverno gọi registry không TLS
kubectl -n kyverno patch deployment kyverno-admission-controller --type=json -p '[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--allowInsecureRegistry=true"}]'

# 2) Cho pod Kyverno resolve tên kind-registry, dùng strategic merge patch từ file
cat > kyverno-patch.yaml <<EOF
spec:
  template:
    spec:
      hostAliases:
        - ip: $REG_IP
          hostnames:
            - kind-registry
EOF
kubectl -n kyverno patch deployment kyverno-admission-controller --type=strategic --patch-file kyverno-patch.yaml

kubectl -n kyverno rollout status deployment/kyverno-admission-controller --timeout=180s
```

Tạo policy `verifyImages` với public key vừa sinh (nhúng trực tiếp `cosign.pub` vào YAML bằng `sed`):

```bash
cat > ch10-kyverno-verify.yaml <<EOF
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: verify-supply-chain-images
spec:
  background: false
  validationFailureAction: Enforce
  webhookConfiguration:
    failurePolicy: Fail
    timeoutSeconds: 30
  rules:
    - name: verify-cosign-signature
      match:
        any:
          - resources:
              kinds:
                - Pod
              namespaces:
                - secure-app
      verifyImages:
        - imageReferences:
            - "kind-registry:5000/secure-app/*"
          mutateDigest: true
          verifyDigest: false
          required: true
          imageRegistryCredentials:
            allowInsecureRegistry: true
          attestors:
            - entries:
                - keys:
                    publicKeys: |
$(sed 's/^/                      /' cosign/cosign.pub)
EOF

kubectl apply -f ch10-kyverno-verify.yaml
kubectl get clusterpolicy verify-supply-chain-images
```

Nghiệm thu thêm: một image cùng repo nhưng **chưa được ký** vẫn bị chặn — đây là điểm mấu chốt của supply chain (tên repo không nói lên điều gì, chữ ký mới nói):


```bash

```

## Câu hỏi phỏng vấn thường gặp {#interview-questions}

**1. Làm thế nào để giảm bề mặt tấn công của một container image?**

Bốn nhóm việc theo thứ tự hiệu quả: (1) chọn base image tối thiểu — distroless/alpine/slim thay cho bản full, ghim bằng digest; (2) dùng multi-stage build để compiler và build tool không vào image cuối, chỉ `COPY --from=` những gì thật sự cần; (3) cấu hình runtime an toàn — `runAsNonRoot`, `readOnlyRootFilesystem`, `drop: [ALL]`, `allowPrivilegeEscalation: false`, `seccompProfile: RuntimeDefault`; (4) bỏ mọi thứ "tiện debug" như shell, curl, package manager, và scan lại image sau mỗi thay đổi. Mục tiêu không chỉ là ít CVE mà còn là **ít công cụ để kẻ tấn công sử dụng** nếu chúng vào được container.

**2. Distroless khác alpine ở điểm nào và khi nào chọn cái nào?**

Distroless không có shell, package manager hay công cụ hệ thống — chỉ có runtime library cần thiết; alpine là một distro đầy đủ nhưng siêu nhỏ dựa trên musl + busybox. Distroless thắng về bề mặt tấn công và tính "không thể tương tác", nhưng debug khó (không `exec` được shell; phải dùng ephemeral container hoặc biến thể `:debug`). Alpine thắng ở tính linh hoạt và tương thích với nhiều build, nhưng có thể vướng vấn đề musl với native extension. Với binary tĩnh (Go/Rust) tôi chọn distroless; với ứng dụng cần debug thường xuyên trong production, tôi chọn biến thể `-slim` của language image thay vì alpine để tránh bất ngờ musl.

**3. SBOM là gì, khác gì scan CVE, và dùng khi nào?**

SBOM là bảng kê thành phần của artifact ở định dạng chuẩn (SPDX hoặc CycloneDX), trả lời "trong artifact có gì". Scan CVE trả lời "thành phần đó có lỗ hổng đang biết không". SBOM không thay thế scan và ngược lại; giá trị lớn nhất của SBOM là ở thời điểm **sau** release: khi có CVE mới, bạn tra trong SBOM đã lưu để biết image nào bị ảnh hưởng mà không cần scan lại toàn bộ. Trong pipeline chuyên nghiệp, SBOM được sinh tự động, lưu cùng artifact (hoặc attest vào image bằng cosign) và dùng làm đầu vào cho scanner khi cần.

**4. Vì sao nên ký image theo digest thay vì theo tag?**

Tag là con trỏ có thể bị ghi đè, digest là định danh nội dung. Nếu bạn ký theo tag, có thể xảy ra TOCTOU: policy verify tag `v1` (là image A), sau đó ai đó push đè `v1` bằng image B, node pull image B — pod chạy thứ chưa từng được verify. Ký và deploy theo digest loại bỏ kịch bản đó; ngoài ra `mutateDigest: true` trong Kyverno khiến pod spec được ghi lại theo digest đã verify. Đây cũng là lý do nên bật immutable tag trên registry: càng ít tag mutable, càng ít đường tấn công.

**5. Nếu kẻ tấn công lấy được private key ký của bạn thì sao?**

Họ ký được image "hợp lệ" theo policy, nên chữ ký một mình không cứu được bạn. Lớp bảo vệ bổ sung: (1) provenance/attestation mô tả pipeline, commit, builder — policy có thể yêu cầu attestation khớp với repo/workflow; (2) transparency log (Rekor) ghi lại mọi lần ký nên việc ký ngoài quy trình có thể bị phát hiện; (3) tách quyền — key nằm trong KMS, CI không đọc được raw key; (4) luân chuyển khóa định kỳ và có playbook revoke. Nói ngắn: chữ ký chứng minh "được ký bằng key X", provenance chứng minh "được tạo bởi pipeline Y" — cần cả hai cho mức bảo vệ cao.

**6. Keyless signing hoạt động thế nào và cần chú ý gì khi verify?**

cosign lấy OIDC token của CI/user, đổi lấy certificate ngắn hạn từ Fulcio gắn với identity, ký image và ghi signature + certificate vào Rekor. Verify keyless không truyền public key mà truyền **identity và issuer chấp nhận** (`--certificate-identity`, `--certificate-oidc-issuer`), có thể ghim cả workflow ref. Chú ý: phải ghim identity chặt (đừng dùng regex quá rộng), phải tin tưởng hạ tầng Fulcio/Rekor, và cần Internet hoặc hạ tầng tương đương nội bộ cho môi trường air-gapped.

**7. Policy verify chữ ký tại admission có thể gây sập deploy như thế nào và bạn phòng thế nào?**

Policy chạy trên mọi request tạo pod khớp `match`, và nếu `failurePolicy: Fail` thì khi webhook lỗi hoặc registry không truy cập được, mọi pod trong phạm vi bị chặn. Các phòng ngừa: khoanh vùng `match` theo namespace (đặc biệt loại trừ `kube-system` và chính namespace của Kyverno), đặt `timeoutSeconds` hợp lý, mở đường mạng/DNS/credential cho controller tới registry (đừng giả định controller giống node), bật cache kết quả verify để giảm tải, và có alert cho webhook error rate. Trong production còn nên chạy chế độ Audit song song trước khi Enforce.

**8. Phân biệt Kubesec, KubeLinter, Trivy và kube-bench?**

Kubesec: chấm điểm một manifest pod/controller theo rule bảo mật, điểm âm là lỗi nghiêm trọng (privileged, hostNetwork, SYS_ADMIN); không scan CVE. KubeLinter: lint manifest theo best practice (resources, probe, label, securityContext), không cần cluster, trả danh sách lỗi kèm remediation. Trivy: scan CVE trong image/filesystem, misconfig trong IaC/manifest và secret — ba trong một. kube-bench: kiểm tra cấu hình cluster theo CIS Benchmark (đã học ở chương 6). Bốn công cụ không thay thế nhau: một cái nhìn vào artifact, ba cái nhìn vào workload, một cái nhìn vào cluster.

**9. Bạn nhận một báo cáo Trivy với 200 lỗ hổng HIGH trên image production. Bạn xử lý thế nào?**

Trước tiên phân loại, không sửa mù: bao nhiêu có bản fix, bao nhiêu là OS package của base (nâng base là giải quyết), bao nhiêu là dependency ứng dụng, bao nhiêu có exploit thực tế (EPSS/KEV). Ưu tiên: nâng base digest và rebuild (giải quyết phần lớn CVE OS), nâng dependency trực tiếp, rồi xử lý nhóm còn lại bằng mitigation (NetworkPolicy, seccomp) hoặc VEX có ghi nhận. Song song, thêm gate vào CI để image mới không vượt qua nếu còn CRITICAL có fix, lên lịch rebuild định kỳ, và theo dõi SLA theo mức severity. Điều sai thường thấy là dùng `.trivyignore` để pipeline xanh — đó là che bệnh, không phải chữa.

**10. Pod của tôi vẫn chạy image cũ dù đã push tag mới lên registry. Vì sao?**

Vì tag là con trỏ và kubelet cache image trên node: với tag `:v1` và `imagePullPolicy: IfNotPresent`, kubelet thấy digest local đã khớp tag nên không pull lại; hoặc bạn dùng `:latest` với policy `Always` nhưng pod cũ chưa được thay. Cách sửa đúng là deploy theo digest (hoặc tag immutable mới như `v1.2.4`), tránh ghi đè tag. `imagePullPolicy: Always` chỉ là giải pháp tạm và **không** giải quyết vấn đề supply chain — nó còn khiến kẻ tấn công ghi đè tag đến được node dễ hơn.

**11. Provenance và SLSA giúp gì mà chữ ký không giúp được?**

Chữ ký trả lời "ai ký" — kẻ tấn công có key vẫn qua được. Provenance trả lời "artifact được tạo ra thế nào: từ commit nào, bằng pipeline nào, trên builder nào, với tham số gì", và bản thân provenance cũng được ký. SLSA phân cấp mức đảm bảo cho phần build: L1 có provenance, L2 provenance được ký bởi nền tảng hosted, L3 build cô lập và provenance không thể giả mạo từ bên trong. Nhờ đó policy có thể yêu cầu "image phải có attestation SLSA L2 từ đúng workflow" — mức bảo vệ cao hơn hẳn "có chữ ký là được".

## Các điểm chính {#key-points}

- Domain Supply Chain Security chiếm **20%** điểm CKS và xoay quanh bốn việc: giảm footprint của image, hiểu chuỗi cung ứng (SBOM, CI/CD, registry), ký/xác thực artifact, và static analysis workload/image.

- Base image quyết định phần lớn bề mặt tấn công: chọn distroless/slim/alpine thay cho bản full, dùng multi-stage để compiler không vào runtime image, chỉ cài package cần thiết, luôn chạy non-root và ghim base bằng digest.

- "Nhỏ hơn" không đồng nghĩa "ít CVE hơn" tại mọi thời điểm — nhưng ít thành phần hơn luôn có nghĩa là ít CVE tiềm năng hơn và ít công cụ để kẻ tấn công lợi dụng. Hãy đánh giá bằng scan thực tế.

- SBOM (SPDX hoặc CycloneDX) là bảng kê thành phần, khác với scan CVE; công cụ chính là syft, có thể attest SBOM vào image bằng cosign, và scan lại bằng `trivy sbom`.

- Artifact repository tin cậy cần: RBAC theo repo, immutable tag, scan-on-push, retention, audit log, và hỗ trợ lưu chữ ký/attestation cạnh image.

- Tag là con trỏ mutable, digest là định danh nội dung. Ký và deploy theo **digest**; `imagePullPolicy: Always` không phải biện pháp bảo mật.

- Cosign ký image với keypair (`generate-key-pair`, `sign`, `verify`) hoặc keyless qua Fulcio/Rekor (verify bằng `--certificate-identity` + `--certificate-oidc-issuer`). Chữ ký được lưu trong registry, gắn với digest; thay đổi image là mất chữ ký.

- `--tlog-upload=false` + `--insecure-ignore-tlog` (và `rekor.ignoreTlog: true` phía Kyverno) là đường đi cho môi trường không có transparency log; mặc định nên giữ tlog để có khả năng truy vết.

- Verify tại admission (Kyverno `verifyImages`, Gatekeeper + external data, Sigstore Policy Controller) gồm: đọc image reference, tải chữ ký từ registry, verify với attestor, deny hoặc mutate sang digest. Ba bẫy chính: controller không truy cập được registry, `failurePolicy: Fail` làm sập diện rộng, và bật `mutateDigest`/`verifyDigest` không đúng.

- Kyverno ClusterPolicy (rule `verifyImages`) đã deprecated từ v1.17 và sẽ được thay bằng **ImageValidatingPolicy** (CEL) — khái niệm không đổi, chỉ khác cú pháp.

- Static analysis: Trivy cho CVE/misconfig/secret của image và IaC; KubeLinter lint manifest theo best practice; Kubesec chấm điểm rủi ro cấu hình pod (gate theo `scoring.critical`, đừng chỉ theo tổng score); kube-bench cho CIS Benchmark của cluster.

- Quản lý lỗ hổng là một quy trình: phân loại (có fix hay không, OS hay app, có exploit thật hay không), remediation theo thứ tự nâng base, nâng dependency, giảm thành phần, mitigation; có SLA theo severity và VEX cho trường hợp chấp nhận.

- Rebuild định kỳ và lưu SBOM theo từng release là hai thói quen giúp bạn trả lời "image nào bị ảnh hưởng?" trong vài phút khi có CVE lớn — nhanh hơn mọi biện pháp phản ứng tại chỗ.

## Câu hỏi thực hành {#practice-questions}

**1. Những phát biểu nào đúng về việc giảm base image footprint? (Chọn tất cả đáp án đúng)**

**A)** Multi-stage build loại bỏ compiler và build tool khỏi runtime image, thường giảm cả kích thước lẫn số CVE tiềm năng.  
**B)** Image distroless thường không có shell và package manager nên debug trong container khó hơn; cần dùng ephemeral container hoặc biến thể `:debug`.  
**C)** Image nhỏ hơn luôn có ít CVE hơn image lớn tại mọi thời điểm, vì vậy chỉ cần chọn base nhỏ nhất là đủ.  
**D)** Thêm `curl`, `bash` và `netcat` vào runtime image là cách tốt để tăng khả năng quan sát khi có sự cố production.

**2. Runtime image nào phù hợp nhất cho ứng dụng Go build ra binary tĩnh, cần bề mặt tấn công nhỏ nhất và chạy non-root?**

**A)** `FROM ubuntu:24.04`, copy binary và cài thêm `ca-certificates`, `curl`, `bash` để tiện vận hành.  
**B)** `FROM gcr.io/distroless/static-debian12:nonroot`, chỉ `COPY --from=builder` binary vào image.  
**C)** `FROM golang:1.24-alpine`, build và giữ nguyên toolchain trong image để tái sử dụng cho lần build sau.  
**D)** `FROM alpine:3.20`, cài `go` và toàn bộ build tool, build trực tiếp trong image cuối.

**3. Những phát biểu nào đúng về SBOM? (Chọn tất cả đáp án đúng)**

**A)** SBOM liệt kê thành phần/phụ thuộc của artifact ở định dạng chuẩn như SPDX hoặc CycloneDX, kèm version và thường có license.  
**B)** Có SBOM thì không cần scan CVE nữa, vì SBOM đã chứa thông tin lỗ hổng.  
**C)** SBOM giúp trả lời nhanh câu hỏi "image nào trong production dính CVE mới công bố?" nếu bạn lưu SBOM theo từng release.  
**D)** `syft` chỉ sinh được SBOM khi có cluster đang chạy, và SBOM không thể dùng lại để scan về sau.

**4. Trivy báo image `full` của bạn có 40 CVE LOW/MEDIUM và 6 CVE HIGH (2 trong đó đã có bản fix); image `distroless` chỉ có 1 CVE MEDIUM. Hành động nào hợp lý nhất?**

**A)** Bật `.trivyignore` cho toàn bộ CVE HIGH để pipeline không fail, và giữ nguyên image hiện tại.  
**B)** Ưu tiên xử lý 2 CVE HIGH có bản fix bằng cách nâng base/dependency và rebuild, chuyển runtime sang distroless, ghi nhận các CVE chưa có fix vào VEX/backlog và ghim digest cho artifact mới.  
**C)** Hạ severity filter xuống chỉ còn LOW để báo cáo không còn HIGH, coi như đã xử lý xong.  
**D)** Chuyển toàn bộ sang distroless và không cần quan tâm các CVE còn lại vì image nhỏ hơn là an toàn hơn.

**5. Những phát biểu nào đúng về cosign với keypair? (Chọn tất cả đáp án đúng)**

**A)** `cosign generate-key-pair` tạo `cosign.key` (private) và `cosign.pub` (public); private key phải được bảo vệ nghiêm ngặt và không được commit vào Git.  
**B)** Chữ ký được gắn với digest của image, nên nếu nội dung image thay đổi thì chữ ký cũ không còn hợp lệ dù giữ nguyên tag.  
**C)** `cosign verify` bắt buộc phải có private key vì quá trình verify cần giải mã chữ ký bằng khóa bí mật.  
**D)** Chỉ cần ký image một lần là đủ; khi rebuild image không cần ký lại vì tag không đổi.

**6. Những phát biểu nào đúng về keyless signing với Fulcio và Rekor? (Chọn tất cả đáp án đúng)**

**A)** Keyless dùng OIDC identity của CI hoặc người dùng để lấy certificate ngắn hạn từ Fulcio, thay vì dùng private key dài hạn.  
**B)** Rekor lưu private key của người ký trong transparency log để có thể ký lại khi cần.  
**C)** Khi verify keyless, bạn phải chỉ định identity và issuer được chấp nhận, không chỉ cung cấp một public key cố định.  
**D)** Keyless loại bỏ hoàn toàn rủi ro, vì không còn bất kỳ bí mật nào có thể bị đánh cắp hoặc lạm dụng.

**7. Một policy Kyverno `verifyImages` có `imageReferences: ["kind-registry:5000/secure-app/*"]`, `mutateDigest: true`, `required: true`, `failurePolicy: Fail` và attestor `keys.publicKeys` là public key của bạn. Những phát biểu nào đúng? (Chọn tất cả đáp án đúng)**

**A)** Pod trong namespace `secure-app` dùng image khớp pattern nhưng chưa được ký sẽ bị chặn khi tạo.  
**B)** Image đã ký bằng một key khác vẫn được chấp nhận miễn là nằm trong registry khớp `imageReferences`.  
**C)** Kyverno phải tự truy cập được registry để tải chữ ký; nếu controller không resolve hoặc không kết nối được registry thì verification fail và với `failurePolicy: Fail` pod có thể bị chặn.  
**D)** `mutateDigest: true` khiến image trong pod spec được ghi lại theo digest sau khi verify, đảm bảo artifact chạy đúng là artifact đã được xác thực.

**8. Bạn push `app:v1` lên registry, deploy và pod chạy bình thường. Sau đó bạn build lại image, push đè lên `app:v1`, rồi xóa pod. Pod mới vẫn chạy code cũ. Nguyên nhân và cách sửa đúng nhất là gì?**

**A)** Registry trả về cache cũ; cần build lại image bằng `docker build --no-cache` rồi push lại.  
**B)** Manifest dùng tag mutable `:v1` với `imagePullPolicy: IfNotPresent`, nên kubelet dùng image đã cache trên node; cách sửa đúng là deploy theo digest (`@sha256:...`) hoặc dùng tag immutable mới cho mỗi lần build.  
**C)** Kubelet cần được restart để xóa image cache; sau khi restart, pod sẽ tự động chạy image mới.  
**D)** Kubernetes chỉ hỗ trợ deploy theo digest, việc dùng tag là nguyên nhân duy nhất và không thể sửa bằng `imagePullPolicy`.

**9. Những phát biểu nào đúng khi so sánh các công cụ static analysis? (Chọn tất cả đáp án đúng)**

**A)** Trivy có thể scan CVE trong image, misconfiguration trong manifest (`trivy config`) và secret bị lộ (`--scanners secret`).  
**B)** KubeLinter lint manifest theo best practice và không cần kết nối tới cluster đang chạy.  
**C)** Kubesec là công cụ scan CVE bên trong container image và có thể thay thế Trivy trong pipeline.  
**D)** Vì các công cụ dùng cùng một nguồn dữ liệu, kết quả của chúng luôn giống nhau nên chỉ cần chạy một công cụ là đủ.

**10. Kẻ tấn công có quyền push vào registry nội bộ và ghi đè tag `v1` bằng một image có backdoor. Những biện pháp nào giảm thiểu rủi ro này? (Chọn tất cả đáp án đúng)**

**A)** Ghim image theo digest trong manifest và trong policy admission.  
**B)** Bật immutable tag trên registry và siết RBAC để tài khoản CI chỉ push được vào đúng repository của mình.  
**C)** Bắt buộc verify chữ ký cosign tại admission với policy `verifyImages` và bật `mutateDigest: true`.  
**D)** Đặt `imagePullPolicy: Always` cho mọi container để luôn kéo image mới nhất từ registry.
