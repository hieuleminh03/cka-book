## Linux trong vận hành hệ thống {#linux-in-operations}

Linux xuất hiện trong khoảng 87% JD DevOps Middle/Senior tại Việt Nam (`RESEARCH.md`), và điều đó không đáng ngạc nhiên: Kubernetes chạy trên Linux, container thực chất là process Linux được cô lập bằng namespace và cgroup, còn mọi sự cố production — pod OOMKilled, node NotReady, disk đầy, service không khởi động — cuối cùng đều chẩn đoán bằng công cụ Linux. Với CKS, phần System Hardening (10%) yêu cầu bạn thao tác thật trên host OS: giảm attack surface, dùng AppArmor và seccomp siết quyền workload.

### Vì sao DevOps engineer phải nắm Linux {#why-devops-needs-linux}

- **Debug pod:** `kubectl exec` đưa bạn vào một hệ thống Linux thu nhỏ; muốn tìm nguyên nhân bạn phải dùng `ps`, `ss`, `df`, `lsof`, `/proc`.
- **Hiểu giới hạn tài nguyên:** `resources.limits` của Kubernetes được thực thi bằng cgroup; hiểu cgroup và OOM killer giúp giải thích vì sao container bị kill dù node còn RAM.
- **Hiểu bảo mật container:** `securityContext`, AppArmor, seccomp, capabilities đều là khái niệm kernel được Kubernetes "bọc" lại bằng API.
- **Vận hành node:** node vẫn là máy Linux phải patch, hardening, cấu hình SSH, firewall và đồng bộ thời gian.

Kubernetes là lớp điều phối, Linux là nền móng — móng yếu thì mọi thứ phía trên đều lung lay.

## Kiến trúc Linux và filesystem hierarchy {#linux-architecture-and-fhs}

### Kiến trúc tổng quan {#linux-architecture-overview}

Linux gồm **kernel** và **user space**. Kernel chạy ở chế độ đặc quyền cao nhất, quản lý CPU, memory, thiết bị, filesystem, network; kernel là khối lớn (monolithic) nhưng hỗ trợ nạp/gỡ module động (`.ko`). User space chứa mọi process bạn thường làm việc (shell, sshd, kubelet, container runtime) và tương tác với kernel qua **system call** (`open`, `read`, `execve`, `socket`, `clone`...). Đây chính là điểm mà seccomp sẽ can thiệp ở cuối chương.

```bash
uname -r              # Phiên bản kernel
lsmod | head          # Module kernel đang nạp
cat /etc/os-release   # Bản phân phối (Ubuntu 24.04, Debian 12, ...)
```

### Các kernel subsystem quan trọng {#important-kernel-subsystems}

| Subsystem | Nhiệm vụ | Vấn đề bạn gặp |
|---|---|---|
| Process scheduler (CFS) | Chia CPU cho process | load average cao, độ trễ tăng |
| Memory management | Cấp phát RAM, page cache, swap | OOM, cache chiếm RAM, swap thrashing |
| Virtual FileSystem (VFS) | Trừu tượng hóa filesystem | ext4/xfs, mount, disk full |
| Network stack | TCP/IP, socket, netfilter | port conflict, mất kết nối, iptables |
| cgroup | Giới hạn/đếm tài nguyên theo nhóm process | `resources.limits` của Kubernetes |
| namespace | Cô lập view hệ thống | container "thấy" filesystem/PID riêng |
| LSM (AppArmor/SELinux) | Mandatory Access Control | chặn hành vi ngoài policy |
| seccomp | Lọc system call | runtime chặn syscall nguy hiểm |

container = namespace + cgroup + filesystem layer. Hiểu công thức này là hiểu phần lớn bản chất container runtime (chương 3).

### Filesystem Hierarchy Standard {#fhs}

| Đường dẫn | Nội dung chính | Ghi chú vận hành |
|---|---|---|
| `/etc` | Cấu hình hệ thống (text file) | Nơi sửa hầu hết cấu hình |
| `/var` | Dữ liệu biến đổi: log, database, cache | Hay đầy đĩa nhất |
| `/var/log` | Log hệ thống và ứng dụng | journal, `auth.log`, `syslog` |
| `/usr/bin`, `/usr/sbin` | Binary của hệ thống | `/bin`, `/sbin` là symlink trên distro hiện đại |
| `/tmp` | File tạm, xóa khi reboot | Có sticky bit; không để dữ liệu quan trọng |
| `/home`, `/root` | Home user thường, home root | Hạn chế service truy cập |
| `/proc` | Filesystem ảo của kernel | Nguồn số liệu process/performance |
| `/sys` | Thiết bị và kernel object | Có `/sys/fs/cgroup` — nơi Kubernetes ghi limit |
| `/dev` | Device file | Ổ đĩa, `null`, `random`, pty |
| `/run` | Dữ liệu runtime (PID file, socket) | Trong RAM, mất khi reboot |
| `/opt`, `/srv` | Ứng dụng bên thứ ba, dữ liệu service | Nơi đặt ứng dụng nội bộ |
| `/mnt`, `/media` | Mount thủ công, thiết bị di động | Tránh dùng production |

`man hier` mô tả đầy đủ chuẩn FHS; `ls -ld /bin /sbin /lib` cho thấy symlink "usrmerge" trên Ubuntu 24.04.

### procfs, sysfs và sysctl {#procfs-sysfs-sysctl}

```bash
cat /proc/cpuinfo                 # CPU
cat /proc/meminfo                 # Memory chi tiết
cat /proc/loadavg                 # Load average + số process theo trạng thái
cat /proc/self/status             # Process hiện tại (Seccomp, CapEff, VmRSS, ...)
```

Tham số kernel chỉnh runtime qua `/proc/sys` gọi là **sysctl**:

```bash
sudo sysctl -w net.ipv4.ip_forward=1                        # Tạm thời
echo 'net.ipv4.ip_forward = 1' | sudo tee /etc/sysctl.d/99-k8s.conf
sudo sysctl --system                                        # Vĩnh viễn
```

Kubernetes cần `net.ipv4.ip_forward=1` và `net.bridge.bridge-nf-call-iptables=1` trên node — hiểu sysctl giúp bạn sửa lỗi mạng cluster (chương 2 và 4).

## Process và job {#processes-and-jobs}

### Process là gì {#what-is-a-process}

Process là chương trình đang thực thi, được kernel cấp **PID** và tài nguyên (memory, file descriptor, socket, thread). Process tạo con bằng `fork()` rồi thay image bằng `execve()`; mọi process có **PPID**, process mồ côi được **PID 1** (systemd) nhận nuôi và reap.

| Trạng thái | Ý nghĩa | Gợi ý xử lý |
|---|---|---|
| `R` | Running/Runnable — đang chạy hoặc chờ CPU | nhiều `R` hơn số core = CPU saturation |
| `S` | Interruptible sleep — chờ sự kiện | trạng thái bình thường của daemon |
| `D` | Uninterruptible sleep — chờ I/O, không nhận signal | dấu hiệu disk/network chậm; `kill -9` vô hiệu |
| `T` | Stopped (Ctrl+Z/SIGSTOP) | tiếp tục bằng `kill -CONT` |
| `Z` | Zombie — đã kết thúc nhưng cha chưa reap | kill cha hoặc sửa code cha |

Trong container, process chính mang PID 1 trong PID namespace của nó; nếu nó không xử lý/không forward SIGTERM, container sẽ "chậm dừng" khi bị terminate — lỗi rất phổ biến trong Kubernetes.

### Quan sát process với ps và top {#observing-processes}

```bash
ps aux | head                          # BSD syntax: USER PID %CPU %MEM VSZ RSS STAT ...
ps -eo pid,ppid,stat,%cpu,%mem,comm --sort=-%cpu | head    # Tùy biến cột
pstree -p $$                           # Cây process từ shell hiện tại
top -b -n1 | head -20                  # Snapshot top
```

Hai cột memory gây nhầm lẫn nhất: **VSZ** (tổng địa chỉ ảo đã map, thường vô nghĩa) và **RSS** (RAM thực nằm trong bộ nhớ vật lý — con số cần quan tâm). Trong `top`: `us/sy/id/wa` là CPU breakdown; phím `M` sort theo memory, `P` theo CPU, `1` hiện từng core.

### Signal {#signals}

| Signal | Số | Hành vi mặc định | Dùng khi nào |
|---|---|---|---|
| SIGHUP | 1 | Kết thúc | Terminal đóng; quy ước reload config |
| SIGINT | 2 | Kết thúc | Tương đương Ctrl+C |
| SIGKILL | 9 | Kết thúc ngay | Không thể bắt; dùng khi bắt buộc |
| SIGUSR1/2 | 10/12 | Tùy ứng dụng | Log rotation, debug |
| SIGTERM | 15 | Kết thúc êm | **Mặc định của `kill`**; graceful shutdown |
| SIGSTOP/SIGCONT | 19/18 | Dừng/Tiếp tục | Debug; SIGSTOP không catch được |

```bash
kill -l                      # Liệt kê toàn bộ signal
kill -TERM 1234              # Thoát êm
kill -9 1234                 # Không thể chặn
pkill -f 'python3 -m http.server'   # Kill theo pattern dòng lệnh
```

Quy ước vận hành: **luôn thử SIGTERM trước SIGKILL** — SIGTERM cho ứng dụng cơ hội đóng connection, flush dữ liệu. Process kết thúc do signal `n` trả exit code `128 + n`, vì thế **137 = SIGKILL**, **143 = SIGTERM** — hai con số bạn gặp liên tục trong `kubectl describe pod` và `docker inspect` (chương 3, 4).

### Job control và chạy nền {#job-control}

```bash
sleep 600 &          # Chạy nền
jobs -l              # Xem job và PID
fg %1 / bg %1        # Foreground/background
# Ctrl+Z tạm dừng process đang chạy
nohup long_task.sh > /var/log/long_task.log 2>&1 &   # Bỏ qua SIGHUP khi thoát SSH
disown -h %1                                          # Tách job khỏi shell
setsid long_task.sh                                   # Session mới, không TTY
```

Với công việc dài, dùng `tmux` hoặc `screen` để thoát SSH an toàn và quay lại xem tiến độ.

### nice và độ ưu tiên {#nice-and-priority}

Nice value từ -20 (ưu tiên cao nhất) đến 19 (thấp nhất), mặc định 0; user thường chỉ tăng nice (giảm ưu tiên), giảm nice cần root.

```bash
nice -n 10 backup.sh        # Chạy với ưu tiên thấp
renice -n 5 -p 1234         # Đổi nice của process đang chạy
```

`top` hiển thị `NI` (nice) và `PR`. Thực tế vận hành điều chỉnh ưu tiên bằng cgroup (CPU weight/limit) nhiều hơn nice — Kubernetes quản lý CPU quota theo cách này.

## systemd, systemctl và journalctl {#systemd-systemctl-journalctl}

### systemd là gì {#what-is-systemd}

systemd là init system của hầu hết bản phân phối hiện đại (Ubuntu, Debian, RHEL, SUSE). Nó chạy với **PID 1**, chịu trách nhiệm khởi động hệ thống theo dependency, quản lý vòng đời service, logging tập trung (journald), mount/timer/socket/target. Các loại unit phổ biến: `service`, `socket`, `timer`, `target`, `mount`, `path`. Trên node Kubernetes, **kubelet và container runtime chạy dưới systemd** — đọc unit file và journal của kubelet là kỹ năng bắt buộc khi debug node (chương 5).

| Đường dẫn | Vai trò |
|---|---|
| `/usr/lib/systemd/system` | Unit do package cài (vendor) — không sửa trực tiếp |
| `/etc/systemd/system` | Unit tùy chỉnh + override của quản trị viên |
| `/etc/systemd/system/<unit>.d/*.conf` | Drop-in override — cách sửa unit vendor đúng chuẩn |

### Quản lý service bằng systemctl {#managing-services}

| Lệnh | Ý nghĩa |
|---|---|
| `systemctl status/start/stop/restart <unit>` | Trạng thái và vòng đời |
| `systemctl reload <unit>` | Nạp lại config không ngắt service (nếu hỗ trợ) |
| `systemctl enable/disable <unit>` | Tự khởi động cùng hệ thống |
| `systemctl is-active/is-enabled <unit>` | Kiểm tra dạng script |
| `systemctl mask/unmask <unit>` | "Khóa" unit — không thể start kể cả khi bị dependency kéo |
| `systemctl daemon-reload` | Nạp lại file unit sau khi sửa/tạo |
| `systemctl cat` / `systemctl edit <unit>` | Xem/override unit an toàn |

`disable` chỉ gỡ symlink khởi động, service vẫn start thủ công hoặc bị kéo chạy được; `mask` trỏ unit vào `/dev/null` nên mọi nỗ lực start đều thất bại — biện pháp mạnh hơn khi hardening node.

```bash
systemctl status ssh
systemctl is-active kubelet           # Trên node Kubernetes
systemctl mask cups                   # Tắt hẳn service không dùng
```

### Viết unit file {#writing-unit-files}

Ví dụ `/etc/systemd/system/cka-web.service`:

```ini
[Unit]
Description=HTTP server cho bài lab CKA/CKS
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=labweb
Group=labweb
WorkingDirectory=/opt/cka-web
ExecStart=/usr/bin/python3 -m http.server 8080
Restart=on-failure
RestartSec=2

[Install]
WantedBy=multi-user.target
```

- `[Unit]`: metadata và dependency. `After` chỉ định thứ tự; `Wants` kéo unit/target vào (không bắt buộc thành công).
- `[Service]`: `Type=simple` = `ExecStart` chạy foreground. `Restart=on-failure` tự chạy lại khi thoát lỗi/bị signal; `Restart=always` chạy lại cả khi thoát sạch; `RestartSec` là thời gian chờ.
- `[Install]`: quyết định unit được gắn vào target nào khi `enable`.

```bash
sudo useradd --system --home /opt/cka-web --shell /usr/sbin/nologin labweb
sudo mkdir -p /opt/cka-web
echo 'Xin chao tu cka-web' | sudo tee /opt/cka-web/index.html
sudo chown -R labweb:labweb /opt/cka-web

sudo systemd-analyze verify /etc/systemd/system/cka-web.service   # Kiểm tra cú pháp
sudo systemctl daemon-reload
sudo systemctl enable --now cka-web

systemctl status cka-web --no-pager
curl -s http://127.0.0.1:8080
journalctl -u cka-web -n 20 --no-pager
```

### Hardening service bằng systemd {#systemd-service-hardening}

systemd có thể sandbox service ngay trong unit file — lớp hardening rẻ và hiệu quả:

```ini
[Service]
# ... (kế thừa các dòng phía trên)
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
ProtectKernelTunables=true
RestrictSUIDSGID=true
CapabilityBoundingSet=CAP_NET_BIND_SERVICE
ReadWritePaths=/var/lib/cka-web
MemoryMax=256M
```

| Directive | Tác dụng |
|---|---|
| `NoNewPrivileges` | Cấm leo thang qua SUID/file capabilities |
| `PrivateTmp` | `/tmp` riêng tư cho service |
| `ProtectSystem=strict` | Filesystem chỉ đọc, trừ `ReadWritePaths` |
| `ProtectHome` | Không truy cập `/home`, `/root` |
| `CapabilityBoundingSet` | Giới hạn tập capability |
| `MemoryMax` | Giới hạn RAM qua cgroup |

```bash
systemd-analyze security cka-web.service --no-pager | head -20
```

Kết quả là exposure score 0–10 (càng thấp càng tốt). Đây cũng là nội dung xuất hiện trong CIS Benchmark mức host.

### journalctl: đọc log hệ thống {#journalctl}

```bash
journalctl -u cka-web -n 50            # 50 dòng cuối của unit
journalctl -u kubelet -f               # Theo dõi realtime
journalctl -b -1 -p err                # Boot trước, mức error trở lên
journalctl --since "30 min ago"        # Theo thời gian
journalctl -k -g oom                   # Log kernel, lọc từ khóa "oom"
journalctl --disk-usage                # Dung lượng journal
journalctl --vacuum-time=7d            # Giữ 7 ngày
```

Điểm quan trọng: **journal có thể chỉ nằm trong RAM**. Nếu `/var/log/journal` không tồn tại, journald chạy volatile (log ở `/run/log/journal`) và mất sau reboot; `journalctl -b -1` sẽ trống.

```bash
sudo mkdir -p /var/log/journal
sudo sed -i 's/#Storage=auto/Storage=persistent/' /etc/systemd/journald.conf
sudo systemctl restart systemd-journald
journalctl --disk-usage    # Verify: journal nằm trong /var/log/journal
```

Nên đặt thêm `SystemMaxUse=` (giới hạn dung lượng) và `MaxRetentionSec=`. journald có rate limiting chống log flood — đừng tắt, hãy sửa nguyên nhân spam.

### Target và thứ tự khởi động {#targets-and-ordering}

```bash
systemctl get-default                                 # Target mặc định
sudo systemctl set-default multi-user.target
systemctl list-dependencies multi-user.target | head -30
```

- `multi-user.target`: server có network, không GUI — đúng cho node Kubernetes.
- `graphical.target`: có GUI; tắt trên server để giảm attack surface.
- `rescue.target`, `emergency.target`: chế độ phục hồi.

Quan hệ unit dùng `After`/`Before` (thứ tự) và `Requires`/`Wants` (kéo unit lên). Lưu ý: `After` **không** có nghĩa unit kia phải chạy.

## User, group, permission và sudo {#users-groups-permissions}

### User và group {#users-and-groups}

| File | Nội dung | Lưu ý bảo mật |
|---|---|---|
| `/etc/passwd` | UID, GID, home, shell | Mọi user đọc được; không chứa hash mật khẩu |
| `/etc/shadow` | Hash mật khẩu, chính sách hết hạn | Chỉ root đọc |
| `/etc/group`, `/etc/gshadow` | Group và thành viên | Supplemental group |
| `/etc/sudoers`, `/etc/sudoers.d/` | Chính sách sudo | Luôn sửa bằng `visudo` |

```bash
id                                                        # UID, GID, group của mình
sudo useradd --system --shell /usr/sbin/nologin appsvc    # Tài khoản service
sudo usermod -aG docker,adm hieul                         # Thêm group bổ sung
sudo passwd -l olduser                                    # Khóa tài khoản
sudo chage -l vinh                                        # Chính sách hết hạn
```

Nguyên tắc: mỗi người một tài khoản riêng (không chia sẻ, không login trực tiếp bằng `root`), tài khoản service luôn `--system --shell /usr/sbin/nologin`.

### Permission cơ bản {#file-permissions}

```text
-rwxr-x---  1 labweb devs 12345 Jan 10 09:00 run.sh
│└┬┘└┬┘└┬┘  owner labweb: rwx | group devs: r-x | others: --- | - file thường, d thư mục, l symlink
```

Với thư mục: `r` = liệt kê tên file con; `w` = tạo/xóa/đổi tên file con (kể cả file không có quyền trên đó); `x` = đi vào/truy cập file con.

```bash
chmod 640 /etc/app/secret.conf        # rw- r-- ---
chmod u+x,g-w run.sh                  # Cộng/trừ theo ký hiệu
chown -R labweb:devs /opt/cka-web     # Đổi owner:group
```

Bảng nhanh: `7=rwx`, `6=rw-`, `5=r-x`, `4=r--`. Bộ quen thuộc: file `644`, thư mục `755`, secret `600`, private key SSH `600`, `.ssh` = `700`.

### umask {#umask}

Mode file mới = `666 AND NOT umask`; mode thư mục mới = `777 AND NOT umask`. File mới không bao giờ có bit thực thi.

| Loại | Mặc định | umask 027 | Kết quả |
|---|---|---|---|
| File | 666 | 666 AND NOT 027 | `640` (`rw-r-----`) |
| Thư mục | 777 | 777 AND NOT 027 | `750` (`drwxr-x---`) |

```bash
umask        # Xem (thường 022, một số distro 027)
umask 027    # Đặt cho shell hiện tại
umask -S     # Hiển thị dạng u=rwx,g=rx,o=
```

Với service systemd, đặt `UMask=0027` trong `[Service]`. Trong container, umask thừa hưởng từ runtime — nguyên nhân lệch quyền file giữa dev và production.

### SUID, SGID và sticky bit {#special-permission-bits}

| Bit | Octal | Trên file | Trên thư mục |
|---|---|---|---|
| SUID | 4000 | Chạy với UID của chủ file (`-rws------`) | Không ý nghĩa |
| SGID | 2000 | Chạy với GID của chủ file | File mới thừa hưởng group của thư mục |
| Sticky | 1000 | Không ý nghĩa | Chỉ chủ file (và root) xóa được file của mình |

```bash
find / -xdev -perm -4000 -type f 2>/dev/null   # Kiểm kê file SUID
ls -ld /tmp                                    # drwxrwxrwt — chữ t = sticky
chmod 2770 /srv/shared                         # SGID cho thư mục nhóm
```

SUID là mục tiêu leo thang đặc quyền kinh điển: binary SUID có lỗ hổng hoặc shell escape là thành root. Hardening phải **kiểm kê SUID định kỳ**, gỡ bit không cần, ưu tiên capabilities cho nhu cầu hẹp.

### Linux capabilities {#linux-capabilities}

Capabilities chia nhỏ đặc quyền root thành đơn vị logic:

| Capability | Cho phép | Rủi ro |
|---|---|---|
| `CAP_NET_BIND_SERVICE` | Bind port < 1024 | Thấp |
| `CAP_NET_RAW` | Raw socket (ping, tcpdump) | Trung bình |
| `CAP_SETUID`/`CAP_SETGID` | Đổi UID/GID tùy ý | Cao |
| `CAP_SYS_PTRACE` | Truy cập memory process khác | Cao |
| `CAP_SYS_ADMIN` | Mount, namespace, cấu hình hệ thống | Rất cao — gần như root |

```bash
getcap /usr/bin/ping                    # cap_net_raw=ep
sudo setcap 'cap_net_bind_service=+ep' /usr/local/bin/agent
sudo setcap -r /usr/local/bin/agent     # Gỡ
capsh --print | head -5                 # Capabilities của shell hiện tại
```

`=+ep` nghĩa là `e` (effective) + `p` (permitted). Trong Docker/Kubernetes, bắt đầu từ `drop: ["ALL"]` rồi add đúng capability cần — nguyên tắc quay lại ở cuối chương và chương 8.

### sudo và least privilege {#sudo-and-least-privilege}

```bash
sudo visudo -f /etc/sudoers.d/deploy     # Sửa file drop-in
sudo visudo -c                           # Validate toàn bộ cấu hình
```

```text
# Chỉ cho phép restart đúng một service, không cần mật khẩu
%deploy ALL=(root) NOPASSWD: /usr/bin/systemctl restart cka-web.service

# Cho xem log mà không cần root đầy đủ
vinh ALL=(root) /usr/bin/journalctl
```

Lưu ý: `NOPASSWD` không miễn phí — command tưởng vô hại vẫn có thể bị lợi dụng để mở shell hoặc đọc file tùy ý; wildcard kiểu `cat *` cho phép đọc mọi file kể cả `/etc/shadow`. Mọi lần sudo đều ghi log (`journalctl -t sudo`, `/var/log/auth.log` trên Debian/Ubuntu) — nguồn log bắt buộc khi điều tra sự cố bảo mật.

```bash
sudo -l              # Quyền sudo của mình
sudo -u labweb id    # Chạy lệnh với user khác
sudo -k              # Xóa cache xác thực
```

### Vệ sinh account {#account-hygiene}

1. Rà soát user thật: `awk -F: '$3 >= 1000 {print $1, $3, $7}' /etc/passwd`.
2. Khóa tài khoản không dùng (`usermod -L`, `passwd -l`); service dùng shell `nologin`.
3. Kiểm soát SSH key trong `/home/*/.ssh/authorized_keys` và `/root/.ssh/authorized_keys`; thu hồi key khi nhân sự rời đi.
4. Password aging (`chage -M 90 -W 7`); cân nhắc chỉ dùng SSH key.
5. Tìm file "mồ côi": `find / -nouser -o -nogroup 2>/dev/null`.
6. Rà cron và timer (`crontab -l -u <user>`, `/etc/cron.*`) — chỗ tác nhân tấn công hay dùng để duy trì hiện diện.

Với Kubernetes, các nguyên tắc này ánh xạ sang **RBAC và ServiceAccount** (chương 7): tài khoản riêng cho workload, không dùng `default`, không cấp quyền rộng. Tư duy "identity + least privilege + audit" là một, chỉ khác lớp thực thi.

## Filesystem, mount và LVM {#filesystem-mount-lvm}

### Block device và filesystem {#block-devices-and-filesystems}

```bash
lsblk -f                 # Cây thiết bị + filesystem + UUID + mountpoint
blkid                    # UUID, TYPE từng phân vùng
df -hT                   # Dung lượng theo filesystem
df -i                    # Inode đã dùng — kiểm tra trước khi kết luận
```

| Tiêu chí | ext4 | XFS |
|---|---|---|
| Tăng dung lượng online | Có (`resize2fs`) | Có (`xfs_growfs`) |
| Giảm dung lượng | Có (offline, nguy hiểm) | **Không hỗ trợ** |
| Kiểm tra | `fsck` khi unmount | `xfs_repair` |

`mkfs` **xóa sạch dữ liệu** — chỉ chạy trên thiết bị đã xác nhận. `fsck` chỉ chạy trên filesystem đã unmount (hoặc chấp nhận downtime), không bao giờ chạy trên filesystem đang mount ở chế độ ghi.

### Mount và fstab {#mount-and-fstab}

```bash
sudo mkdir -p /mnt/labdata
sudo mount /dev/sdb1 /mnt/labdata     # Mount tạm thời
findmnt /mnt/labdata                  # Verify
sudo umount /mnt/labdata              # Unmount
```

Dòng trong `/etc/fstab` dùng **UUID** thay vì `/dev/sdX` (tên thiết bị có thể đổi giữa các lần boot):

```text
UUID=1234-abcd-5678  /data      ext4  defaults,noatime  0  2
UUID=9876-zyxw-5432  /backup    xfs   defaults,nofail   0  0
```

Các trường: thiết bị, mount point, fs type, options, dump, fsck pass. Lưu ý: `nofail` giúp hệ thống vẫn boot khi thiết bị không tồn tại — bắt buộc cho volume phụ; `noatime` giảm I/O. Trước khi reboot sau khi sửa fstab, luôn chạy `sudo mount -a` và `findmnt --verify`.

### LVM cơ bản {#lvm-basics}

LVM chèn lớp trừu tượng giữa ổ đĩa vật lý và filesystem: **PV** (đĩa đăng ký) → **VG** (pool dung lượng) → **LV** (đĩa ảo cho filesystem).

```bash
sudo pvcreate /dev/sdb /dev/sdc
sudo vgcreate vg_data /dev/sdb /dev/sdc
sudo lvcreate -L 10G -n lv_app vg_data
sudo mkfs.ext4 /dev/vg_data/lv_app
sudo mount /dev/vg_data/lv_app /srv/app

pvs; vgs; lvs                          # Trạng thái nhanh

sudo lvextend -L +5G /dev/vg_data/lv_app    # Tăng LV (VG phải còn free)
sudo resize2fs /dev/vg_data/lv_app          # Giãn filesystem ext4
# Một bước: sudo lvextend -r -L +5G /dev/vg_data/lv_app
```

LVM là lý do câu hỏi "filesystem đầy, mở rộng thế nào?" có câu trả lời gọn gàng và online trên server.

## Phân tích hiệu năng hệ thống {#performance-analysis}

### Load average và CPU {#load-average-and-cpu}

Load average (1/5/15 phút) là **số process trung bình ở trạng thái R hoặc D**. Vì tính cả D-state, load phản ánh cả CPU lẫn I/O — điểm rất hay bị hiểu sai.

```bash
uptime                 # load average: 1.20, 0.80, 0.50
nproc                  # Số core — mốc so sánh
vmstat 1 5             # r, b, si, so, us, sy, id, wa
```

- `r` > số core + `us` cao → CPU saturation.
- `wa` cao + `b` lớn → I/O saturation; CPU không phải nút cổ chai.
- `so` > 0 kéo dài → thiếu RAM, đang swap — nguy hiểm với latency.

`mpstat -P ALL 1` xem tải từng core; `pidstat 1` xem CPU theo process.

### Memory {#memory-analysis}

`free` là RAM chưa dùng cho bất cứ thứ gì; **`available`** là RAM có thể cấp cho ứng dụng mới (bao gồm page cache thu hồi được) — đây mới là con số cần theo dõi. `buff/cache` lớn là dấu hiệu tốt: kernel dùng RAM nhàn rỗi tăng tốc I/O và tự giải phóng khi cần. Swap giúp tránh OOM nhưng đánh đổi latency; tham số đáng nhớ: `vm.swappiness` (mặc định 60; database thường giảm còn 1–10).

### Disk I/O {#disk-io-analysis}

```bash
iostat -xz 1 3
```

Chỉ số cần nhớ: `r/s`, `w/s` (IOPS); `rkB/s`, `wkB/s` (throughput); `await` (thời gian trung bình mỗi I/O — tăng vọt là đĩa nghẽn); `aqu-sz` (độ dài hàng đợi); `%util` (tỷ lệ bận; gần 100% là bão hòa — với NVMe hãy nhìn `await` và hàng đợi). Kết hợp `iotop -oPa` để biết process nào gây I/O.

### Network và các chỉ số khác {#network-and-other-metrics}

```bash
ss -tulpn                # Socket LISTEN + process sở hữu (phát hiện port conflict)
ip -s link               # Thống kê lỗi/drop theo interface
```

`ss -tulpn` là lệnh đầu tiên khi điều tra mạng trên máy: nó trả lời ngay "service có listen không, port nào, ai giữ port". Chương 2 đào sâu toàn bộ networking.

### sar và dữ liệu lịch sử {#sar-and-history}

`sar` (gói **sysstat**) lưu dữ liệu lịch sử vào `/var/log/sysstat` — công cụ duy nhất trả lời "hệ thống đã chậm từ bao giờ":

```bash
sudo apt-get install -y sysstat && sudo systemctl enable --now sysstat
sar -u 1 5                 # CPU realtime; sar -r / sar -d cho memory/disk
sar -u -f /var/log/sa/sa14 # Dữ liệu ngày 14 — điều tra quá khứ
```

### Phương pháp luận USE {#use-methodology}

Thay vì nhìn vài con số ngẫu nhiên, dùng checklist **Utilization – Saturation – Errors**:

| Tài nguyên | Utilization | Saturation | Errors |
|---|---|---|---|
| CPU | `top` us+sy, `mpstat` | `vmstat r`, load average | `dmesg` |
| Memory | `free -h` used | `so`, OOM | `dmesg` OOM |
| Disk | `iostat %util` | `await`, `aqu-sz` | `smartctl`, kernel log |
| Network | `ip -s link` | drop/retransmit | `ss -s` |

Mỗi tài nguyên phải trả lời đủ ba câu hỏi trước khi kết luận nút cổ chai. Ở mức observability hiện đại, USE được bổ sung bằng bốn tín hiệu vàng khi làm SLI/SLO (chương 14).

## Troubleshooting hệ thống {#system-troubleshooting}

### Quy trình xử lý sự cố {#troubleshooting-process}

1. **Thu thập bằng chứng trước khi thay đổi** — đừng restart vội, restart xóa mất dấu vết.
2. **Xác định phạm vi:** một process, service, node hay cả cụm; bắt đầu từ lúc nào (đối chiếu `sar`, journal).
3. **Khoanh vùng theo lớp:** application → container/runtime → OS → network → kernel.
4. **Chỉ thay đổi một thứ một lúc** và ghi lại đã làm gì.
5. **Verify bằng cùng chỉ số đã dùng để phát hiện**, rồi viết postmortem (chương 16).

| Triệu chứng | Lệnh kiểm tra đầu tiên |
|---|---|
| Máy chậm, lag | `uptime`, `vmstat 1`, `top` |
| Service không chạy | `systemctl status`, `journalctl -u <unit> -b` |
| Không ghi được file | `df -h`, `df -i`, `dmesg -T` |
| Process biến mất | `dmesg -T | grep -i oom`, `journalctl -k` |
| Port không mở | `ss -tulpn` |
| Latency tăng vọt | `iostat -xz 1`, `vmstat 1` |

### OOM killer {#oom-killer}

Khi cạn memory, kernel chọn process để kết thúc dựa trên `oom_score` (chủ yếu theo lượng memory đang dùng). Process điểm cao nhất bị SIGKILL — không thể bắt. `oom_score_adj` (-1000 đến 1000) cho phép can thiệp: -1000 gần như bảo vệ khỏi bị kill, giá trị dương khiến dễ bị kill hơn.

```bash
dmesg -T | grep -i -E 'oom|killed process'      # Bằng chứng
journalctl -k -g oom                            # Truy vấn hiện đại
cat /proc/<pid>/oom_score                       # Điểm hiện tại
echo -500 | sudo tee /proc/<pid>/oom_score_adj  # Bảo vệ process quan trọng
```

Với cgroup v2 (mặc định trên Ubuntu 24.04 và Kubernetes hiện đại), kiểm tra `/sys/fs/cgroup/<path>/memory.max` (limit) và `memory.events` (bộ đếm `oom`, `oom_kill`). `oom_kill` tăng nghĩa là process trong cgroup bị kill vì vượt limit — chính xác là container/Kubernetes bị **OOMKilled** (exit code 137, lý do OOMKilled trong `kubectl describe pod`). Thứ tự xử lý: (1) tìm memory leak/cấu hình heap; (2) đặt limit phù hợp (`resources.limits.memory`, `MemoryMax=`, `--memory=`); (3) thêm RAM hoặc swap có kiểm soát — đừng để OOM thành cơ chế vận hành bình thường.

### Disk full và inode exhaustion {#disk-full-and-inodes}

```bash
df -h     # Dung lượng
df -i     # Inode — nếu %IUse 100% thì hết inode dù còn dung lượng
```

```bash
du -x -h --max-depth=1 / | sort -h      # Thư mục ngốn dung lượng
lsof +L1                                 # File đã xóa nhưng process còn giữ handle
journalctl --vacuum-size=500M            # Thu gọn journal
```

Tình huống kinh điển: xóa file log to nhưng `df` vẫn đầy — process vẫn giữ **file descriptor** của file đã unlink; `du` không thấy, `df` vẫn tính. Xử lý: reload/restart process giữ file (hoặc truncate qua `/proc/<pid>/fd/<fd>` nếu hiểu rõ rủi ro). Với inode, tìm nơi chứa nhiều file nhỏ rồi xử lý nguồn tạo:

```bash
find /var -xdev -type f -printf '%h\n' | sort | uniq -c | sort -rn | head
```

Tăng inode đòi hỏi tạo lại filesystem nên chỉ là phương án cuối — điều trị gốc là log rotation, TTL cache và dọn định kỳ.

### Service khởi động thất bại {#service-startup-failure}

1. `systemctl status <unit>` — xem exit code, log gần nhất. Trạng thái `activating (auto-restart)` kèm "start request repeated too quickly" nghĩa là crash liên tục, đã chạm **StartLimitBurst** (mặc định 5 lần/10 giây); sửa nguyên nhân rồi `systemctl reset-failed <unit>` và start lại.
2. `journalctl -u <unit> -b -n 100` — lỗi thật sự (thiếu file, sai quyền, lỗi config).
3. Kiểm tra `ExecStart` (đường dẫn, quyền thực thi) và `User=`/`Group=`.
4. Kiểm tra port conflict: `ss -tulpn | grep <port>`.
5. Kiểm tra AppArmor/SELinux (`journalctl -k | grep -i denied`), rồi `systemd-analyze verify <file>` để bắt lỗi cú pháp unit. Sửa xong: `systemctl reset-failed cka-web && systemctl start cka-web`.

## Hardening host {#host-hardening}

### Nguyên tắc giảm attack surface {#attack-surface-reduction}

Attack surface là tổng số "cửa" kẻ tấn công có thể thử: service listen, package đã cài, tài khoản, quyền đặc biệt, port mở. Triết lý: **cái gì không cần thì không tồn tại**.

- Kiểm kê service và port: `systemctl list-units --type=service --state=running`, `ss -tulpn`.
- Gỡ package không dùng; trình biên dịch (`gcc`, `make`) trên node production là món quà cho kẻ chiếm được shell.
- `systemctl mask` service thừa (mạnh hơn `stop`); blacklist kernel module không cần trong `/etc/modprobe.d/`.
- Tắt GUI: target `multi-user.target` thay vì `graphical.target`.
- Least privilege xuyên suốt: user, sudo command, capability, service account.
- Với container/Kubernetes: base image nhỏ (chương 3, 10) và `securityContext` siết quyền (chương 8, 9).

### Quản lý patch {#patch-management}

```bash
sudo apt update && apt list --upgradable
sudo apt upgrade -y                                   # Kiểm thử staging trước với production
cat /var/run/reboot-required 2>/dev/null              # Có cần reboot không (kernel/glibc/systemd)
```

Ba trụ cần nhớ: **tự động hóa** (`unattended-upgrades`), **theo dõi CVE** đối chiếu phiên bản đang chạy (`uname -r`, `containerd --version`, `kubelet --version`), và **lịch reboot có kế hoạch** trong maintenance window. Với Kubernetes node, đây là quy trình drain → patch → uncordon (chương 5), và là gốc rễ yêu cầu "nâng cấp cluster để vá lỗ hổng" ở chương 7.

### SSH hardening {#ssh-hardening}

```text
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
MaxAuthTries 3
AllowGroups ssh-users
```

| Directive | Ý nghĩa |
|---|---|
| `PermitRootLogin no` | Buộc qua user riêng + sudo (có audit) |
| `PasswordAuthentication no` | Chỉ SSH key — loại bỏ brute-force mật khẩu |
| `KbdInteractiveAuthentication no` | Đóng đường xác thực PAM/interactive |
| `AllowGroups ssh-users` | Whitelist nhóm được login |

```bash
sudo sshd -t                      # Validate trước khi reload
sudo systemctl reload ssh         # Giữ một session SSH dự phòng khi thao tác
```

Đổi port SSH chỉ giảm log rác, **không** thay thế key auth. Nên quản lý `authorized_keys` tập trung để thu hồi dễ dàng, cân nhắc `fail2ban`, và ghi log phiên nếu cần compliance.

### Firewall cơ bản {#firewall-basics}

Chính sách mặc định nên là **deny incoming, allow outgoing**, rồi mở đúng thứ cần. Trên Ubuntu dùng `ufw`:

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow OpenSSH
sudo ufw allow from 10.0.0.0/24 to any port 8080 proto tcp   # Chỉ mở nội bộ
sudo ufw enable && sudo ufw status verbose
```

Cảnh báo với node Kubernetes: **không** bật firewall host tùy tiện vì pod-to-pod traffic và các port control plane (6443, 10250, 10257, 10259, 2379–2380) cần được thiết kế cẩn thận; firewall sai cách là nguyên nhân cluster hỏng kinh điển. Trên cloud, security group là lớp firewall chính và cũng phải least privilege. Việc bảo vệ API server/kubelet khỏi mạng ngoài thuộc chương 5–6.

### CIS Benchmark mức host {#cis-benchmark-host}

**CIS Benchmark** là bộ hướng dẫn cấu hình an toàn của Center for Internet Security, có bản cho Ubuntu, RHEL, Docker và Kubernetes. Hai mức: **Level 1** (cơ bản, hầu như không ảnh hưởng chức năng) và **Level 2** (phòng thủ sâu, có thể ảnh hưởng tính năng). Mỗi mục được đánh dấu *scored* hoặc *not scored*.

```bash
sudo apt-get install -y lynis
sudo lynis audit system            # Đánh giá host Ubuntu; xem /var/log/lynis-report.dat
```

Với Kubernetes, công cụ tương ứng là **kube-bench** — chấm điểm cấu hình etcd, kube-apiserver, kubelet (chương 5, 6 sẽ chạy trong lab). Ba nguyên tắc: đọc hiểu từng mục trước khi áp dụng, ghi lại ngoại lệ có lý do, và đưa audit vào định kỳ.

### Audit logging {#audit-logging}

Khi đã bị xâm nhập, chỉ audit log trả lời được "chuyện gì đã xảy ra". Dùng **auditd**:

```bash
sudo apt-get install -y auditd
sudo tee /etc/audit/rules.d/cka.rules <<'EOF'
-w /etc/passwd -p wa -k identity
-w /etc/shadow -p wa -k identity
-w /etc/sudoers -p wa -k privileged
-w /etc/ssh/sshd_config -p wa -k sshd
-a always,exit -F arch=b64 -S execve -F euid=0 -k rootcmd
EOF
sudo augenrules --load
sudo auditctl -l                      # Verify
sudo ausearch -k identity -ts recent  # Truy vấn
```

`-w` theo dõi file, `-p wa` bắt write/attribute change, `-k` là key để truy vấn. Bổ sung: **file integrity monitoring** (AIDE hoặc `rpm -Va`/`debsums`) phát hiện binary bị sửa, và **central logging** (Loki/ELK — chương 14) để kẻ tấn công không xóa được dấu vết cục bộ. Tinh thần này tái xuất hiện ở Kubernetes audit logs (chương 11).

### Đồng bộ thời gian {#time-sync}

Thời gian sai gây lỗi rất khó tìm: chứng chỉ TLS vô hiệu, log nối nhân quả sai, Kubernetes/etcd bất ổn, JWT không hợp lệ.

```bash
timedatectl                          # Trạng thái + timezone
sudo timedatectl set-timezone Asia/Ho_Chi_Minh
sudo timedatectl set-ntp true
timedatectl timesync-status          # Verify
```

## AppArmor và seccomp {#apparmor-and-seccomp}

### DAC, MAC và vai trò của LSM {#dac-mac}

Mô hình truyền thống là **DAC (Discretionary Access Control)** — chủ sở hữu quyết định quyền rwx. Điểm yếu chí mạng: khi process leo thang lên root (hoặc bị RCE), nó đọc/ghi gần như mọi thứ. **MAC (Mandatory Access Control)** bổ sung chính sách do quản trị viên định nghĩa mà process **không thể tự vượt qua**, kể cả khi chạy bằng root — được thực thi qua **LSM (Linux Security Module)**.

| Tiêu chí | AppArmor | SELinux |
|---|---|---|
| Bản phân phối tiêu biểu | Ubuntu, Debian, SUSE | RHEL, CentOS, Fedora |
| Diễn đạt policy | Theo đường dẫn file (path-based) | Theo nhãn (label/context) |
| Độ phức tạp | Thấp hơn, dễ hiểu | Cao hơn, chi tiết hơn |

Cùng capabilities và seccomp, đây là bộ hardening mức kernel; Kubernetes điều khiển AppArmor/seccomp qua `securityContext` — nội dung thi CKS.

### AppArmor {#apparmor}

AppArmor giới hạn chương trình bằng **profile**: được đọc/ghi đường dẫn nào, dùng network gì. Profile nằm trong `/etc/apparmor.d/`, tên file theo đường dẫn đầy đủ của binary. Ba chế độ:

| Chế độ | Hành vi | Dùng khi nào |
|---|---|---|
| `enforce` | Chặn vi phạm và ghi log | Production |
| `complain` | Chỉ ghi log, không chặn | Xây dựng/debug profile |
| `unconfined` | Không áp dụng profile | Khi chưa có profile |

```bash
sudo apt-get install -y apparmor-utils
sudo aa-status                                   # Profile và chế độ hiện tại
sudo apparmor_parser -r /etc/apparmor.d/cka-deny-write   # Reload profile
sudo aa-enforce /etc/apparmor.d/cka-deny-write           # Bật enforce
sudo journalctl -k | grep -i 'apparmor.*DENIED'          # Vi phạm
```

AppArmor là lớp phòng thủ thứ hai: nếu nginx bị khai thác, profile vẫn ngăn nó ghi vào `/etc` hay đọc `/root`. Trong Kubernetes, profile phải được nạp sẵn trên **mỗi node** rồi chọn qua `securityContext`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: apparmor-demo
spec:
  securityContext:
    appArmorProfile:
      type: Localhost
      localhostProfile: cka-deny-write
  containers:
    - name: demo
      image: nginx:stable
```
AppArmor dùng field `securityContext` từ v1.30 (thay annotation cũ) và **GA từ v1.31** — bản v1.33 dùng trong sách không cần feature gate. `type` nhận `RuntimeDefault`, `Localhost` (kèm tên profile qua `localhostProfile`) hoặc `Unconfined`.

### seccomp {#seccomp}

Nếu AppArmor giới hạn "được chạm vào cái gì", **seccomp** giới hạn "được gọi kernel bằng cách nào" — lọc **system call**. Kẻ tấn công muốn làm gì cũng phải qua syscall (`execve` để chạy shell, `mount`, `ptrace`...). seccomp có ba chế độ: `disabled` (0), `strict` (1, gần như không dùng), `filter` (2 — BPF filter dùng thực tế).

```bash
grep Seccomp /proc/self/status       # Seccomp: 2 = đang có filter
docker run --rm ubuntu:24.04 grep Seccomp /proc/self/status                       # 2
docker run --rm --security-opt seccomp=unconfined ubuntu:24.04 \
  grep Seccomp /proc/self/status                                                  # 0
```

Docker/containerd áp profile mặc định (cho phép danh sách syscall an toàn, chặn syscall hiếm/nguy hiểm). Bạn có thể tự siết chặt hơn bằng profile JSON (`SCMP_ACT_ALLOW` mặc định, chặn từng syscall với `SCMP_ACT_ERRNO`). Cách xây dựng profile thực tế: chạy application ở chế độ audit/complain, dùng `strace -c` hoặc `oci-seccomp-bpf-hook` để liệt kê syscall thật sự dùng, rồi cho phép tối thiểu. Trong Kubernetes:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: seccomp-demo
spec:
  securityContext:
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: demo
      image: nginx:stable
```

`seccompProfile.type` nhận `RuntimeDefault`, `Localhost` (kèm `localhostProfile` trỏ tới file trong `/var/lib/kubelet/seccomp/` trên node) hoặc `Unconfined`. Seccomp GA từ Kubernetes v1.19; kubelet có thể bật `--seccomp-default` để mọi pod mặc định `RuntimeDefault` — chuẩn mực mà Pod Security Standards mức `restricted` yêu cầu.

### Kernel hardening trong Kubernetes {#kernel-hardening-in-kubernetes}

Trong Kubernetes, mọi kỹ thuật trên khai báo tập trung qua `securityContext`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: hardened-app
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 10001
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: app
      image: registry.example.com/app:1.2.3
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop: ["ALL"]
          add: ["NET_BIND_SERVICE"]
      volumeMounts:
        - name: tmp
          mountPath: /tmp
  volumes:
    - name: tmp
      emptyDir: {}
```

| Cấu hình | Tác dụng |
|---|---|
| `runAsNonRoot` + `runAsUser` | Không chạy root trong container — giảm thiệt hại khi bị RCE |
| `seccompProfile: RuntimeDefault` | Lọc syscall theo profile của runtime |
| `allowPrivilegeEscalation: false` | Không leo thang qua SUID/file capabilities |
| `readOnlyRootFilesystem: true` | Không ghi được vào root filesystem của container |
| `drop: ["ALL"]` rồi add đúng cái cần | Least privilege thay vì `privileged: true` |
| `emptyDir` cho `/tmp` | Vẫn có chỗ ghi file tạm khi root fs read-only |

Các ràng buộc này cũng chính là **Pod Security Standards** mức `restricted` và nội dung của admission controller (OPA/Kyverno) ở chương 9.

### Cầu nối tới Kubernetes và CKS {#bridge-to-kubernetes-and-cks}

Ba sợi dây nối chương này với phần còn lại của cuốn sách:

- **Chương 4–5:** node Kubernetes là một máy Linux; kubelet và runtime chạy dưới systemd, cấu hình node nằm trên host, troubleshooting node (NotReady, disk pressure, OOM) dùng đúng bộ công cụ ở đây. RBAC/ServiceAccount là phiên bản Kubernetes của user/group/permission.
- **Chương 8 (System Hardening):** nâng kiến thức hardening host lên mức cluster — giảm OS footprint, CIS Benchmark cho kubelet/etcd, AppArmor/seccomp cho pod, hạn chế network exposure. Chương 1 là điều kiện cần để học tốt chương 8.
- **Chương 9 và 11:** seccomp/AppArmor/capabilities xuất hiện trong `securityContext` và Pod Security Standards (chương 9); Falco (chương 11) phát hiện tấn công dựa trên chính syscall bạn đã học cách lọc.

Bạn không học Linux để "thi qua môn" — bạn học để hiểu chính xác lớp đang bảo vệ mọi workload trong cluster.

```bash
#!/usr/bin/env bash
```

### Bước 6: Mount với loop device {#lab-step-6}

Bước này cần root (container `--privileged` hoặc WSL2/VM); nếu môi trường chặn `losetup`, hãy đọc để nắm thứ tự lệnh.

```bash
sudo fallocate -l 512M /opt/disk.img
sudo losetup -fP /opt/disk.img
LOOP=$(losetup -j /opt/disk.img | cut -d: -f1)
sudo mkfs.ext4 "$LOOP" && sudo mkdir -p /mnt/labdata
sudo mount "$LOOP" /mnt/labdata && findmnt /mnt/labdata
echo hello > /mnt/labdata/hello.txt && cat /mnt/labdata/hello.txt
sudo umount /mnt/labdata && sudo losetup -d "$LOOP" && sudo rm -f /opt/disk.img
```

Verify: `findmnt` thấy loop device tại `/mnt/labdata` và thao tác ghi/đọc file thành công. LVM (tùy chọn, cần gói `lvm2`) khi có ổ thật: `pvcreate /dev/sdb` → `vgcreate vg_lab /dev/sdb` → `lvcreate -L 300M -n lv_lab vg_lab` → `mkfs.ext4` → `lvextend -r -L +100M /dev/vg_lab/lv_lab`; kiểm tra bằng `pvs`, `vgs`, `lvs`.

### Bước 7: Stress CPU, RAM, disk và quan sát {#lab-step-7}

### Bước 8: Kiểm tra OOM killer {#lab-step-8}

**Cách A — Docker memory limit 256MB:**

```bash
docker run -it --rm --memory=256m --name oom-lab ubuntu:24.04 bash
# Trong container:
apt-get update && apt-get install -y stress-ng
cat /sys/fs/cgroup/memory.max      # ~268435456 (cgroup v2)
stress-ng --vm 1 --vm-bytes 400M --vm-keep --timeout 60s   # Vượt limit
```

`stress-ng` bị kill với exit code **137** (128 + SIGKILL). Trên host (Linux/WSL2), tìm bằng chứng:

```bash
dmesg -T | tail -30 | grep -i -E 'oom|killed process'
journalctl -k -g oom --no-pager | tail -20
```

**Cách B — systemd cgroup (WSL2/VM), không cần Docker:**

```bash
sudo systemd-run --scope -p MemoryMax=256M stress-ng --vm 1 --vm-bytes 400M --vm-keep --timeout 30s
journalctl -k -g oom --no-pager | tail -20
```

Verify: tìm thấy thông báo OOM trong `dmesg`/journal hoặc bộ đếm `oom_kill` trong `memory.events` tăng. Liên hệ Kubernetes: pod vượt `resources.limits.memory` bị `OOMKilled` với exit code 137 — đúng cơ chế vừa quan sát (chương 4, 9).

### Bước 9: Minh họa AppArmor và seccomp {#lab-step-9}

**seccomp (chạy được với Docker trên host):**

```bash
docker run --rm ubuntu:24.04 grep Seccomp /proc/self/status        # Seccomp: 2
docker run --rm --security-opt seccomp=unconfined ubuntu:24.04 \
  grep Seccomp /proc/self/status                                   # Seccomp: 0

cat > /tmp/deny-mkdir.json <<'EOF'
```

## Câu hỏi phỏng vấn thường gặp {#interview-questions}

**Câu 1. Phân biệt SIGTERM và SIGKILL. Vì sao Kubernetes dùng SIGTERM trước SIGKILL?**

SIGTERM (15) là đề nghị kết thúc có thể bắt và xử lý — ứng dụng dọn dẹp connection, flush dữ liệu, hoàn tất giao dịch. SIGKILL (9) buộc kernel kết thúc ngay, không thể bắt, không có cơ hội dọn dẹp. Kubernetes gửi SIGTERM cho PID 1 trong container, chờ tối đa `terminationGracePeriodSeconds` (mặc định 30 giây), rồi gửi SIGKILL nếu process vẫn sống. App không handle SIGTERM hoặc PID 1 không forward signal sẽ bị kill cứng, có thể mất dữ liệu.

**Câu 2. Load average là gì? Load 8 trên máy 4 vCPU nói lên điều gì, và khi nào chưa đủ kết luận?**

Load average là số process trung bình ở trạng thái R hoặc D trong 1/5/15 phút. Load 8 trên 4 core là hàng đợi gấp đôi số core — dấu hiệu tài nguyên bão hòa. Nhưng chưa đủ kết luận vì D-state (chờ I/O) cũng được tính: phải xem `vmstat` (`r`, `b`, `wa`) để biết bottleneck thật sự là CPU hay disk.

**Câu 3. `available` khác `free` thế nào? Vì sao cache chiếm nhiều RAM là chuyện tốt?**

`free` là RAM chưa dùng cho bất cứ thứ gì; `available` là ước lượng RAM cấp được cho ứng dụng mới, bao gồm page cache thu hồi được. Kernel dùng RAM nhàn rỗi làm cache đĩa để tăng tốc I/O và tự giải phóng khi ứng dụng cần — vì vậy hãy theo dõi `available`, không lo vì `free` nhỏ.

**Câu 4. Process ở trạng thái D là gì và xử lý thế nào?**

D-state là process đang chờ I/O ở kernel với signal bị hoãn — nó không phản hồi `kill -9` (signal chỉ xử lý sau khi syscall I/O trả về). D-state hàng loạt thường do storage/network treo hoặc driver/NFS mất kết nối. Xử lý: xem `vmstat` (cột `b`), `iostat`, `dmesg` tìm thiết bị treo, xử lý nguyên nhân thay vì cố kill process.

**Câu 5. `df -h` báo còn dung lượng nhưng ghi file nhận "No space left on device". Điều tra thế nào?**

Khả năng chính: hết inode (`df -i`), hết quota (kiểm tra quota user/group), hoặc filesystem read-only/lỗi (`dmesg`, mount option). Quy trình: `df -h` → `df -i` → `dmesg` → kiểm tra mount. Với inode, tìm thư mục chứa nhiều file nhỏ và xử lý nguồn tạo file, không chỉ xóa file hiện có.

**Câu 6. OOM killer chọn process thế nào? Tìm bằng chứng ở đâu và liên hệ container ra sao?**

Kernel tính `oom_score` (chủ yếu theo lượng memory đang dùng), điều chỉnh được qua `oom_score_adj` (-1000 đến 1000); process điểm cao nhất bị SIGKILL. Bằng chứng: `dmesg -T | grep -i oom`, `journalctl -k -g oom`, hoặc `memory.events` với bộ đếm `oom_kill` trong cgroup v2. Container/Kubernetes vượt memory limit bị kill với exit code 137 và lý do `OOMKilled`. Phòng ngừa: limit phù hợp, tìm memory leak, cấu hình heap JVM.

**Câu 7. `systemctl daemon-reload` dùng khi nào? `disable` khác `mask` thế nào?**

`daemon-reload` bắt systemd đọc lại file unit sau khi tạo/sửa (kể cả drop-in); nó không restart service — muốn áp dụng phải thêm `restart`. `disable` chỉ gỡ symlink khởi động (vẫn start thủ công hoặc bị dependency kéo chạy được); `mask` trỏ unit vào `/dev/null` nên mọi nỗ lực start đều thất bại — dùng khi hardening.

**Câu 8. Vì sao `journalctl -b -1` có thể không có dữ liệu? Cách bật log persistent?**

Nếu `/var/log/journal` không tồn tại, journald chạy volatile — log ở `/run/log/journal` (RAM) và mất sau reboot. Khắc phục: tạo `/var/log/journal`, đặt `Storage=persistent` trong `/etc/systemd/journald.conf`, restart `systemd-journald`; nên thêm `SystemMaxUse` để không làm đầy `/var`.

**Câu 9. SUID là gì, rủi ro ra sao, và capabilities thay thế thế nào?**

SUID khiến chương trình chạy với quyền của chủ sở hữu (thường root) bất kể ai gọi — mọi lỗ hổng hoặc shell escape trong binary SUID là đường leo thang đặc quyền. Hardening: kiểm kê (`find / -perm -4000`), gỡ bit không cần, thay bằng capabilities đúng nhu cầu (`cap_net_bind_service` thay vì SUID root). Trong Kubernetes, `allowPrivilegeEscalation: false` chặn cả SUID lẫn file capabilities.

**Câu 10. AppArmor và seccomp khác nhau thế nào? Khi nào dùng cái nào?**

seccomp lọc system call (chặn `mkdir`, `ptrace`, `mount`...), còn AppArmor là MAC lọc theo đường dẫn file và quyền network (cấm nginx ghi vào `/etc`). Cả hai đều hiệu lực với cả process chạy bằng root. Thực tế dùng kết hợp: seccomp `RuntimeDefault` cho mọi workload, AppArmor `Localhost` profile cho workload cần siết cụ thể — cả hai khai báo qua `securityContext` trên Kubernetes.

**Câu 11. Làm sao giảm attack surface của node Kubernetes?**

Kiểm kê trước: `ss -tulpn`, `systemctl list-units --state=running`. Sau đó gỡ package/service không dùng, `mask` service thừa, tắt GUI, blacklist kernel module không cần, hardening SSH (key-only, no root login), patch định kỳ, giới hạn mạng bằng security group/firewall chỉ mở port cần, bật AppArmor/seccomp cho workload và đối chiếu CIS Benchmark bằng kube-bench. Đây là nền tảng của chương 8.

## Các điểm chính {#key-points}

- Linux là nền móng của Kubernetes: container = namespace + cgroup + filesystem layer; node vẫn là máy Linux phải vận hành và hardening.
- `/proc` và `/sys` là giao diện với kernel; sysctl chỉnh tham số runtime (Kubernetes cần `net.ipv4.ip_forward=1`).
- Trạng thái process cần nhớ: `R` (chạy/chờ CPU), `S` (chờ sự kiện), `D` (chờ I/O, không nhận signal), `T` (stopped), `Z` (zombie).
- Luôn SIGTERM trước SIGKILL; exit code 137 = SIGKILL, 143 = SIGTERM — các con số quen thuộc khi debug container.
- systemd quản lý service bằng unit file; sửa unit phải `daemon-reload`; `mask` mạnh hơn `disable` và là công cụ hardening.
- `Restart=on-failure` + StartLimitBurst là cơ chế tự phục hồi của systemd; lỗi "start request repeated too quickly" cần sửa nguyên nhân rồi `reset-failed`.
- journalctl truy vấn log theo unit, boot, mức độ, thời gian; muốn log sống qua reboot phải có `/var/log/journal` với `Storage=persistent`.
- umask quyết định quyền mặc định: file = 666 AND NOT umask, thư mục = 777 AND NOT umask.
- SUID/SGID là đường leo thang kinh điển; ưu tiên capabilities (`cap_net_bind_service`, `cap_net_raw`) với nguyên tắc drop ALL rồi add tối thiểu.
- sudo phải cấp theo command cụ thể qua `visudo`/`sudoers.d`; NOPASSWD và wildcard ẩn chứa rủi ro leo thang; mọi lần sudo đều được ghi log.
- Performance: load average tính cả D-state nên phải đọc `vmstat` để xác định bottleneck; `free` khác `available` — `available` mới là RAM cấp được cho ứng dụng, page cache lớn là dấu hiệu tốt.
- OOM killer dùng `oom_score`/`oom_score_adj`; bằng chứng ở `dmesg`/`journalctl -k`/`memory.events`; container vượt limit bị OOMKilled với exit code 137.
- Hết dung lượng gồm hết block (`df -h`) và hết inode (`df -i`); file đã xóa nhưng còn open làm `df` đầy mà `du` không thấy — dùng `lsof +L1`.
- Hardening host gồm: giảm attack surface, patch management, SSH key-only, firewall least privilege, CIS Benchmark (lynis/kube-bench), auditd và đồng bộ thời gian.
- AppArmor và seccomp là MAC mức kernel, hiệu lực cả với root, được Kubernetes điều khiển qua `securityContext` — cầu nối tới chương 8 (System Hardening) và chương 9.

**7. (Chọn tất cả đáp án đúng.) Bạn điều tra một process bị kernel OOM killer kết thúc trên host Linux. Phát biểu nào đúng?**

**8. Ứng dụng chạy dưới systemd ghi log vào journal, nhưng sau mỗi lần reboot, toàn bộ log cũ biến mất và `journalctl -b -1` báo không có dữ liệu cho boot trước. Nguyên nhân khả dĩ nhất và cách khắc phục đúng là gì?**

**C)** Cần chạy `systemctl enable systemd-journald` vì journald mặc định không được enable.
**D)** Log cũ bị `logrotate` xóa trong vòng một giờ; cần tăng tham số `rotate` trong `/etc/logrotate.conf`.

**9. (Chọn tất cả đáp án đúng.) Phát biểu nào đúng về AppArmor và seccomp trên Linux?**

**A)** seccomp hoạt động ở mức system call (lọc syscall), còn AppArmor là MAC lọc theo đường dẫn file, quyền network và một số hành vi của process.
**B)** Process chạy dưới AppArmor profile ở chế độ enforce vẫn bị giới hạn kể cả khi có UID 0 (root); vi phạm profile bị chặn bất kể quyền DAC.
**C)** Chế độ `complain` của AppArmor chặn mọi hành vi vi phạm profile và chỉ ghi log khi đã chặn xong.
**D)** seccomp chỉ áp dụng được cho process chạy bằng quyền root; process user thường không thể bị seccomp filter.

**10. (Chọn tất cả đáp án đúng.) Một container cần bind port 80 trên Kubernetes nhưng phải chạy với quyền tối thiểu. Cấu hình `securityContext` nào phù hợp?**

**A)** `capabilities.drop: ["ALL"]` kết hợp `capabilities.add: ["NET_BIND_SERVICE"]`.
**B)** `runAsNonRoot: true` kết hợp `allowPrivilegeEscalation: false`.
**C)** `privileged: true` để container có thể bind mọi port mà không gặp giới hạn.
**D)** `allowPrivilegeEscalation: true` kết hợp `readOnlyRootFilesystem: false` để dễ gỡ lỗi trên production.
