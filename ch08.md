## System Hardening trong kỳ thi CKS {#system-hardening-trong-ky-thi-cks}

Domain **System Hardening** chiếm **10%** trọng số kỳ thi CKS — nhỏ nhất trong sáu domain, nhưng lại là domain "nền móng": nếu node bị chiếm quyền, mọi biện pháp phòng thủ ở tầng Kubernetes đều vô nghĩa. Trong đề thi, các task thuộc domain này thường xuất hiện ở dạng:

- Kiểm tra và siết `securityContext` của một pod/deployment đang chạy (drop capabilities, `runAsNonRoot`, `readOnlyRootFilesystem`, seccomp profile).
- Nạp một AppArmor profile lên node rồi gán cho pod qua `securityContext`.
- Tạo seccomp profile tùy biến (block một syscall cụ thể) và áp vào pod.
- Kiểm tra node có đang chạy service/package thừa không, tắt hoặc mask chúng.
- Đọc `/etc/sysctl.d`, áp dụng các kernel parameter hardening rồi verify bằng `sysctl`.

Đặc điểm chung của các task này: **kết quả được chấm trên trạng thái thật của node và pod**, không phải trên việc bạn đã gõ đúng cú pháp. Bạn có thể viết đúng YAML mà profile chưa được nạp lên node — pod sẽ bị `CreateContainerError` hoặc `FailedCreatePodSandBox`, và task coi như sai.

### Domain 10% này hỏi gì {#domain-10-nay-hoi-gi}

| Competency | Bạn phải làm được | Phần lý thuyết |
|---|---|---|
| Giảm host OS footprint | Kiểm kê service/package, tắt/mask, hiểu immutable OS, chỉ chạy agent cần thiết | [Giảm host OS footprint](#giam-host-os-footprint) |
| Least-privilege IAM | User/group/sudo tối thiểu, bảo vệ file nhạy cảm, không chạy root, capabilities | [Least-privilege identity](#least-privilege-identity-va-access-management) |
| Giảm truy cập mạng ngoài | Firewall host đúng cách, security group, private cluster, bastion | [Giảm truy cập mạng từ bên ngoài](#giam-truy-cap-mang-tu-ben-ngoai) |
| Kernel hardening tools | AppArmor profile, seccomp profile, sysctl, giới thiệu SELinux | [Kernel hardening](#kernel-hardening), [securityContext](#ap-dung-vao-kubernetes) |

### Quan hệ với chương 1 và các chương khác {#quan-he-voi-chuong-1}

Chương 1 đã dạy bạn hardening Linux ở mức cơ bản: process, user/permission, firewall cơ bản, `aa-status`, seccomp và `securityContext`. Chương này **không lặp lại** những gì đã có, mà nâng lên mức độ CKS:

- Chương 1 trả lời "làm sao để host an toàn"; chương này trả lời "trên node Kubernetes, làm sao áp nó cho workload và chứng minh nó có hiệu lực".
- Chương 1 giới thiệu AppArmor/seccomp; chương này đi sâu vào **profile tùy biến, đường dẫn profile trên node, và cách gắn vào pod** — đúng dạng đề thi.
- Các trường `securityContext` ở đây là nền để hiểu **Pod Security Standards** (chương 9) và các admission policy (OPA/Kyverno).
- Các kernel parameter `kernel.*` liên quan tới **runtime security** và Falco (chương 11).

Nói cách khác: chương 1 cho bạn công cụ, chương 8 cho bạn quy trình và bằng chứng.

## Giảm host OS footprint {#giam-host-os-footprint}

### Attack surface của một node {#attack-surface-cua-mot-node}

Attack surface là **tổng số con đường mà kẻ tấn công có thể thử** trên một node: process đang chạy, port đang listen, package đã cài, user có quyền đặc biệt, kernel module đã nạp, credential nằm trên đĩa. Nguyên tắc bất di bất dịch: **thứ gì không cần thì không nên tồn tại**.

Trên một node Kubernetes, các nguồn attack surface thường bị bỏ quên:

| Nguồn | Ví dụ | Hệ quả nếu bị khai thác |
|---|---|---|
| Service thừa | `apache2`, Docker daemon chạy song song containerd | Lỗ hổng web/daemon trở thành cửa vào node |
| Package thừa | `gcc`, `make`, `python`, `netcat` | Kẻ chiếm shell có công cụ compile/exploit ngay trên node |
| Port listen | kubelet 10250, read-only 10255, dashboard, monitoring agent | Lộ API, lộ thông tin, thậm chí RCE qua kubelet |
| Kernel module | driver không dùng, module filesystem lạ | Mở rộng bề mặt kernel |
| User quyền cao | user trong group `docker`, sudo NOPASSWD | Leo thang lên root dễ dàng |
| File nhạy cảm | kubeconfig, `/var/lib/kubelet`, chứng chỉ CA | Lấy được credential của cluster |

Giảm footprint nghĩa là thu nhỏ dần danh sách trên theo từng vòng: **kiểm kê → đánh giá → loại bỏ → verify**. Không có bước nào được bỏ, vì "tắt rồi verify" là khác biệt giữa làm đúng và nghĩ là đã làm đúng.

### Kiểm kê và loại bỏ service, package {#kiem-ke-va-loai-bo-service-package}

Đầu tiên là nhìn thấy toàn bộ những gì đang chạy:

```bash
# Service đang chạy và port đang listen
systemctl list-units --type=service --state=running
ss -tulpn                                   # port + process tương ứng

# Package đã cài và lịch sử cài thủ công (hữu ích để phát hiện thừa)
apt list --installed 2>/dev/null | wc -l
grep -E '^(Commandline|Install)' /var/log/apt/history.log | tail -n 20
```

Với các service không cần thiết, **mask** mạnh hơn **stop**: `stop` chỉ dừng phiên hiện tại, `mask` chặn cả việc vô tình bật lại.

```bash
sudo systemctl disable --now apache2          # tắt và không tự khởi động cùng hệ thống
sudo systemctl mask bluetooth cups avahi-daemon
systemctl is-enabled bluetooth                # masked

# Gỡ package thừa (trình biên dịch trên node production là rủi ro thật)
sudo apt-get purge -y gcc make python3-pip telnet
sudo apt-get autoremove -y
```

Với kernel module, blacklist những module không dùng (filesystem lạ, protocol hiếm):

```text
# /etc/modprobe.d/blacklist-rare.conf
blacklist dccp
blacklist sctp
blacklist rds
blacklist tipc
```

Sau đó verify bằng `lsmod` và ghi chú ngoại lệ có lý do — ví dụ SCTP có thể cần cho ứng dụng thoại nội bộ.

```bash
lsmod | grep -E 'dccp|sctp|rds|tipc' || echo "cac module da duoc blacklist"
```

> Lưu ý với node Kubernetes: **đừng tắt service mà bạn chưa hiểu**. Mất `systemd-resolved` sẽ ảnh hưởng DNS của node; mất container runtime sẽ khiến pod chết hàng loạt; containerd, kubelet và các thành phần CNI phải được giữ nguyên. Quy trình đúng là test trên node lab trước, có rollback plan.

### Immutable OS: Flatcar, Bottlerocket, Talos {#immutable-os}

Cách triệt để nhất để giảm footprint là **làm cho node không thể thay đổi**: filesystem gốc chỉ đọc, quản lý phiên bản theo image, cập nhật nguyên khối (atomic update), rollback tự động. Các node như vậy được gọi là **immutable OS**.

| Nền tảng | Đặc điểm | Ghi chú cho CKS |
|---|---|---|
| **Flatcar Container Linux** | Filesystem gốc read-only, `/usr` versioned, update tự động có rollback, gần như chỉ chạy container | Kế thừa tinh thần CoreOS |
| **Bottlerocket** (AWS) | Image tối giản, không SSH, quản trị qua API container (`apiclient`) | Host không có package manager/shell tương tác |
| **Talos Linux** | Không có SSH, quản trị qua `talosctl` (gRPC), machine config khai báo | Phổ biến cho cluster tự dựng |
| **Managed node image** (EKS AMI, GKE COS) | Image do cloud quản lý, không SSH mặc định, cập nhật qua cloud | Thực tế nhất trên production |

Lợi ích bảo mật: kẻ tấn công không thể cài package, không sửa được binary hệ thống, không persist sau reboot; mọi thay đổi phải đi qua image mới. Đổi lại, debug khó hơn (không `apt install tcpdump` được), nên phải chuẩn bị pod debug (như netshoot) và thu thập log tập trung.

Trong đề thi CKS bạn **không phải cài immutable OS** — kiến thức này chủ yếu xuất hiện ở câu hỏi lý thuyết/phỏng vấn và ở việc hiểu vì sao node managed không cho SSH.

### Quản lý package và patch trên node {#quan-ly-package-va-patch-tren-node}

Node dù ít package tới đâu vẫn phải được vá. Ba trụ cần nhớ:

1. **Tự động hóa**: `unattended-upgrades` (Debian/Ubuntu) hoặc `dnf-automatic` (RHEL family).
2. **Theo dõi CVE theo phiên bản đang chạy**: `kubelet --version`, `containerd --version`, `uname -r` — đối chiếu với advisory của upstream.
3. **Cửa sổ reboot có kế hoạch**: vá kernel/glibc/systemd thường cần reboot; với node Kubernetes, đó là quy trình `cordon → drain → patch → reboot → uncordon` (chương 5).

```bash
# Ubuntu: kiểm tra và áp patch
sudo apt update && apt list --upgradable
sudo apt upgrade -y
cat /var/run/reboot-required 2>/dev/null    # có cần reboot không

# Red Hat family
sudo dnf updateinfo list security
sudo dnf update --security -y
```

Một chiến lược thực dụng hơn cả "vá từng node": **tạo node mới từ image đã vá rồi thay thế node cũ** (immutable infrastructure). Cách này tránh drift cấu hình và giảm thời gian từ lúc có CVE đến lúc toàn cluster được vá.

### Chỉ cài agent cần thiết {#chi-cai-agent-can-thiet}

Mỗi agent là một process chạy bằng quyền cao, đọc được tài nguyên nhạy cảm và có kết nối ra ngoài — tức là một **chuỗi cung ứng mới cần tin tưởng**. Trên node, chỉ nên có:

- `kubelet`, `containerd` (hoặc runtime bạn dùng).
- CNI plugin.
- Node exporter/monitoring agent (chương 14).
- Security agent (Falco, antivirus) nếu tổ chức yêu cầu — nhưng phải nằm trong danh sách được review.

Những thứ nên tránh trên node production: Docker daemon chạy song song (tạo thêm bề mặt và xung đột quản lý), GUI, tool phát triển, và các agent "tiện ích" cài tay rồi bị lãng quên.

```bash
# Kiểm kê nhanh các process không thuộc Kubernetes
sudo systemd-cgls | head -n 40
ps -eo user,pid,ppid,cmd --sort=user | grep -vE '\[|kubelet|containerd|coredns'
```

Với container agent, nguyên tắc least privilege cũng áp dụng: agent chỉ nên mount đúng những đường dẫn cần (Falco cần kernel header/module tùy driver), không chạy `privileged: true` nếu có thể.

### SSH hardening trên node Kubernetes {#ssh-hardening-tren-node-kubernetes}

Chương 1 đã trình bày các directive cơ bản; trên node Kubernetes, mục tiêu là **giảm tối đa khả năng đăng nhập trực tiếp**. File `/etc/ssh/sshd_config.d/99-hardening.conf`:

```text
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
MaxAuthTries 3
LoginGraceTime 20
AllowGroups ssh-users
AllowTcpForwarding no
X11Forwarding no
```

| Directive | Tác dụng trên node Kubernetes |
|---|---|
| `PermitRootLogin no` | Buộc qua user riêng + sudo, mọi thao tác có audit qua sudo log |
| `PasswordAuthentication no` | Loại bỏ brute-force, chỉ dùng SSH key |
| `AllowGroups ssh-users` | Whitelist nhóm được login — thu hồi quyền bằng cách remove khỏi group |
| `AllowTcpForwarding no` | Chặn dùng node làm proxy tunnel (trừ khi cần cho debug) |
| `MaxAuthTries 3` | Giảm bề mặt dò mật khẩu/key |

Quy trình đổi cấu hình SSH **phải** giữ một session dự phòng đang mở, và validate trước khi reload:

```bash
sudo sshd -t                                  # kiểm tra syntax trước
sudo systemctl reload ssh                     # giữ session cũ mở cho tới khi verify xong

# Từ máy khác, verify bằng key
ssh -o PasswordAuthentication=no deploy@node-01 'echo OK'
```

Trên production, tầng trên SSH nên có: bastion/VPN (xem [mục dưới](#bastion-host-thay-vi-ssh-truc-tiep)), session recording và audit logging. Với immutable OS (Bottlerocket/Talos), SSH thường bị tắt hoàn toàn — đó là mức hardening cao nhất: **không có cửa để siết**.

## Least-privilege identity và access management {#least-privilege-identity-va-access-management}

### Least privilege trên node: user, group, sudo {#least-privilege-tren-node}

Least privilege bắt đầu từ tài khoản người dùng trên node. Mỗi người vận hành chỉ nên có **đúng quyền cho đúng việc, trong đúng khoảng thời gian cần thiết**.

```bash
# Liệt kê user có shell đăng nhập và user hệ thống quyền thấp
awk -F: '$3 >= 1000 && $7 !~ /nologin|false/ {print $1, $3, $7}' /etc/passwd

# Kiểm tra nhóm quyền cao và user trong nhóm đó
getent group sudo wheel docker 2>/dev/null
getent group docker | cut -d: -f4

# Xem một user làm được gì với sudo
sudo -l -U deploy
ls -l /etc/sudoers.d/
```

Cấu hình sudo theo nguyên tắc tối thiểu — thay vì `ALL=(ALL) NOPASSWD: ALL`, hãy giới hạn lệnh cụ thể:

```text
# /etc/sudoers.d/deploy  (sửa bằng: sudo visudo -f /etc/sudoers.d/deploy)
deploy ALL=(root) /usr/bin/systemctl restart kubelet, /usr/bin/journalctl -u kubelet
```

Ba lỗi phổ biến cần kiểm tra khi audit node:

- User nằm trong group **`docker`**: quyền tương đương root (có thể mount host filesystem vào container). Trên node chỉ dùng containerd qua CRI, group này thường không cần tồn tại.
- `NOPASSWD: ALL` rải rác trong `/etc/sudoers.d/`.
- Tài khoản service dùng chung, không truy vết được ai làm gì.

| Cấp độ | Đối tượng | Công cụ kiểm soát |
|---|---|---|
| Cloud IAM | Instance role, user quản trị hạ tầng | IAM policy, condition, MFA |
| OS identity | User/group trên node | `/etc/passwd`, `sudoers`, SSH key |
| Container identity | User trong container | `securityContext` (`runAsUser`, `runAsNonRoot`) |
| Workload identity | ServiceAccount của pod | RBAC (chương 7) |

### Bảo vệ file nhạy cảm: kubeconfig, kubelet, CA {#bao-ve-file-nhay-cam}

Node chứa nhiều credential quyền lực nhất của cluster. CIS Benchmark dành hẳn nhóm check cho quyền của những file này:

| File / thư mục | Quyền khuyến nghị | Vì sao |
|---|---|---|
| `/etc/kubernetes/admin.conf` (kubeconfig admin) | `600`, chủ `root:root` | File này là quyền cluster-admin |
| `/etc/kubernetes/kubelet.conf` | `600`, `root:root` | Credential của kubelet |
| `/etc/kubernetes/pki/` (CA, key) | `700` thư mục, `600` key | Ký cert cho toàn cluster |
| `/var/lib/kubelet/config.yaml` | `600`, `root:root` | Cấu hình authentication của kubelet |
| `/var/lib/kubelet/` | `750` hoặc chặt hơn | Chứa token, pod spec |
| `~/.kube/config` của user | `600` | Đừng để nhóm/others đọc |

```bash
# Audit nhanh quyền file
sudo stat -c '%a %U:%G %n' /etc/kubernetes/admin.conf /etc/kubernetes/kubelet.conf
sudo stat -c '%a %n' /var/lib/kubelet/config.yaml
sudo find /etc/kubernetes/pki -name '*.key' -exec stat -c '%a %n' {} \;

# Remediate mẫu
sudo chmod 600 /etc/kubernetes/admin.conf
sudo chown root:root /etc/kubernetes/admin.conf
```

Đừng xem nhẹ mục này: một file kubeconfig `644` trên node bị chiếm là **toàn bộ cluster bị chiếm**. Đây cũng là dạng task CKS rất dễ gặp — chỉnh quyền file rồi verify bằng `stat`.

### Service account của container runtime {#service-account-cua-container-runtime}

Container runtime (containerd, CRI-O) là process quyền lực nhất trên node sau kubelet. Cần kiểm soát ba thứ:

```bash
# Process và user của containerd
ps -o user,pid,cmd -C containerd

# Socket runtime: ai truy cập được?
ls -l /run/containerd/containerd.sock

# Quyền thực thi của kubelet
ps -o user,pid,cmd -C kubelet | head -n 2
```

- **Socket của runtime** (`/run/containerd/containerd.sock`) phải chỉ truy cập được bởi root — ai chạm được socket này có thể tạo container với `privileged: true` và thoát ra host. Tuyệt đối không mount socket này vào pod không cần thiết.
- kubelet dùng credential riêng (`/etc/kubernetes/kubelet.conf`), không đọc được `admin.conf`; nếu phải giao tiếp qua API, nó dùng ServiceAccount/token theo cơ chế của cluster.
- Systemd unit của runtime/kubelet nên bật các cờ hardening mà distro hỗ trợ (`NoNewPrivileges`, `ProtectSystem`...) — kiểm tra bằng `systemctl cat containerd`.
- Trên cluster nhiều tenant, hạn chế `hostPath` mount tới các đường dẫn nhạy cảm vì hostPath cho phép pod đọc/ghi host; nếu buộc dùng, phải kèm admission policy để whitelist path.

### Không chạy workload bằng root {#khong-chay-workload-bang-root}

Đây là thay đổi mang lại nhiều giá trị bảo mật nhất trên mỗi dòng YAML. Khi container chạy bằng root:

- Kẻ tấn công có RCE sẽ đứng ở **uid 0 trong namespace của container** — nếu có bất kỳ lỗ hổng kernel/runtime nào, việc leo thang ra node trở nên đáng kể.
- Các thao tác ghi file, đọc secret, mount volume trở nên dễ dàng hơn nhiều.

Cách siết trong pod spec:

```yaml
# ch08-nonroot.yaml
apiVersion: v1
kind: Pod
metadata:
  name: nonroot-demo
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    runAsGroup: 3000
    fsGroup: 2000
  containers:
    - name: app
      image: alpine:3.20
      command: ["sh", "-c", "id && sleep 3600"]
```

| Trường | Ý nghĩa |
|---|---|
| `runAsNonRoot: true` | kubelet **từ chối chạy** container nếu image chỉ định user root (kiểm tra ở tầng admission, không chỉ runtime) |
| `runAsUser` / `runAsGroup` | uid/gid cụ thể cho process |
| `fsGroup` | group sở hữu volume, để process ghi được vào volume dùng chung |
| `supplementalGroups` | group phụ được thêm vào |

Hai cạm bẫy khi đi thi:

1. **Image không có user khác root**: `runAsNonRoot: true` sẽ khiến pod lỗi `CreateContainerConfigError` với thông báo `container has runAsNonRoot and image will run as root` (trường hợp này xảy ra khi không set `runAsUser` và image mặc định root). Cách xử lý: dùng image có user non-root (ví dụ `nginxinc/nginx-unprivileged`) hoặc set `runAsUser` cụ thể.
2. **Nhiều image mặc định chạy root**: kể cả `alpine` cũng vậy. Đừng quên kiểm tra `USER` trong Dockerfile của image thay vì đoán.

Kiểm tra pod đang thực sự chạy bằng uid nào:

```bash
kubectl exec nonroot-demo -- id
# uid=1000 gid=3000 groups=3000,2000

kubectl get pod nonroot-demo -o jsonpath='{.spec.securityContext.runAsNonRoot}{"\n"}'
# true
```

### Linux capabilities: thay thế cho root {#linux-capabilities}

Capabilities chia nhỏ đặc quyền của root thành các đơn vị riêng biệt. Container mặc định (Docker/containerd) đã drop nhiều capability nguy hiểm, nhưng vẫn giữ khoảng 14 capability — trong đó `NET_RAW`, `CHOWN`, `SETUID`, `SETGID`, `DAC_OVERRIDE` là những thứ workload bình thường hiếm khi cần.

Nguyên tắc CKS: **drop toàn bộ, chỉ add lại đúng cái cần**.

```yaml
# ch08-caps.yaml
apiVersion: v1
kind: Pod
metadata:
  name: caps-demo
spec:
  containers:
    - name: nginx
      image: nginxinc/nginx-unprivileged:1.27-alpine
      securityContext:
        allowPrivilegeEscalation: false
        capabilities:
          drop: ["ALL"]
          add: ["NET_BIND_SERVICE"]     # cho phép bind port < 1024 mà không cần root
```

| Capability | Khi nào thật sự cần |
|---|---|
| `NET_BIND_SERVICE` | Bind port < 1024 (80, 443) khi process không phải root |
| `NET_ADMIN` | Cấu hình network, VPN, eBPF tooling — rất rộng, cân nhắc kỹ |
| `SYS_TIME` | Chỉnh đồng hồ hệ thống — hiếm, thường không cần |
| `SYS_PTRACE` | Debug process khác — là "vũ khí" khi bị lạm dụng |
| `SYS_ADMIN` | Gần như root (mount, namespace...) — tránh tuyệt đối |

```bash
# Verify capability thực tế của process trong container
kubectl exec caps-demo -- grep Cap /proc/1/status
# CapPrm: 0000000000000400  ← chỉ còn bit của NET_BIND_SERVICE
kubectl exec caps-demo -- capsh --decode=0000000000000400 2>/dev/null \
  || echo "capsh không có trong image — đọc bit tương ứng tài liệu capabilities(7)"
```

Đừng dùng `privileged: true` để "cho nhanh": nó bật toàn bộ capability và gỡ hầu hết giới hạn thiết bị, tương đương root trên host. Nếu một workload buộc phải privileged (CNI, storage plugin), hãy cô lập nó trong namespace hoặc dedicated node pool riêng biệt.

Một lưu ý nhỏ về `allowPrivilegeEscalation`: khi đặt `false`, process trong container không thể nhận thêm quyền qua setuid/setcap, tức là lớp phòng thủ bổ sung cho việc drop capabilities.

### readOnlyRootFilesystem và filesystem chỉ đọc {#readonlyrootfilesystem}

Kẻ tấn công đã có RCE thường cố ghi payload (web shell, binary, cron) để tồn tại lâu dài. Nếu **root filesystem của container chỉ đọc**, đường persist này bị chặn. Đó là trường `readOnlyRootFilesystem: true` trong container `securityContext`.

Hệ quả thực tế: process nào cần ghi (cache, pid, tmp) sẽ lỗi ngay. Cách xử lý là **mount `emptyDir`/`tmpfs` cho đúng những đường dẫn cần ghi**:

```yaml
# ch08-readonly.yaml
apiVersion: v1
kind: Pod
metadata:
  name: readonly-demo
spec:
  containers:
    - name: nginx
      image: nginxinc/nginx-unprivileged:1.27-alpine
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop: ["ALL"]
      volumeMounts:
        - name: cache
          mountPath: /var/cache/nginx
        - name: run
          mountPath: /var/run
        - name: tmp
          mountPath: /tmp
  volumes:
    - name: cache
      emptyDir: {}
    - name: run
      emptyDir: {}
    - name: tmp
      emptyDir: {}
```

Verify:

```bash
# Ghi vào root fs phải fail
kubectl exec readonly-demo -- sh -c 'touch /probe' 2>&1
# touch: /probe: Read-only file system

# Ghi vào /tmp phải OK
kubectl exec readonly-demo -- sh -c 'touch /tmp/probe && echo OK'
# OK
```

Mẹo trong đề thi: nếu đề yêu cầu "container must not write to its root filesystem" mà ứng dụng cần ghi log/cache, hãy tạo `emptyDir` đúng chỗ ứng dụng cần — **không tắt tính năng hardening đi**.

## Giảm truy cập mạng từ bên ngoài {#giam-truy-cap-mang-tu-ben-ngoai}

### Nguyên tắc: chỉ mở đúng thứ cần {#nguyen-tac-chi-mo-dung-thu-can}

Phần lớn sự cố "cluster bị tấn công từ Internet" không bắt nguồn từ lỗi Kubernetes, mà từ **một port bị mở quá rộng**. Mô hình phòng thủ gồm nhiều lớp:

```text
Internet
   |
   v
[ Security group / Cloud firewall ]   <- lớp 1: chặn ở mức hạ tầng
   |
   v
[ Firewall trên node: nftables/ufw ]  <- lớp 2: chặn ở mức OS
   |
   v
[ Kubelet/API auth + NetworkPolicy ]  <- lớp 3: chặn ở mức cluster
```

Cấu hình đúng là "default deny inbound, allow đúng nguồn/port cần", và mỗi lớp chỉ mở đúng thứ mà lớp trên đã giới hạn. Kiểm tra định kỳ từ bên ngoài là cách duy nhất biết cấu hình có thật sự hiệu lực:

```bash
# Từ máy ngoài cluster: kiểm tra port nhạy cảm (không có output nghĩa là đã chặn)
for p in 22 2379 2380 6443 10250 10255; do
  nc -zv -w2 <node-ip> $p 2>&1 | tail -n1
done
```

### Firewall host: nftables, ufw, iptables {#firewall-host-nftables-ufw-iptables}

Trên node, các công cụ phổ biến:

| Công cụ | Ghi chú |
|---|---|
| **nftables** (`nft`) | Hiện đại, thay thế iptables trên distro mới; là backend của `ufw` |
| **ufw** | Lớp wrapper dễ dùng trên Ubuntu/Debian |
| **firewalld** | Chuẩn trên RHEL family, dùng `firewall-cmd` |
| **iptables** | Vẫn gặp trên hệ thống cũ, kube-proxy có thể dùng mode này |

Nguyên tắc số một khi làm firewall trên node Kubernetes: **hiểu trước khi siết**. kube-proxy, CNI và các control plane port tạo ra rất nhiều rule; đặt policy DROP sai có thể phá pod-to-pod hoặc làm mất kết nối etcd. Cách an toàn nhất là:

1. Bật firewall ở chế độ log/audit trước, xem traffic thật.
2. Thêm rule allow cho **các port trong bảng bên dưới**, giới hạn source theo CIDR nội bộ.
3. Đặt default policy DROP ở ngoài cùng, giữ session dự phòng.
4. Verify bằng `ss`, `nc` và test workload.

Ví dụ với `ufw` (default deny, mở SSH và các port nội bộ):

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow from 10.0.0.0/24 to any port 22 proto tcp      # SSH chỉ từ bastion/VPN
sudo ufw allow from 10.0.0.0/24 to any port 6443 proto tcp    # API server nội bộ
sudo ufw allow from 10.0.0.0/24 to any port 10250 proto tcp   # kubelet cho control plane
sudo ufw enable && sudo ufw status verbose
```

Ví dụ tương đương với `nftables` (dùng bảng riêng, không đụng rule của kube-proxy):

```bash
sudo nft add table inet hostguard
sudo nft add chain inet hostguard input '{ type filter hook input priority 0; policy drop; }'
sudo nft add rule inet hostguard input ct state established,related accept
sudo nft add rule inet hostguard input iif lo accept
sudo nft add rule inet hostguard input ip saddr 10.0.0.0/24 tcp dport { 22, 6443, 10250 } accept
sudo nft list ruleset
```

### Các port phải nhớ trên node Kubernetes {#cac-port-phai-nho-tren-node-kubernetes}

Bảng này nên nằm trong đầu bạn cả khi đi thi lẫn khi review security group trên cloud:

| Port | Thành phần | Ai được phép kết nối |
|---|---|---|
| `6443` | kube-apiserver | Admin (VPN/bastion), node khác, control plane |
| `2379`, `2380` | etcd (client, peer) | **Chỉ control plane** — không bao giờ từ ngoài |
| `10250` | kubelet API (đọc + exec/log) | kube-apiserver; không từ Internet |
| `10255` | kubelet read-only (deprecated) | **Không ai** — phải đóng (`readOnlyPort: 0`) |
| `10257`, `10259` | controller-manager, scheduler metrics/health | Chỉ nội bộ control plane (thường chỉ localhost) |
| `30000–32767` | NodePort service | Tùy service; hạn chế source nếu có thể |
| `80`, `443` | Ingress/load balancer | Người dùng/dịch vụ hợp lệ |

```bash
# Kiểm tra port nào đang listen ở đâu
sudo ss -tulpn | grep -E ':(6443|2379|10250|10255)\b'

# Xác nhận kubelet read-only port đã đóng (kết nối thất bại là tốt)
curl --max-time 3 http://127.0.0.1:10255/pods 2>&1 | head -n 2
# curl: (7) Failed to connect to 127.0.0.1 port 10255
```

Kubelet phải được cấu hình xác thực/ủy quyền (`authentication.x509.clientCAFile`, `webhook`, `authorization.mode: Webhook`) — chương 6 đã đi sâu phần kubelet config và CIS check 4.x.

### Security group và private cluster {#security-group-va-private-cluster}

Trên cloud, **security group là lớp firewall chính** và cũng là nơi xảy ra lỗi least privilege phổ biến nhất. Checklist:

- API server: private endpoint + CIDR allowlist (VPN/bastion), hoặc public endpoint có allowlist chặt. Không mở `0.0.0.0/0`.
- etcd: chỉ mở giữa các control plane; nên **tạo security group riêng** cho control plane và node, rule tham chiếu SG thay vì CIDR để quản lý theo "thành viên" thay vì địa chỉ.
- Node: chỉ mở port cần giữa các node trong cluster (kubelet, VXLAN/IPIP cho CNI), không mở node ra Internet.
- **Private cluster**: node nằm trong private subnet, không có IP public; Internet đi qua NAT Gateway; quản trị đi qua VPN/bastion. Đây là mặc định nên nhắm tới cho production.
- Egress cũng cần kiểm soát: giới hạn đích (registry nội bộ, package mirror, NTP) thay vì cho node ra Internet tùy ý.

```bash
# AWS CLI: kiểm tra rule inbound quá rộng của một security group
aws ec2 describe-security-groups --group-ids sg-xxxxxxxx \
  --query 'SecurityGroups[].IpPermissions[].[FromPort,ToPort,IpRanges[].CidrIp]' --output json
```

### Bastion host thay vì SSH trực tiếp {#bastion-host-thay-vi-ssh-truc-tiep}

Node production **không nên** có SSH expose ra Internet, kể cả khi đã đổi port. Kiến trúc chuẩn:

```text
Admin --(VPN / SSO + MFA)--> Bastion (public subnet, hardened, ít quyền)
                                |
                                +--(SSH nội bộ, key riêng)--> Node (private subnet)
```

Đặc điểm bastion đúng chuẩn: chỉ cho SSH từ IP quản trị, user có thể `sudo` giới hạn, log mọi session (auditd/session recording), MFA ở tầng VPN/SSO, và bản thân bastion không giữ credential tới cluster (không copy kubeconfig lên bastion). AWS còn cung cấp **SSM Session Manager** để thay thế SSH hoàn toàn — kết nối đi qua agent theo chiều ra, không mở port `22` nào cả.

Với cluster quan trọng, hãy nhớ nguyên tắc: **đường quản trị phải khác đường dữ liệu**, và mọi đường quản trị đều phải có audit.

### Network segmentation giữa các node {#network-segmentation-giua-cac-node}

Compromise một node không nên leo thang thành compromise cả cluster. Segment mạng để giới hạn di chuyển ngang (lateral movement):

- Control plane và worker node ở subnet/SG khác nhau; worker không kết nối trực tiếp tới etcd.
- Node thuộc các môi trường khác nhau (dev/staging/prod) nằm trong VPC/subnet riêng, không routing trực tiếp cho nhau.
- Với workload nhạy cảm, dùng **dedicated node pool** + taint để cô lập (ví dụ workload PCI), có thể kèm NetworkPolicy chặt ở tầng pod (chương 6).
- Bật luồng traffic: VPC Flow Logs, audit log của security group — khi có sự cố, đây là bản ghi cho bạn biết kết nối đi đâu.

Đây cũng là tinh thần "giảm truy cập mạng từ bên ngoài" ở mức cluster: không chỉ chặn Internet, mà giới hạn cả đường giữa các thành phần nội bộ.

## Kernel hardening: sysctl, AppArmor, seccomp, SELinux {#kernel-hardening}

### sysctl: tinh chỉnh kernel đúng cách {#sysctl}

`sysctl` điều khiển các tham số của kernel lúc chạy. Trong CKS, bạn cần biết hai nhóm: **hardening mức node** và **sysctl mức pod** (namespaced).

Các tham số hardening quan trọng:

| Parameter | Giá trị an toàn | Ý nghĩa |
|---|---|---|
| `net.ipv4.ip_forward` | `1` trên node K8s (bắt buộc cho CNI) | Cho phép forward packet — bật có chủ đích |
| `net.ipv4.conf.all.rp_filter` | `1` (hoặc `2` theo CNI) | Chống giả mạo địa chỉ nguồn (spoofing) |
| `net.ipv4.conf.all.accept_redirects` | `0` | Không nhận ICMP redirect — chống MITM |
| `net.ipv4.conf.all.send_redirects` | `0` | Node không gửi redirect |
| `net.ipv4.conf.all.accept_source_route` | `0` | Chặn source routing |
| `net.ipv4.icmp_echo_ignore_broadcasts` | `1` | Chống smurf attack |
| `net.ipv4.tcp_syncookies` | `1` | Chống SYN flood |
| `kernel.randomize_va_space` | `2` | ASLR đầy đủ |
| `kernel.dmesg_restrict` | `1` | Ngăn user thường đọc kernel log (lộ địa chỉ) |
| `kernel.kptr_restrict` | `2` | Che địa chỉ kernel trong `/proc` |
| `kernel.yama.ptrace_scope` | `1` | Giới hạn `ptrace` giữa các process |
| `fs.protected_symlinks` | `1` | Chống tấn công symlink trong shared dir |

Cách áp dụng **đúng chuẩn và bền vững** là file cấu hình trong `/etc/sysctl.d/`:

```text
# /etc/sysctl.d/99-cks-hardening.conf
net.ipv4.conf.all.accept_redirects = 0
net.ipv4.conf.all.send_redirects = 0
net.ipv4.conf.all.accept_source_route = 0
net.ipv4.icmp_echo_ignore_broadcasts = 1
net.ipv4.tcp_syncookies = 1
net.ipv4.conf.all.rp_filter = 1
kernel.randomize_va_space = 2
kernel.dmesg_restrict = 1
kernel.kptr_restrict = 2
kernel.yama.ptrace_scope = 1
fs.protected_symlinks = 1
```

```bash
# Áp dụng và verify
sudo sysctl --system                       # nạp /etc/sysctl.d và /etc/sysctl.conf
sysctl -n kernel.dmesg_restrict            # 1
sysctl -n net.ipv4.tcp_syncookies          # 1

# Xem cảnh báo/ghi đè khi nạp (thứ tự đọc file quan trọng)
sudo sysctl --system 2>&1 | grep -iE 'conflict|error'

# Chỉnh nhanh trong phiên (không persist — chỉ dùng để test)
sudo sysctl -w kernel.dmesg_restrict=1
```

Trong cluster, kubelet chia sysctl thành hai loại:

| Loại | Ví dụ | Cách dùng |
|---|---|---|
| Safe (namespaced) | `net.ipv4.ip_unprivileged_port_start`, `net.ipv4.tcp_syncookies`, `kernel.shm_rmid_forced` | Set trực tiếp trong pod `securityContext.sysctls` |
| Unsafe | `net.core.somaxconn`, `kernel.msgmax`, `net.ipv4.ip_forward` | Kubelet phải bật `--allowed-unsafe-sysctls`, hạn chế dùng |

`securityContext.sysctls` là trường cấp **pod** (áp dụng cho mọi container trong pod), và chỉ nhận sysctl đã được namespaced — set `net.ipv4.ip_forward` từ pod sẽ bị từ chối.

```yaml
# ch08-sysctl-pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: sysctl-demo
spec:
  securityContext:
    sysctls:
      - name: net.ipv4.ip_unprivileged_port_start
        value: "0"          # cho phép bind port 80 khi chạy non-root
  containers:
    - name: web
      image: nginxinc/nginx-unprivileged:1.27-alpine
      securityContext:
        runAsNonRoot: true
        allowPrivilegeEscalation: false
        capabilities:
          drop: ["ALL"]
```

```bash
# Verify bên trong pod
kubectl exec sysctl-demo -- cat /proc/sys/net/ipv4/ip_unprivileged_port_start
# 0
kubectl exec sysctl-demo -- id
# uid=101 ...   (nginx-unprivileged chạy uid 101)
```

### AppArmor: giới hạn chương trình theo profile {#apparmor}

**AppArmor** là LSM (Linux Security Module) giới hạn chương trình bằng **profile**: chương trình được đọc/ghi đường dẫn nào, dùng loại network nào. AppArmor phổ biến trên Ubuntu/Debian/SUSE — cũng là nền tảng của hầu hết node lab. Ba chế độ:

| Chế độ | Hành vi | Dùng khi |
|---|---|---|
| `enforce` | Chặn vi phạm + ghi log | Production, sau khi profile đã ổn định |
| `complain` | Chỉ ghi log, không chặn | Xây dựng/debug profile |
| `unconfined` | Không áp dụng profile | Khi chưa có profile |

```bash
sudo apt-get install -y apparmor apparmor-utils
sudo aa-status                                   # module đang bật? profile nào đang load?
cat /sys/module/apparmor/parameters/enabled      # Y
```

Một profile tối giản chặn ghi vào `/etc`:

```text
# /etc/apparmor.d/ch08-deny-write
#include <tunables/global>

profile ch08-deny-write /usr/bin/yes flags=(attach_disconnected) {
  #include <abstractions/base>
  /etc/** r,        # được đọc /etc
  /tmp/** rw,
  deny /etc/** w,   # chặn mọi ghi vào /etc
}
```

```bash
sudo apparmor_parser -r /etc/apparmor.d/ch08-deny-write   # load/replace
sudo aa-enforce /etc/apparmor.d/ch08-deny-write           # chuyển enforce
sudo aa-complain /etc/apparmor.d/ch08-deny-write          # chuyển complain (khi debug)

# Xem vi phạm bị chặn
sudo journalctl -k | grep -i 'apparmor.*DENIED'
```

Trong Kubernetes, profile **phải được nạp sẵn trên mọi node** mà pod có thể chạy (tên profile phải khớp), rồi chọn qua `securityContext`:

```yaml
# ch08-apparmor.yaml
apiVersion: v1
kind: Pod
metadata:
  name: apparmor-demo
spec:
  securityContext:
    appArmorProfile:
      type: Localhost
      localhostProfile: ch08-deny-write   # tên profile đã nạp trên node
  containers:
    - name: demo
      image: alpine:3.20
      command: ["sleep", "3600"]
```

Field `appArmorProfile` trong `securityContext` **GA từ Kubernetes v1.31** (thay cho annotation `container.apparmor.security.beta.kubernetes.io/<name>` trước đây). Trên v1.33 dùng trong sách, bạn không cần feature gate. `type` nhận `RuntimeDefault`, `Localhost` hoặc `Unconfined`.

Verify:

```bash
kubectl exec apparmor-demo -- cat /proc/1/attr/current
# ch08-deny-write (enforce)
```

### seccomp: lọc system call {#seccomp}

Nếu AppArmor giới hạn "được chạm vào đâu", **seccomp** giới hạn "được gọi kernel bằng cách nào" — bằng cách lọc **system call**, giao diện duy nhất giữa process và kernel. Kẻ tấn công muốn chạy shell, mount filesystem hay tạo namespace mới đều phải đi qua syscall. seccomp có ba chế độ: `disabled` (0), `strict` (1, hầu như không dùng), `filter` (2 — BPF filter, dùng thực tế).

Container runtime (containerd/Docker/CRI-O) áp **profile mặc định** với khoảng 300+ syscall phổ biến, chặn những syscall nguy hiểm/ít dùng. Trong Kubernetes:

```yaml
# ch08-seccomp.yaml
apiVersion: v1
kind: Pod
metadata:
  name: seccomp-demo
spec:
  securityContext:
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: demo
      image: alpine:3.20
      command: ["sleep", "3600"]
```

| `seccompProfile.type` | Hành vi |
|---|---|
| `RuntimeDefault` | Dùng profile mặc định của container runtime — khuyến nghị cho mọi workload |
| `Unconfined` | Không lọc — chỉ dùng cho workload đặc biệt, cần lý do rõ ràng |
| `Localhost` | Dùng file JSON riêng, đặt dưới seccomp root của kubelet |

Với `Localhost`, kubelet đọc file theo đường dẫn **tương đối** so với **seccomp root** (mặc định `/var/lib/kubelet/seccomp/`, đổi được qua `--seccomp-default-root`):

```text
# Trên node
/var/lib/kubelet/seccomp/profiles/ch08-deny-unshare.json
```

```yaml
# Pod dùng profile localhost
spec:
  securityContext:
    seccompProfile:
      type: Localhost
      localhostProfile: profiles/ch08-deny-unshare.json   # tương đối so với seccomp root
```

Profile JSON theo chuẩn OCI — ví dụ chặn họ syscall `unshare` và `setns` (dùng để tạo/chuyển namespace, kỹ thuật quan trọng khi leo thang):

```json
{
  "defaultAction": "SCMP_ACT_ALLOW",
  "architectures": ["SCMP_ARCH_X86_64"],
  "syscalls": [
    {
      "names": ["unshare", "setns"],
      "action": "SCMP_ACT_ERRNO",
      "errnoRet": 1
    }
  ]
}
```

Các `action` thường gặp: `SCMP_ACT_ALLOW` (cho qua), `SCMP_ACT_ERRNO` (trả lỗi — process thấy "Operation not permitted"), `SCMP_ACT_KILL_PROCESS` (giết process — dùng cho syscall tuyệt đối cấm), `SCMP_ACT_LOG` (chỉ ghi log — dùng khi xây dựng profile).

Verify seccomp đang hoạt động bên trong container:

```bash
kubectl exec seccomp-demo -- grep Seccomp /proc/self/status
# Seccomp:         2        <- đang có filter
# Seccomp_filters: 1
```

### SELinux: giới thiệu và khi nào gặp {#selinux}

**SELinux** là LSM gốc của Red Hat (RHEL/CentOS/Fedora), áp chính sách theo **nhãn (label/context)** thay vì đường dẫn:

```bash
getenforce                       # Enforcing / Permissive / Disabled
ls -Z /var/lib/kubelet/          # system_u:object_r:container_var_lib_t:s0

# Thêm context cho thư mục tùy biến rồi restore
sudo semanage fcontext -a -t container_file_t "/data/app(/.*)?"
sudo restorecon -Rv /data/app
```

Với Kubernetes, container runtime gán nhãn cho container process/volume (thường qua `seLinuxOptions` trong `securityContext`), và runtime phải được bật SELinux (`--selinux-enabled`). Điểm cần nhớ: SELinux mạnh và chi tiết hơn AppArmor, nhưng phức tạp hơn (viết policy cần `audit2allow`, `semanage`); nếu cluster chạy trên Ubuntu/dùng AppArmor, SELinux thường không phải trọng tâm. Trong đề CKS, SELinux chủ yếu xuất hiện ở **câu hỏi so sánh** với AppArmor/seccomp.

### So sánh AppArmor, seccomp và SELinux {#so-sanh-apparmor-seccomp-selinux}

| Tiêu chí | AppArmor | seccomp | SELinux |
|---|---|---|---|
| Câu hỏi trả lời | Process được truy cập file/mạng nào? | Process được gọi syscall nào? | Process tương tác với tài nguyên nào (theo nhãn)? |
| Cách diễn đạt policy | Path-based (đường dẫn file) | Danh sách syscall + action (JSON/BPF) | Label/type enforcement |
| Mức độ chi tiết | Trung bình | Chi tiết ở mức syscall | Rất chi tiết, phức tạp |
| Distro tiêu biểu | Ubuntu/Debian/SUSE | Mọi distro (kernel >= 3.5) | RHEL/CentOS/Fedora |
| Đơn vị cấu hình cho pod | `appArmorProfile` (`Localhost`/`RuntimeDefault`) | `seccompProfile` (`Localhost`/`RuntimeDefault`) | `seLinuxOptions` (level/type/role/user) |
| Dùng phổ biến ở CKS | Có — dạng nạp profile + gắn pod | Có — dạng RuntimeDefault/Localhost | Ít hơn, chủ yếu lý thuyết |
| Điểm mạnh | Dễ viết, phù hợp nginx/agent | Chuẩn mực, nhẹ, phòng chống khai thác | Bao phủ rộng, nhiều policy sẵn có |

Cả ba đều là lớp phòng thủ thứ hai: khi process bị RCE, LSM/seccomp vẫn giới hạn thiệt hại, ngay cả khi process chạy bằng uid 0 trong namespace. Đó là lý do CKS xếp chúng vào domain System Hardening.

## Áp dụng vào Kubernetes: securityContext {#ap-dung-vao-kubernetes}

### Bảng các trường securityContext quan trọng {#bang-securitycontext}

Toàn bộ nội dung hardening ở trên hội tụ trong `securityContext` — khai báo ở **cấp pod** (áp dụng mọi container, chủ yếu là các trường identity) và **cấp container** (quyền chi tiết; container-level override pod-level):

| Trường | Cấp | Ý nghĩa | Ví dụ |
|---|---|---|---|
| `runAsUser` / `runAsGroup` | Pod/Container | uid/gid của process | `runAsUser: 1000` |
| `runAsNonRoot` | Pod/Container | Từ chối chạy nếu user root | `runAsNonRoot: true` |
| `fsGroup` | Pod | Group sở hữu volume | `fsGroup: 2000` |
| `capabilities.drop` / `.add` | Container | Thêm/bớt Linux capabilities | `drop: ["ALL"]` |
| `allowPrivilegeEscalation` | Container | Cấm setuid/setcap leo thang đặc quyền | `false` |
| `readOnlyRootFilesystem` | Container | Root filesystem chỉ đọc | `true` |
| `privileged` | Container | Toàn quyền host — tránh dùng | không set |
| `seccompProfile.type` | Pod/Container | RuntimeDefault/Localhost/Unconfined | `RuntimeDefault` |
| `appArmorProfile.type` | Pod/Container | RuntimeDefault/Localhost/Unconfined | `Localhost` |
| `seLinuxOptions.level` | Pod/Container | Nhãn SELinux (MCS/MLS) | `s0:c123,c456` |
| `procMount` | Container | `Default` hoặc `Unmasked` (tránh) | `Default` |
| `sysctls` | Pod | Kernel parameter namespaced | `net.ipv4.tcp_syncookies` |

Một pod "hardened mức CKS" trông như thế này:

```yaml
# ch08-hardened.yaml
apiVersion: v1
kind: Pod
metadata:
  name: hardened
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    runAsGroup: 3000
    fsGroup: 2000
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: app
      image: nginxinc/nginx-unprivileged:1.27-alpine
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop: ["ALL"]
      resources:
        requests:
          cpu: 100m
          memory: 64Mi
        limits:
          cpu: 500m
          memory: 128Mi
      volumeMounts:
        - name: cache
          mountPath: /var/cache/nginx
        - name: run
          mountPath: /var/run
        - name: tmp
          mountPath: /tmp
  volumes:
    - name: cache
      emptyDir: {}
    - name: run
      emptyDir: {}
    - name: tmp
      emptyDir: {}
```

Lưu ý thứ tự ưu tiên: **container-level override pod-level** cho các trường trùng nhau. Khi đánh giá một pod có bị "lỏng" không, đừng chỉ đọc pod-level — kẻ tấn công có thể cố tình set container-level để ghi đè (đây cũng là kiểu bẫy trong câu hỏi CKS).

### seccompProfile trong pod spec {#seccompprofile-trong-pod-spec}

Từ Kubernetes v1.19 seccomp đã GA với field `seccompProfile`; kubelet có thể bật `--seccomp-default` để **mọi pod mặc định RuntimeDefault** mà không cần khai báo:

```bash
# Trên node: kiểm tra kubelet có bật seccomp-default không
ps -ef | grep -o -- '--seccomp-default[^ ]*' | head -n1
# hoặc trong file flags của kubeadm
grep -o 'seccomp-default' /var/lib/kubelet/kubeadm-flags.env 2>/dev/null || true
```

Trong phòng thi, hai tình huống thường gặp:

1. Đề cho sẵn file profile JSON và yêu cầu áp cho pod: bạn phải **copy profile vào đúng seccomp root trên node** (`/var/lib/kubelet/seccomp/...`), rồi khai `type: Localhost` + `localhostProfile` (đường dẫn tương đối).
2. Đề yêu cầu "không cho container gọi syscall X": bạn viết profile với `SCMP_ACT_ERRNO` cho syscall đó, nạp vào node rồi verify từ trong pod.

Profile JSON hợp lệ phải có `defaultAction` và `architectures` phù hợp kiến trúc node (ví dụ `SCMP_ARCH_X86_64`, thêm `SCMP_ARCH_AARCH64` nếu cluster hỗn hợp). Đường dẫn trong `localhostProfile` là tương đối so với seccomp root — sai một cấp thư mục là pod fail với `failed to load seccomp profile`.

### appArmorProfile trong pod spec {#apparmorprofile-trong-pod-spec}

Với AppArmor, quy trình hai bước ngược với seccomp (profile phải **load trên host** trước, rồi tham chiếu bằng tên):

```bash
# 1. Trên node: tạo file profile + load
sudo tee /etc/apparmor.d/ch08-deny-write >/dev/null <<'EOF'
#include <tunables/global>

profile ch08-deny-write /usr/bin/yes flags=(attach_disconnected) {
  #include <abstractions/base>
  /etc/** r,
  deny /etc/** w,
}
EOF
sudo apparmor_parser -r /etc/apparmor.d/ch08-deny-write
sudo aa-enforce /etc/apparmor.d/ch08-deny-write
sudo aa-status | grep ch08-deny-write
```

```yaml
# 2. Trên pod: tham chiếu profile theo tên
spec:
  securityContext:
    appArmorProfile:
      type: Localhost
      localhostProfile: ch08-deny-write
```

Hai điều cần nhớ: profile phải tồn tại **trên mọi node** pod có thể chạy tới (`Localhost` không tự nhân bản), và tên trong `localhostProfile` phải **khớp đúng** tên profile đã nạp. Nếu không, pod fail với lỗi `failed to apply apparmor profile`. Khi dùng Helm để deploy, phần `securityContext` này có thể được templated bình thường (cú pháp bên dưới là Go template của Helm, đặt trong `{% raw %}...{% endraw %}` để Jekyll không parse nhầm):

{% raw %}
```text
{{- if .Values.hardening.apparmor }}
appArmorProfile:
  type: Localhost
  localhostProfile: {{ .Values.hardening.apparmorProfile | quote }}
{{- end }}
```
{% endraw %}

Điểm mấu chốt là **giá trị cuối cùng sau render** phải khớp tên profile trên node, còn cú pháp Go template của Helm (viết trong cặp ngoặc nhọn kép) chỉ là cách viết — đoạn template được bọc trong cặp thẻ `raw` của Jekyll để không bị hiểu nhầm là Liquid.

### sysctl mức pod {#sysctl-muc-pod}

Như đã trình bày ở [phần sysctl](#sysctl), chỉ **namespaced + safe sysctls** mới set được qua `securityContext.sysctls`. Một số trường hợp thực tế:

- `net.ipv4.ip_unprivileged_port_start: 0` — cho app non-root bind port thấp (thay vì cấp `NET_BIND_SERVICE`).
- `net.ipv4.tcp_syncookies: 1` — bật syncookies trong network namespace của pod.
- `net.ipv4.ping_group_range` — cho phép nhóm user dùng `ping` (một số image cần).

```bash
# Kiểm tra giá trị sysctl trong pod
kubectl exec sysctl-demo -- cat /proc/sys/net/ipv4/tcp_syncookies
```

Nếu set một sysctl unsafe (ví dụ `net.core.somaxconn`) mà kubelet chưa bật `--allowed-unsafe-sysctls`, pod sẽ bị **từ chối ngay khi tạo** với lỗi `forbidden sysctl: forbidden sysctl: "net.core.somaxconn" not allowlisted`. Đây là ranh giới quan trọng: sysctl unsafe ảnh hưởng toàn node nên không thể cho từng pod tự đặt.

### Dẫn nhập Pod Security Standards {#dan-nhap-pod-security-standards}

Tất cả các trường bạn vừa học được chuẩn hóa trong **Pod Security Standards (PSS)** — bộ ba mức `privileged`, `baseline`, `restricted` do Pod Security Admission enforce theo label namespace:

| Mức | Đặc điểm | Liên hệ chương này |
|---|---|---|
| `privileged` | Không giới hạn | Ngược hoàn toàn với hardening |
| `baseline` | Cấm `hostNetwork`/`hostPID`/`privileged`, chặn capabilities nguy hiểm | Các trường "phải có" tối thiểu |
| `restricted` | Yêu cầu `runAsNonRoot`, drop ALL capabilities, `seccompProfile: RuntimeDefault`, `allowPrivilegeEscalation: false` | Gần như chính là `ch08-hardened.yaml` |

Ví dụ bật restricted cho một namespace:

```bash
kubectl label namespace secure-app \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/enforce-version=v1.33
```

Đây là cầu nối sang chương 9: PSS là cách **enforce tập trung** các cấu hình hardening bạn đã học trong chương này, còn admission policy (OPA/Kyverno) là mức tùy biến cao hơn.

### Bước 2 - seccomp: RuntimeDefault, Unconfined và Localhost profile {#lab-step-2}

Trước tiên chứng minh môi trường có bật seccomp và **kubelet mặc định là Unconfined** (chưa bật `--seccomp-default`):

```bash
# Kubelet flags liên quan seccomp (không có seccomp-default nghĩa là pod mặc định unconfined)
docker exec ch08-lab-control-plane bash -c "ps aux | grep '[k]ubelet' | tr ' ' '\n' | grep seccomp"
# (không có output)

# Xác nhận kernel bật seccomp trong node container
docker exec ch08-lab-control-plane cat /proc/self/status | grep -i seccomp
# Seccomp: 2        <- Docker áp profile mặc định cho chính container node
```

Tạo pod đầu tiên với `Unconfined` và pod thứ hai với `RuntimeDefault`:

```yaml
# ch08-seccomp-cmp.yaml
apiVersion: v1
kind: Pod
metadata:
  name: seccomp-unconfined
spec:
  securityContext:
    seccompProfile:
      type: Unconfined
  containers:
    - name: test
      image: alpine:3.20
      command: ["sleep", "3600"]
---
apiVersion: v1
kind: Pod
metadata:
  name: seccomp-runtime
spec:
  securityContext:
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: test
      image: alpine:3.20
      command: ["unshare", "-U", "true"]
```

```bash
kubectl apply -f ch08-seccomp-cmp.yaml
kubectl get pod seccomp-runtime
# seccomp-runtime sẽ CrashLoopBackOff: unshare bị RuntimeDefault chặn (Operation not permitted)
kubectl logs seccomp-runtime
# unshare: unshare failed: Operation not permitted
```

Chuyển pod `seccomp-unconfined` sang chạy lệnh test tương tự để thấy khác biệt (nếu capability cho phép, `unshare` sẽ chạy được khi seccomp không chặn):

```bash
kubectl exec seccomp-unconfined -- grep Seccomp /proc/self/status
# Seccomp:         0        <- không filter

kubectl exec seccomp-runtime -- true 2>/dev/null || kubectl delete pod seccomp-runtime

# Chạy lệnh test trong pod unconfined
kubectl exec seccomp-unconfined -- sh -c 'unshare -U true && echo "unshare OK (seccomp khong chan)"' || \
  echo "unshare bi chan boi capability/runtime"
```

Bây giờ tạo **Localhost profile** chặn thêm các syscall đổi quyền file (`chmod`, `fchmod`, `fchmodat`) — syscall mà RuntimeDefault vẫn cho phép:

```bash
# Ghi profile vào đúng seccomp root của kubelet trong node kind
docker exec ch08-lab-control-plane bash -c 'mkdir -p /var/lib/kubelet/seccomp/profiles && cat > /var/lib/kubelet/seccomp/profiles/ch08-deny-chmod.json <<EOF
{
  "defaultAction": "SCMP_ACT_ALLOW",
  "architectures": ["SCMP_ARCH_X86_64"],
  "syscalls": [
    {
      "names": ["chmod", "fchmod", "fchmodat"],
      "action": "SCMP_ACT_ERRNO",
      "errnoRet": 1
    }
  ]
}
EOF'

# Verify file đã nằm đúng chỗ
docker exec ch08-lab-control-plane cat /var/lib/kubelet/seccomp/profiles/ch08-deny-chmod.json
```

> Nếu node của bạn dùng `--seccomp-default-root` khác, profile phải nằm trong root đó. Trên kind mặc định seccomp root là `/var/lib/kubelet/seccomp`.

```yaml
# ch08-seccomp-localhost.yaml
apiVersion: v1
kind: Pod
metadata:
  name: seccomp-localhost
spec:
  securityContext:
    seccompProfile:
      type: Localhost
      localhostProfile: profiles/ch08-deny-chmod.json   # tương đối so với seccomp root
  containers:
    - name: test
      image: alpine:3.20
      command: ["sleep", "3600"]
```

```bash
kubectl apply -f ch08-seccomp-localhost.yaml
kubectl get pod seccomp-localhost
# Running

# Verify filter đang áp
kubectl exec seccomp-localhost -- grep Seccomp /proc/self/status
# Seccomp:         2
# Seccomp_filters: 1

# chmod phải bị chặn bởi profile Localhost
kubectl exec seccomp-localhost -- sh -c 'touch /tmp/f && chmod 400 /tmp/f' 2>&1
# chmod: /tmp/f: Operation not permitted

# Cùng lệnh trên một pod không có seccomp (hoặc RuntimeDefault) phải thành công
kubectl exec seccomp-unconfined -- sh -c 'touch /tmp/f && chmod 400 /tmp/f && echo "chmod OK"'
# chmod OK
```

**Kết quả mong đợi của bước 2** (ghi lại để đối chiếu):

| Pod | `seccompProfile.type` | `unshare -U` | `chmod` |
|---|---|---|---|
| `seccomp-unconfined` | Unconfined | tùy capability/kernel | OK |
| `seccomp-runtime` | RuntimeDefault | bị chặn (Operation not permitted) | OK |
| `seccomp-localhost` | Localhost (chặn chmod) | bị chặn | bị chặn |

Đây chính là điều đề thi CKS kiểm tra: bạn phân biệt được **layer nào chặn việc gì** — seccomp chặn syscall, capability chặn thao tác đặc quyền, và profile tùy biến chặn đúng thứ bạn muốn.

### Bước 3 - securityContext hardening: nonRoot, capabilities, read-only rootfs {#lab-step-3}

Tạo ba pod để so sánh trực tiếp trên cùng một cluster:

```yaml
# ch08-hardening.yaml
apiVersion: v1
kind: Pod
metadata:
  name: bad-root            # baseline: chạy root, quyền rộng
spec:
  containers:
    - name: app
      image: busybox:1.36
      command: ["sh", "-c", "id && sleep 3600"]
---
apiVersion: v1
kind: Pod
metadata:
  name: good-nonroot        # least privilege: non-root, drop ALL, read-only
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    runAsGroup: 3000
    fsGroup: 2000
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: app
      image: busybox:1.36
      command: ["sh", "-c", "id && sleep 3600"]
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop: ["ALL"]
      volumeMounts:
        - name: tmp
          mountPath: /tmp
  volumes:
    - name: tmp
      emptyDir: {}
---
apiVersion: v1
kind: Pod
metadata:
  name: root-without-nonroot-check   # cố tình vi phạm runAsNonRoot
spec:
  securityContext:
    runAsUser: 0
    runAsNonRoot: true
  containers:
    - name: app
      image: busybox:1.36
      command: ["sleep", "3600"]
```

```bash
kubectl apply -f ch08-hardening.yaml
```

Verify từng điểm, so sánh cặp `bad-root` ↔ `good-nonroot`:

```bash
# 1. Identity: root vs uid 1000
kubectl exec bad-root -- id
# uid=0(root) gid=0(root) groups=0(root)
kubectl exec good-nonroot -- id
# uid=1000 gid=3000 groups=3000,2000

# 2. Capabilities: đầy đủ vs rỗng
kubectl exec bad-root -- grep '^CapEff' /proc/1/status
# CapEff: 00000000a80425fb     <- nhiều bit, gồm cả cap nguy hiểm
kubectl exec good-nonroot -- grep '^CapEff' /proc/1/status
# CapEff: 0000000000000000     <- dropped ALL

# 3. readOnlyRootFilesystem: ghi root fs
kubectl exec bad-root -- sh -c 'touch /probe && echo "bad-root ghi duoc /"'
# bad-root ghi duoc /
kubectl exec good-nonroot -- sh -c 'touch /probe' 2>&1
# touch: /probe: Read-only file system

# 4. /tmp vẫn ghi được nhờ emptyDir
kubectl exec good-nonroot -- sh -c 'touch /tmp/probe && echo "tmp OK"'
# tmp OK

# 5. Pod vi phạm runAsNonRoot bị kubelet từ chối
kubectl get pod root-without-nonroot-check
# STATUS: CreateContainerConfigError
kubectl describe pod root-without-nonroot-check | grep -A2 'Warning'
# Error: container has runAsNonRoot and image will run as root
```

Thử thêm tình huống capability: pod non-root bind port 80. Khi drop ALL capabilities, bind thất bại; thêm `NET_BIND_SERVICE` (hoặc dùng sysctl `ip_unprivileged_port_start` ở bước 4) sẽ thành công:

```bash
kubectl exec good-nonroot -- sh -c 'nc -l -p 80' 2>&1 | head -n1
# nc: bind: Permission denied      (thiếu NET_BIND_SERVICE)
```

### Bước 4 - sysctl hardening: mức node và mức pod {#lab-step-4}

**Mức node** — trên host Linux/WSL2, tạo file hardening và nạp:

```bash
# Xem giá trị hiện tại trên host
sysctl kernel.dmesg_restrict net.ipv4.tcp_syncookies

# Tạo file hardening
sudo tee /etc/sysctl.d/99-cks-hardening.conf >/dev/null <<'EOF'
net.ipv4.conf.all.accept_redirects = 0
net.ipv4.conf.all.send_redirects = 0
net.ipv4.tcp_syncookies = 1
kernel.dmesg_restrict = 1
kernel.kptr_restrict = 2
kernel.yama.ptrace_scope = 1
EOF

sudo sysctl --system
sysctl -n kernel.dmesg_restrict
# 1
sysctl -n net.ipv4.tcp_syncookies
# 1
```

Trên **WSL2/Docker Desktop**, một số giá trị bị khóa bởi kernel/VM của Docker Desktop (ví dụ `sysctl -w net.ipv4.tcp_syncookies=$x` có thể trả `Read-only file system`). Đó không phải lỗi làm bài — hãy ghi nhận và kiểm chứng bằng giá trị đọc được:

```bash
# Kiểm tra một tham số có ghi được không
sudo sysctl -w net.ipv4.tcp_syncookies=1 2>&1 || echo "khong ghi duoc trong WSL2 - binh thuong"
```

Sysctl bên trong node kind cũng chịu giới hạn tương tự vì node là container:

```bash
docker exec ch08-lab-control-plane sysctl kernel.dmesg_restrict
# kernel.dmesg_restrict = 1 (kế thừa từ host/VM) hoặc lỗi tùy môi trường
```

**Mức pod** — dùng sysctl namespaced để cho phép bind port thấp:

```yaml
# ch08-sysctl-pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: sysctl-demo
spec:
  securityContext:
    sysctls:
      - name: net.ipv4.ip_unprivileged_port_start
        value: "0"
  containers:
    - name: web
      image: busybox:1.36
      command: ["sh", "-c", "nc -l -p 80 -e echo ok & sleep 3600"]
      securityContext:
        runAsNonRoot: true
        runAsUser: 1000
        allowPrivilegeEscalation: false
        capabilities:
          drop: ["ALL"]
```

```bash
kubectl apply -f ch08-sysctl-pod.yaml
kubectl get pod sysctl-demo
# Running

# Verify trong network namespace của pod
kubectl exec sysctl-demo -- cat /proc/sys/net/ipv4/ip_unprivileged_port_start
# 0

# Bind port 80 thành công dù uid 1000 và không có capability nào
kubectl exec sysctl-demo -- sh -c 'nc -z 127.0.0.1 80 && echo "port 80 dang listen"' || \
  kubectl exec sysctl-demo -- netstat -tln | grep ':80 '
```

Thử set một sysctl **unsafe** để thấy kubelet từ chối (đây là ranh giới quan trọng của mô hình bảo mật):

```yaml
# ch08-sysctl-unsafe.yaml  (kỳ vọng: bị từ chối)
apiVersion: v1
kind: Pod
metadata:
  name: sysctl-unsafe
spec:
  securityContext:
    sysctls:
      - name: net.core.somaxconn
        value: "1024"

    - name: app
      image: busybox:1.36
      command: ["sleep", "3600"]
```

```bash

# forbidden sysctl: "net.core.somaxconn" not allowlisted
```

### Bước 5 - AppArmor trên node Linux (và giới hạn của kind/WSL2) {#lab-step-5}

AppArmor cần kernel có module LSM này. Kiểm tra trước khi làm:

```bash
# Trên host Linux / WSL2
cat /sys/module/apparmor/parameters/enabled 2>/dev/null || echo "AppArmor khong co tren host nay"
sudo aa-status 2>/dev/null | head -n 5 || echo "aa-status chua cai (can apparmor-utils)"
```

Nếu AppArmor bật, tạo profile chặn ghi `/etc` và áp cho một process:

```bash
sudo apt-get install -y apparmor-utils 2>/dev/null   # nếu chưa có
sudo tee /etc/apparmor.d/ch08-deny-write >/dev/null <<'EOF'
#include <tunables/global>

profile ch08-deny-write /usr/bin/sleep flags=(attach_disconnected) {
  #include <abstractions/base>
  deny /etc/** w,
  /tmp/** rw,
}
EOF

# Load ở complain mode để xem log trước, rồi chuyển enforce
sudo apparmor_parser -r /etc/apparmor.d/ch08-deny-write
sudo aa-complain /etc/apparmor.d/ch08-deny-write
sudo aa-enforce /etc/apparmor.d/ch08-deny-write

# Verify profile đã load và đang enforce
sudo aa-status | grep ch08-deny-write
# /etc/apparmor.d/ch08-deny-write

# Trong lúc luyện, bạn có thể đổi qua complain rồi chạy lại để thấy profile
# chỉ ghi log (không chặn) — hành vi này dùng khi xây dựng profile mới:
sudo aa-complain /etc/apparmor.d/ch08-deny-write
sudo aa-enforce /etc/apparmor.d/ch08-deny-write

# Xem vi phạm bị chặn (nếu có process bị profile quản lý ghi vào /etc)
sudo journalctl -k | grep -i 'apparmor.*DENIED' | tail -n 3
```

> Trong profile mẫu ở trên, `deny /etc/** w` chỉ áp cho chương trình khớp `/usr/bin/sleep`. Khi luyện trên host, hãy thay đường dẫn binary bằng chương trình bạn muốn test (ví dụ `/usr/bin/cat`) và kiểm tra xem `/etc/apparmor.d/` trên distro bạn dùng đã có profile mặc định trùng tên chưa.

Sau khi profile đã load, gắn vào pod — **trên node có AppArmor** (host Linux hoặc VM Ubuntu):

```yaml
# ch08-apparmor-pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: apparmor-demo
spec:
  securityContext:
    appArmorProfile:
      type: Localhost
      localhostProfile: ch08-deny-write
  containers:
    - name: demo
      image: alpine:3.20
      command: ["sleep", "3600"]
```

```bash
# Chạy trên cluster có node với AppArmor đã nạp profile, ví dụ kind trên host Ubuntu:
kubectl apply -f ch08-apparmor-pod.yaml

kubectl exec apparmor-demo -- cat /proc/1/attr/current
# ch08-deny-write (enforce)
kubectl exec apparmor-demo -- sh -c 'echo test > /etc/probe' 2>&1
# sh: can't create /etc/probe: Permission denied
```

**Ghi chú giới hạn khi chạy trên Windows/WSL2:** node kind là container Docker; container này có profile AppArmor riêng do Docker áp lúc tạo (bạn thấy được qua `head /proc/1/attr/current`), nhưng **không thể nạp AppArmor profile mới để kubelet áp cho pod** vì AppArmor namespace của node container bị tách khỏi host. `aa-status` trên WSL2 thường báo `AppArmor is not enabled`. Cách kiểm chứng đầy đủ là chạy bước này trên **VM Ubuntu (Multipass/VirtualBox)** hoặc **host Linux thật**, nơi bạn kiểm tra:

```bash
# Trên VM Ubuntu có cluster kind
multipass shell ch08-ubuntu      # hoặc ssh vào VM
sudo aa-status | grep ch08-deny-write
kubectl get pod apparmor-demo -o yaml | grep -A3 appArmorProfile
kubectl exec apparmor-demo -- cat /proc/1/attr/current
```

Nếu môi trường của bạn không hỗ trợ AppArmor, hãy **viết ra giấy quy trình 3 bước** (load profile trên node → đặt tên đúng → khai `appArmorProfile` trong pod) và kiểm chứng bằng `kubectl get pod -o jsonpath` — trong phòng thi dạng task này xuất hiện thường xuyên.

## Câu hỏi phỏng vấn thường gặp {#interview-questions}

**1. Bạn giảm host OS footprint của một node Kubernetes như thế nào, và đo hiệu quả bằng gì?**

Quy trình của tôi là kiểm kê rồi loại bỏ theo lớp: `systemctl list-units --type=service --state=running` và `ss -tulpn` để thấy service/port thực tế; `apt list --installed` để soi package cài tay; `lsmod` cho kernel module. Sau đó mask service thừa, purge trình biên dịch và tool không cần, blacklist module hiếm trong `/etc/modprobe.d/`. Đo hiệu quả bằng ba chỉ số: số port listen, số process ngoài danh sách kubelet/containerd/CNI, và diện tích patch khi có CVE (ít package hơn nghĩa là ít thứ phải kiểm tra). Trên production tôi ưu tiên node image tối giản (immutable OS hoặc managed node image) để footprint được kiểm soát bằng image thay vì bằng thao tác tay.

**2. Immutable OS có nhược điểm gì khi vận hành? Khi nào không nên dùng?**

Nhược điểm chính là debug tại chỗ khó: không SSH, không cài được `tcpdump`, `strace` hay package chẩn đoán; mọi thay đổi phải đi qua image/machine config mới. Với đội chưa quen, thời gian xử lý sự cố ban đầu sẽ tăng. Ngoài ra một số agent bảo mật/observability cần driver hoặc mount đặc biệt có thể không tương thích với distro tối giản. Không nên dùng khi bạn cần app chạy trực tiếp trên host (không container hóa được), hoặc khi tổ chức chưa có quy trình cập nhật image tự động — lúc đó node "đóng băng" sẽ lâu ngày thành node lỗi thời, rủi ro còn cao hơn.

**3. Vì sao không nên chạy container bằng root? Nếu ứng dụng buộc phải bind port 80 thì xử lý thế nào?**

Chạy root nghĩa là kẻ tấn công có RCE đứng ở uid 0 trong container; cộng thêm một lỗ hổng kernel/runtime hoặc cấu hình sai (hostPath, privileged, capability rộng) thì đường thoát ra node rất ngắn. Đây là lý do `runAsNonRoot: true` là yêu cầu của Pod Security Standards mức restricted. Nếu buộc bind port 80, có ba cách đúng: (1) dùng image build sẵn user non-root lắng nghe port cao rồi Service map 80 xuống port đó; (2) thêm đúng capability `NET_BIND_SERVICE` sau khi `drop: ["ALL"]`; (3) đặt sysctl namespaced `net.ipv4.ip_unprivileged_port_start=0` cho pod. Cả ba đều giữ được nguyên tắc least privilege; cách sai là chạy root hoặc `privileged: true`.

**4. AppArmor khác seccomp và SELinux ở điểm cốt lõi nào?**

Ba cơ chế bổ sung nhau chứ không thay thế nhau. AppArmor là LSM theo **đường dẫn**: nó quyết định process được đọc/ghi file nào, được dùng loại network nào — mạnh trong việc giới hạn phạm vi file của một daemon như nginx. seccomp lọc **system call**: nó quyết định process được gọi kernel bằng cách nào (`unshare`, `mount`, `ptrace`...) — nhẹ, chạy trên mọi distro, là chuẩn mực để chống khai thác. SELinux là LSM theo **nhãn**: chi tiết và mạnh nhất nhưng phức tạp nhất, gắn với RHEL family. Trong thực tế tôi dùng seccomp (RuntimeDefault) cho mọi workload, AppArmor cho các daemon có file access đặc thù, và chỉ chạm SELinux khi hạ tầng chạy RHEL.

**5. seccomp profile tùy biến được đặt ở đâu và pod tham chiếu thế nào?**

File profile (JSON theo chuẩn OCI) phải nằm trên **node**, trong seccomp root của kubelet — mặc định `/var/lib/kubelet/seccomp/`. Trong pod, khai `securityContext.seccompProfile.type: Localhost` cùng `localhostProfile` là **đường dẫn tương đối** so với seccomp root, ví dụ `profiles/ch08-deny-unshare.json`. Hai lỗi thường gặp: đặt file sai thư mục (pod fail với lỗi load profile) và quên rằng profile phải có mặt trên **mọi node** pod có thể chạy — trong DAEMON-like deployment bạn phải phân phối profile đồng loạt, thường qua init container, node bootstrap script (cloud-init) hoặc image.

**6. Muốn chặn một syscall trong khi vẫn cho phép mọi syscall khác, viết profile thế nào?**

Tôi dùng `defaultAction: SCMP_ACT_ALLOW` để mọi syscall bình thường đi qua, rồi liệt kê syscall cần chặn trong `syscalls` với action `SCMP_ACT_ERRNO`. `errnoRet: 1` khiến lỗi trả về là `EPERM` ("Operation not permitted") — dễ nhận biết khi test. Cần liệt kê đủ các biến thể: muốn chặn `chmod` thực tế phải chặn cả `fchmod` và `fchmodat` vì glibc gọi wrapper theo kiến trúc. Cách xây ngược lại (default `ERRNO`, allow từng syscall) an toàn hơn về lý thuyết nhưng dễ làm app lỗi, thường dùng cho workload tĩnh có hệ thống syscall đã đo bằng `strace`.

**7. `allowPrivilegeEscalation: false` chặn điều gì? Đặt nó có thể gây lỗi gì?**

Nó chặn process con nhận thêm đặc quyền qua cơ chế setuid/setcap hoặc qua các đường leo thang tương tự — tức là dù binary có bit setuid root, process vẫn không thể "nâng cấp" lên uid 0. Đây là trường bắt buộc ở mức restricted. Lỗi có thể gặp: một số init script cũ dùng `sudo` bên trong container sẽ ngừng hoạt động; các binary dựa vào file capability (setcap) cũng bị vô hiệu. Khi đó cách đúng không phải bật lại flag, mà là loại bỏ nhu cầu leo thang — chạy đúng user và thêm capability cần thiết ở tầng `securityContext`.

**8. `readOnlyRootFilesystem` làm hỏng ứng dụng đang chạy production. Bạn xử lý thế nào?**

Trước hết xác định đúng đường dẫn ứng dụng cần ghi bằng cách đọc log lỗi và kiểm tra `strace`/config của ứng dụng. Sau đó mount `emptyDir` hoặc `tmpfs` vào đúng những điểm đó (cache, pid, tmp, log nếu ghi file) — không tắt hardening. Trong deploy an toàn, tôi thử trên staging trước, ghi lại danh sách đường dẫn cần ghi, rồi áp rollout theo từng bước. Với ứng dụng có volume dữ liệu, cần chú ý `fsGroup` để process non-root ghi được vào volume.

**9. Trên node, những file nào bạn luôn kiểm tra quyền đầu tiên?**

`/etc/kubernetes/admin.conf` (thường bị để `644` — đây là quyền cluster-admin), `/etc/kubernetes/kubelet.conf`, toàn bộ `/etc/kubernetes/pki` (đặc biệt các file `*.key`), `/var/lib/kubelet/config.yaml`, và `~/.kube/config` của user vận hành. Tiêu chuẩn là `600` với file, `700` với thư mục nhạy cảm, chủ sở hữu `root:root` (trừ kubeconfig cá nhân). Tôi verify bằng `stat -c '%a %U:%G %n'` và đưa nó vào script audit/CI check thay vì dựa vào trí nhớ.

**10. Bastion host hơn gì so với để SSH trực tiếp trên node, và còn cách nào thay thế?**

Bastion tập trung hóa và kiểm soát được đường quản trị: chỉ một điểm có IP public, whitelist nguồn ở tầng security group, MFA/SSO ở tầng VPN, log session tập trung, và đặc biệt — bastion không giữ credential cluster. Lợi ích cộng dồn là giảm bề mặt (node không cần public IP/port 22) và tăng khả năng truy vết. Thay thế hiện đại là **SSM Session Manager** (AWS) hoặc **Teleport**/Boundary — kết nối đi qua agent theo chiều ra, không mở port SSH nào, và có audit tích hợp.

**11. Kiểm tra network exposure của cluster từ bên ngoài như thế nào, và verify kết quả ra sao?**

Từ một máy ngoài cluster, quét các port trọng yếu: `6443` (API), `2379/2380` (etcd), `10250` (kubelet), `10255` (read-only), `30000-32767` (NodePort), `80/443` (Ingress). Tôi dùng `nc -zv -w2` hoặc `nmap`; kết quả phải là: etcd/10255 không kết nối được, API chỉ mở cho CIDR quản trị, kubelet không lộ ra ngoài. Sau đó kiểm tra chéo ở tầng cloud bằng security group rule và VPC Flow Logs. Khi phát hiện port mở sai, remediate ở lớp ngoài cùng trước (security group), rồi mới tới firewall host — và verify lại từ **cùng máy quét ban đầu**, không tự đánh giá trong nội bộ.

**12. Đánh giá một pod đang chạy có thực sự hardened không — bạn kiểm tra gì và theo thứ tự nào?**

Đầu tiên đọc spec: `kubectl get pod <name> -o yaml` để kiểm tra `securityContext` — ưu tiên container-level vì nó override pod-level. Kiểm tra theo checklist: `runAsNonRoot`/`runAsUser` khác 0, `allowPrivilegeEscalation: false`, `readOnlyRootFilesystem: true`, `capabilities.drop: [ALL]`, `seccompProfile.type` khác Unconfined, không `privileged`, không `hostNetwork`/`hostPID`. Nhưng spec chưa đủ — tôi verify runtime: `kubectl exec ... -- id`, `grep CapEff /proc/1/status`, `grep Seccomp /proc/self/status`, và thử ghi vào root fs. Nếu cluster có Pod Security Admission, đối chiếu thêm với mức label của namespace (`restricted` là mạnh nhất).

**13. Vì sao phải bật `runAsNonRoot` khi image đã chạy non-root sẵn? Nó khác gì "tin vào image"?**

Image có thể thay đổi: một lần rebuild từ Dockerfile khác, một tag bị overwrite, hoặc base image cập nhật mà quên `USER`. `runAsNonRoot: true` biến giả định đó thành **ràng buộc được kubelet enforce**: nếu image chỉ định user root, pod không được tạo. Đây là nguyên tắc "defense in depth" — image đúng là điều kiện cần, policy đúng là điều kiện đủ. Trong audit, tôi coi việc chỉ dựa vào `USER` của Dockerfile là thiếu sót, đặc biệt khi cluster có nhiều team cùng push image.

**14. Kể một sự cố thật mà hardening chủ động đã giúp giảm thiệt hại (hoặc ngược lại).**

Một ví dụ tôi từng gặp: một container web bị khai thác qua lỗ hổng thư viện, kẻ tấn công thử ghi web shell vào thư mục webroot và thiết lập cron. Vì image build với `USER` non-root, `readOnlyRootFilesystem: true` và `capabilities.drop: [ALL]`, cả hai nỗ lực đều thất bại và để lại log — Falco alert ngay từ lần ghi đầu tiên. Nếu container chạy root với root fs ghi được, sự cố sẽ thành máy chủ bị persist và phải rebuild node. Bài học: các kiểm soát đơn giản này không ngăn được xâm nhập, nhưng chặn giai đoạn "thiết lập chỗ đứng" — giai đoạn quyết định chi phí xử lý.

## Các điểm chính {#key-points}

- **System Hardening (10%)** là domain nền móng: node bị chiếm thì mọi kiểm soát Kubernetes đều vô nghĩa. Đề thi chấm trên trạng thái thật của node/pod, không chấm cú pháp.

- Giảm host OS footprint theo chu trình **kiểm kê → đánh giá → loại bỏ → verify**: mask service thừa, purge package không cần (đặc biệt trình biên dịch), blacklist kernel module hiếm. Immutable OS (Flatcar, Bottlerocket, Talos, managed node image) là mức triệt để nhất.

- Patch node là quy trình **cordon → drain → patch → reboot → uncordon**; chiến lược tối ưu là thay node từ image đã vá thay vì vá từng node.

- SSH hardening: key-only, `PermitRootLogin no`, whitelist group, `AllowTcpForwarding no`, luôn giữ session dự phòng và validate bằng `sshd -t` trước khi reload.

- Least privilege bốn tầng: **cloud IAM → OS user/group → container identity → ServiceAccount**. File nhạy cảm (`admin.conf`, `kubelet.conf`, `*.key`, `config.yaml`) phải là `600`, chủ `root:root` — audit bằng `stat`.

- Socket container runtime (`/run/containerd/containerd.sock`) chỉ root được truy cập; không mount vào pod nếu không cần vì tương đương quyền root trên host.

- Không chạy workload bằng root: `runAsNonRoot: true` bị kubelet enforce (pod fail với image root), `runAsUser` phải khác 0, xử lý `CreateContainerConfigError` bằng image non-root hoặc set uid cụ thể.

- Capabilities: **drop ALL rồi add lại đúng cái cần** (`NET_BIND_SERVICE` cho port < 1024, `SYS_ADMIN` là điều cấm); `allowPrivilegeEscalation: false` chặn setuid/setcap. Không dùng `privileged: true` thay thế.

- `readOnlyRootFilesystem: true` chặn persist payload; mount `emptyDir`/`tmpfs` vào đúng đường dẫn cần ghi (cache, tmp, pid) thay vì tắt hardening.

- Network exposure: default deny inbound; nhớ port trọng yếu **6443, 2379/2380, 10250, 10255 (phải đóng), 30000-32767**; security group là lớp chính trên cloud; production dùng private cluster + bastion/VPN, ưu tiên SSM/Teleport không mở SSH.

- sysctl hardening qua `/etc/sysctl.d/*.conf` + `sysctl --system`: `accept_redirects=0`, `rp_filter=1`, `tcp_syncookies=1`, `dmesg_restrict=1`, `kptr_restrict=2`, `ptrace_scope=1`. Chỉ **safe sysctl namespaced** mới set được trong pod; unsafe bị kubelet từ chối với `not allowlisted`.

- AppArmor: profile theo đường dẫn, `enforce/complain/unconfined`; profile phải nạp trên node rồi khai `appArmorProfile.type: Localhost` + tên profile (GA từ v1.31). seccomp: `RuntimeDefault` là chuẩn, `Localhost` trỏ file JSON trong seccomp root (mặc định `/var/lib/kubelet/seccomp/`), action hay dùng `SCMP_ACT_ERRNO`/`SCMP_ACT_KILL_PROCESS`.

- `securityContext` là điểm hội tụ: pod-level cho identity, container-level override cho quyền chi tiết. Bộ đầy đủ gồm `runAsNonRoot`, `runAsUser`, `fsGroup`, `capabilities.drop`, `allowPrivilegeEscalation`, `readOnlyRootFilesystem`, `seccompProfile`, `appArmorProfile`, `sysctls`.

- Các cấu hình này chính là nội dung **Pod Security Standards mức restricted** (chương 9) — PSS enforce tập trung; verify runtime luôn cần: `id`, `CapEff`, `Seccomp`, và thử ghi root fs.

## Câu hỏi thực hành {#practice-questions}

**1. Đội bạn đang chuẩn bị hardening cho các worker node chạy Kubernetes v1.33. Những việc nào thực sự giúp giảm host OS footprint? (Chọn tất cả đáp án đúng)**

**A)** Mask các service không dùng (`bluetooth`, `cups`, `avahi-daemon`) và purge trình biên dịch (`gcc`, `make`) khỏi node production.  
**B)** Mở SSH ra Internet nhưng đổi sang port 2222 để tránh bị scan tự động.  
**C)** Dùng node image tối giản/immutable (ví dụ Bottlerocket, Flatcar hoặc managed node image) thay vì OS đầy đủ.  
**D)** Cài thêm công cụ chẩn đoán (`tcpdump`, `nmap`, `python3`) trên mọi node để tiện debug sự cố.

**2. Khi audit quyền truy cập trên một node Kubernetes, những phát hiện nào là vi phạm nguyên tắc least privilege? (Chọn tất cả đáp án đúng)**

**A)** `/etc/kubernetes/admin.conf` có quyền `644`, chủ sở hữu `root:root`.  
**B)** User `deploy` nằm trong group `docker` trên node chỉ chạy containerd.  
**C)** `/etc/sudoers.d/ops` chứa `ops ALL=(ALL) NOPASSWD: ALL`.  
**D)** Container của ứng dụng chạy bằng `runAsUser: 0` nhưng đã bật `readOnlyRootFilesystem: true`.

**3. Bạn có file seccomp profile `profiles/ch08-deny-unshare.json` muốn áp cho pod. Cách làm nào đúng?**

**A)** Đặt file ở `/var/lib/kubelet/seccomp/profiles/` trên node, pod khai `seccompProfile.type: Localhost` và `localhostProfile: profiles/ch08-deny-unshare.json`.  
**B)** Nhúng nội dung JSON vào `securityContext.seccompProfile.profile` trong pod spec.  
**C)** Đặt file ở `/etc/seccomp/` trên node vì kubelet tự quét mọi thư mục; pod chỉ cần `type: RuntimeDefault`.  
**D)** Cài profile vào image ở `/usr/share/seccomp/` và khai `type: Localhost` — kubelet đọc từ root filesystem của container.

**4. Bạn cần tăng cường kernel cho node theo CIS. Những cách nào đúng? (Chọn tất cả đáp án đúng)**

**A)** Thêm `net.ipv4.tcp_syncookies = 1` và `kernel.dmesg_restrict = 1` vào `/etc/sysctl.d/99-hardening.conf`, sau đó chạy `sysctl --system`.  
**B)** Chạy `sysctl -w net.ipv4.tcp_syncookies=1` và coi đó là cấu hình vĩnh viễn.  
**C)** Set `net.ipv4.ip_unprivileged_port_start: "0"` trong `securityContext.sysctls` của pod vì đây là sysctl namespaced an toàn.  
**D)** Set `net.core.somaxconn` trong pod `securityContext.sysctls` vì kubelet chấp nhận mọi sysctl nếu pod có `runAsNonRoot`.

**5. Khi kiểm tra mức độ phơi bày mạng của một node Kubernetes, kết quả nào là dấu hiệu cần xử lý ngay? (Chọn tất cả đáp án đúng)**

**A)** Port 10255 (kubelet read-only) trả về JSON khi truy cập từ một máy khác trong cùng mạng.  
**B)** etcd port 2379 chỉ listen trên `127.0.0.1` của control plane.  
**C)** Port 6443 của kube-apiserver mở với `0.0.0.0/0` trên security group của cluster production.  
**D)** Port 10250 của kubelet chỉ cho phép kết nối từ CIDR của control plane/node.

**6. Một pod chạy nginx bằng user non-root vẫn cần bind port 80. Cách xử lý nào giữ được least privilege? (Chọn tất cả đáp án đúng)**

**A)** Thêm capability `NET_BIND_SERVICE` vào container sau khi `drop: ["ALL"]`.  
**B)** Set `runAsUser: 0` cho container để nginx bind được port 80, kèm `readOnlyRootFilesystem: true`.  
**C)** Set sysctl namespaced `net.ipv4.ip_unprivileged_port_start: "0"` trong `securityContext.sysctls` của pod.  
**D)** Thêm `privileged: true` cho container vì nginx cần quyền bind port thấp.

**7. Bạn muốn mọi pod trong namespace `secure-app` bị ràng buộc các chuẩn hardening (non-root, drop capabilities, seccomp RuntimeDefault...). Cách tiếp cận nào đúng?**

**A)** Gắn label `pod-security.kubernetes.io/enforce: restricted` cho namespace để Pod Security Admission tự chặn pod vi phạm.  
**B)** Tự viết webhook đọc từng pod rồi gửi email nhắc nhở các team chỉnh sửa thủ công.  
**C)** Yêu cầu mọi deployment gắn `securityContext` thủ công rồi kiểm tra bằng mắt trước khi merge.  
**D)** Tắt hoàn toàn khả năng tạo pod trong namespace bằng cách xóa ServiceAccount mặc định.

**8. Bạn nhận task: "Đảm bảo container `web` trong deployment `frontend` không thể ghi vào root filesystem, không được leo thang đặc quyền và không giữ capability nào, nhưng ứng dụng cần ghi cache vào `/var/cache/web` và log vào `/tmp`." Cách làm nào đúng nhất?**

**A)** Set `readOnlyRootFilesystem: true`, `allowPrivilegeEscalation: false`, `capabilities.drop: ["ALL"]` và mount `emptyDir` vào `/var/cache/web` cùng `/tmp`.  
**B)** Set `readOnlyRootFilesystem: true` cho toàn bộ pod và tắt log của ứng dụng để không cần ghi.  
**C)** Giữ nguyên cấu hình cũ, chỉ thêm `runAsNonRoot: true` vì hai yêu cầu còn lại không thể thỏa mãn đồng thời.  
**D)** Dùng `privileged: true` rồi chặn ghi bằng AppArmor profile vì cách này đơn giản hơn.

**9. Trong một deployment, pod-level `securityContext` đặt `runAsNonRoot: true`, nhưng container-level `securityContext` đặt `runAsUser: 0` và `privileged: true`; container cũng khai `readOnlyRootFilesystem: false`. Những phát biểu nào đúng? (Chọn tất cả đáp án đúng)**

**A)** Cấu hình container-level override pod-level, nên container thực tế chạy root và privileged — vi phạm hoàn toàn mục tiêu hardening.  
**B)** Pod sẽ bị kubelet từ chối vì container-level xung đột với pod-level.  
**C)** Khi audit pod, chỉ đọc pod-level `securityContext` là chưa đủ; phải kiểm tra cả container-level.  
**D)** `readOnlyRootFilesystem: false` ở container vô hiệu hóa `runAsNonRoot: true` ở pod.

**10. Về việc áp dụng sysctl trên node và cách nó tồn tại qua reboot, những phát biểu nào đúng? (Chọn tất cả đáp án đúng)**

**A)** `sysctl -w net.ipv4.tcp_syncookies=1` thay đổi giá trị ngay lập tức nhưng không tồn tại qua reboot, nên chỉ dùng để test.  
**B)** Giá trị trong `/etc/sysctl.d/99-hardening.conf` được nạp khi chạy `sysctl --system` và khi boot; thứ tự giữa các file có thể quan trọng khi nhiều file set cùng một key.  
**C)** File trong `/etc/sysctl.d/` phải theo định dạng YAML để `sysctl --system` parse được.  
**D)** Kubernetes tự đồng bộ mọi sysctl mức node xuống pod qua ConfigMap `kube-system/sysctl-config`, nên không cần chỉnh trên node.
