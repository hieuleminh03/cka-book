## Container là gì {#what-is-a-container}

Container không phải máy ảo thu nhỏ, cũng không phải một công nghệ đơn lẻ. Nó là một **process bình thường trên Linux**, được chạy trong một môi trường bị cô lập và giới hạn bởi ba tính năng của kernel:

- **Namespace** — process "nhìn thấy" một thế giới riêng: cây process riêng, interface mạng riêng, hostname riêng, filesystem riêng.
- **Cgroup** — process bị giới hạn và đo lường tài nguyên: CPU, memory, số process, I/O.
- **UnionFS / overlay filesystem** — process thấy một filesystem ghép từ nhiều layer chỉ đọc, cộng thêm một layer ghi được riêng cho nó.

Nói cách khác: container = process + namespace + cgroup + rootfs. Trên máy host, bạn hoàn toàn có thể nhìn thấy process này và phân biệt nó chỉ bằng... các namespace mà nó đang tham gia.

```bash
docker run -d --name demo-nginx -p 8080:80 nginx:1.27-alpine

# Process nginx trong container vẫn là process trên host, có PID thật
ps -ef | grep '[n]ginx: master'
docker top demo-nginx        # Docker hiển thị PID trên host của các process trong container
```

Điểm mấu chốt này giải thích rất nhiều hành vi về sau: container "chết" thực chất là process chính thoát, `docker stop` là gửi tín hiệu tới PID 1 trong namespace của container, và mọi rò rỉ tài nguyên của container đều là rò rỉ trên host.

### So sánh container và VM {#container-vs-vm}

| Tiêu chí | Virtual Machine | Container |
|---|---|---|
| Đơn vị ảo hóa | Phần cứng (hypervisor) | Process (kernel) |
| Kernel | Mỗi VM có kernel riêng | Chia sẻ kernel với host |
| OS guest | Cài đầy đủ hệ điều hành | Chỉ chứa app và thư viện cần thiết |
| Thời gian khởi động | Hàng chục giây đến vài phút | Mili giây đến vài giây |
| Kích thước | GB đến chục GB | MB đến vài trăm MB |
| Mức độ cô lập | Mạnh (ranh giới phần cứng ảo) | Yếu hơn (chung kernel) |
| Mật độ trên một máy | Vài chục VM | Hàng trăm container |
| Bảo mật | Ranh giới rõ ràng hơn, escape khó | Kernel là bề mặt tấn công chung, cần hardening |
| Use case | Nhiều hệ điều hành khác nhau, cô lập mạnh | Microservice, CI/CD, đóng gói app nhất quán |

Cả hai đều là công cụ đúng cho các bài toán khác nhau. VM cô lập mạnh hơn nhưng nặng; container nhẹ và nhanh nhưng đòi hỏi bạn hiểu rõ tầng bảo mật kernel. Trong Kubernetes, bạn thậm chí gặp cả hai mô hình cùng lúc: **runtime class** như gVisor hoặc Kata Containers chạy container trong sandbox nhẹ có kernel riêng, dung hòa giữa hai thái cực.

### Vì sao container nhẹ hơn VM {#why-containers-are-lightweight}

Container không cần boot, không chạy init system, không có kernel riêng. Toàn bộ "hệ điều hành" của container chỉ là một vài thư viện user-space trong image. Khi bạn chạy `docker run nginx`, Docker không cài Ubuntu — nó chỉ:

1. Giải nén image `nginx` xuống filesystem host.
2. Tạo namespace và cgroup mới.
3. Chạy process `nginx` bên trong namespace đó.

Vì không có lớp ảo hóa phần cứng, CPU và I/O gần như đạt hiệu năng native. Đổi lại, container và host dùng chung kernel, nên một lỗ hổng kernel khai thác được từ container có thể ảnh hưởng toàn bộ node — đây là lý do CKS dành hẳn một phần cho **Minimize Microservice Vulnerabilities** (securityContext, seccomp, AppArmor, drop capabilities).

## Namespace, cgroup và UnionFS {#namespaces-cgroups-and-unionfs}

Ba cơ chế dưới đây là toàn bộ nền tảng của container. Khi một container "lạ" — không thấy process, mất mạng, đầy đĩa — bạn sẽ lần về đúng một trong ba cơ chế này.

### Namespace: cô lập tầm nhìn {#linux-namespaces}

Namespace chia tách các tài nguyên toàn cục của kernel thành nhiều "góc nhìn" riêng. Process trong namespace này không thấy tài nguyên của namespace khác (trừ khi được cấu hình chia sẻ).

| Namespace | Cô lập cái gì | Hệ quả thực tế |
|---|---|---|
| `pid` | Cây process | PID 1 trong container là process chính; container không thấy process của host |
| `net` | Interface, route, port, iptables | Container có IP riêng, `localhost` riêng, port riêng |
| `mnt` | Mount point, filesystem | Container chỉ thấy rootfs của mình |
| `uts` | Hostname, domain name | Mỗi container có hostname riêng |
| `ipc` | Shared memory, semaphore, message queue | Hai container không dùng chung `/dev/shm` (trừ khi `--ipc=host`) |
| `user` | Ánh xạ UID/GID | Root trong container có thể được map thành user thường trên host (rootless) |
| `cgroup` | Cây cgroup | Container thấy cây cgroup của riêng mình, không thấy toàn bộ host |
| `time` | Đồng hồ hệ thống (boot time, monotonic) | Hữu ích cho checkpoint/restore (từ kernel 5.6) |

Vài hệ quả cần nhớ:

- `docker run --pid=host alpine ps aux` — container **thấy toàn bộ process của host** vì chia sẻ PID namespace. Tương tự với `--net=host`, `--ipc=host`.
- Container không thấy được process nào khi dùng `ps` bên trong là chuyện bình thường: chỉ có tiến trình của chính nó trong PID namespace.
- Trong Kubernetes, các container trong **cùng một pod** chia sẻ `net`, `ipc` và `uts` namespace (qua pause container) nhưng có `mnt` và `pid` riêng — đó là lý do chúng giao tiếp qua `localhost` và cùng hostname.

### Cgroup: giới hạn tài nguyên {#cgroups}

Cgroup (control group) giới hạn và đo tài nguyên. Nếu namespace là "không thấy", thì cgroup là "không được vượt quá". Kernel hiện đại dùng **cgroup v2** với các file điều khiển dạng hợp nhất.

| Tài nguyên | Docker flag | File cgroup v2 | Kubernetes |
|---|---|---|---|
| CPU | `--cpus=0.5` | `cpu.max` (`50000 100000` = 0.5 CPU) | `resources.requests.cpu`/`limits.cpu` |
| Memory | `--memory=128m` | `memory.max` | `resources.requests.memory`/`limits.memory` |
| Số process | `--pids-limit=100` | `pids.max` | `pids.max` qua `securityContext` |
| Block I/O | `--blkio-weight` | `io.weight` | Ít dùng trực tiếp |

```bash
# Chạy container giới hạn 0.5 CPU và 128 MiB memory
docker run -d --name limited --memory=128m --cpus=0.5 nginx:1.27-alpine

# Nhìn trực tiếp giới hạn từ bên trong container (cgroup v2)
docker exec limited cat /sys/fs/cgroup/memory.max     # 134217728
docker exec limited cat /sys/fs/cgroup/cpu.max        # 50000 100000

docker stats --no-stream limited
```

Vượt giới hạn memory thì **không có "cảnh báo nhẹ"**: kernel OOM killer giết process (thường là process chính) và container thoát với exit code 137 (128 + 9 = SIGKILL).

```bash
# Demo OOM có kiểm soát
docker run -d --name oom-demo --memory=64m \
  polinux/stress stress --vm 1 --vm-bytes 200M --vm-hang 0

sleep 5
docker ps -a --filter name=oom-demo        # Exited (137)
docker inspect oom-demo | grep -i oomkilled  # "OOMKilled": true
docker rm -f oom-demo
```

Trong Kubernetes, giới hạn này do bạn khai báo trong `resources.limits` và kubelet chuyển xuống runtime. Một chi tiết gây nhiều sự cố production: **CPU limit là giới hạn cứng theo chu kỳ**, ứng dụng single-thread bị throttle khi chạm trần dù node còn rảnh; trong khi memory vượt trần là bị giết ngay. Chương 4 sẽ đi sâu vào request/limit và QoS.

### UnionFS và copy-on-write {#unionfs-and-copy-on-write}

Một container nhìn thấy một filesystem "ghép" từ nhiều thư mục chỉ đọc xếp chồng lên nhau, cộng một layer ghi được ở trên cùng. Docker dùng **overlay2** làm storage driver mặc định trên Linux.

```text
        ┌────────────────────────────────────────────┐
        │  Container layer (writable, upperdir)      │  ← mọi thay đổi khi runtime
        ├────────────────────────────────────────────┤
        │  Image layer 3 (read-only, lowerdir)       │  ← RUN npm ci
        ├────────────────────────────────────────────┤
        │  Image layer 2 (read-only, lowerdir)       │  ← COPY package.json
        ├────────────────────────────────────────────┤
        │  Image layer 1 (read-only, lowerdir)       │  ← FROM node:22-alpine
        └────────────────────────────────────────────┘
                     merged → /  (container nhìn thấy)
```

Cơ chế quan trọng nhất là **copy-on-write**: khi process ghi vào một file thuộc layer chỉ đọc, kernel copy toàn bộ file đó lên layer ghi trước khi sửa. Hệ quả thực tế:

- Sửa một file 100 MB trong image layer làm container layer tăng thêm 100 MB (đúng bằng kích thước file), vì cả file bị copy lên.
- Xóa một file trong container **không** giải phóng dung lượng của image: kernel chỉ tạo "whiteout" ở layer trên để che file, dữ liệu gốc vẫn nằm trong layer dưới. Đây cũng là lý do `RUN rm -rf` một file lớn ở instruction khác không làm image nhỏ đi.

```bash
docker history nginx:1.27-alpine      # kích thước từng layer
docker diff demo-nginx                 # A/C/D: file added/changed/deleted so với image
docker system df                       # tổng dung lượng image, container, volume
```

### Tự tay tạo namespace với unshare và nsenter {#unshare-and-nsenter}

Cách nhanh nhất để "tin" vào namespace là tự tạo chúng mà không cần Docker. Trên Linux (máy thật, VM hoặc WSL2), dùng `unshare` để chạy process trong namespace mới và `nsenter` để nhảy vào namespace có sẵn.

```bash
# 1. UTS namespace: hostname riêng mà không ảnh hưởng host
sudo unshare --uts --fork bash
hostname demo-container
hostname                 # demo-container
exit
hostname                 # vẫn là hostname cũ
```

```bash
# 2. PID namespace: process đầu tiên trở thành PID 1
sudo unshare --pid --fork --mount-proc bash
echo $$                  # 1
ps aux                   # chỉ thấy vài process của chính namespace này
exit
```

```bash
# 3. Network namespace: chỉ có loopback
sudo unshare --net --fork bash
ip -br a                 # lo
ip link add dummy0 type dummy   # thoải mái vì không ảnh hưởng host
ip -br a
exit
```

`--mount-proc` trong ví dụ PID là bắt buộc trên thực tế: nếu không mount lại `/proc`, lệnh `ps` sẽ đọc `/proc` cũ của host và bạn vẫn thấy process host — một hiểu nhầm kinh điển.

Chiều ngược lại, `nsenter` cho phép từ host nhảy vào namespace của một process (chính là cách Docker/Kubernetes debug container):

```bash
docker run -d --name ns-demo -p 8080:80 nginx:1.27-alpine

# Tìm PID trên host của process trong container
docker top ns-demo
# hoặc: ps -ef | grep '[n]ginx: master'

# Nhảy vào network namespace của container đó
sudo nsenter --target <PID> --net -- ip -br a
sudo nsenter --target <PID> --net -- ss -tlnp
```

Lệnh này là kỹ năng sống còn khi image không có shell: bạn không cần `docker exec` cũng vẫn soi được mạng, mount và process của container từ host.

## Kiến trúc Docker và chuẩn OCI {#docker-architecture}

### Docker client và daemon {#docker-client-and-daemon}

`docker` mà bạn gõ trên terminal chỉ là **client**. Nó không tự chạy container; nó gọi **Docker daemon (`dockerd`)** qua REST API, mặc định qua Unix socket `/var/run/docker.sock`. Biến môi trường `DOCKER_HOST` cho phép trỏ client tới socket hoặc TCP endpoint khác.

Điều này giải thích hai tình huống rất hay gặp:

- Trong container CI, muốn build Docker thường phải mount `/var/run/docker.sock` vào (rách bảo mật — ai có socket là có quyền root trên host) hoặc dùng rootless/kaniko/BuildKit tách biệt.
- `docker context` cho phép một client quản lý nhiều daemon: máy local, VM trên cloud, cụm Docker Swarm. Với kind, `kubectl` và `docker` hoàn toàn không liên quan tới nhau — đây là gốc rễ của hiểu nhầm "tạo image bằng Docker rồi kind không thấy".

Từ Docker 20.10, việc build do **BuildKit** đảm nhiệm (không còn dùng builder cũ), mang lại build song song, cache mount, secret mount và output dạng OCI.

### containerd, runc và shim {#containerd-runc-and-shim}

`dockerd` không tự tạo container. Trách nhiệm được chia theo tầng:

| Thành phần | Vai trò |
|---|---|
| `docker` (CLI) | Gửi lệnh qua REST API tới daemon |
| `dockerd` | Quản lý API, volume, network, build; điều phối xuống containerd |
| `containerd` | Quản lý vòng đời container, image store, snapshot; push/pull registry |
| `containerd-shim-runc-v2` | Tiến trình đệm giữ container sống, thu thập exit code, giữ stdio |
| `runc` | Runtime OCI: tạo namespace, cgroup, mount rồi `exec` process — sau đó thoát |

`runc` chạy rất ngắn: nó thiết lập môi trường rồi nhường chỗ cho process thật. **Shim** mới là thứ sống suốt vòng đời container, cho phép `dockerd`/`containerd` restart mà container không chết theo.

```bash
# Xem các process này phân tầng trên host
ps -ef | grep -E 'dockerd|containerd|containerd-shim' | grep -v grep
```

### Chuẩn OCI {#oci-standards}

Open Container Initiative định nghĩa ba chuẩn mở, tách "container" khỏi bất kỳ nhà cung cấp nào:

| Chuẩn | Nội dung | Ví dụ sử dụng |
|---|---|---|
| Image spec | Định dạng image: manifest, config, layer tar | Docker, containerd, podman dùng chung image |
| Runtime spec | Cấu hình runtime: `config.json` mô tả process, mount, namespace | runc, crun, kata, gVisor |
| Distribution spec | API registry: push/pull, manifest, blob | Docker Hub, Harbor, ECR, GHCR |

Chính vì OCI, image bạn build bằng `docker build` chạy được trong Kubernetes với containerd mà không cần Docker. Và vì runtime spec được chuẩn hóa, bạn có thể đổi `runc` sang runtime sandbox mà không đổi image.

### Từ `docker run` tới process {#docker-run-flow}

```text
docker run nginx:1.27-alpine
   │
   ▼
docker CLI ──HTTP──▶ dockerd
   │                    │ 1. tìm image trong image store, thiếu thì pull từ registry
   │                    ▼
   │                containerd ──▶ snapshotter tạo rootfs từ các layer
   │                    │
   │                    ▼
   │                containerd-shim
   │                    │
   │                    ▼
   │                runc (tạo namespace + cgroup + mount, exec nginx)
   │                    │
   │                    ▼
   └──────────────  nginx chạy như process bình thường trên host (PID thật)
```

Hiểu sơ đồ này, bạn tự trả lời được các câu hỏi: tại sao `docker exec` không cần image có ssh; tại sao kubelet chỉ cần nói CRI với containerd mà không cần dockerd; tại sao container chết khi process chính thoát (runc chỉ chạy một process làm PID 1).

## Image và layer {#images-and-layers}

### Image thực chất là gì {#what-is-an-image}

Một image OCI gồm ba phần:

- **Manifest** — danh sách layer (tham chiếu theo digest `sha256:...`), config và media type.
- **Config** — metadata: entrypoint, cmd, env, user, port, lịch sử build.
- **Layer** — các file tar chứa thay đổi filesystem, xếp chồng theo thứ tự, layer sau ghi đè layer trước.

Điểm đáng nhớ: image **không chứa** filesystem hoàn chỉnh ở từng layer, mỗi layer chỉ chứa *phần chênh lệch* so với layer cha. Vì vậy các layer giống nhau giữa các image được chia sẻ trên host: `nginx:1.27-alpine` và `nginx:1.28-alpine` nếu dùng chung base `alpine:3.21` sẽ chia sẻ layer đó trong image store.

```bash
docker image inspect nginx:1.27-alpine      # manifest, config, Env, Cmd, RootFS
docker images --digests nginx               # digest bất biến của image
```

Image là **bất biến**: tag chỉ là con trỏ, có thể trỏ sang image khác bất cứ lúc nào; digest mới là định danh bất biến theo nội dung.

### Layer và copy-on-write {#layers-and-copy-on-write}

Mỗi instruction `RUN`, `COPY`, `ADD` trong Dockerfile tạo một layer. Số layer càng nhiều thì:

- Image càng phân mảnh, pull/storage kém hiệu quả hơn (dù BuildKit tối ưu một phần).
- Cache càng "nhạy" — đổi một instruction làm mất cache của mọi instruction phía sau.

Vì UnionFS chỉ đọc layer dưới, **không có cách nào xóa dữ liệu khỏi layer đã tạo**. Muốn image nhỏ, bạn phải tránh đưa dữ liệu vào ngay từ đầu, hoặc gộp việc tạo và dọn vào cùng một layer:

```dockerfile
# Sai: dữ liệu vẫn nằm trong layer của apt-get, chỉ bị che bởi whiteout
RUN apt-get update && apt-get install -y curl
RUN rm -rf /var/lib/apt/lists/*

# Đúng: cài và dọn trong cùng một RUN, một layer duy nhất
RUN apt-get update \
    && apt-get install -y --no-install-recommends curl \
    && rm -rf /var/lib/apt/lists/*
```

## Dockerfile {#dockerfile}

### Các instruction quan trọng {#dockerfile-instructions}

| Instruction | Mục đích | Ghi chú thực chiến |
|---|---|---|
| `FROM` | Chọn base image | Ghim version; `FROM ... AS build` cho multi-stage |
| `WORKDIR` | Đặt thư mục làm việc | Tạo thư mục nếu chưa có; dùng thay `cd` |
| `COPY` | Copy từ build context | Ưu tiên hơn `ADD`; hỗ trợ `--from=<stage>` |
| `ADD` | Như `COPY` + URL/tar tự giải nén | Hạn chế dùng để tránh hành vi "ẩn" |
| `RUN` | Chạy lệnh tạo layer | Gộp các lệnh liên quan bằng `&&`, dọn dẹp trong cùng lệnh |
| `ENV` | Biến môi trường | Tồn tại cả khi build lẫn runtime |
| `ARG` | Biến chỉ tồn tại khi build | Không có trong container chạy; không dùng cho secret |
| `EXPOSE` | Metadata port | Không tự mở port — chỉ có tính tài liệu |
| `USER` | User chạy process | Dùng ngay sau khi cài xong; tránh chạy root |
| `CMD` | Lệnh mặc định | Dễ bị override khi `docker run` truyền tham số |
| `ENTRYPOINT` | Lệnh cố định của image | Dùng exec form (JSON) để nhận tín hiệu đúng |
| `HEALTHCHECK` | Kiểm tra sức khỏe | Docker dùng; **Kubernetes bỏ qua** (dùng probe thay thế) |
| `VOLUME` | Khai báo mount point | Tạo anonymous volume; ít dùng trong image Kubernetes |
| `LABEL` | Metadata | Dùng bộ `org.opencontainers.image.*` |
| `STOPSIGNAL` | Tín hiệu khi stop | Mặc định SIGTERM; đổi khi app cần tín hiệu khác |
| `SHELL` | Shell cho form string | Dùng khi cần `bash -o pipefail` thay `/bin/sh -c` |

### RUN, CMD và ENTRYPOINT {#run-cmd-and-entrypoint}

Ba instruction này hay bị nhầm nhất:

- `RUN` chạy **lúc build**, kết quả (thay đổi filesystem) được lưu vào layer.
- `CMD` và `ENTRYPOINT` khai báo process **lúc runtime**, không tạo layer.
- `CMD` là **giá trị mặc định**, bị thay thế hoàn toàn khi `docker run` truyền đối số.
- `ENTRYPOINT` là **lệnh cố định**; `CMD` đóng vai trò tham số mặc định cho nó.

| Dockerfile | `docker run img` | `docker run img --port=9090` |
|---|---|---|
| `CMD ["--port=8080"]` | chạy `--port=8080` | chạy `--port=9090` (CMD bị thay) |
| `ENTRYPOINT ["app"]` + `CMD ["--port=8080"]` | `app --port=8080` | `app --port=9090` (CMD bị thay) |
| `ENTRYPOINT ["app", "--port=8080"]` | `app --port=8080` | `app --port=8080` (tham số bị bỏ qua) |

Hai dạng cú pháp khác nhau về ngữ nghĩa:

```dockerfile
ENTRYPOINT /app                # shell form: PID 1 là /bin/sh -c, không nhận tín hiệu trực tiếp
ENTRYPOINT ["/app"]            # exec form: PID 1 là chính /app — luôn dùng dạng này
```

Nếu process không phải PID 1 xử lý SIGTERM, `docker stop` sẽ chờ hết timeout rồi SIGKILL — dẫn tới thoát không êm, mất dữ liệu đang ghi. Với app không tự xử lý zombie, thêm `--init` khi run hoặc dùng `tini`.

### Layer caching {#layer-caching}

BuildKit cache từng instruction theo **parent layer + nội dung instruction**. Chỉ cần một instruction thay đổi, nó và **toàn bộ instruction phía sau** mất cache. Đây là lý do thứ tự instruction quan trọng:

```dockerfile
# Kém: sửa bất kỳ file nào trong context cũng làm COPY . . mất cache
#      => npm ci phải chạy lại mỗi lần build
FROM node:22-alpine
WORKDIR /app
COPY . .
RUN npm ci
CMD ["node", "server.js"]

# Tốt: dependency chỉ cài lại khi package.json/package-lock.json thay đổi
FROM node:22-alpine
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
CMD ["node", "server.js"]
```

Với những ngôn ngữ có cache nội bộ (Go build cache, pip, apt), BuildKit hỗ trợ cache mount để tái sử dụng giữa các lần build mà không nhét cache vào image:

```dockerfile
RUN --mount=type=cache,target=/root/.cache/go-build \
    --mount=type=cache,target=/go/pkg/mod \
    go build -o /out/app .
```

Vài lệnh kiểm soát cache:

```bash
docker build -t demo:1 .                       # build thường, dùng cache
docker build --no-cache -t demo:1 .            # bỏ toàn bộ cache
docker build --progress=plain -t demo:1 .      # xem từng bước, phát hiện cache hit/miss
```

### Multi-stage build {#multi-stage-build}

Multi-stage build giải quyết bài toán: **toolchain để build rất nặng nhưng không cần thiết khi chạy**. Bạn build ở stage đầu, rồi chỉ copy artifact sang stage cuối.

```dockerfile
# Stage 1: build — image này KHÔNG xuất hiện trong kết quả cuối
FROM golang:1.24-alpine AS build
WORKDIR /src
COPY go.mod ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" -o /out/app .

# Stage 2: runtime — distroless, không shell, không package manager
FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /out/app /app
USER nonroot:nonroot
EXPOSE 8080
ENTRYPOINT ["/app"]
```

Với Python, kỹ thuật tương tự: build wheel ở stage đầu, cài wheel ở stage sau để image cuối không chứa compiler:

```dockerfile
FROM python:3.13-slim AS build
WORKDIR /wheels
COPY requirements.txt .
RUN pip wheel --no-cache-dir --wheel-dir /wheels -r requirements.txt

FROM python:3.13-slim
WORKDIR /app
COPY --from=build /wheels /wheels
RUN pip install --no-cache-dir --no-index --find-links=/wheels /wheels/* \
    && rm -rf /wheels
COPY app.py .
USER 10001
CMD ["python", "app.py"]
```

`COPY --from=` cũng có thể lấy trực tiếp từ một image khác (ví dụ `COPY --from=nginx:1.27-alpine /usr/share/nginx/html /usr/share/nginx/html`) mà không cần stage build tương ứng.

### ARG và ENV {#args-and-envs}

```dockerfile
ARG GO_VERSION=1.24          # có thể override bằng --build-arg, không tồn tại khi chạy
FROM golang:${GO_VERSION}-alpine AS build
ARG GIT_SHA=unknown
RUN echo "build ${GIT_SHA}" > /build-info.txt

FROM alpine:3.21
ENV APP_ENV=production       # tồn tại trong container chạy
LABEL org.opencontainers.image.revision="${GIT_SHA}"
```

Hai lưu ý bảo mật quan trọng:

- **Không bao giờ truyền secret qua `ARG`/`ENV`** — chúng nằm vĩnh viễn trong lịch sử layer và `docker history`/`docker inspect` đọc được. Dùng BuildKit secret mount: `RUN --mount=type=secret,id=npmrc ...`.
- `ENV` cũng lộ trong `docker inspect` và trong môi trường process. Config nhạy cảm nên nạp từ Secret của Kubernetes, không bake vào image.

## Best practices cho image {#image-best-practices}

### Image nhỏ: alpine, distroless và scratch {#small-images}

| Base image | Kích thước điển hình | Có shell? | Ghi chú |
|---|---|---|---|
| `scratch` | 0 MB | Không | Chỉ chứa binary tĩnh; phải tự thêm CA cert, tzdata |
| `gcr.io/distroless/static-debian12` | ~2 MB | Không | Có CA cert, tzdata, passwd tối thiểu |
| `gcr.io/distroless/static-debian12:nonroot` | ~2 MB | Không | Chạy sẵn UID 65532 |
| `alpine:3.21` | ~8 MB | Có (`/bin/sh`) | Dùng musl libc; một số binary glibc cần lưu ý |
| `debian:bookworm-slim` | ~80 MB | Có | Thân thiện với binary glibc, apt |
| `python:3.13-slim` | ~120 MB | Có | Base phổ biến cho ứng dụng Python |
| `golang:1.24` | ~800 MB | Có | Chỉ nên dùng ở stage build |
| `node:22` | ~1.1 GB | Có | Dùng `node:22-slim` hoặc `-alpine` khi có thể |

Đổi base image có thể giảm image từ hàng trăm MB xuống vài MB, kéo theo giảm thời gian pull, giảm dung lượng node và **giảm số CVE** vì ít package hơn. Distroless còn có lợi thế bảo mật: không shell, không package manager, kẻ tấn công khó "sống" trong container sau khi khai thác.

Đánh đổi: distroless/scratch không có shell nên debug phức tạp hơn (mục sau), và alpine dùng musl có thể gây lỗi DNS hoặc crash với binary build cho glibc. Với ứng dụng Go/C/Rust build tĩnh, distroless gần như là lựa chọn mặc định.

### Chạy non-root {#non-root}

Mặc định container chạy UID 0 (root). Nếu kẻ tấn công thoát được khỏi container (kernel exploit, mount nhầm, CVE runtime), quyền root trong container thường trở thành quyền root trên node — nhất là khi không bật user namespace. Chạy non-root là biện pháp rẻ nhất và hiệu quả nhất:

```dockerfile
FROM alpine:3.21
RUN addgroup -S app && adduser -S -G app app
WORKDIR /app
COPY --chown=app:app . .
USER app
ENTRYPOINT ["/app/server"]
```

Hoặc thậm chí chỉ cần dùng UID số, không cần tạo user:

```dockerfile
USER 65532:65532
```

Khi run, có thể ép cứng bằng `--user` và thêm các lớp bảo vệ:

```bash
docker run -d \
  --user 65532:65532 \
  --read-only \
  --tmpfs /tmp \
  --cap-drop=ALL \
  --security-opt no-new-privileges \
  demo-app:1.0
```

`--read-only` khiến filesystem chỉ đọc (dùng `--tmpfs` cho thư mục cần ghi), `--cap-drop=ALL` bỏ toàn bộ Linux capability mặc định, `no-new-privileges` chặn leo thang đặc quyền. Trong Kubernetes, những giá trị này ánh xạ sang `securityContext` và Pod Security Admission — càng biết trước càng dễ đạt CKS.

### .dockerignore {#dockerignore}

Build context là toàn bộ thư mục gửi cho builder. Quên `.dockerignore` dẫn tới ba hệ quả: build chậm (gửi hàng trăm MB), cache bị vô hiệu hóa liên tục (file rác thay đổi), và rò rỉ dữ liệu (`COPY . .` mang cả `.env`, `.git`, key vào image).

```text
# .dockerignore
.git
.gitignore
.env
*.pem
node_modules
dist
bin
**/*_test.go
Dockerfile*
docker-compose*.yml
```

Lưu ý `COPY . .` vẫn copy các file mà `.dockerignore` không chặn — kể cả secret. Nguyên tắc vàng: **không bao giờ để secret trong build context**, kể cả khi đã ignore, vì một lần sửa `.dockerignore` sai là đủ để secret đi vào image.

### HEALTHCHECK và tín hiệu {#healthcheck-and-signals}

```dockerfile
HEALTHCHECK --interval=30s --timeout=3s --start-period=5s --retries=3 \
  CMD wget -qO- http://localhost:8080/healthz || exit 1
```

Với Docker thuần, `HEALTHCHECK` giúp `docker ps` hiển thị trạng thái `healthy`/`unhealthy` và có thể dùng để tự động restart (qua orchestration bên ngoài). Với Kubernetes, **HEALTHCHECK bị bỏ qua hoàn toàn** — bạn khai báo `livenessProbe`, `readinessProbe`, `startupProbe` trong manifest (chương 4). Vẫn nên giữ endpoint `/healthz` trong ứng dụng vì cả hai thế giới đều dùng chung endpoint đó.

Hai tinh chỉnh thường gặp khác:

- `STOPSIGNAL SIGINT` nếu ứng dụng đặc biệt cần SIGINT thay SIGTERM.
- Thêm `tini` hoặc `--init` khi ứng dụng sinh process con và không `wait()` chúng.

## Volume và network Docker {#volume-and-network}

### Volume, bind mount và tmpfs {#volumes-and-bind-mounts}

Container layer là tạm thời: xóa container là mất dữ liệu. Docker có ba cách đưa dữ liệu ra ngoài:

| Cơ chế | Khai báo | Vị trí trên host | Use case |
|---|---|---|---|
| Named volume | `-v appdata:/data` | `/var/lib/docker/volumes/appdata/_data` | Dữ liệu bền (DB), do Docker quản lý |
| Bind mount | `-v /host/path:/data` | Đúng đường dẫn chỉ định | Config, source code khi dev, log |
| tmpfs | `--tmpfs /data` | RAM, không ghi xuống đĩa | Dữ liệu tạm nhạy cảm, cache |

```bash
docker volume create appdata

docker run --rm -v appdata:/data alpine:3.21 sh -c 'echo hello-volumes > /data/hello.txt'
docker run --rm -v appdata:/data alpine:3.21 cat /data/hello.txt   # hello-volumes

docker volume ls
docker volume inspect appdata        # Mountpoint thật trên host
docker volume prune                  # dọn volume không còn dùng — cẩn thận mất dữ liệu
```

Bind mount thường dùng khi dev:

```bash
mkdir -p site
echo '<h1>hello bind mount</h1>' > site/index.html

docker run -d --name web -p 8082:80 \
  -v "$PWD/site:/usr/share/nginx/html:ro" \
  nginx:1.27-alpine

curl -s localhost:8082
```

Lưu ý: named volume có thể **che mất nội dung image** ở cùng đường dẫn. Chạy `nginx` với volume rỗng mount vào `/usr/share/nginx/html` sẽ khiến web server trả 403 vì thư mục trống — lỗi kinh điển của người mới dùng volume.

### Các network driver {#docker-network-drivers}

| Driver | Đặc điểm | Khi nào dùng |
|---|---|---|
| `bridge` (default) | Mạng riêng `docker0`, có NAT ra ngoài, **không có DNS tên container** | Chạy nhanh một container đơn lẻ |
| `bridge` (user-defined) | Do bạn tạo; **có DNS nội bộ** theo tên container/alias | Mọi trường hợp nhiều container giao tiếp |
| `host` | Bỏ network namespace, dùng thẳng mạng host | Hiệu năng cao, giới hạn port; không dùng trên K8s |
| `none` | Chỉ có loopback | Cô lập hoàn toàn, xử lý offline |
| `overlay` | Mạng nhiều host (Swarm) | Cụm Docker Swarm |
| `macvlan`/`ipvlan` | Cấp MAC/IP "thật" trong LAN | Thiết bị cần xuất hiện như máy trong LAN |

```bash
docker network ls
docker network create demo-net
docker run -d --name app1 --network demo-net nginx:1.27-alpine
docker network inspect demo-net      # xem container nào đang tham gia, IP nào
```

Với `-p 8080:80`, Docker dùng DNAT (iptables) để chuyển traffic từ `0.0.0.0:8080` của host vào IP container. Đây là lý do bạn không cần biết IP container, nhưng cũng là lý do source IP của client bị đổi (thành gateway của docker0) khi app đọc logs.

### DNS nội bộ giữa các container {#container-dns}

Trên default bridge, hai container **không** gọi nhau bằng tên được — chỉ có IP. Trên user-defined network, Docker chạy một DNS resolver tại `127.0.0.11` cho mỗi container, phân giải tên container và alias:

```bash
docker network create demo-net

docker run -d --name api --network demo-net demo-app:1.0
docker run --rm --network demo-net curlimages/curl:8.14.1 -s http://api:8080/

# Trên default bridge, tên không phân giải được
docker run --rm curlimages/curl:8.14.1 -s --max-time 3 http://api:8080/ ; echo "exit=$?"
```

Kỹ thuật này (`--network-alias`) chính là tổ tiên tinh thần của Service trong Kubernetes: client chỉ cần biết một tên ổn định, DNS trả về IP của các backend đang chạy. Chương 4 sẽ nối tiếp với DNS `service.namespace.svc.cluster.local` và CoreDNS.

## Registry và tagging {#registries}

### Cấu trúc tên image {#image-naming}

```text
[registry/][namespace/]repository[:tag][@digest]

docker.io/library/nginx:1.27-alpine
localhost:5000/demo-app:1.0.0
ghcr.io/acme/shop/api:2.3.1@sha256:8f2c...
```

- Không ghi registry ⇒ mặc định `docker.io`; không ghi namespace ⇒ namespace `library` cho official image.
- `tag` là nhãn người đọc; `digest` là hash nội dung image. Cùng một tag có thể trỏ tới nhiều digest khác nhau theo thời gian, digest thì bất biến.

### Tagging convention và immutable tag {#tagging-convention}

Một convention thực dụng cho pipeline:

| Loại tag | Ví dụ | Mục đích |
|---|---|---|
| Semver | `shop-api:1.4.2` | Release chính thức, con người đọc |
| Git SHA | `shop-api:sha-9f3c1ab` | Truy vết chính xác commit, mỗi build một tag |
| Môi trường | `shop-api:staging`, `shop-api:prod` | Trỏ tới bản đang deploy — **nên là alias, không phải nguồn sự thật** |
| Digest | `shop-api@sha256:8f2c...` | Pin bất biến cho production |

Quy tắc cho production:

- **Không dùng `latest`**: không biết đang chạy bản nào, rollback không xác định, `imagePullPolicy` mặc định có thể khiến node cũ giữ image cũ.
- Deploy theo **semver + digest**: tag để đọc, digest để đảm bảo artifact không đổi giữa các lần pull.
- Bật **immutable tag** trên registry (ECR, Harbor, Artifact Registry đều hỗ trợ): push đè tag đã tồn tại bị từ chối — chống tình trạng "tag cũ nội dung mới".

```bash
docker tag demo-app:latest localhost:5000/demo-app:1.0.0
docker push localhost:5000/demo-app:1.0.0

docker pull nginx:1.27-alpine
docker images --digests | grep nginx        # lấy digest
docker pull nginx@sha256:<digest>           # pin theo digest
```

### Private registry {#private-registry}

| Registry | Ghi chú |
|---|---|
| Docker Hub | Mặc định, có rate limit; phù hợp public image |
| Harbor | Mã nguồn mở, self-hosted; RBAC, replication, scan Trivy tích hợp, immutable tag |
| Amazon ECR | Managed; IAM; hỗ trợ scan và ký (KMS) |
| GHCR / Artifact Registry / ACR | Managed tương ứng GitHub / Google / Azure |
| `registry:2.8` | Registry tối giản để lab; không có auth, không scan |

```bash
# Registry local cho lab (Docker cho phép insecure với localhost)
docker run -d -p 5000:5000 --name registry registry:2.8.3

docker tag demo-app:1.0.0 localhost:5000/demo-app:1.0.0
docker push localhost:5000/demo-app:1.0.0
docker rmi localhost:5000/demo-app:1.0.0
docker pull localhost:5000/demo-app:1.0.0
curl -s http://localhost:5000/v2/_catalog
```

Trong Kubernetes, để pull từ private registry cần `imagePullSecrets` (một Secret chứa `dockerconfigjson`). Đây là cầu nối trực tiếp sang chương 4 và chương 8.

### Push, pull và rate limit {#push-pull-and-rate-limit}

Docker Hub giới hạn số lượt pull theo IP/tài khoản (anonymous thấp hơn nhiều so với tài khoản đăng nhập; con số cụ thể thay đổi theo chính sách từng thời điểm). Trong production, vấn đề này thường được xử lý bằng:

- Registry mirror/cache nội bộ (Harbor proxy-cache, registry mirror của cloud).
- Chuyển sang registry riêng cho image nội bộ.
- Ghim digest + `imagePullPolicy: IfNotPresent` để giảm pull thừa (nhưng vẫn phải pull khi image chưa có trên node).

## Debug container {#debugging-containers}

### docker logs {#docker-logs}

```bash
docker logs demo-nginx                 # toàn bộ stdout/stderr của PID 1
docker logs -f --tail=100 demo-nginx   # theo dõi realtime, 100 dòng cuối
docker logs --since=10m demo-nginx
docker logs -t demo-nginx              # kèm timestamp
```

Quy tắc bất di bất dịch: **log phải ghi ra stdout/stderr**, không ghi vào file trong container. Docker bắt stdout/stderr và lưu theo driver (mặc định `json-file`) — nền tảng cho việc thu thập log tập trung trong Kubernetes (chương 6).

### docker exec và docker inspect {#docker-exec-and-inspect}

```bash
docker exec -it demo-nginx sh                  # shell vào container (nếu image có shell)
docker exec -u 0 -it demo-nginx sh             # vào với quyền root khi image chạy non-root
docker exec demo-nginx env                     # xem biến môi trường
docker exec demo-nginx ss -tlnp                # port nào đang listen bên trong

docker inspect demo-nginx                      # toàn bộ JSON: State, Config, HostConfig, NetworkSettings
docker inspect demo-nginx | grep -i oomkilled
docker inspect --size demo-nginx               # thêm kích thước writable layer
```

`docker inspect` là nguồn sự thật khi container "không chạy như mong đợi": `State.ExitCode`, `State.Error`, `HostConfig.Memory`, `NetworkSettings.Ports`, `Config.Entrypoint`, `Config.User`. Trên Kubernetes, object tương đương là `kubectl get pod -o yaml` cùng events.

### docker diff, docker stats và docker top {#docker-diff-and-stats}

```bash
docker diff demo-nginx                # A/C/D — file thêm/sửa/xóa so với image
docker stats --no-stream              # CPU, memory, network, block I/O của mọi container
docker top demo-nginx                 # process bên trong container (PID trên host)
docker events --filter container=demo-nginx   # stream sự kiện start/stop/die/oom
docker system df                      # dung lượng image/container/volume đang chiếm
```

`docker diff` đặc biệt hữu ích để phát hiện container đang ghi log vào filesystem (dấu hiệu sắp đầy đĩa node) thay vì stdout.

### dive: soi từng layer {#dive}

`dive` là công cụ phân tích image theo layer, hiển thị nội dung và "điểm hiệu quả" của Dockerfile.

```bash
# Cài đặt (Linux/macOS): xem hướng dẫn tại github.com/wagoodman/dive
dive demo-app:naive          # xem từng layer, file nào chiếm bao nhiêu MB
dive --ci demo-app:naive     # chế độ CI: fail nếu vượt ngưỡng efficiency
```

Mục tiêu thực dụng: tìm ra layer nào phình to, file rác nào lọt vào image (`apt` cache, `.git`, node_modules không cần thiết), và kiểm chứng việc dọn dẹp đã đúng chưa.

### Debug container không có shell {#debug-without-shell}

Với image distroless/scratch, `docker exec ... sh` báo lỗi `executable file not found`. Các cách xử lý theo thứ tự ưu tiên:

1. **Log và inspect trước**: phần lớn sự cố (cấu hình sai, thiếu env, exit code) đọc được từ `docker logs` + `docker inspect` mà không cần shell.
2. **Debug variant của base image**: distroless có tag `:debug` (kèm busybox shell), alpine/debian chắc chắn có shell.
   ```bash
   docker run --rm -it --entrypoint busybox demo-app:debug-nonroot sh
   ```
3. **nsenter từ host**: `docker top` để lấy PID, rồi `nsenter --target <PID> --net|--mount ...`.
4. **Docker Desktop**: `docker debug <container>` mở toolbox tạm thời gắn vào container (tính năng của Docker Desktop trả phí).
5. **Trên Kubernetes**: dùng ephemeral container — `kubectl debug -it pod/<pod> --image=busybox:1.37 --target=<container>` (chương 5 sẽ thực hành).

## Bảo mật image {#image-security}

### Scan CVE với Trivy {#trivy}

Trivy là scanner mã nguồn mở phổ biến nhất cho container image: đọc layer, liệt kê package (OS + ngôn ngữ), so với database CVE.

```bash
# Quét các CVE mức HIGH/CRITICAL
trivy image --severity HIGH,CRITICAL demo-app:naive
trivy image --severity HIGH,CRITICAL demo-app:slim

# Chỉ hiện lỗi đã có bản vá
trivy image --ignore-unfixed nginx:1.27-alpine

# Gate trong CI: trả exit code 1 nếu tìm thấy lỗi mức chỉ định
trivy image --severity HIGH,CRITICAL --exit-code 1 demo-app:slim

# Quét cả cấu hình Dockerfile và secret lọt vào image
trivy config .
trivy fs --scanners secret .
trivy image --format spdx-json -o sbom.json demo-app:slim     # xuất SBOM
```

Vài nguyên tắc đọc kết quả:

- **Base image quyết định phần lớn CVE.** Cùng một ứng dụng, đổi từ `golang:1.24` sang `distroless` có thể giảm hàng trăm CVE chỉ vì ít package hơn.
- CVE của OS package có bản vá bằng cách **rebuild với base image mới**. Vì vậy pipeline nên rebuild định kỳ, không chỉ khi đổi code.
- `--ignore-unfixed` lọc các CVE chưa có bản vá để tập trung vào việc có thể xử lý được, nhưng không nên dùng để "làm đẹp" báo cáo.
- Nên chạy scan ở **ba chỗ**: khi build (chặn sớm), trước khi deploy (verify), và định kỳ trên cluster (phát hiện CVE mới công bố sau khi deploy).

### Giảm attack surface {#reduce-attack-surface}

Checklist theo thứ tự tác động:

- Dùng base image nhỏ nhất đủ dùng (distroless/scratch/alpine) — ít package đồng nghĩa ít CVE.
- Chạy non-root, `--read-only`, `--cap-drop=ALL`, `no-new-privileges`.
- Không chứa secret trong image (ARG/ENV/COPY đều sai).
- Ghim version và digest của base image; không dùng tag trôi nổi.
- Bật healthcheck/probe và resource limit để container "ốm" không kéo cả node xuống.
- Rebuild thường xuyên, đừng để image "nằm mộ" vài tháng rồi mới deploy lại.

### Ký image với cosign {#cosign}

Scan trả lời câu hỏi "image có lỗ hổng gì"; ký số trả lời câu hỏi "image này có đúng do pipeline của tôi tạo ra và chưa bị sửa không". `cosign` (thuộc dự án sigstore) ký image theo chuẩn OCI, chữ ký lưu trong registry cạnh image.

```bash
# Cách 1: cặp khóa đơn giản (lab)
cosign generate-key-pair
cosign sign --key cosign.key localhost:5000/demo-app:1.0.0
cosign verify --key cosign.pub localhost:5000/demo-app:1.0.0

# Cách 2: keyless — dùng OIDC identity của CI, không cần quản lý khóa
cosign sign --yes ghcr.io/acme/shop-api:1.4.2
cosign verify ghcr.io/acme/shop-api:1.4.2 \
  --certificate-identity-regexp 'https://github.com/acme/shop-api/.github/workflows/.*' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

Trên cluster, admission controller (Kyverno, Sigstore policy-controller) xác minh chữ ký trước khi cho phép Pod chạy — khép kín chuỗi **build → scan → sign → verify**. Đây là nội dung cốt lõi của chương 10 (Supply Chain Security); ở chương này bạn chỉ cần nắm vị trí của ký số trong bức tranh.

### Từ Docker tới Kubernetes {#from-docker-to-kubernetes}

Đến đây bạn đã có đủ mảnh ghép để thấy vì sao kiến thức Docker chuyển thẳng sang Kubernetes được:

- Kubernetes dùng **cùng chuẩn OCI**: image bạn build hôm nay chạy nguyên vẹn trong cluster.
- kubelet không nói chuyện với Docker; nó dùng **CRI** để gọi containerd (hoặc CRI-O). dockershim đã bị gỡ từ Kubernetes v1.24.
- Namespace/cgroup là cơ chế bên dưới của cả `docker run` và Pod. `resources.limits` chính là cgroup; `securityContext` chính là UID/capability/seccomp.
- Khác biệt lớn nhất: Docker quản lý container đơn lẻ; Kubernetes quản lý **Pod** — nhóm container chia sẻ network namespace, có vòng đời, probe, restart policy và scheduling do control plane điều khiển.

```bash
# Cùng một image, hai thế giới: Docker
docker run -d --name api -p 8080:8080 demo-app:1.0

# Kubernetes (chi tiết đầy đủ ở chương 4)
kubectl create deployment api --image=demo-app:1.0 --port=8080
kubectl expose deployment api --port=8080
```

### Bước 1: Tạo ứng dụng mẫu {#lab-step-1}

`main.go` — HTTP server tối giản, in ra `version`, `hostname` và `uid` để kiểm chứng container:

```go
package main

import (
	"fmt"
	"log"
	"net/http"
	"os"
	"time"
)

func main() {
	port := os.Getenv("PORT")
	if port == "" {
		port = "8080"
	}
	version := os.Getenv("APP_VERSION")
	if version == "" {
		version = "dev"
	}
	host, err := os.Hostname()
	if err != nil {
		host = "unknown"
	}

	http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintf(w, "service=demo version=%s host=%s uid=%d gid=%d\n",
			version, host, os.Getuid(), os.Getgid())
	})
	http.HandleFunc("/healthz", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, "ok")
	})

	log.Printf("starting version=%s uid=%d gid=%d port=%s", version, os.Getuid(), os.Getgid(), port)
	srv := &http.Server{Addr: ":" + port, ReadHeaderTimeout: 5 * time.Second}
	log.Fatal(srv.ListenAndServe())
}
```

### Bước 7: unshare và nsenter — tự tay làm "container" {#lab-step-7}

Phần này cần Linux/WSL2. Ta tự tạo namespace y như Docker làm:

```bash
# PID namespace: shell này trở thành PID 1
sudo unshare --pid --fork --mount-proc bash
ps aux          # chỉ vài process, không thấy process của host
echo $$         # 1
exit

# Network namespace: chỉ có loopback
sudo unshare --net --fork bash
ip -br a        # lo
exit

# UTS namespace: hostname riêng
sudo unshare --uts --fork bash
hostname lab-container && hostname
exit
```

Giờ dùng `nsenter` để nhảy vào namespace của container đang chạy:

```bash
docker run -d --name ns-demo -p 8083:80 nginx:1.27-alpine
docker top ns-demo                     # ghi lại PID của "nginx: master"

sudo nsenter --target <PID> --net -- ip -br a
sudo nsenter --target <PID> --net -- ss -tlnp
sudo nsenter --target <PID> --uts -- hostname
```

So sánh với thế giới bên ngoài: `ip -br a` trên host hoàn toàn khác, hostname hoàn toàn khác. Bạn vừa tự chứng minh "container chỉ là process + namespace".

## Câu hỏi phỏng vấn thường gặp {#interview-questions}

**1. Container khác VM ở điểm cốt lõi nào, và điều đó ảnh hưởng gì đến bảo mật?**

Container là process chạy trong namespace/cgroup của kernel host, không có kernel riêng; VM ảo hóa phần cứng và có kernel riêng. Hệ quả: container nhẹ, khởi động nhanh, mật độ cao, nhưng **mức cô lập yếu hơn**. Một lỗ hổng kernel khai thác từ container có thể ảnh hưởng cả node. Vì vậy cần chạy non-root, drop capability, seccomp/AppArmor, và khi yêu cầu cô lập cao thì dùng sandbox runtime (gVisor, Kata) hoặc phân tách workload bằng VM.

**2. Phân biệt namespace và cgroup. Kể tên các namespace chính và ứng dụng của chúng trong container.**

Namespace cô lập **tầm nhìn** (process thấy gì), cgroup giới hạn và đo **tài nguyên** (process được dùng bao nhiêu). Namespace chính: `pid` (cây process riêng), `net` (interface/route/port riêng), `mnt` (rootfs riêng), `uts` (hostname riêng), `ipc`, `user` (ánh xạ UID/GID cho rootless), `cgroup`, `time`. Container = process chạy trong tập namespace mới + cgroup riêng + rootfs overlay. Trong Kubernetes, các container cùng Pod chia sẻ `net`/`uts`/`ipc` nên giao tiếp qua `localhost`.

**3. Vì sao Kubernetes bỏ Docker (dockershim) và chuyển sang containerd?**

Kubernetes cần một runtime interface chuẩn là CRI. Docker không implement CRI; trước v1.24 kubelet dùng adapter `dockershim` để "dịch" CRI sang API của Docker, kéo theo cả daemon và nhiều lớp không cần thiết. containerd đã nằm sẵn bên dưới Docker, nói CRI trực tiếp, nhẹ hơn, ít lớp hơn, không ảnh hưởng gì tới image vì cùng chuẩn OCI. Việc bỏ dockershim **không** làm image Docker ngừng chạy trên Kubernetes.

**4. Layer là gì? Vì sao `RUN rm -rf` một file lớn ở layer sau không làm image nhỏ đi?**

Layer là tập thay đổi filesystem (diff) của một instruction, xếp chồng và chỉ đọc; container thêm một layer ghi được. Khi bạn xóa file ở layer trên, UnionFS chỉ tạo "whiteout" che file khỏi cái nhìn của container, còn dữ liệu gốc vẫn nằm trong layer dưới và vẫn bị tính vào kích thước image. Muốn giảm size phải gộp thao tác tạo và dọn vào **cùng một RUN**, hoặc tốt hơn là không đưa dữ liệu vào image ngay từ đầu (multi-stage).

**5. Phân biệt RUN, CMD và ENTRYPOINT.**

`RUN` chạy lúc build và kết quả được lưu vào layer. `CMD` và `ENTRYPOINT` khai báo process lúc runtime. `CMD` là giá trị mặc định, bị thay hoàn toàn khi `docker run` truyền đối số. `ENTRYPOINT` là lệnh cố định; `CMD` bổ sung tham số mặc định cho nó. Luôn dùng **exec form** (`["app"]`) cho ENTRYPOINT để process thật là PID 1 và nhận được tín hiệu SIGTERM, tránh tình trạng `docker stop` phải chờ hết timeout rồi kill cứng.

**6. Multi-stage build giải quyết vấn đề gì và kỹ thuật chính là gì?**

Nó tách "môi trường build" khỏi "môi trường chạy": stage đầu chứa toolchain nặng để compile, stage cuối chỉ nhận artifact qua `COPY --from=<stage>`. Nhờ đó image runtime nhỏ (từ hàng trăm MB xuống vài MB), giảm CVE và thời gian pull. Kèm theo cần copy artifact tĩnh (Go với `CGO_ENABLED=0`), hoặc cài CA cert/tzdata nếu chạy `scratch`.

**7. Khi nào chọn alpine, khi nào chọn distroless/scratch?**

Alpine khi cần shell và package manager để debug, chấp nhận musl. Distroless/scratch khi muốn image tối giản và bảo mật cao: không shell, không package manager, ít CVE; đổi lại debug phải dùng log/inspect, `nsenter`, debug image hoặc ephemeral container. Với binary tĩnh (Go, Rust, C) thì distroless/scratch là lựa chọn tốt nhất; với Python/Node cần thư viện động phức tạp thì `-slim` thường thực dụng hơn.

**8. Vì sao phải chạy container non-root, và làm thế nào?**

Chạy root trong container làm tăng nghiêm trọng hậu quả nếu bị escape hoặc mount nhầm: quyền root trong container thường tương đương quyền root trên node (trừ khi bật user namespace). Cách làm: tạo user trong Dockerfile và `USER`, dùng base `:nonroot` của distroless, ép bằng `--user` khi run; kèm `--read-only`, `--cap-drop=ALL`, `no-new-privileges`. Trong Kubernetes, khai báo `runAsNonRoot: true` và `allowPrivilegeEscalation: false` trong `securityContext` (chương 8).

**9. Debug một container không có shell như thế nào?**

Theo thứ tự: (1) `docker logs` và `docker inspect` (State, ExitCode, OOMKilled, Config); (2) chạy image variant có shell (`-debug`, alpine) hoặc override entrypoint nếu có busybox; (3) từ host dùng `docker top` lấy PID rồi `nsenter --target <PID> --net|--mount` để soi namespace; (4) trên Kubernetes dùng `kubectl debug` tạo ephemeral container. Nguyên tắc: không cần shell để đọc log và metadata — đó là nguồn thông tin giải quyết phần lớn sự cố.

**10. Vì sao không nên dùng tag `latest` trong production?**

`latest` là con trỏ có thể đổi nội dung bất cứ lúc nào, nên không biết chính xác node nào đang chạy phiên bản nào, rollback không xác định, và `imagePullPolicy` mặc định (`IfNotPresent` nếu không phải latest... nhưng với latest là `Always`) khiến hành vi pull khó đoán. Cách đúng: deploy theo **tag bất biến** (semver kèm git SHA) và/hoặc **pin theo digest**; bật immutable tag trên registry; ghi lại digest của artifact trong mỗi lần release.

**11. Hai container trên default bridge không gọi nhau bằng tên được. Vì sao, và cách xử lý đúng?**

Default bridge `docker0` không có DNS nội bộ, chỉ có IP — thêm nữa container mới không tự kết nối vào đó một cách thuận tiện. Tạo **user-defined bridge network** và gắn các container vào: Docker chạy embedded DNS tại `127.0.0.11`, phân giải tên container và network alias. Cách này cũng cho phép gắn/tháo container vào mạng mà không cần khởi động lại, và là tiền thân mô hình của Service + CoreDNS trong Kubernetes.

**12. Trivy và cosign khác nhau thế nào trong pipeline image?**

Trivy trả lời "image chứa lỗ hổng đã biết nào" (scan CVE theo package, có thể block CI bằng exit code). cosign trả lời "image này có đúng do pipeline của tôi tạo và chưa bị sửa không" (ký và xác minh chữ ký theo digest). Hai câu hỏi bổ trợ nhau: scan mà không ký thì kẻ tấn công có thể thay image khác sau khi scan; ký mà không scan thì bạn xác thực một image đầy CVE. Cả hai nên là bước bắt buộc trong pipeline và được enforce trên cluster bằng admission controller (chương 10).

## Các điểm chính {#key-points}

- Container = process + namespace + cgroup + rootfs overlay; không phải máy ảo thu nhỏ, không có kernel riêng.
- Namespace cô lập tầm nhìn (`pid`, `net`, `mnt`, `uts`, `ipc`, `user`, `cgroup`, `time`); cgroup giới hạn tài nguyên (`cpu.max`, `memory.max`, `pids.max`).
- Vượt memory limit ⇒ OOM kill (exit 137); CPU limit là giới hạn cứng theo chu kỳ và có thể gây throttle.
- UnionFS/overlay2 dùng copy-on-write; xóa file ở layer trên không giải phóng dung lượng của layer dưới — muốn nhỏ phải gộp RUN hoặc không đưa vào image.
- Kiến trúc Docker: client → dockerd → containerd → shim → runc → process; Kubernetes dùng CRI nói trực tiếp với containerd từ v1.24, và ba chuẩn OCI (image, runtime, distribution) đảm bảo image build bằng Docker chạy được trên mọi runtime.
- Tag `RUN`, `CMD`, `ENTRYPOINT` đúng vai: `RUN` tạo layer, `CMD` bị thay bởi đối số, `ENTRYPOINT` cố định; luôn dùng exec form.
- Layer caching phụ thuộc thứ tự instruction: copy file dependency trước, source code sau; BuildKit hỗ trợ cache mount và secret mount.
- Multi-stage build là công cụ giảm size lớn nhất: toolchain ở stage build, artifact sang stage runtime.
- Image nhỏ (distroless/scratch/alpine) giảm đồng thời kích thước, thời gian pull và số CVE; đổi lại debug khó hơn.
- Non-root + `--read-only` + `--cap-drop=ALL` + `no-new-privileges` là bộ bảo vệ tối thiểu; không truyền secret qua `ARG`/`ENV`/`COPY` mà dùng `--mount=type=secret` và Secret của Kubernetes.
- `.dockerignore` giảm build context, tăng cache hit và tránh rò rỉ dữ liệu vào image.
- Named volume do Docker quản lý, bind mount do bạn quản lý, tmpfs nằm trong RAM; user-defined network có DNS nội bộ theo tên container.
- `HEALTHCHECK` của Docker bị Kubernetes bỏ qua — cluster dùng liveness/readiness/startup probe.
- Production deploy theo tag bất biến hoặc digest, không dùng `latest`; ghim version base image và rebuild định kỳ.
- Trivy scan CVE, cosign ký/xác minh image; chuỗi build → scan → sign → verify → enforce bằng admission controller là nội dung chương 10.

## Câu hỏi thực hành {#practice-questions}

**1. Phát biểu nào đúng khi so sánh container và virtual machine? (Chọn tất cả đáp án đúng)**

**A)** Container chia sẻ kernel với host nên không cần cài hệ điều hành riêng cho từng ứng dụng, nhờ đó khởi động nhanh và nhẹ.
**B)** Mỗi VM có kernel riêng, cô lập mạnh hơn nhưng tốn tài nguyên hơn vì phải chạy cả một hệ điều hành.
**C)** Vì dùng chung kernel, container cung cấp mức cô lập bảo mật mạnh hơn hoặc tương đương VM.
**D)** Một image container build trên kiến trúc x86 luôn chạy được nguyên vẹn trên mọi kernel và kiến trúc CPU miễn là có Docker.

**2. Cho Dockerfile sau:**

```dockerfile
FROM node:22-alpine
WORKDIR /app
COPY . .
RUN npm ci
CMD ["node", "server.js"]
```

**Bạn chỉ sửa một dòng trong `server.js`. Điều gì xảy ra ở lần build tiếp theo, và cách viết lại nào tốt hơn?**

**A)** Chỉ layer chứa `server.js` bị rebuild; `npm ci` vẫn được cache vì dependency không đổi.
**B)** `COPY . .` mất cache nên `RUN npm ci` và mọi instruction sau đó chạy lại từ đầu; cách tốt hơn là copy `package.json`/`package-lock.json` rồi `npm ci` **trước** khi `COPY . .`.
**C)** Không layer nào mất cache vì `CMD` không tạo layer.
**D)** Docker tự động tách `server.js` khỏi `COPY` để giữ cache cho `npm ci`.

**3. Một image có `ENTRYPOINT ["/app"]` và `CMD ["--port=8080"]`. Lệnh `docker run demo-app --port=9090` sẽ chạy process nào?**

**A)** `/bin/sh -c "/app --port=8080"`
**B)** `/app --port=9090`
**C)** `/app --port=8080`
**D)** Lỗi vì `CMD` bị ghi đè nhưng `ENTRYPOINT` vẫn giữ nguyên.

**4. Một container distroless không có shell đang chạy nhưng bạn cần kiểm tra interface mạng và bảng route **bên trong network namespace** của nó. Cách nào đúng nhất thực hiện từ host?**

**A)** `docker attach <container>` rồi chạy `ip route` trong container.
**B)** `docker exec -it <container> ip route` — Docker tự cung cấp binary cho lệnh này.
**C)** Lấy PID trên host bằng `docker top <container>`, sau đó chạy `nsenter --target <PID> --net -- ip -br a`.
**D)** `docker logs <container>` — log chứa sẵn thông tin interface và route.

**5. Phát biểu nào đúng về multi-stage build và image runtime? (Chọn tất cả đáp án đúng)**

**A)** Stage build (chứa compiler, toolchain) không xuất hiện trong image cuối nếu bạn không copy gì từ nó vào stage runtime.
**B)** `COPY --from=build /out/app /app` là cách chuyển artifact từ stage này sang stage khác.
**C)** Khi dùng `FROM scratch`, nếu ứng dụng gọi HTTPS ra ngoài, bạn phải tự thêm certificate CA (và có thể cả tzdata) vì scratch không có gì.
**D)** Image cuối vẫn giữ toàn bộ layer của stage build để phục vụ debug khi cần, chỉ khác là chúng ở dạng nén.

**6. Cho Dockerfile sau:**

```dockerfile
FROM debian:bookworm
RUN apt-get update && apt-get install -y curl
RUN rm -rf /var/lib/apt/lists/*
```

**Dù đã xóa `/var/lib/apt/lists/*`, image vẫn lớn. Vì sao?**

**A)** `docker build` khóa các layer nên không thao tác nào có thể xóa file sau khi đã ghi.
**B)** `rm` chỉ tạo whiteout ở layer trên; dữ liệu vẫn nằm trong layer của `apt-get`, nên image không nhỏ đi — cần gộp cài đặt và dọn dẹp vào cùng một `RUN`.
**C)** `apt-get` ghi dữ liệu vào một Docker volume nằm ngoài image.
**D)** Build cache giữ một bản sao của các file đã xóa và bản sao đó nằm trong image.

**7. Trivy báo nhiều CVE HIGH/CRITICAL trên image build một stage từ `golang:1.24`. Hành động nào thực sự giảm rủi ro? (Chọn tất cả đáp án đúng)**

**A)** Chuyển sang multi-stage với base image distroless/alpine và rebuild định kỳ để nhận bản vá mới.
**B)** Ghim base image theo digest và có quy trình cập nhật base image có kiểm soát.
**C)** Dùng cosign ký image — chữ ký sẽ loại bỏ các package chứa CVE khỏi image.
**D)** Chặn trong CI bằng `trivy image --severity HIGH,CRITICAL --exit-code 1` để không cho image lọt qua pipeline.

**8. Để rollback xác định và tránh "tag trôi nổi", production nên tham chiếu image như thế nào?**

**A)** `myapp:latest` kèm `imagePullPolicy: Always` để luôn lấy bản mới nhất.
**B)** `myapp:stable` — một tag ổn định luôn trỏ tới bản tốt nhất hiện tại.
**C)** Tag bất biến kèm phiên bản (`myapp:1.4.2`, `myapp:sha-9f3c1ab`) và/hoặc pin theo digest (`myapp@sha256:...`) để đảm bảo đúng cùng một artifact.
**D)** Dùng `myapp:latest` và ghi lại hash của node đã pull image.

**9. Hai container trên default bridge `docker0` không thể gọi nhau bằng tên. Cách xử lý đúng theo thực hành hiện đại là gì?**

**A)** Thêm cờ `--link` giữa các container — đây là cách được khuyến nghị hiện nay.
**B)** Tạo user-defined bridge network và gắn cả hai container vào đó; Docker cung cấp DNS nội bộ (127.0.0.11) phân giải tên container và alias.
**C)** Chạy cả hai container với `--network host` để chúng thấy nhau qua localhost.
**D)** Default bridge có DNS nội bộ, chỉ cần khai báo `--hostname` trùng tên muốn gọi.

**10. Về mối quan hệ giữa Docker, containerd và Kubernetes, phát biểu nào đúng? (Chọn tất cả đáp án đúng)**

**A)** Từ Kubernetes v1.24, dockershim đã bị gỡ; kubelet nói chuyện với container runtime qua CRI (containerd hoặc CRI-O).
**B)** Image OCI build bằng Docker chạy được trên cluster dùng containerd vì cả hai tuân theo chuẩn OCI, không phụ thuộc Docker daemon.
**C)** Trong kind, `kind load docker-image` là cần thiết vì containerd trong node kind không tự thấy image của Docker daemon trên host; có thể kiểm chứng bằng `crictl images` bên trong node.
**D)** Kubernetes yêu cầu mọi image phải được build trực tiếp trên node bằng Docker daemon của node đó.
