## Kiến trúc cluster Kubernetes {#cluster-architecture}
Kubernetes là một hệ thống orchestration chạy theo mô hình **control loop**: bạn khai báo trạng thái mong muốn (desired state) trong manifest, các controller liên tục so sánh với trạng thái thực tế (observed state) và hành động để thu hẹp khoảng cách. Hiểu kiến trúc cluster chính là hiểu những thành phần nào tham gia vào vòng lặp đó.

Chương này bám sát bốn domain của kỳ thi CKA: **Cluster Architecture (25%)**, **Workloads & Scheduling (15%)**, **Services & Networking (20%)** và **Storage (10%)**. Domain Troubleshooting (30%) sẽ được đào sâu trong chương 5 — ở đây bạn học nền tảng và các kỹ năng vận hành cơ bản.

### Control plane {#control-plane}
Control plane là "bộ não" của cluster. Trên cluster dựng bằng kubeadm, các thành phần control plane chạy như **static pod** — đó là lý do chúng xuất hiện trong namespace `kube-system` và được kubelet khởi động trực tiếp từ manifest trong `/etc/kubernetes/manifests`.

- **kube-apiserver** — "cửa ngõ" duy nhất của cluster. Mọi client (kubectl, controller, kubelet) đều nói chuyện với API server. Nó xác thực (authentication), phân quyền (authorization), chạy admission control, validate object rồi ghi vào etcd. API server là thành phần **duy nhất** được phép đọc/ghi etcd.
- **etcd** — cơ sở dữ liệu key-value phân tán, lưu toàn bộ trạng thái cluster (object spec, trạng thái, secret, config...). etcd dùng thuật toán đồng thuận Raft nên cần đa số (quorum) để ghi: cụm 3 node chịu được 1 node chết, cụm 5 node chịu được 2. Chỉ API server nói chuyện với etcd (mặc định port 2379). Backup/restore etcd là kỹ năng sống còn khi vận hành — bạn sẽ làm kỹ trong chương 5.
- **kube-scheduler** — theo dõi các Pod chưa được gán node (`spec.nodeName` trống), lọc ra node đủ điều kiện (đủ resource, khớp nodeSelector/affinity, không bị taint) rồi chấm điểm và **bind** Pod vào node phù hợp nhất.
- **kube-controller-manager** — chạy hàng chục controller: Deployment controller tạo ReplicaSet, ReplicaSet controller tạo/xóa Pod, Node controller theo dõi sức khỏe node, Job controller đếm số lần chạy thành công, EndpointSlice controller cập nhật endpoint cho Service... Tất cả đều là các vòng lặp reconcile.
- **cloud-controller-manager** — tách logic đặc thù nhà cung cấp cloud khỏi core Kubernetes: cấp LoadBalancer, gán IP cho node, quản lý route. Trên kind/minikube không có thành phần này, nên Service type LoadBalancer sẽ không có external IP cho tới khi bạn cài một giải pháp như MetalLB.

```bash
# Xem các thành phần control plane trong cluster kubeadm (static pod)
kubectl get pods -n kube-system -o wide
```

### Node {#node-components}
Mỗi node là một máy (VM hoặc máy vật lý) chạy workload:

- **kubelet** — agent chạy trên mọi node. Nó đăng ký node với API server, watch các Pod được gán cho node mình, gọi container runtime để start/stop container, chạy probe, ghi trạng thái Pod trở lại API server và báo cáo tài nguyên qua heartbeat (Lease). kubelet không quản lý container không do Kubernetes tạo.
- **kube-proxy** — lập trình các rule mạng (iptables, IPVS hoặc nftables) trên mọi node để mọi Service IP hoạt động: traffic tới ClusterIP được chuyển tới một Pod trong EndpointSlice. Một số CNI hiện đại (Cilium) thay thế hoàn toàn kube-proxy.
- **container runtime** — hiện nay gần như luôn là **containerd** (dùng CRI interface, bên dưới gọi runc). Đây chính là "động cơ" đã học ở chương 3.
- **CNI plugin** — cấp IP và định tuyến traffic giữa các Pod. kind dùng kindnet mặc định; production thường dùng Calico, Cilium hoặc Flannel.

### Add-on {#cluster-addons}
Add-on là các thành phần mở rộng, thường chạy trong namespace `kube-system` dưới dạng Deployment hoặc DaemonSet:

- **CoreDNS** — DNS nội bộ cluster. Service `kube-dns` trong `kube-system` trỏ tới các Pod CoreDNS. Mọi Pod đều được cấu hình DNS để tự động resolve tên Service.
- **CNI plugin** — bắt buộc để Pod có IP.
- **metrics-server** — cung cấp số liệu CPU/memory cho `kubectl top` và HPA. kind không cài sẵn.
- **Ingress controller** — xử lý Ingress resource (ingress-nginx, Traefik, HAProxy...).
- **CSI driver** — cấp persistent storage.

### Luồng điều khiển khi tạo Pod {#pod-creation-control-flow}
Khi bạn chạy `kubectl apply -f deployment.yaml`, một chuỗi sự kiện diễn ra:

1. **kubectl** gửi request HTTP tới **kube-apiserver**. Request đi qua authentication, authorization (RBAC) và admission control; nếu hợp lệ, object Deployment được ghi vào **etcd**.
2. **Deployment controller** (trong kube-controller-manager) nhận thông báo qua watch, tạo một **ReplicaSet** với selector và pod template tương ứng.
3. **ReplicaSet controller** tạo các **Pod** với `spec.nodeName` còn trống. Pod được ghi vào etcd.
4. **kube-scheduler** phát hiện Pod chưa có node, thực hiện filter rồi score để chọn node, và cập nhật binding (`nodeName`) vào Pod.
5. **kubelet** trên node được chọn thấy Pod mới qua watch: nó gọi CNI để gán IP, gọi CRI (containerd) để pull image và start container, sau đó báo trạng thái `Running` về API server.
6. **EndpointSlice controller** thêm Pod vào endpoint của Service khớp selector (chỉ khi Pod **ready**), và **kube-proxy** cập nhật rule để traffic tới Service chảy tới Pod.

Nắm luồng này giúp bạn debug nhanh: Pod `Pending` thường do scheduler chưa bind được, container `CrashLoopBackOff` là lỗi ứng dụng/runtime phía kubelet, còn Service không có endpoint là do selector hoặc readiness.

## kubectl và context {#kubectl-and-context}
kubectl là client chính bạn dùng cả trong công việc lẫn phòng thi. Nguyên tắc vàng của kỳ thi performance-based: **đổi context đúng ngay từ đầu mỗi task**, và **sinh manifest bằng imperative command kèm `--dry-run=client -o yaml`** thay vì gõ YAML từ đầu.

### kubeconfig và context {#kubeconfig-and-context}
kubectl đọc cấu hình từ file **kubeconfig** (mặc định `~/.kube/config`, hoặc file chỉ định qua biến môi trường `KUBECONFIG`). File gồm bốn phần: `clusters` (địa chỉ API server + CA), `users` (credential), `contexts` (ghép cluster + user + namespace mặc định) và `current-context`.

```bash
# Xem toàn bộ context đang có
kubectl config get-contexts

# Chuyển sang context khác (thao tác đầu tiên của mọi task CKA)
kubectl config use-context kind-cka

# Xem nhanh context hiện tại kèm namespace mặc định
kubectl config view --minify

# Đổi namespace mặc định cho context hiện tại
kubectl config set-context --current --namespace=demo
```

Mẹo phòng thi: gõ `alias k=kubectl` và `export do="--dry-run=client -o yaml"` ngay khi bắt đầu để tiết kiệm thời gian.

### Namespace {#namespaces}
Namespace chia cluster thành các "phòng" logic: RBAC, quota, limit range và tên object đều theo namespace. Cluster có sẵn `default`, `kube-system`, `kube-public` và `kube-node-lease`.

```bash
kubectl create namespace demo          # tạo namespace
kubectl get pods -n demo               # thao tác trong namespace demo
kubectl get pods -A                    # xem mọi namespace
```

Hai lưu ý quan trọng:

- Namespace **không phải** ranh giới mạng: Pod ở namespace khác vẫn nói chuyện được với nhau trừ khi bạn dùng NetworkPolicy (chương 2 và chương 6).
- Không phải mọi object đều thuộc namespace. Node, PersistentVolume, StorageClass, ClusterRole là **cluster-scoped**. Kiểm tra bằng `kubectl api-resources --namespaced=false`.

### Imperative command và `--dry-run` {#imperative-commands-and-dry-run}
Trong kỳ thi, cách nhanh nhất để có manifest đúng cú pháp là để kubectl sinh ra nó:

```bash
# Sinh YAML của Pod rồi tự chỉnh sửa
kubectl run nginx --image=nginx:1.27 --dry-run=client -o yaml > pod.yaml

# Sinh YAML của Deployment
kubectl create deployment web --image=nginx:1.27 --replicas=3 $do > deploy.yaml

# Sinh YAML của Service NodePort từ Deployment có sẵn
kubectl expose deployment web --port=80 --target-port=80 --type=NodePort $do > svc.yaml

# Sinh Job và CronJob
kubectl create job batch-demo --image=busybox:1.36 $do -- sh -c 'echo done' > job.yaml
kubectl create cronjob hello --image=busybox:1.36 --schedule="*/5 * * * *" $do -- date > cronjob.yaml
```

Các thao tác imperative hay dùng khác:

```bash
kubectl set image deployment/web nginx=nginx:1.28   # đổi image, kích hoạt rollout
kubectl scale deployment/web --replicas=5           # scale
kubectl rollout status deployment/web               # theo dõi rollout
kubectl rollout undo deployment/web                 # rollback revision trước
kubectl rollout history deployment/web              # xem lịch sử revision
kubectl explain pod.spec.containers                 # tra cứu field ngay trên terminal
kubectl api-resources | grep -i ingress             # tìm API resource và group
```

### Label, selector và annotation {#labels-selectors-and-annotations}
**Label** là cặp key-value gắn vào object để nhận diện và nhóm. **Selector** là cách chọn object theo label — đây là cơ chế "dây thần kinh" nối Deployment với Pod, Service với Pod, NetworkPolicy với Pod.

```bash
# Gắn và sửa label
kubectl label pod nginx env=prod
kubectl label pod nginx env=staging --overwrite

# Selector dạng equality
kubectl get pods -l app=web
kubectl get pods -l 'app=web,tier!=frontend'

# Selector dạng set-based (In, NotIn, Exists)
kubectl get pods -l 'env in (prod,staging),app'
```

Trong manifest, Deployment dùng `matchLabels` và `matchExpressions`:

```yaml
selector:
  matchLabels:
    app: web
  matchExpressions:
    - key: tier
      operator: In
      values: ["frontend", "api"]
```

**Annotation** cũng là key-value nhưng dùng cho metadata **không** phục vụ việc chọn lọc: mô tả, link dashboard, cấu hình riêng của tool (ví dụ `nginx.ingress.kubernetes.io/rewrite-target`, `kubectl.kubernetes.io/restartedAt`). Annotation không dùng được trong selector, và ngược lại label không nên chứa dữ liệu lớn.

```bash
kubectl annotate pod nginx description="web server cho demo"
kubectl get pod nginx -o jsonpath='{.metadata.annotations}'
```

Một lưu ý sống còn: `.spec.selector` của Deployment/StatefulSet/DaemonSet là **immutable** sau khi tạo. Chọn sai label thì phải xóa và tạo lại object.

## Pod {#pods}
Pod là đơn vị triển khai nhỏ nhất của Kubernetes — một nhóm gồm một hoặc nhiều container chia sẻ network namespace (cùng IP, cùng port space), IPC và volume. Container trong cùng Pod liên lạc với nhau qua `localhost`.

Trên production bạn hiếm khi tạo bare Pod vì nó không tự phục hồi khi node chết. Pod thường được tạo gián tiếp qua Deployment, StatefulSet, DaemonSet, Job. Manifest tối thiểu của Pod chỉ cần `apiVersion: v1`, `kind: Pod`, tên và danh sách container.

### Vòng đời Pod {#pod-lifecycle}
`status.phase` của Pod chỉ có 5 giá trị: `Pending`, `Running`, `Succeeded`, `Failed`, `Unknown`. Nhưng trạng thái bạn thực sự quan tâm nằm ở container status:

```text
NAME    READY   STATUS             RESTARTS   AGE
web-0   0/1     CrashLoopBackOff   4          3m
web-1   0/1     ImagePullBackOff   0          2m
web-2   0/1     Init:0/1           0          30s
web-3   1/1     Running            0          1m
```

- `restartPolicy` quyết định container được restart thế nào: `Always` (mặc định), `OnFailure`, `Never`. Giá trị này áp dụng cho **mọi container trong Pod** — lý do Job phải đặt `Never` hoặc `OnFailure`.
- Khi container thoát, kubelet áp dụng exponential backoff (10s, 20s, 40s... tối đa 5 phút) trước khi restart — biểu hiện là `CrashLoopBackOff`.

### Multi-container, init container và sidecar {#multi-container-init-containers-and-sidecars}
Các mẫu phối hợp container trong Pod:

- **Init container** chạy **tuần tự, từng cái một**, phải thành công hết trước khi container chính start. Dùng để chờ dependency, migrate schema, tải dữ liệu ban đầu. Nếu init container fail, kubelet restart nó theo `restartPolicy` (với `Always`/`OnFailure`) hoặc đánh dấu Pod `Failed` (với `Never`).
- **Sidecar** — container phụ trợ chạy song song: log shipper, proxy, adapter. Kubernetes hỗ trợ **native sidecar** bằng init container có `restartPolicy: Always` (từ v1.29, beta bật mặc định), giúp sidecar khởi động trước app và bị dọn cùng lifecycle của Pod.
- **Ambassador / adapter / log shipper** là các pattern kinh điển khi container chính không nên tự làm mọi thứ.

```yaml
spec:
  initContainers:
    - name: init-db
      image: busybox:1.36
      # Chờ database sẵn sàng trước khi app khởi động
      command: ["sh", "-c", "until nslookup db-headless; do sleep 2; done"]
  containers:
    - name: app
      image: myapp:1.0
      # Native sidecar: khởi động cùng lúc và tự restart độc lập
    - name: log-agent
      image: busybox:1.36
      restartPolicy: Always
      command: ["sh", "-c", "tail -f /var/log/app.log"]
```

### Probe: liveness, readiness và startup {#probes}
Probe là cách kubelet kiểm tra sức khỏe container. Ba loại probe có mục đích hoàn toàn khác nhau:

| Probe | Khi fail | Dùng để |
|-------|----------|---------|
| `livenessProbe` | kubelet **restart container** (theo restartPolicy) | Phát hiện container bị treo/deadlock |
| `readinessProbe` | Pod bị **loại khỏi EndpointSlice** của Service (không restart) | Chỉ nhận traffic khi app sẵn sàng |
| `startupProbe` | kubelet **kill container** và thử lại | Bảo vệ app khởi động chậm khỏi bị liveness kill oan |

Cơ chế probe: `httpGet`, `tcpSocket`, `exec`, `grpc`. Giá trị mặc định: `periodSeconds: 10`, `timeoutSeconds: 1`, `failureThreshold: 3`, `successThreshold: 1`.

```yaml
containers:
  - name: app
    image: myapp:1.0
    ports:
      - containerPort: 8080
    startupProbe:              # cho app tối đa 30 * 10s = 300s để khởi động
      httpGet:
        path: /healthz
        port: 8080
      failureThreshold: 30
      periodSeconds: 10
    readinessProbe:            # gate traffic vào Service
      httpGet:
        path: /ready
        port: 8080
      periodSeconds: 5
    livenessProbe:             # restart nếu treo
      httpGet:
        path: /healthz
        port: 8080
      periodSeconds: 10
```

Khi `startupProbe` được cấu hình, liveness và readiness **không chạy** cho tới khi startup thành công. Đây là lý do app Java khởi động 2 phút trong khi `initialDelaySeconds` không đủ linh hoạt.

### Resource request, limit và QoS {#resource-requests-and-limits}
- `requests` — lượng tài nguyên **đảm bảo tối thiểu**, là cơ sở để scheduler chọn node.
- `limits` — trần tài nguyên. Vượt CPU limit → container bị throttle; vượt memory limit → container bị OOMKilled.
- QoS class được suy ra tự động, ảnh hưởng thứ tự bị evict khi node thiếu tài nguyên:

| QoS | Điều kiện | Ưu tiên khi node hết tài nguyên |
|-----|-----------|--------------------------------|
| `Guaranteed` | Mọi container có requests = limits (cả CPU và memory) | Bị evict cuối cùng |
| `Burstable` | Có requests nhưng không đủ điều kiện Guaranteed | Trung bình |
| `BestEffort` | Không container nào khai báo requests/limits | Bị evict đầu tiên |

```bash
kubectl get pod web-1 -o jsonpath='{.status.qosClass}'; echo
```

## Workload {#workloads}
Workload resource là các controller quản lý Pod thay bạn: đảm bảo đủ replica, cập nhật phiên bản, cấp identity và storage ổn định, hoặc chạy đến khi hoàn thành.

### Deployment và ReplicaSet {#deployments-and-replicasets}
Deployment quản lý ReplicaSet; ReplicaSet quản lý Pod. Mỗi khi pod template thay đổi, Deployment tạo ReplicaSet mới — đó là nền tảng của rolling update và rollback.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: nginx
          image: nginx:1.27
```

Vài điểm cần nhớ cho đề thi:

- `apiVersion: apps/v1`, `selector` bắt buộc và bất biến.
- `revisionHistoryLimit` mặc định 10; đặt 0 nghĩa là không giữ revision cũ (mất khả năng undo).
- `progressDeadlineSeconds` mặc định 600s; nếu rollout không tiến triển trong khoảng này, Deployment bị đánh dấu `ProgressDeadlineExceeded` (rollout vẫn tiếp tục chạy nền).

### Rolling update và rollback {#rolling-update-and-rollback}
Mặc định Deployment dùng chiến lược `RollingUpdate` với `maxSurge: 25%` và `maxUnavailable: 25%`:

- `maxSurge` — số Pod được tạo **vượt** số replica mong muốn trong lúc update.
- `maxUnavailable` — số Pod được phép **không sẵn sàng** trong lúc update.

Ví dụ cấu hình an toàn cho update không downtime: `maxSurge: 1`, `maxUnavailable: 0` (luôn đủ replica ready).

```bash
kubectl set image deployment/web nginx=nginx:1.28   # rollout
kubectl rollout status deployment/web               # chờ hoàn tất
kubectl rollout history deployment/web              # xem các revision
kubectl rollout undo deployment/web                 # quay về revision trước
kubectl rollout undo deployment/web --to-revision=2 # về revision cụ thể
kubectl rollout restart deployment/web              # restart toàn bộ Pod
```

`kubectl rollout restart` hoạt động bằng cách cập nhật annotation `kubectl.kubernetes.io/restartedAt` trong pod template, tạo ra revision mới. Chiến lược `Recreate` (kill toàn bộ Pod cũ rồi tạo Pod mới) chỉ dùng khi app không thể chạy hai phiên bản song song.

### StatefulSet {#statefulsets}
StatefulSet dành cho workload **stateful** cần identity ổn định: database, message broker, hệ thống quorum (etcd, ZooKeeper, Kafka).

- Pod có tên cố định theo ordinal: `db-0`, `db-1`, `db-2` — xóa đi tạo lại vẫn giữ nguyên tên và DNS.
- Cần một **headless Service** (`clusterIP: None`) làm "governing service" để cấp DNS `db-0.db-headless.<namespace>.svc.cluster.local`.
- Tạo Pod tuần tự `0 → N-1` và xóa theo thứ tự ngược lại (`podManagementPolicy: OrderedReady` mặc định; đặt `Parallel` nếu app không cần).
- `volumeClaimTemplates` tự sinh PVC riêng cho từng Pod; PVC **không** bị xóa khi Pod bị xóa — đây là chủ ý để dữ liệu không mất.
- Update mặc định cũng xoay vòng theo thứ tự ngược ordinal, hỗ trợ `partition` để canary từng nhóm Pod.

### DaemonSet {#daemonsets}
DaemonSet đảm bảo **một Pod trên mỗi node** (hoặc mỗi node đủ điều kiện). Khi thêm node mới, Pod tự động được tạo; khi node bị xóa, Pod theo node biến mất. Dùng cho log agent (Fluent Bit), node exporter (Prometheus), CNI, security agent.

DaemonSet tự thêm toleration cho một số taint hệ thống (`node.kubernetes.io/not-ready`, `unreachable`, `disk-pressure`...) để không bị đuổi khỏi node. Muốn chạy cả trên control plane node, bạn phải tự thêm toleration cho `node-role.kubernetes.io/control-plane`.

### Job và CronJob {#jobs-and-cronjobs}
**Job** chạy Pod đến khi hoàn thành thành công một số lần nhất định — dùng cho batch, migration, backup.

- `completions` — số lần chạy thành công cần đạt (mặc định 1).
- `parallelism` — số Pod chạy song song tối đa (mặc định 1).
- `backoffLimit` — số lần thử lại trước khi Job bị đánh dấu `Failed` (mặc định 6).
- `activeDeadlineSeconds` — giới hạn tổng thời gian chạy.
- `ttlSecondsAfterFinished` — tự động dọn Job và Pod sau khi xong.

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: batch-demo
spec:
  completions: 3
  parallelism: 2
  backoffLimit: 3
  template:
    spec:
      restartPolicy: Never        # Job bắt buộc Never hoặc OnFailure
      containers:
        - name: worker
          image: busybox:1.36
          command: ["sh", "-c", "echo dang xu ly"]
```

**CronJob** tạo Job theo lịch cron (theo timezone UTC mặc định, có thể đặt `timeZone`):

- `schedule` — cú pháp cron 5 trường, ví dụ `"*/5 * * * *"`.
- `concurrencyPolicy` — `Allow` (mặc định), `Forbid` (bỏ qua lần chạy mới nếu Job cũ chưa xong), `Replace`.
- `successfulJobsHistoryLimit` (3) / `failedJobsHistoryLimit` (1) — số Job giữ lại.

```bash
# Tạo Job thủ công từ một CronJob có sẵn — mẹo kiểm thử rất nhanh
kubectl create job --from=cronjob/hello hello-manual
```

### HorizontalPodAutoscaler (HPA) {#horizontalpodautoscaler}
HPA tự động thay đổi số replica của Deployment/StatefulSet/ReplicaSet dựa trên metric. HPA thuộc `autoscaling/v2` và **cần metrics-server** (hoặc adapter như Prometheus Adapter) để lấy số liệu.

```bash
kubectl autoscale deployment web --cpu-percent=70 --min=2 --max=10
```

Cấu hình chi tiết hơn cho phép scale theo memory hoặc custom metric, kèm `behavior` để kiểm soát tốc độ scale up/down (tránh flapping). Manifest dùng `apiVersion: autoscaling/v2` với `scaleTargetRef` trỏ tới Deployment và khối `metrics` khai báo chỉ số cùng ngưỡng (ví dụ CPU `averageUtilization: 70`).

### So sánh các workload resource {#workload-comparison}
| Resource | Dùng cho | Tên Pod | Storage | Hành vi chính |
|----------|----------|---------|---------|---------------|
| Pod | một instance, debug, static pod | ngẫu nhiên | không | không self-healing khi node chết |
| Deployment | app stateless, web/API | ngẫu nhiên (`web-7d9c...`) | không | rolling update, rollback, scale |
| StatefulSet | database, quorum app | ổn định (`db-0`, `db-1`) | `volumeClaimTemplates` | tạo/xóa theo ordinal, DNS ổn định |
| DaemonSet | agent chạy mọi node | sinh theo node | tùy chọn | tự thêm Pod khi có node mới |
| Job | batch chạy một lần | ngẫu nhiên | tùy chọn | chạy đến đủ `completions` |
| CronJob | tác vụ định kỳ | ngẫu nhiên | tùy chọn | tạo Job theo lịch cron |

## ConfigMap và Secret {#configmaps-and-secrets}
ConfigMap và Secret tách cấu hình khỏi image — nguyên tắc 12-factor. Cả hai là object thuộc namespace, dữ liệu là key-value, nhưng Secret có thêm type và được xử lý khác biệt về bảo mật (dù chỉ ở mức base64 nếu bạn không bật encryption at rest).

### Tạo ConfigMap và Secret {#creating-configmaps-and-secrets}
```bash
# ConfigMap từ literal và từ file
kubectl create configmap web-config --from-literal=APP_ENV=dev --from-literal=APP_COLOR=blue

# Secret generic từ literal
kubectl create secret generic db-secret --from-literal=DB_PASSWORD='S3cr3t123!'

# Secret dùng để pull image private registry
kubectl create secret docker-registry regcred \
  --docker-server=registry.example.com \
  --docker-username=ci --docker-password='token'

# Secret TLS cho Ingress
kubectl create secret tls web-tls --cert=tls.crt --key=tls.key

# Sinh manifest để chỉnh sửa
kubectl create secret generic db-secret --from-literal=DB_PASSWORD=x $do > secret.yaml
```

Trong manifest, Secret dùng `data` (giá trị base64) hoặc `stringData` (giá trị plain, Kubernetes tự encode khi ghi). Giá trị có thể kiểm tra bằng `kubectl get secret db-secret -o jsonpath='{.data.DB_PASSWORD}' | base64 -d`.

Các `type` Secret hay gặp: `Opaque` (mặc định), `kubernetes.io/tls`, `kubernetes.io/dockerconfigjson`, `kubernetes.io/service-account-token`, `bootstrap.kubernetes.io/token`.

### Dùng ConfigMap và Secret trong Pod {#using-configmaps-and-secrets}
Có hai cách chính. **Biến môi trường** — nạp một lần lúc container start, **không** tự cập nhật khi ConfigMap đổi:

```yaml
containers:
  - name: app
    image: myapp:1.0
    env:
      - name: APP_ENV
        valueFrom:
          configMapKeyRef:
            name: web-config
            key: APP_ENV
      - name: DB_PASSWORD
        valueFrom:
          secretKeyRef:
            name: db-secret
            key: DB_PASSWORD
    envFrom:                       # nạp toàn bộ key thành env var
      - configMapRef:
          name: web-config
      - secretRef:
          name: db-secret
```

**Volume mount** — mỗi key thành một file trong thư mục mount; kubelet **có** đồng bộ lại nội dung khi ConfigMap/Secret thay đổi (trễ tối đa khoảng một chu kỳ sync + cache, thường dưới 1 phút). Chú ý: ứng dụng phải tự đọc lại file; mount bằng `subPath` sẽ **không** được cập nhật.

```yaml
    volumeMounts:
      - name: config
        mountPath: /etc/app-config
        readOnly: true
volumes:
  - name: config
    configMap:
      name: web-config
```

Có thể dùng `items` để chỉ mount một số key và đổi tên file phía trong volume.

### Immutability và lưu ý bảo mật {#immutability-and-security-notes}
- Đặt `immutable: true` cho ConfigMap/Secret: object không thể sửa, chỉ xóa và tạo lại. Lợi ích: bảo vệ cấu hình đang chạy khỏi sửa nhầm và giảm tải cho API server (kubelet không phải watch nữa).
- Secret chỉ là base64 — **không phải mã hóa**. Mặc định chúng được lưu plaintext trong etcd. Muốn an toàn cần bật encryption at rest, giới hạn RBAC đọc secret và dùng external secret manager (Vault, SOPS) — nội dung CKS ở chương 9.

## Service {#services}
### Vì sao cần Service {#why-services-are-needed}
Pod có IP động: mỗi lần Pod bị thay mới, IP đổi. Service giải quyết bằng một **virtual IP ổn định** và DNS name cố định, đứng trước một nhóm Pod và load-balance L4 tới chúng. Service chọn Pod qua **selector** và liên tục cập nhật danh sách endpoint.

Một Service cơ bản cần `selector` (chọn Pod theo label), `ports` (với `port` là port của Service và `targetPort` là port container lắng nghe; nếu không ghi, `targetPort` mặc định bằng `port`). Endpoint chỉ chứa Pod **ready** — readinessProbe fail thì Pod bị loại khỏi traffic. Manifest đầy đủ nằm trong lab thực hành.

### Các loại Service {#service-types}
| Type | Cơ chế | Truy cập từ | Khi nào dùng |
|------|--------|-------------|--------------|
| `ClusterIP` (mặc định) | VIP ảo trong cluster, kube-proxy lập trình iptables/IPVS | Trong cluster | Service nội bộ, backend cho Ingress |
| `NodePort` | Mở cùng một port (mặc định 30000–32767) trên mọi node, forward vào ClusterIP | `<NodeIP>:<NodePort>` | Dev/test, bare metal, giải pháp tạm |
| `LoadBalancer` | NodePort + external load balancer do cloud provider cấp | Internet/ngoài cluster | Production trên cloud |
| `ExternalName` | DNS CNAME trỏ ra tên ngoài cluster | Trong cluster | Trỏ tới service bên ngoài (database managed...) |
| Headless (`clusterIP: None`) | Không VIP; DNS trả về IP từng Pod | Trong cluster | StatefulSet, service discovery tự quản |

Ghi chú cho đề thi:

- Dải NodePort đổi được ở tham số `--service-node-port-range` của **kube-apiserver**. Có thể chỉ định `nodePort: 31000` trong manifest.
- Trên kind/minikube, `LoadBalancer` không có ai cấp IP nên `EXTERNAL-IP` sẽ là `Pending` — cần `kubectl port-forward` hoặc MetalLB. Đề CKA có thể yêu cầu tạo LoadBalancer nhưng chấm trên trạng thái object, không chấm external IP.
- `sessionAffinity: ClientIP` giữ client dính một Pod; `externalTrafficPolicy: Local` giữ source IP nhưng drop traffic tới node không có endpoint.

```bash
# Tạo Service từ Deployment có sẵn
kubectl expose deployment web --port=80 --target-port=80 --type=ClusterIP
kubectl get svc
```

### Headless Service và EndpointSlice {#headless-services-and-endpointslices}
- Headless Service dùng `clusterIP: None`. DNS truy vấn tên Service trả về danh sách A record là IP của tất cả Pod ready — client tự chọn backend. Đây là cơ chế StatefulSet cần.
- Với StatefulSet, mỗi Pod còn có DNS riêng: `db-0.db-headless.demo.svc.cluster.local`.
- **EndpointSlice** (`discovery.k8s.io/v1`) là API thay thế Endpoints: chia endpoint thành nhiều slice để scale tốt hơn. Từ Kubernetes v1.33, API `Endpoints` chính thức bị deprecated — khi debug, hãy nhìn EndpointSlice.

```bash
kubectl get endpointslices -o wide
```

### DNS trong cluster {#cluster-dns}
CoreDNS là DNS server của cluster. FQDN chuẩn có dạng `<service>.<namespace>.svc.cluster.local`; StatefulSet + headless Service có thêm bản ghi riêng dạng `<pod-name>.<service>.<namespace>.svc.cluster.local`. Trường `search` trong `/etc/resolv.conf` giúp tên ngắn gọn (ví dụ `web-svc`) hoạt động trong cùng namespace. Kiểm tra bằng `kubectl exec -it web-1 -- nslookup web-svc.demo.svc.cluster.local`.

## Ingress {#ingress}
### Ingress, IngressClass và Ingress controller {#ingress-and-ingress-controller}
Service chỉ giải quyết L4 (TCP/UDP). **Ingress** giải quyết L7 (HTTP/HTTPS): định tuyến theo host và path, kết thúc TLS, dùng một điểm vào duy nhất cho nhiều service. Điều quan trọng nhất cần nhớ: **Ingress resource chỉ là khai báo — không có tác dụng nếu cluster không có Ingress controller**. Controller là một Deployment/DaemonSet thực sự lắng nghe và cấu hình reverse proxy (nginx, Traefik, HAProxy...).

Ở Kubernetes hiện hành:

- **Ingress** thuộc `networking.k8s.io/v1`.
- **IngressClass** khai báo controller nào phục vụ Ingress. Có thể đánh dấu default qua annotation `ingressclass.kubernetes.io/is-default-class: "true"`.
- Ingress có thể chọn class bằng `spec.ingressClassName` (khuyến nghị) hoặc annotation `kubernetes.io/ingress.class` (cũ).
- Một số hành vi (rewrite, rate limit, sticky session) cấu hình qua **annotation** đặc thù của controller — không phải đặc tả Ingress chuẩn. Đừng mang annotation của nginx sang controller Traefik.

Ghi chú thời sự cho người học năm 2026: dự án **ingress-nginx đã công bố retirement (tháng 3/2026)** và không còn release mới; nó vẫn hữu ích để ôn thi và học khái niệm, nhưng khi làm hệ thống mới bạn nên cân nhắc **Gateway API** hoặc các controller còn được duy trì. Đề CKA vẫn kiểm tra tư duy Ingress, nên hãy nắm chắc cả hai.

### Viết Ingress resource {#writing-an-ingress-resource}
```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-ingress
  namespace: demo
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - demo.local
      secretName: web-tls        # Secret type kubernetes.io/tls
  rules:
    - host: demo.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-svc
                port:
                  number: 80
```

- `pathType` gồm `Prefix` (khớp tiền tố theo từng path segment), `Exact`, `ImplementationSpecific` (phụ thuộc controller). Đây là lỗi cấu hình phổ biến — dùng `Prefix` khi không chắc.
- Request không khớp rule nào sẽ rơi vào `defaultBackend` nếu có, ngược lại controller trả 404.
- Mỗi rule host cần DNS trỏ về IP của Ingress controller (hoặc dùng `curl -H "Host: ..."` khi test local).

```bash
kubectl describe ingress web-ingress
kubectl get ingressclass
```

### Gateway API {#gateway-api}
Gateway API là bộ API kế thừa Ingress, thuộc `gateway.networking.k8s.io`, đã GA từ v1.0. Triết lý chính: **role-oriented** — tách vai trò hạ tầng (platform team quản lý Gateway) khỏi vai trò ứng dụng (app team quản lý Route), biểu đạt được nhiều tính năng hơn (header matching, traffic splitting, mirroring) mà không cần annotation.

Ba resource cốt lõi:

- **GatewayClass** — do nhà cung cấp controller định nghĩa (tương tự IngressClass).
- **Gateway** — instance load balancer thật, quản lý listener (port, protocol, TLS).
- **HTTPRoute / GRPCRoute / TCPRoute / TLSRoute** — luật định tuyến gắn vào Gateway.

```bash
kubectl get gatewayclass
kubectl get gateway -A
kubectl get httproute -A
```

Bạn chưa cần viết Gateway API thành thạo để đỗ CKA, nhưng phải biết nó tồn tại, giải quyết vấn đề gì và resource nào đóng vai trò gì — đây là câu hỏi phỏng vấn senior rất phổ biến khi hệ thống đã chuyển sang Gateway API.

## Storage {#storage}
### Volume và các loại volume phổ biến {#volumes}
Volume trong Kubernetes tồn tại cùng vòng đời Pod (trừ persistent volume). Các loại hay dùng:

| Volume | Đặc điểm | Mất dữ liệu khi |
|--------|----------|-----------------|
| `emptyDir` | Thư mục tạm trên node, chia sẻ giữa container trong Pod | Pod bị xóa/đổi node |
| `hostPath` | Mount path trực tiếp từ node | Node bị thay; rủi ro bảo mật cao |
| `configMap`, `secret` | File cấu hình | — |
| `persistentVolumeClaim` | Yêu cầu storage bền vững | Phụ thuộc reclaim policy |
| `nfs`, `csi` | Storage mạng/plugin hiện đại | Phụ thuộc backend |

`emptyDir` có biến thể `medium: Memory` (tmpfs) hữu ích cho cache hoặc volume cần bảo mật (không ghi xuống đĩa).

### PersistentVolume và PersistentVolumeClaim {#persistentvolumes-and-persistentvolumeclaims}
Mô hình tách **người cung cấp storage** và **người dùng storage**:

- **PersistentVolume (PV)** — tài nguyên storage thật, cluster-scoped. Có `capacity`, `accessModes`, `persistentVolumeReclaimPolicy`, `storageClassName`.
- **PersistentVolumeClaim (PVC)** — yêu cầu của ứng dụng (namespaced): "tôi cần 5Gi, ReadWriteOnce". Kubernetes bind PVC với PV phù hợp nhất.
- **StorageClass (SC)** — "profile" storage cho phép **dynamic provisioning**: khi PVC được tạo, provisioner trong SC tự cấp PV. Đây là cách làm chuẩn trên cloud.

Vòng đời một PV/PVC: `Available` → `Bound` → (khi PVC xóa) `Released` → `Failed`/xóa tùy reclaim policy.

```yaml
# PVC — thường chỉ cần thế này, không cần tạo PV thủ công nếu có SC
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data-pvc
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 1Gi
```

Pod tiêu thụ PVC bằng khối `volumes` với `persistentVolumeClaim.claimName: data-pvc` (xem manifest đầy đủ trong lab).

### StorageClass và dynamic provisioning {#storageclasses-and-dynamic-provisioning}
```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast
provisioner: ebs.csi.aws.com
parameters:
  type: gp3
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true
```

- `provisioner` — plugin CSI chịu trách nhiệm tạo volume thật.
- `volumeBindingMode`:
  - `Immediate` — tạo PV ngay khi PVC được tạo.
  - `WaitForFirstConsumer` — chờ tới khi có Pod dùng PVC mới tạo. Điều này cho phép scheduler đặt Pod đúng zone/ node trước khi volume được cấp. **kind dùng chế độ này**, nên PVC `Pending` khi chưa có Pod là bình thường, không phải lỗi.
- `allowVolumeExpansion: true` — cho phép tăng dung lượng PVC bằng cách sửa `resources.requests.storage` (chỉ tăng, không giảm). Một số provisioner cần restart Pod để filesystem thực sự resize.
- StorageClass mặc định có annotation `storageclass.kubernetes.io/is-default-class: "true"`. PVC không ghi `storageClassName` sẽ dùng class mặc định. Ghi `storageClassName: ""` để **tắt** dynamic provisioning (chỉ dùng PV tĩnh).

```bash
kubectl get pv
kubectl get pvc
kubectl describe pvc data-pvc
```

### Access mode, reclaim policy và volume mode {#access-modes-reclaim-policies-and-volume-modes}
| Access mode | Viết tắt | Ý nghĩa |
|-------------|----------|---------|
| `ReadWriteOnce` | RWO | Một **node** mount read-write (nhiều Pod trên cùng node vẫn dùng được) |
| `ReadOnlyMany` | ROX | Nhiều node mount read-only |
| `ReadWriteMany` | RWX | Nhiều node mount read-write (cần backend hỗ trợ: NFS, CephFS...) |
| `ReadWriteOncePod` | RWOP | Chỉ **một Pod duy nhất** mount read-write (ổn định từ v1.29) |

Reclaim policy quyết định số phận PV khi PVC bị xóa:

- `Delete` — xóa luôn volume thật (mặc định của PV do SC tạo động).
- `Retain` — giữ lại volume, PV chuyển sang `Released`; phải xử lý thủ công (thường dùng cho dữ liệu quan trọng).
- `Recycle` — đã bị loại bỏ từ lâu, đừng dùng.

`volumeMode` có hai giá trị: `Filesystem` (mặc định) và `Block` (đưa block device thô cho app như database tự quản lý filesystem).

Cẩn thận khi làm bài: access mode là năng lực **của backend storage**, không phải của PVC. RWO không có nghĩa "một Pod" — muốn vậy phải dùng RWOP. Và PVC đã Bound thì `volumeName`, `storageClassName`... phần lớn field là immutable; muốn đổi phải xóa PVC (và chấp nhận mất dữ liệu tùy reclaim policy).

## Debug nhanh với kubectl {#kubectl-debugging}
Chương 5 dành cho troubleshooting chuyên sâu; ở đây là bộ lệnh bạn phải phản xạ trong 10 giây đầu khi có sự cố.

| Triệu chứng | Lệnh chạy trước | Gợi ý |
|-------------|-----------------|-------|
| Pod `Pending` | `kubectl describe pod <pod>` xem Events | Thiếu CPU/memory, taint, affinity, PVC chưa Bound |
| `CrashLoopBackOff` | `kubectl logs <pod> --previous`, `kubectl describe pod` | App exit; xem exit code và log lần chạy trước |
| `ImagePullBackOff` | `kubectl describe pod` xem Events | Sai tag/registry, thiếu `imagePullSecret` |
| Service không có endpoint | `kubectl get endpointslices -o wide`, `kubectl describe svc` | Selector không khớp label Pod, hoặc Pod chưa ready |
| Ingress trả 404/503 | `kubectl get ingress`, `kubectl describe ingress`, kiểm tra controller | Sai IngressClass, chưa cài controller, backend Service sai port |
| Pod chạy nhưng không phản hồi | `kubectl exec -it <pod> -- sh`, `kubectl port-forward` | Kiểm tra app trong container, port có listen không |
| Không rõ cluster đang làm gì | `kubectl get events -A --sort-by=.metadata.creationTimestamp` | Dòng thời gian sự kiện của mọi object |

```bash
kubectl get events -n demo --sort-by=.metadata.creationTimestamp
kubectl describe pod -l app=web          # spec, status, events của Pod
kubectl logs -l app=web --previous       # log lần chạy trước khi crash
kubectl exec -it web-1 -- sh             # vào shell trong container
kubectl port-forward svc/web-svc 8080:80 # test không cần Service external
```

## Câu hỏi phỏng vấn thường gặp {#interview-questions}
**1. Điều gì xảy ra từ lúc bạn chạy `kubectl apply -f deployment.yaml` cho tới khi container chạy trên node?**

kubectl gửi request tới kube-apiserver; request qua authentication, authorization (RBAC) và admission control rồi object Deployment được ghi vào etcd. Deployment controller tạo ReplicaSet, ReplicaSet controller tạo các Pod chưa có node. kube-scheduler filter/score rồi bind Pod vào node. kubelet trên node đó watch thấy Pod, gọi CNI cấp IP, gọi containerd pull image và start container, báo trạng thái về API server. EndpointSlice controller thêm Pod ready vào endpoint của Service khớp selector, và kube-proxy cập nhật rule để traffic tới Service.

**2. Vì sao chỉ có kube-apiserver được nói chuyện trực tiếp với etcd?**

etcd là nguồn sự thật duy nhất (single source of truth) của cluster. Tập trung mọi truy cập qua API server đảm bảo mọi thay đổi đều đi qua authentication, authorization, admission và validation — tránh ghi trực tiếp phá vỡ tính nhất quán, đồng thời giảm số client phải quản lý chứng chỉ với etcd. Ngoài ra, giới hạn truy cập etcd chỉ từ control plane là yêu cầu bảo mật cơ bản (CIS Benchmark).

**3. Deployment, StatefulSet và DaemonSet khác nhau thế nào? Khi nào dùng cái nào?**

Deployment cho workload stateless: Pod thay thế lẫn nhau, tên ngẫu nhiên, rolling update và rollback. StatefulSet cho workload cần identity ổn định (tên theo ordinal, DNS riêng, PVC riêng qua `volumeClaimTemplates`) và thứ tự khởi động/dừng — dùng cho database, Kafka, etcd. DaemonSet đảm bảo một Pod trên mỗi node đủ điều kiện, dùng cho agent hạ tầng như log collector, node exporter, CNI.

**4. Liveness, readiness và startup probe khác nhau ra sao?**

Liveness fail → kubelet restart container (theo restartPolicy); dùng để phát hiện treo/deadlock. Readiness fail → Pod bị loại khỏi EndpointSlice, không nhận traffic nhưng không restart; dùng để gate traffic. Startup probe chạy trước, tắt liveness/readiness cho tới khi app khởi động xong; dùng cho app khởi động chậm (JVM, migration) để tránh liveness kill oan. Cả ba không thay thế nhau: thiếu readiness sẽ làm client nhận lỗi khi rollout vì traffic vào Pod chưa sẵn sàng.

**5. Vì sao phải khai báo resource requests/limits? QoS class ảnh hưởng gì?**

Requests là cơ sở scheduler đặt Pod đúng node và đảm bảo tài nguyên tối thiểu; limits ngăn một Pod "ăn" hết tài nguyên node. Không khai báo gì → QoS `BestEffort`, bị evict đầu tiên khi node áp lực. Requests bằng limits trên mọi container → `Guaranteed`, bị evict cuối. Còn lại là `Burstable`. Trên production, mọi workload nên có requests; limits memory đặc biệt quan trọng để cô lập lỗi rò rỉ.

**6. ClusterIP, NodePort, LoadBalancer khác nhau thế nào? Headless Service dùng khi nào?**

ClusterIP là VIP ảo chỉ truy cập được trong cluster — mặc định và là backend cho Ingress. NodePort mở một port cố định trên mọi node, dùng khi cần expose đơn giản hoặc không có cloud LB. LoadBalancer mở rộng NodePort và yêu cầu cloud-controller-manager (hoặc MetalLB) cấp external IP. Headless Service (`clusterIP: None`) không có VIP, DNS trả về toàn bộ IP Pod — dùng cho StatefulSet hoặc khi client cần tự chọn backend (ví dụ client-side load balancing).

**7. Ingress khác Service ở đâu? Vì sao bắt buộc phải có Ingress controller?**

Service làm load balancing L4 cho một tập Pod. Ingress làm routing L7: nhiều host/path về các Service khác nhau, kết thúc TLS, một IP công khai duy nhất. Ingress chỉ là khai báo cấu hình; không có controller (ingress-nginx, Traefik...) đọc và lập trình reverse proxy thì object Ingress nằm đó vô tác dụng, cột ADDRESS trống và request trả 404. IngressClass chỉ định controller nào phục vụ Ingress nào.

**8. Cập nhật ConfigMap: env var và volume mount khác nhau thế nào?**

Env var được resolve một lần khi container khởi động — sửa ConfigMap/Secret không làm thay đổi process đang chạy, cần `kubectl rollout restart` (hoặc xóa Pod) để nạp lại. Volume mount được kubelet đồng bộ định kỳ (thường dưới một phút), file trong container được cập nhật nhưng ứng dụng phải tự đọc lại; mount bằng `subPath` thì không được cập nhật. Với `immutable: true`, không thể sửa — phải xóa và tạo lại.

**9. Rolling update mặc định của Deployment diễn ra thế nào? Rollback hoạt động ra sao?**

Mặc định RollingUpdate với maxSurge 25% và maxUnavailable 25%: Deployment tạo ReplicaSet mới, tăng dần replica của RS mới và giảm RS cũ, đảm bảo tổng số Pod ready không xuống dưới ngưỡng. Mỗi lần pod template đổi tạo một revision; `kubectl rollout undo` tạo revision mới trỏ về template cũ (không "quay ngược thời gian"), có thể chọn `--to-revision`. `revisionHistoryLimit` quyết định số revision giữ lại (mặc định 10).

**10. PV, PVC và StorageClass quan hệ thế nào? Delete và Retain khác gì?**

PVC là yêu cầu storage của app (dung lượng, access mode), PV là tài nguyên storage thật, StorageClass định nghĩa "profile" và provisioner để tự động cấp PV khi PVC xuất hiện (dynamic provisioning). Không có SC thì admin phải tạo PV thủ công rồi PVC mới bind được. Khi PVC bị xóa: reclaim policy `Delete` xóa luôn volume thật (mặc định cho dynamic), `Retain` giữ volume lại ở trạng thái `Released` để xử lý thủ công — bắt buộc cho dữ liệu quan trọng.

## Các điểm chính {#key-points}
- Control plane gồm kube-apiserver (cửa ngõ duy nhất), etcd (nguồn sự thật, cần quorum), kube-scheduler (bind Pod vào node) và kube-controller-manager (các vòng lặp reconcile). Node gồm kubelet, kube-proxy, container runtime và CNI plugin.
- Luồng tạo Pod: kubectl → apiserver → etcd → Deployment/ReplicaSet controller → scheduler bind → kubelet gọi CRI/CNI để chạy container → EndpointSlice + kube-proxy cập nhật traffic.
- Luôn đổi context (`kubectl config use-context`) ngay khi bắt đầu task; đặt namespace mặc định bằng `kubectl config set-context --current --namespace=<ns>`.
- Sinh manifest nhanh bằng imperative command kèm `--dry-run=client -o yaml` với alias `export do="--dry-run=client -o yaml"`.
- Pod chia sẻ network namespace, IPC và volume giữa các container; init container chạy tuần tự tới thành công trước container chính; native sidecar là init container có `restartPolicy: Always`.
- Liveness probe restart container khi fail; readiness probe loại Pod khỏi endpoint khi fail (không restart); startup probe bảo vệ app khởi động chậm. Probe mặc định: period 10s, timeout 1s, failureThreshold 3.
- Deployment quản lý ReplicaSet; mặc định RollingUpdate với maxSurge/maxUnavailable 25%; `kubectl rollout undo` quay về revision trước, `--to-revision` chọn revision cụ thể; `rollout restart` tạo revision mới qua annotation.
- StatefulSet cấp identity ổn định (pod-0, pod-1), cần headless Service, và `volumeClaimTemplates` cấp PVC riêng không bị xóa cùng Pod. DaemonSet chạy một Pod mỗi node, tự mở rộng khi thêm node.
- Job chạy đến `completions` lần thành công, giới hạn song song bằng `parallelism` và retry bằng `backoffLimit`; CronJob tạo Job theo lịch với `concurrencyPolicy`, history limits. HPA cần metrics-server và dùng `autoscaling/v2`.
- ConfigMap/Secret dùng qua env (nạp một lần, không tự cập nhật) hoặc volume mount (kubelet đồng bộ lại, trừ `subPath`). `immutable: true` khóa object; Secret chỉ là base64, không phải mã hóa.
- Service cung cấp VIP ổn định: ClusterIP (nội bộ), NodePort (30000–32767), LoadBalancer (cần cloud controller/MetalLB), ExternalName (CNAME), Headless (`clusterIP: None`) cho StatefulSet. Endpoint chỉ gồm Pod ready; dùng EndpointSlice (`discovery.k8s.io/v1`) khi debug.
- Ingress là routing L7 cần Ingress controller; chọn controller qua `spec.ingressClassName` và IngressClass. Gateway API (GatewayClass/Gateway/HTTPRoute) là hướng kế thừa role-oriented; ingress-nginx đã retirement từ tháng 3/2026.
- PV là storage thật (cluster-scoped), PVC là yêu cầu (namespaced), StorageClass bật dynamic provisioning. `volumeBindingMode: WaitForFirstConsumer` giải thích vì sao PVC Pending khi chưa có Pod. Reclaim policy Delete xóa volume, Retain giữ lại.
- Bộ lệnh debug cốt lõi: `kubectl describe` (events), `kubectl logs --previous`, `kubectl exec`, `kubectl port-forward`, `kubectl get events --sort-by=.metadata.creationTimestamp`.

## Câu hỏi thực hành {#practice-questions}
**1. Bạn triển khai một Deployment và thấy Pod ở trạng thái `Pending` suốt 6 phút. `kubectl describe pod` hiển thị sự kiện `FailedScheduling: 0/3 nodes are available: 3 Insufficient cpu`.**

**Hành động nào hợp lý nhất tiếp theo?**

**A)** Chạy `kubectl logs` trên Pod `Pending` để xem log ứng dụng bị lỗi gì.
**B)** Chạy `kubectl exec -it` vào Pod để kiểm tra tiến trình bên trong.
**C)** So sánh tổng CPU requests của các Pod với `Allocatable` của node (`kubectl describe node`), rồi giảm requests hoặc thêm node/dọn workload.
**D)** Sửa Pod thành `restartPolicy: Never` rồi apply lại để scheduler thử lại.

**2. Những phát biểu nào sau đây đúng về rolling update và rollback của Deployment? (Chọn tất cả đáp án đúng.)**

**A)** Theo mặc định, Deployment dùng chiến lược `Recreate` để tránh hai phiên bản chạy cùng lúc.
**B)** Mặc định `maxSurge` và `maxUnavailable` đều là 25%, có thể chỉnh trong `spec.strategy.rollingUpdate`.
**C)** `kubectl rollout undo deployment/web` không kèm `--to-revision` sẽ quay về revision liền trước.
**D)** `kubectl rollout restart deployment/web` tạo revision mới bằng cách cập nhật annotation `restartedAt` trong pod template.

**3. Những phát biểu nào sau đây đúng về các loại Service? (Chọn tất cả đáp án đúng.)**

**A)** ClusterIP (mặc định) chỉ có thể truy cập từ bên trong cluster.
**B)** NodePort tự động tạo load balancer của cloud provider và cấp external IP.
**C)** LoadBalancer mở rộng NodePort và cần cloud-controller-manager hoặc một giải pháp như MetalLB để cấp external IP.
**D)** Headless Service có `clusterIP: None`, DNS trả về IP của từng Pod và thường được StatefulSet sử dụng.

**4. Deployment `api` nhận cấu hình qua `envFrom: configMapRef`. Bạn cập nhật ConfigMap nhưng các Pod đang chạy vẫn dùng giá trị cũ. Kết luận nào đúng?**

**A)** Cần chờ tối đa 60 giây; kubelet sẽ tự đồng bộ env var giống như volume mount.
**B)** Phải xóa ConfigMap rồi tạo lại với cùng tên để kubelet phát hiện thay đổi.
**C)** Env var chỉ được nạp một lần khi container start, nên cần `kubectl rollout restart deployment/api` để Pod nhận giá trị mới.
**D)** ConfigMap không hỗ trợ env var; phải chuyển toàn bộ sang Secret.

**5. PVC `data-pvc` khai báo `storageClassName: fast-ssd` nhưng mãi ở trạng thái `Pending`. Cách nào xác định nguyên nhân nhanh và đúng nhất?**

**A)** Chạy `kubectl get pv`; nếu không có PV nào thì chắc chắn PVC không thể bind.
**B)** Chạy `kubectl describe pvc data-pvc` để đọc Events và `kubectl get storageclass` để kiểm tra class tồn tại, provisioner sẵn sàng, cùng `volumeBindingMode`.
**C)** Chạy `kubectl top nodes` để kiểm tra dung lượng đĩa còn trống của các node.
**D)** Đổi `accessModes` sang `ReadWriteMany` vì kind chỉ hỗ trợ RWX.

**6. Những phát biểu nào sau đây đúng về StatefulSet? (Chọn tất cả đáp án đúng.)**

**A)** Với `podManagementPolicy: OrderedReady` (mặc định), Pod được tạo tuần tự theo ordinal `0..N-1` và xóa theo thứ tự ngược lại.
**B)** Pod có network identity ổn định nhờ headless Service, và PVC sinh từ `volumeClaimTemplates` không bị xóa khi Pod bị xóa.
**C)** StatefulSet xóa Pod theo thứ tự ngẫu nhiên để giảm downtime.
**D)** Có thể chạy `kubectl scale statefulset db --replicas=5` để tăng số replica.

**7. Sau khi apply Ingress `web-ingress` (backend là Service ClusterIP), cột `ADDRESS` trống và `curl -H "Host: demo.local" http://localhost/` trả về 404. Hành động nào đúng nhất tiếp theo?**

**A)** Sửa Service backend từ ClusterIP sang LoadBalancer để Ingress tìm thấy.
**B)** Thêm annotation `rewrite-target` cho Ingress.
**C)** Kiểm tra NetworkPolicy trong namespace có đang chặn port 80 không.
**D)** Kiểm tra IngressClass và Ingress controller: `kubectl get ingressclass`, `kubectl get pods -n ingress-nginx`, `kubectl describe ingress web-ingress`.

**8. Pod có 1 init container, startupProbe, livenessProbe và readinessProbe. Những phát biểu nào đúng? (Chọn tất cả đáp án đúng.)**

**A)** Init container chạy tuần tự và phải thành công trước khi container chính start; nếu fail, kubelet xử lý theo `restartPolicy` của Pod.
**B)** Khi startupProbe được cấu hình, liveness và readiness không chạy cho tới khi startupProbe thành công.
**C)** readinessProbe fail khiến Pod bị loại khỏi EndpointSlice của Service nhưng container không bị restart.
**D)** livenessProbe fail khiến Pod bị xóa và scheduler tạo Pod mới trên node khác.

**9. Một Job có `completions: 6`, `parallelism: 2`, `backoffLimit: 3`. Những phát biểu nào đúng? (Chọn tất cả đáp án đúng.)**

**A)** Tối đa 2 Pod chạy đồng thời và Job hoàn thành khi đạt 6 lần chạy thành công.
**B)** `backoffLimit` chỉ áp dụng cho CronJob, không áp dụng cho Job.
**C)** `backoffLimit: 3` giới hạn số lần retry trước khi Job bị đánh dấu `Failed` (giá trị mặc định là 6).
**D)** `ttlSecondsAfterFinished` giúp tự động dọn Job và các Pod sau khi hoàn thành.

**10. Sau khi chạy `kubectl set image deployment/web nginx=nginx:1.99.0`, `kubectl rollout status` báo chờ mãi không xong; `kubectl get pods` cho thấy Pod mới ở trạng thái `ImagePullBackOff` trong khi các Pod cũ vẫn chạy. Hành động nào đúng nhất?**

**A)** Xóa Deployment rồi apply lại manifest cũ để cluster sạch sẽ.
**B)** Chạy `kubectl rollout undo deployment/web` để quay về revision tốt gần nhất, sau đó sửa tag image và triển khai lại.
**C)** Restart kubelet trên node chứa Pod lỗi vì node đang có vấn đề.
**D)** Tăng `progressDeadlineSeconds` để rollout không bị đánh dấu timeout.
