## GitOps là gì? {#gitops-la-gi}

Nếu chương 12 nói về con đường đưa code từ laptop tới cluster, thì chương này trả lời câu hỏi tiếp theo: **ai thực sự thi hành thay đổi trong cluster**. GitOps là cách vận hành trong đó Git (hoặc một Git server nội bộ) là **nguồn chân lý duy nhất** cho trạng thái mong muốn của hệ thống, và một agent chạy trong cluster liên tục đối soát, kéo trạng thái thực tế về đúng như trong Git.

Điểm cốt lõi không nằm ở chữ "Git" — nhiều đội vẫn commit manifest rồi để CI chạy `kubectl apply` (đó là push, chưa phải GitOps). Điểm cốt lõi là **vòng lặp đối soát liên tục** và **chiều di chuyển của thay đổi**: agent trong cluster chủ động *pull* thay vì bên ngoài *push* vào.

Khảo sát JD trong phần mở đầu cho thấy GitOps/ArgoCD xuất hiện trong khoảng 30% tin tuyển DevOps, và tỉ lệ này cao hơn hẳn ở các product company chạy Kubernetes — vì vậy đây là phần bạn nên nắm chắc cả lý thuyết lẫn thực hành.

### Bốn nguyên lý của GitOps {#bon-nguyen-ly-cua-gitops}

Chuẩn OpenGitOps định nghĩa bốn nguyên lý, có thể nhớ gọn là **D-V-P-C**:

| Nguyên lý | Nội dung | Trên Kubernetes nghĩa là gì |
|---|---|---|
| Declarative | Trạng thái mong muốn được mô tả khai báo, không phải một chuỗi lệnh | Manifest YAML (Deployment, Service, Helm chart, Kustomize overlay) |
| Versioned and immutable | Trạng thái được lưu có version, có lịch sử đầy đủ và bất biến | Một commit/hash Git; không sửa lại lịch sử, thay đổi bằng commit mới |
| Pulled automatically | Agent tự động kéo khai báo từ nguồn về | ArgoCD/Flux trong cluster clone repo theo chu kỳ, CI không cần quyền ghi cluster |
| Continuously reconciled | Agent liên tục quan sát trạng thái thực và cố đưa về trạng thái mong muốn | Vòng lặp so sánh desired vs live, tự sửa drift (self-heal) |

Bỏ nguyên lý thứ ba hoặc thứ tư, bạn sẽ có "config as code" hoặc "deploy bằng Git" — nhưng không phải GitOps. Đây là câu hỏi phỏng vấn rất hay gặp để phân biệt người đã vận hành thật và người chỉ đọc blog.

### Push model và pull model {#push-model-va-pull-model}

| Tiêu chí | Push model | Pull model |
|---|---|---|
| Ai khởi động thay đổi | CI/CD pipeline (`kubectl apply`, `helm upgrade`) | Agent trong cluster (ArgoCD, Flux) |
| Credential của cluster nằm ở đâu | Trong CI (thường là quyền lớn, sống lâu) | Trong cluster, agent chỉ cần quyền đọc Git |
| Phát hiện drift | Không có, trừ khi có tool riêng | Có sẵn, liên tục |
| Khi CI down | Không deploy được, nhưng cluster vẫn ổn định | Cluster vẫn tự đối soát; CI không nằm trên đường chạy |
| Audit | Log pipeline | Lịch sử Git + lịch sử sync của agent |
| Rủi ro chính | Lộ credential CI = chiếm cluster; deploy "lén" ngoài Git | Agent bị chiếm; repo là single point of truth |
| Ví dụ | GitHub Actions + `kubectl`, Jenkins, GitLab CI | ArgoCD, Flux |

Pull model an toàn hơn vì **cluster không mở đường vào từ ngoài**: CI chỉ cần push code, không giữ kubeconfig của production. Ngược lại, push model cho phép làm mọi thứ CI có thể làm (chạy script, migrate, gọi API) — hữu ích cho các bước không khai báo được, nhưng cũng là lý do credential trong CI trở thành mục tiêu tấn công số một.

Trên thực tế nhiều đội dùng **hybrid**: CI build image và mở PR cập nhật tag/digest, agent pull phần deploy; CI chỉ giữ quyền ghi vào Git. Miễn là việc sync vẫn do agent trong cluster làm, bạn vẫn đang làm GitOps.

### Lợi ích và trade-off {#loi-ich-va-trade-off}

Lợi ích rõ nhất mà tôi thấy sau vài năm vận hành:

- **Một nguồn chân lý**: trạng thái cluster luôn suy ra được từ một commit. Ai đó hỏi "production đang chạy version nào, ai đổi, lúc nào" — trả lời bằng `git log`.
- **Rollback là `git revert`**: nhanh, có review, không cần nhớ lệnh của từng công cụ.
- **Giảm config drift**: agent tự sửa thay đổi tay. `kubectl edit` trở thành thao tác tạm thời, không phải cách làm việc.
- **Bảo mật tốt hơn**: credential cluster không rời khỏi cluster; CI bị chiếm cũng khó leo thang sang production.
- **Tái lập được cluster**: cùng repo đó dựng lại cluster mới, hoặc bootstrap môi trường mới trong vài phút.

Trade-off cần nói thẳng, vì đây là phần người phỏng vấn senior sẽ đào:

- **Secret**: Git không phải vault. Bạn buộc phải có chiến lược mã hóa (SOPS, Sealed Secrets) hoặc external secret manager — nội dung cuối chương này.
- **Vòng lặp chậm hơn push**: sửa manifest xong phải commit → push → agent phát hiện → sync. `kubectl apply` vẫn nhanh hơn, nên đội cần kỷ luật "không sửa tay" và một quy trình break-glass cho sự cố.
- **Repo là critical path**: mất quyền truy cập Git hoặc Git down đúng lúc cần deploy là kịch bản phải tính trước; bootstrap cluster cũng phụ thuộc repo.
- **Không phải mọi thứ đều khai báo được**: build image, migration dữ liệu, restore backup, thao tác với hệ thống ngoài vẫn cần CI hoặc con người.
- **Học và vận hành thêm một hệ thống**: ArgoCD/Flux có CRD, RBAC, phiên bản, cách nâng cấp riêng; đội nhỏ phải cân nhắc chi phí này.

## ArgoCD {#argocd}

ArgoCD là GitOps agent phổ biến nhất hiện nay, đã tốt nghiệp CNCF. Nó theo dõi repo Git và đảm bảo cluster khớp với manifest, hỗ trợ plain YAML, Helm, Kustomize, Jsonnet, và có cả UI để nhìn trạng thái từng resource.

### Kiến trúc {#kien-truc-argocd}

Cài mặc định bằng `install.yaml`, bạn sẽ thấy các thành phần sau trong namespace `argocd`:

| Thành phần | Vai trò | Ghi chú vận hành |
|---|---|---|
| `argocd-server` | API (REST/gRPC), UI, session, điểm vào của RBAC | Không render manifest, không reconcile; scale ngang được |
| `argocd-repo-server` | Clone repo, cache, render Helm/Kustomize/Jsonnet/YAML | Là nơi "build" manifest; cần CPU/RAM, scale ngang; tách biệt để giới hạn rủi ro |
| `argocd-application-controller` | So sánh desired state với live state, quyết định sync, đánh giá health | Chạy dạng StatefulSet; sharding khi có nhiều cluster/app |
| `argocd-applicationset-controller` | Sinh `Application` từ generator (list, cluster, git, matrix...) | Dùng cho multi-env/multi-cluster |
| `argocd-dex-server` | SSO (OIDC/SAML/LDAP) | Có thể thay bằng OIDC trực tiếp qua `argocd-cm` |
| `argocd-redis` | Cache manifest và trạng thái | Không phải datastore; mất Redis chỉ làm chậm |
| `argocd-notifications-controller` | Gửi thông báo Slack/webhook khi app đổi trạng thái | Tùy chọn nhưng rất nên có |

Luồng hoạt động: bạn push manifest lên Git → repo-server clone và render → application-controller so sánh với cluster → nếu OutOfSync và auto-sync bật, nó apply bằng chính quyền của ArgoCD → health check các resource → cập nhật status và lịch sử sync. Mặc định ArgoCD kiểm tra lại repo sau khoảng ba phút; với webhook từ GitHub/GitLab, thời gian này giảm xuống vài giây.

Lưu ý bảo mật: `install.yaml` cấp quyền cluster-admin cho ArgoCD. Production nên dùng `namespace-install.yaml` nếu chỉ deploy ra cluster ngoài, hoặc giới hạn bằng `AppProject`, và tuyệt đối không cho ArgoCD quản lý những namespace nhạy cảm (kube-system) nếu không cần.

### Application và sync policy {#application-va-sync-policy}

Đối tượng trung tâm là CRD `Application` (`argoproj.io/v1alpha1`). Một Application khai báo *nguồn* (repo, revision, path) và *đích* (cluster, namespace):

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: demo-dev
  namespace: argocd
  finalizers:
    - resources-finalizer.argocd.argoproj.io   # xóa app thì xóa luôn resource con
spec:
  project: default
  source:
    repoURL: https://git.internal/gitops/gitops-repo.git
    targetRevision: main
    path: apps/demo/overlays/dev
  destination:
    server: https://kubernetes.default.svc   # in-cluster
    namespace: demo-dev
  syncPolicy:
    automated:
      prune: true        # xóa resource không còn trong Git
      selfHeal: true     # revert thay đổi tay trên cluster
    syncOptions:
      - CreateNamespace=true
```

Ba khái niệm trong `syncPolicy` cần phân biệt chính xác:

- **auto-sync**: khi phát hiện OutOfSync, ArgoCD tự sync thay vì chờ bấm nút.
- **selfHeal**: khi resource bị sửa ngoài Git (`kubectl edit`, `scale`, controller khác ghi đè), ArgoCD đưa về giá trị trong Git.
- **prune**: khi một resource bị xóa khỏi Git, ArgoCD xóa nó trên cluster. Đây là phần nguy hiểm nhất — bật cho dev/staging là hợp lý, nhưng với production nên kèm review kỹ và cân nhắc `Prune=false` cho từng resource đặc biệt.

Một số `syncOptions` dùng thường xuyên: `CreateNamespace=true`, `PruneLast=true` (prune sau khi resource mới healthy), `ApplyOutOfSyncOnly=true` (chỉ apply cái lệch), `ServerSideApply=true` (dùng server-side apply — quan trọng khi có nhiều field manager), `FailOnSharedResource` (không cho hai app quản lý cùng resource), `RespectIgnoreDifferences=true`.

Bảng lệnh CLI bạn sẽ dùng hàng ngày:

| Lệnh | Việc |
|---|---|
| `argocd app get <app>` | Trạng thái sync/health, resource, revision |
| `argocd app diff <app>` | Diff giữa desired và live |
| `argocd app sync <app>` | Sync thủ công (kể cả khi auto-sync tắt) |
| `argocd app history <app>` | Lịch sử các lần sync kèm revision |
| `argocd app rollback <app> <id>` | Quay lại một mốc trong history |
| `argocd app wait <app> --health` | Chờ tới khi healthy (dùng trong script) |
| `argocd app terminate-op <app>` | Hủy sync đang chạy khi bị treo |
| `argocd app set <app> --sync-policy none` | Tạm tắt auto-sync trong sự cố |

### Sync wave, hook và drift detection {#sync-wave-hook-va-drift-detection}

Thứ tự apply điều khiển bằng annotation `argocd.argoproj.io/sync-wave` (số nhỏ chạy trước, mặc định `0`): CRD và namespace ở wave `-2`, controller ở `-1`, workload ở `0`. Hook của ArgoCD gồm `PreSync`, `Sync`, `PostSync`, `SyncFail`, `Skip` — dùng cho migration job, smoke test, thông báo.

Với chart Helm, ArgoCD render bằng `helm template` và **map hook của Helm sang hook của chính nó**: `pre-install`/`pre-upgrade` → `PreSync`, `post-install`/`post-upgrade` → `PostSync`, `helm.sh/hook-weight` → `sync-wave`. Hệ quả cần nhớ: ArgoCD không phân biệt được "install lần đầu" với "upgrade" — mọi lần đều là sync — nên `pre-install` và `pre-upgrade` sẽ chạy cùng nhau; `pre-rollback`, `post-rollback`, `test-success`, `test-failure` không được hỗ trợ. Vì vậy hook phải **idempotent** và nên để `hook-delete-policy: before-hook-creation`. Nếu bạn tự định nghĩa hook ArgoCD trong cùng chart, toàn bộ hook Helm sẽ bị bỏ qua.

Drift detection là giá trị cốt lõi: trạng thái `Synced`/`OutOfSync` đến từ phép so sánh liên tục. Vài field do controller khác tự ghi (ví dụ `replicas` của HPA, `spec.clusterIP`, một số default của webhook) thường xuyên tạo diff giả — xử lý bằng `ignoreDifferences` (khai báo theo `group`/`kind` và `jsonPointers`, ví dụ bỏ qua `/spec/replicas` của Deployment) chứ không phải tắt auto-sync. Để ép kiểm tra ngay thay vì chờ chu kỳ, dùng `argocd app get <app> --refresh` (hoặc `--hard-refresh` để xóa cache). Khi một Application kẹt ở `Progressing` mãi, hãy xem resource nào chưa healthy bằng UI hoặc `argocd app get -o tree`.

### App of apps và ApplicationSet {#app-of-apps-va-applicationset}

Khi số application tăng, bạn cần cách sinh chúng thay vì viết tay từng file.

**App of apps** là pattern đơn giản nhất: một Application "root" trỏ vào thư mục chứa các file `Application` khác; sync root sẽ tạo toàn bộ app con. Ưu điểm là dễ hiểu, không cần CRD mới; nhược điểm là lồng sâu khó debug, thứ tự sync giữa các app không được đảm bảo chặt.

**ApplicationSet** giải quyết các hạn chế đó bằng generator. Ví dụ sinh Application cho mọi thư mục con trong `apps/`:

{% raw %}
```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: apps-dev
  namespace: argocd
spec:
  goTemplate: true
  generators:
    - git:
        repoURL: https://git.internal/gitops/gitops-repo.git
        revision: main
        directories:
          - path: apps/*
  template:
    metadata:
      name: '{{.path.basename}}-dev'
    spec:
      project: default
      source:
        repoURL: https://git.internal/gitops/gitops-repo.git
        targetRevision: main
        path: '{{.path.path}}/overlays/dev'
      destination:
        server: https://kubernetes.default.svc
        namespace: '{{.path.basename}}-dev'
```
{% endraw %}

Các generator thường dùng: `list` (cố định), `git` (theo file/directory), `cluster` (mọi cluster đã đăng ký), `matrix` (tổ hợp cluster × app), `merge`, `pullRequest` (môi trường preview cho từng PR), `scmProvider`. Với `goTemplate: true` bạn dùng cú pháp Go template; không bật thì dùng cú pháp fasttemplate cũ. ApplicationSet còn hỗ trợ `strategy.rollingSync` để sync theo nhóm — hữu ích khi rollout nhiều cluster và muốn dừng giữa đường nếu nhóm đầu lỗi.

### Project và RBAC {#project-va-rbac}

`AppProject` là ranh giới multi-tenancy: giới hạn repo được dùng, cluster/namespace được phép deploy, loại resource được tạo, và quyền của từng role:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: team-payments
  namespace: argocd
spec:
  sourceRepos:
    - https://git.internal/payments/*.git
  destinations:
    - namespace: payments-*
      server: https://kubernetes.default.svc
  syncWindows:
    - kind: deny
      schedule: "0 8 * * 1-5"
      duration: 10h
      applications: ["*"]
  roles:
    - name: developer
      policies:
        - p, proj:team-payments:developer, applications, sync, team-payments/*, allow
      groups:
        - payments-devs
```

RBAC chi tiết khai báo trong ConfigMap `argocd-rbac-cm` (dòng `policy.csv`) hoặc trong `roles` của project. Nguyên tắc tôi luôn áp dụng: `policy.default: role:readonly` để ai cũng xem được trạng thái, nhưng chỉ role cụ thể mới được `sync`/`delete`; SSO qua OIDC và map group thay vì cấp tài khoản local; `syncWindows` để chặn deploy ngoài giờ cho các hệ thống nhạy cảm. Cuối cùng, nhớ rằng AppProject chỉ giới hạn ArgoCD — người có kubeconfig vẫn vào được cluster, nên đừng xem đây là ranh giới bảo mật duy nhất.

### Flux và so sánh nhanh {#flux-va-so-sanh-nhanh}

Flux (v2.9.x tại thời điểm viết) không phải một ứng dụng nguyên khối mà là **bộ controller tách rời**, mỗi controller giữ một mối quan tâm: `source-controller` (GitRepository, OCIRepository, HelmRepository, Bucket), `kustomize-controller` (Kustomization), `helm-controller` (HelmRelease), `notification-controller` (Alert, Provider, Receiver), cùng nhóm `image-reflector`/`image-automation` để cập nhật tag image tự động. Cách cài chuẩn là `flux bootstrap github|gitlab|git`, biến chính cluster thành self-managed từ Git.

Ví dụ deploy app bằng GitRepository + Kustomization:

```yaml
apiVersion: source.toolkit.fluxcd.io/v1
kind: GitRepository
metadata:
  name: podinfo
  namespace: flux-system
spec:
  interval: 1m
  url: https://github.com/stefanprodan/podinfo
  ref:
    branch: master
---
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: podinfo
  namespace: flux-system
spec:
  interval: 5m
  targetNamespace: default
  sourceRef:
    kind: GitRepository
    name: podinfo
  path: ./kustomize
  prune: true      # tương đương prune của ArgoCD
  wait: true       # chờ resource healthy
  timeout: 2m
```

Với Helm, Flux có `helm-controller` native (không cần qua `helm template`): bạn khai báo `HelmRelease` với `chart.spec` (chart, version, `sourceRef` tới `HelmRepository`/`OCIRepository`), `values`, và phần `install.remediation`/`upgrade.remediation` để retry và tự rollback khi upgrade thất bại — khác với ArgoCD, nơi mọi sync đều là render + apply chứ không tạo release Helm thật.

Điểm mạnh khác của Flux: multi-tenancy "đúng kiểu Kubernetes" (mỗi Kustomization có thể impersonate một ServiceAccount, kèm cờ `--no-cross-namespace-refs`), giải mã SOPS native ngay trong Kustomization, và image automation tích hợp sẵn. Đổi lại, Flux không có UI mặc định và bạn phải viết nhiều CRD hơn — với người mới, ArgoCD thường dễ tiếp cận hơn.

| Tiêu chí | ArgoCD | Flux |
|---|---|---|
| Mô hình | Ứng dụng nhiều thành phần, có UI/API tập trung | Bộ controller tách rời, Git-centric |
| CRD chính | `Application`, `AppProject`, `ApplicationSet` | `GitRepository`, `Kustomization`, `HelmRelease` |
| Rendering | `helm template` / `kustomize build` trong repo-server | Kustomize build trong controller; Helm qua helm-controller (tạo release thật) |
| Sync / prune / self-heal | `syncPolicy.automated` với `prune`, `selfHeal` | `Kustomization.spec.prune`, `wait`, `healthChecks`; drift correction mặc định |
| Helm release | Không tạo release Helm; không có `helm history` | Tạo release thật, hỗ trợ remediation/retry, `flux get hr` |
| UI | Có sẵn (rất mạnh) | Không có mặc định (Weave GitOps, Capacitor là bên thứ ba) |
| Multi-tenancy | AppProject + RBAC, một instance phục vụ nhiều team | ServiceAccount impersonation, tách theo namespace |
| Secret | Cần plugin (SOPS/ksops/AVP) hoặc ESO | Giải mã SOPS native trong Kustomization |
| Image automation | `argocd-image-updater` (project riêng) | `image-reflector` + `image-automation` tích hợp |
| Độ phổ biến ở VN | Rất cao trong JD | Thấp hơn, thường gặp ở đội cloud-native thuần |

Kinh nghiệm chọn nhanh: đội cần UI, nhiều team dùng chung một nền tảng, hoặc muốn quản lý app như một "dashboard" — chọn ArgoCD. Đội nhỏ, thích mô hình "một cluster một bộ controller", làm nhiều cluster và đã quen viết Kustomization — Flux rất thoải mái. Cả hai đều là CNCF và đều làm đúng GitOps; chọn cái mà đội bạn vận hành được.

## Cấu trúc repository GitOps {#cau-truc-repository-gitops}

### Mô hình repository {#mo-hinh-repository}

Tách **app repo** (code + CI build image) khỏi **config repo** (manifest deploy). CI của app repo không có quyền ghi vào cluster; nó chỉ mở PR cập nhật tag image trong config repo — hoặc để image automation làm việc đó.

Ba cách chia config repo:

- **Một repo cho tất cả môi trường** (khuyến nghị cho đa số đội): đơn giản, một chỗ để review, dễ đồng bộ version giữa các service.
- **Mỗi môi trường một repo**: ranh giới quyền rõ hơn (dev có thể tự do hơn prod), nhưng promotion cần PR liên repo và dễ lệch phiên bản.
- **Mỗi team/mỗi cluster một repo**: hợp với tổ chức lớn, nhiều đơn vị tự trị; đổi lại mỗi repo phải có pipeline validate riêng.

Về promotion, đừng dùng nhánh dài (`dev`, `staging`, `prod` là ba nhánh song song) — nó tái tạo đúng vấn đề của GitFlow ở chương 12: code không merge về mainline, diff giữa các nhánh ngày càng lớn. Kiểu được khuyến nghị là **directory-based**: một nhánh main, môi trường là các thư mục; promotion là PR thay đổi overlay của môi trường đích, review bởi người chịu trách nhiệm môi trường đó.

### Tổ chức theo môi trường với Kustomize và Helm {#to-chuc-theo-moi-truong}

Một layout tôi thường dùng, dễ đọc với cả ArgoCD và Flux:

```text
gitops-repo/
├── apps/
│   ├── demo/
│   │   ├── base/                 # manifest gốc, chạy được ở mọi môi trường
│   │   │   ├── kustomization.yaml
│   │   │   ├── deployment.yaml
│   │   │   └── service.yaml
│   │   └── overlays/
│   │       ├── dev/              # chỉ chứa phần khác biệt
│   │       │   └── kustomization.yaml
│   │       ├── staging/
│   │       └── prod/
│   └── payments/
├── infrastructure/               # ingress, cert-manager, monitoring, policy
├── charts/                       # chart nội bộ (nếu dùng Helm)
├── secrets/                      # SealedSecret hoặc file SOPS
└── clusters/                     # Flux: clusters/<cluster-name>/...
```

Overlay của dev rất gọn, chỉ ghi những gì khác base:

```yaml
# apps/demo/overlays/dev/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
namespace: demo-dev
resources:
  - ../../base
  - sealed-db.yaml        # secret đã mã hóa, commit an toàn
replicas:
  - name: demo
    count: 1
images:
  - name: ghcr.io/stefanprodan/podinfo
    newTag: 6.9.0
```

Overlay prod có cùng cấu trúc, khác ở `namespace: demo-prod`, `count: 3`, và ghim image bằng `digest: sha256:...` thay vì `newTag` — production nên dùng artifact bất biến để rollback luôn khôi phục đúng image.

Với Helm, cấu trúc tương tự nhưng phần khác biệt nằm ở values: `values-dev.yaml`, `values-staging.yaml`, `values-prod.yaml`, còn chart version được ghim trong Application/HelmRelease. Nguyên tắc bất di bất dịch: **image phải ghim bất biến** (digest ở prod, tag semver ở dev), không bao giờ để `latest`; và không commit cả source lẫn manifest đã render — chọn một trong hai để tránh lệch trạng thái.

### Quy tắc vận hành repository {#quy-tac-van-hanh-repository}

- **CI validate manifest trước khi merge**: `kustomize build`, `helm template`, rồi `kubeconform -strict` hoặc `kube-linter`/`conftest` để bắt lỗi schema và policy. Một commit lỗi vào main nghĩa là cluster lệch ngay sau vài phút.
- **CODEOWNERS + required review** cho các thư mục môi trường production; bảo vệ nhánh main.
- **Không có plaintext secret** trong bất kỳ thư mục nào, kể cả file test. Bật secret scanning trên repo.
- **Bootstrap được từ Git**: bản thân ArgoCD/Flux cũng nên được quản lý bằng Git (ArgoCD quản lý chính Application của nó, Flux bootstrap tự cập nhật). Khi cluster mất, việc dựng lại chỉ còn là chạy vài lệnh bootstrap.
- **Quy trình break-glass** viết sẵn: khi sự cố khẩn, được phép sửa trực tiếp trên cluster, nhưng phải có bước bắt buộc cập nhật lại Git trong vòng N phút và một người kiểm tra. Không có quy trình này, đội sẽ hoặc là vi phạm GitOps trong im lặng, hoặc là chần chừ với sự cố vì sợ "sai quy trình".

## Helm {#helm}

Helm là trình quản lý package cho Kubernetes: đóng gói manifest thành **chart** có version, tham số hóa bằng values, quản lý **release** theo vòng đời và cho phép rollback. Trong GitOps, Helm thường đóng vai "cách viết manifest", còn ArgoCD/Flux là "cách deploy manifest đó".

### Cấu trúc chart {#cau-truc-chart}

```text
demo/
├── Chart.yaml          # metadata của chart
├── values.yaml         # giá trị mặc định
├── values.schema.json  # (tùy chọn) JSON Schema validate values
├── templates/
│   ├── _helpers.tpl    # định nghĩa template dùng lại
│   ├── deployment.yaml
│   ├── service.yaml
│   ├── NOTES.txt       # ghi chú hiện sau khi install
│   └── hooks/migrate-job.yaml
├── charts/             # subchart (dependency) đã vendor
└── crds/               # CRD cài kèm, không template được
```

`Chart.yaml` hiện hành dùng `apiVersion: v2`:

```yaml
apiVersion: v2
name: demo
description: Chart cho ứng dụng demo trong sách
type: application        # hoặc library
version: 0.3.0           # version của chart, tăng khi sửa template
appVersion: "6.9.0"      # version của ứng dụng (thường là image tag)
kubeVersion: ">=1.29.0-0"
```

Phân biệt `version` và `appVersion` là lỗi kinh điển: `version` dùng cho việc đóng gói/rollback chart, `appVersion` chỉ là metadata mô tả ứng dụng — đổi image nên đổi `appVersion`, nhưng chỉ cần bump `version` khi bản thân template thay đổi.

### Template, values và các hàm thường dùng {#template-values-va-cac-ham}

Một deployment template hoàn chỉnh cho thấy gần như mọi kỹ thuật bạn cần: helper dùng lại, giá trị mặc định, `toYaml` cho resource, và annotation checksum để pod restart khi ConfigMap đổi.

{% raw %}
```yaml
# templates/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "demo.fullname" . }}
  labels:
    {{- include "demo.labels" . | nindent 4 }}
spec:
  replicas: {{ .Values.replicaCount }}
  selector:
    matchLabels:
      {{- include "demo.selectorLabels" . | nindent 6 }}
  template:
    metadata:
      labels:
        {{- include "demo.selectorLabels" . | nindent 8 }}
      annotations:
        # Đổi ConfigMap -> checksum đổi -> pod được rollout lại
        checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}
    spec:
      containers:
        - name: app
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag | default .Chart.AppVersion }}"
          imagePullPolicy: {{ .Values.image.pullPolicy | default "IfNotPresent" }}
          ports:
            - containerPort: {{ .Values.service.targetPort }}
          envFrom:
            - configMapRef:
                name: {{ include "demo.fullname" . }}
          readinessProbe:
            httpGet:
              path: /readyz
              port: {{ .Values.service.targetPort }}
```
{% endraw %}

`values.yaml` tương ứng:

```yaml
replicaCount: 1

image:
  repository: ghcr.io/stefanprodan/podinfo
  tag: ""            # rỗng thì lấy .Chart.AppVersion
  pullPolicy: IfNotPresent

service:
  type: ClusterIP
  port: 80
  targetPort: 9898
```

Các hàm template dùng nhiều nhất:

| Hàm | Công dụng |
|---|---|
| `include` / `template` | Render một template con (`include` trả về string nên pipe được) |
| `required` | Bắt buộc có value, thiếu thì fail ngay khi render |
| `default` | Giá trị mặc định khi value rỗng |
| `toYaml` + `nindent` | Chèn khối YAML với thụt lề đúng (cặp bài trùng phổ biến nhất) |
| `quote` | Bọc giá trị trong dấu nháy, tránh YAML hiểu sai kiểu |
| `tpl` | Render chuỗi như template (cho values chứa template) |
| `lookup` | Đọc resource đang tồn tại trong cluster (dùng cẩn thận — làm mất tính khai báo) |
| `semverCompare`, `sha256sum`, `printf`, `dict`, `list` | So sánh version, tính hash, tạo cấu trúc dữ liệu |

Thứ tự ưu tiên của values, từ thấp đến cao: `values.yaml` của chart → values của subchart/parent → `-f values-dev.yaml` (file sau ghi đè file trước) → `--set`/`--set-string`. Một cái bẫy khi vận hành: `helm upgrade` mặc định **reset** values về `values.yaml` cộng với những gì bạn truyền lần này; muốn giữ values của lần upgrade trước thì dùng `--reuse-values`. Trong GitOps, lỗi này ít gặp vì mọi values đều nằm trong Git, nhưng khi chạy tay thì rất hay quên.

### Vòng đời release và hook {#vong-doi-release-va-hook}

Helm 3 trở đi lưu release dưới dạng Secret `sh.helm.release.v1.<release>.v<revision>` trong chính namespace của release. Trạng thái release gồm `deployed`, `superseded`, `failed`, `uninstalling`... Mỗi lần `install`/`upgrade`/`rollback` thành công tạo một revision mới. Ba lệnh chẩn đoán nên thuộc lòng: `helm history <release>`, `helm get values <release>`, `helm get manifest <release>`.

Hook là resource có annotation `helm.sh/hook`, chạy ở các thời điểm trong vòng đời:

| Hook | Chạy khi nào |
|---|---|
| `pre-install`, `post-install` | Trước khi resource được tạo / sau khi tất cả resource đã tạo |
| `pre-upgrade`, `post-upgrade` | Trước khi resource được cập nhật / sau khi cập nhật xong |
| `pre-rollback`, `post-rollback` | Trước / sau khi rollback |
| `pre-delete`, `post-delete` | Trước / sau khi uninstall |
| `test` | Khi chạy `helm test` |

Hook dùng phổ biến nhất là Job migrate database chạy `pre-upgrade`:

{% raw %}
```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: {{ include "demo.fullname" . }}-migrate
  annotations:
    "helm.sh/hook": pre-install,pre-upgrade
    "helm.sh/hook-weight": "-5"                      # chạy trước các hook weight lớn hơn
    "helm.sh/hook-delete-policy": before-hook-creation,hook-succeeded
spec:
  backoffLimit: 1
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrate
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag | default .Chart.AppVersion }}"
          command: ["./app", "migrate"]
```
{% endraw %}

Hai cạm bẫy về hook mà tôi đã từng trả giá:

- **Hook không được quản lý như tài nguyên của release.** Helm tạo hook rồi "quên" nó đi; `helm uninstall` không xóa hook resource. Muốn dọn thì phải dùng `hook-delete-policy` (`before-hook-creation` là mặc định — xóa resource cũ trước khi chạy hook mới), `hook-succeeded`, `hook-failed`, hoặc `ttlSecondsAfterFinished` cho Job.
- **Hook chạy đồng bộ theo weight, nhưng phải idempotent.** Nếu hook fail giữa đường, release có thể ở trạng thái `failed`; lần upgrade sau hook sẽ chạy lại từ đầu.

### upgrade, rollback và các lệnh quan trọng {#upgrade-rollback-va-lenh}

| Lệnh | Việc |
|---|---|
| `helm template <name> ./chart -f values.yaml` | Render offline, xem trước manifest (dùng cả trong CI) |
| `helm lint ./chart` | Kiểm tra lỗi cấu trúc/template cơ bản |
| `helm upgrade --install demo ./chart -n demo --create-namespace -f values-prod.yaml` | Install nếu chưa có, upgrade nếu đã có |
| `helm upgrade ... --wait --timeout 5m --rollback-on-failure` | Chờ resource healthy, tự rollback nếu fail (`--atomic` là tên cũ) |
| `helm history demo -n demo` | Danh sách revision và trạng thái |
| `helm rollback demo 3 -n demo` | Quay về revision 3 (tạo revision mới) |
| `helm uninstall demo -n demo --keep-history` | Gỡ release nhưng giữ history để tra cứu |
| `helm push demo-0.3.0.tgz oci://registry.internal/charts` | Phát hành chart qua OCI registry |

Cơ chế quan trọng nhất cần hiểu là **three-way merge**: khi upgrade, Helm tính patch từ (1) manifest cũ của release, (2) manifest mới render, (3) trạng thái live. Nhờ đó các field do controller khác ghi (ví dụ `replicas` do HPA sửa) không bị Helm ghi đè vô tội vạ. Đây cũng là lý do `helm upgrade` "thông minh" hơn `kubectl apply -f` thuần ở chỗ nó biết cái gì thuộc về mình.

### Helm 4: những thay đổi cần biết {#helm-4-nhung-thay-doi}

Helm 4 đã là bản ổn định hiện tại (Helm 3 chỉ còn nhận bug fix tới 9/2026 và security fix tới 2/2027, sau đó dừng hẳn). Chart `apiVersion: v2` vẫn chạy nguyên vẹn, template và values không đổi, nhưng có năm điểm ảnh hưởng trực tiếp tới pipeline và GitOps:

- **Server-side apply mặc định cho install mới**. Các release tạo bởi Helm 3 vẫn tiếp tục dùng client-side apply khi upgrade (cơ chế "latching") trừ khi bạn truyền `--server-side`. Khi nhiều công cụ cùng quản lý một resource (Helm + ArgoCD + operator), hãy chọn một chiến lược apply nhất quán và theo dõi conflict của field manager.
- **Đổi tên flag**: `--atomic` → `--rollback-on-failure`, `--force` → `--force-replace` (tên cũ vẫn chạy nhưng cảnh báo, sẽ thành lỗi ở bản sau).
- **`--wait` dùng kstatus** để đánh giá readiness thay vì chỉ nhìn trạng thái pod; service account chạy Helm cần quyền `watch` trên resource liên quan.
- **Plugin system mới (WASM)**: post-renderer phải là plugin, không truyền executable trực tiếp như trước.
- **`helm registry login` chỉ nhận domain**, bỏ `https://` khi đăng nhập OCI registry.

Với GitOps, lưu ý lớn nhất là SSA: ArgoCD có sync option `ServerSideApply=true`, còn Flux dùng helm-controller (tạo release thật). Nếu nửa đường đổi cơ chế apply, bạn sẽ thấy các conflict "field owned by another manager" — cách xử lý là chọn một cơ chế, ghi rõ trong runbook, và không trộn `kubectl apply` tay vào cùng resource.

### Helm so với Kustomize {#helm-so-voi-kustomize}

| Tiêu chí | Helm | Kustomize |
|---|---|---|
| Cách hoạt động | Template Go với điều kiện, vòng lặp, hàm | Patch/overlay trên YAML gốc, không template |
| Đóng gói & version | Chart có `version`, đóng gói `.tgz`, đẩy lên registry | Không có package/version (trừ khi tự quản lý bằng Git tag) |
| Tham số hóa | `values.yaml`, `--set`, schema validate | Overlay, patch, `images`, `namePrefix`, `configMapGenerator` |
| Vòng đời release | Có (`helm history`, `helm rollback`, hook) | Không có khái niệm release |
| Render offline | `helm template` | `kubectl kustomize`, có sẵn trong kubectl |
| Độ phức tạp | Cao hơn khi chart lớn (logic trong template khó test) | Thấp, dễ đọc, diff sát với manifest cuối |

Chọn theo câu hỏi: *bạn cần phân phối và version hóa package cho người khác dùng, hay chỉ cần biến thể của manifest bạn tự viết?* Chart dùng chung (ingress-nginx, kube-prometheus-stack, internal platform) → Helm. Manifest nội bộ với ba môi trường hơi khác nhau → Kustomize thường nhanh và dễ kiểm soát hơn. Rất nhiều đội dùng cả hai: Helm cho third-party, Kustomize cho app của mình — và cách kết hợp này hoàn toàn hợp lệ: Kustomize có `helmCharts` generator để render chart rồi patch tiếp, còn Flux thì đặt `HelmRelease` bên trong một `Kustomization`.

## Các chiến lược deployment {#cac-chien-luoc-deployment}

Deployment strategy là cách thay thế phiên bản cũ bằng phiên bản mới. Ba trục đánh đổi luôn hiện diện: **rủi ro** (bao nhiêu người dùng gặp lỗi nếu bản mới hỏng), **chi phí** (cần thêm bao nhiêu tài nguyên), và **tốc độ rollback**. Không có chiến lược tốt nhất — chỉ có chiến lược phù hợp với mức rủi ro và ngân sách của hệ thống.

### Recreate {#recreate}

```yaml
spec:
  strategy:
    type: Recreate
```

Tắt toàn bộ pod cũ rồi tạo pod mới: đơn giản, không bao giờ có hai version chạy song song, nhưng **có downtime**. Dùng cho môi trường dev, workload không nhận traffic, hoặc ứng dụng không thể chạy hai bản cùng lúc (ví dụ chỉ một instance được giữ lock, schema không tương thích). Với production có người dùng, đây gần như không bao giờ là lựa chọn.

### Rolling update {#rolling-update}

Đây là chiến lược mặc định của Deployment và là nền tảng cho mọi thứ phía sau:

```yaml
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1          # được phép có thêm 1 pod trong lúc rollout
      maxUnavailable: 0    # không được phép thiếu pod nào
  minReadySeconds: 10      # pod phải Ready liên tục 10s mới coi là xong
  progressDeadlineSeconds: 600
  revisionHistoryLimit: 10
```

Bảng tổ hợp hai tham số:

| maxSurge | maxUnavailable | Hành vi | Dùng khi |
|---|---|---|---|
| 25% (mặc định) | 25% (mặc định) | Nhanh, có thể thiếu capacity tạm thời | Hệ thống chịu tải dư |
| 1 | 0 | Không downtime, thêm tối đa 1 pod | Production ưu tiên an toàn |
| 50% | 0 | Rollout nhanh hơn nhưng tốn gấp rưỡi tài nguyên | Đội có headroom |
| 0 | 1 | Tiết kiệm tài nguyên, chấp nhận thiếu 1 pod | Cluster chật, chịu giảm capacity |

Để rolling update thực sự zero-downtime, cấu hình Deployment chưa đủ. Checklist đầy đủ:

- **Readiness probe đúng**: Kubernetes chỉ chuyển traffic khi pod Ready. Probe phải kiểm tra thứ đại diện cho "phục vụ được" (không chỉ process còn sống); liveness probe chỉ để restart khi treo.
- **`preStop` hook + `terminationGracePeriodSeconds`**: khi pod bị xóa, nó cần thời gian để rời endpoint và xử lý request đang bay. Một `preStop: sleep 5` thường rẻ hơn nhiều so với một sự cố 502.
- **PDB (PodDisruptionBudget)**: bảo vệ khi node bị drain (nâng cấp cluster) — đảm bảo số pod tối thiểu luôn Ready. PDB không điều khiển rolling update của Deployment, đừng nhầm hai cơ chế này.
- **Ứng dụng hỗ trợ graceful shutdown**: nhận SIGTERM, ngừng nhận request mới, hoàn tất request đang chạy.
- **Migration database tương thích ngược**: schema mới phải chạy được với cả code cũ lẫn code mới trong khoảng thời gian hai version cùng tồn tại.

Các lệnh vận hành cần nằm trong tay:

```bash
kubectl rollout status deploy/demo -n demo --timeout=180s
kubectl rollout pause deploy/demo -n demo      # tạm dừng giữa rollout để kiểm tra
kubectl rollout resume deploy/demo -n demo
kubectl set image deploy/demo app=ghcr.io/stefanprodan/podinfo:6.9.1 -n demo
kubectl rollout restart deploy/demo -n demo    # restart theo cách rolling (đổi ConfigMap chẳng hạn)
kubectl rollout history deploy/demo -n demo
```

Nếu rollout kẹt (pod mới không Ready, image pull lỗi), mặc định Deployment sẽ báo `ProgressDeadlineExceeded` sau `progressDeadlineSeconds` nhưng **không tự rollback**. Muốn tự rollback, bạn cần công cụ phía trên (Argo Rollouts, Flagger, Helm `--rollback-on-failure`) hoặc CI theo dõi `rollout status`.

### Blue-green {#blue-green}

Hai môi trường chạy song song: **blue** (đang phục vụ) và **green** (bản mới). Bạn deploy đầy đủ green, kiểm tra, rồi **chuyển traffic bằng một thao tác nguyên tử** — thường là đổi selector của Service từ `version: blue` sang `version: green` (hoặc dùng hai Service như Argo Rollouts làm).

Ưu điểm: rollback cực nhanh (đổi selector về blue), không có khoảng thời gian hai version cùng nhận traffic (nên dễ kiểm soát hành vi), phù hợp khi cần kiểm thử kỹ trước khi mở cửa. Nhược điểm: **tốn gấp đôi tài nguyên** trong lúc chuyển, và mọi kết nối dài (WebSocket, gRPC stream) sẽ đứt khi switch. Blue-green cũng đòi hỏi schema database tương thích cả hai version trong thời gian chuyển — đôi khi đây là rào cản lớn nhất.

Argo Rollouts hỗ trợ blue-green "hạng nhất" với `activeService`/`previewService`, `autoPromotionEnabled: false` (chờ người xác nhận), `scaleDownDelaySeconds` (giữ blue thêm một lúc để rollback), và `prePromotionAnalysis` (chạy smoke test tự động trước khi mở traffic).

### Canary với Argo Rollouts và Flagger {#canary-voi-argo-rollouts-va-flagger}

Canary đưa một phần nhỏ traffic thật sang bản mới, tăng dần theo bước, kèm phân tích metric; nếu metric xấu thì dừng và rollback tự động. Đây là chiến lược "progressive delivery" đúng nghĩa: rủi ro được giới hạn theo phần trăm người dùng gặp lỗi, và quyết định promote/abort dựa trên dữ liệu thay vì cảm giác.

**Argo Rollouts** thay thế Deployment bằng CRD `Rollout` và bổ sung `AnalysisTemplate`. Ví dụ canary 4 pod, tăng dần 25% → 50% → 100%, mỗi bước dừng để quan sát:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: podinfo
spec:
  replicas: 4
  selector:
    matchLabels:
      app: podinfo
  template:
    metadata:
      labels:
        app: podinfo
    spec:
      containers:
        - name: podinfo
          image: ghcr.io/stefanprodan/podinfo:6.9.0
          ports:
            - containerPort: 9898
  strategy:
    canary:
      canaryService: podinfo-canary   # Service cho bản mới
      stableService: podinfo-stable   # Service cho bản cũ
      steps:
        - setWeight: 25
        - pause: { duration: 60s }
        - setWeight: 50
        - pause: { duration: 60s }
        - setWeight: 100
```

Khi bạn đổi image trong `Rollout`, Argo Rollouts tạo ReplicaSet canary và tiến qua từng bước. Lệnh vận hành: `kubectl argo rollouts get rollout podinfo -w`, `kubectl argo rollouts promote podinfo` (bỏ qua pause), `kubectl argo rollouts abort podinfo` (dừng và quay về stable). Nếu không cấu hình `trafficRouting`, `setWeight` được hiện thực bằng **tỉ lệ replica** — 25% nghĩa là 1/4 pod là bản mới; muốn chia traffic thật theo phần trăm, bạn cần traffic routing qua ingress controller hoặc service mesh (NGINX, Istio, ALB, Traefik, Gateway API, APISIX, SMI).

Phần "tự động" nằm ở `AnalysisTemplate`: một truy vấn Prometheus (hoặc webhook, Job) được chạy nền trong lúc canary, so với `successCondition`. Nếu vi phạm quá `failureLimit` lần, Argo Rollouts tự abort và rollback. Một template tối giản:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: success-rate
spec:
  metrics:
    - name: success-rate
      interval: 30s
      successCondition: result[0] >= 0.99
      failureLimit: 3
      provider:
        prometheus:
          address: http://prometheus.monitoring.svc:9090
          query: |
            sum(rate(nginx_ingress_controller_requests{service="podinfo",status!~"5.*"}[2m]))
            / sum(rate(nginx_ingress_controller_requests{service="podinfo"}[2m]))
```

Lưu ý hai điều kiện để canary có ý nghĩa: (1) **observability phải đủ tốt** — không có metric đáng tin theo version thì đừng nói tới canary tự động (chương 14 là tiền đề); (2) **số bước và thời gian pause phải đủ dài** để tín hiệu tích tụ — canary 5% trong 10 giây chỉ là nghi thức.

**Flagger** là lựa chọn thay thế, hoạt động như một operator trên CRD `Canary`: bạn trỏ tới một Deployment bình thường, Flagger tự tạo `primary`/`canary` service, tăng `stepWeight` theo `interval`, chạy `analysis.metrics` và rollback khi quá `threshold` lần thất bại. Flagger còn hỗ trợ webhook (load test, smoke test) trước khi tăng traffic và làm việc với nhiều provider mesh/ingress. Nói ngắn gọn: Argo Rollouts cho bạn kiểm soát chi tiết trong hệ sinh thái Argo; Flagger cho bạn automation "cài là chạy" với các provider được hỗ trợ sẵn.

### Shadow traffic {#shadow-traffic}

Shadow (mirror) traffic là bản sao của traffic thật được gửi song song tới bản mới, nhưng **response của bản mới bị bỏ đi** — người dùng vẫn nhận response từ bản cũ. Với Istio, bạn cấu hình `mirror` (kèm `mirrorPercentage`) trong `VirtualService` để trỏ một phần hoặc toàn bộ request sang host của bản canary.

Ứng dụng: kiểm thử hiệu năng và tính đúng đắn của bản mới với payload thật, phát hiện lỗi chỉ xuất hiện với dữ liệu production, mà không ảnh hưởng người dùng. Cảnh báo quan trọng: nếu handler không idempotent, bạn đang **ghi dữ liệu hai lần**; cần đảm bảo bản canary chỉ đọc, hoặc dùng DB riêng, và tuyệt đối không mirror các luồng thanh toán/gửi email. Ngoài ra phải tách metric của traffic mirror khỏi SLO, nếu không dashboard sẽ nhiễu. Vì vậy shadow traffic là công cụ để *kiểm chứng*, không phải để *thay thế* canary.

### Feature flag {#feature-flag}

Feature flag tách **deploy** khỏi **release**: code mới đã nằm trên production nhưng tính năng còn tắt; bật/tắt là một thay đổi config (không cần deploy), thường có targeting theo user/tenant/percentage. Lợi ích lớn nhất là **rollback tức thời** — tệ hơn cả canary rollback vì không cần điều chỉnh traffic hay chờ pod mới. Trong GitOps, flag config nằm trong Git hoặc trong hệ thống flag (LaunchDarkly, Flagsmith, OpenFeature...) và mọi thay đổi đều có audit.

Feature flag bổ trợ chứ không thay thế các chiến lược deploy: flag kiểm soát *hành vi*, còn rolling/canary kiểm soát *phiên bản code đang chạy*. Đội trưởng thành thường kết hợp: code mới ra sau flag → deploy bằng rolling update (rủi ro thấp vì chưa ai chạm tới code mới) → bật flag cho 1% user → quan sát → tăng dần. Nhớ dọn flag cũ: nợ flag là nguyên nhân của những bug "chỉ xảy ra với tổ hợp flag hiếm gặp" mà không ai tái hiện được.

### So sánh các chiến lược {#so-sanh-cac-chien-luoc}

| Chiến lược | Downtime | Chi phí tài nguyên | Rollback | Rủi ro với người dùng | Độ phức tạp | Hợp với |
|---|---|---|---|---|---|---|
| Recreate | Có | 1x | Chậm (deploy lại) | Cao, toàn bộ người dùng | Rất thấp | Dev, workload one-off |
| Rolling update | Không | ~1x (+surge) | Trung bình (`rollout undo`) | Trung bình — lỗi lan dần theo pod | Thấp | Mặc định cho hầu hết service |
| Blue-green | Không | 2x trong lúc chuyển | Rất nhanh (đổi selector) | Thấp nếu test kỹ; nhưng "all or nothing" | Trung bình | Release lớn, cần kiểm thử kỹ trước khi mở traffic |
| Canary + analysis | Không | ~1x (+surge) | Nhanh, tự động nếu có analysis | Thấp, tăng dần theo % | Cao | Service có metric tốt, cần rollout an toàn |
| Shadow | Không | ~2x | Không cần (không phục vụ traffic thật) | Không | Cao | Xác thực phiên bản mới với traffic thật |
| Feature flag | Không | ~1x | Tức thời | Thấp, giới hạn theo targeting | Trung bình | Tính năng có thể bật/tắt, A/B test |

Nguyên tắc chọn nhanh mà tôi hay nói với đội: nếu hệ thống chưa có readiness probe đúng và metric theo version, việc cần làm trước tiên là **rolling update tử tế** (maxUnavailable thấp, probe tốt, graceful shutdown), rồi mới nâng cấp dần lên canary. Nhảy thẳng từ `kubectl apply` sang canary tự động khi chưa có observability là cách chắc chắn nhất để tạo sự cố nhanh hơn.

## Rollback và migration database {#rollback-va-migration-database}

Rollback là câu hỏi kiểm tra bản lĩnh vận hành: khi bản mới hỏng, bạn quay lại trong bao lâu và bằng cách nào. Mỗi công cụ có một cơ chế khác nhau, và điểm chung là **rollback chỉ đáng tin khi bạn đã thử nó trước khi cần**.

### kubectl rollout undo {#kubectl-rollout-undo}

Với Deployment và DaemonSet (không áp dụng cho StatefulSet), Kubernetes giữ lịch sử ReplicaSet:

```bash
kubectl rollout history deploy/demo -n demo
kubectl rollout undo deploy/demo -n demo                  # quay về revision trước
kubectl rollout undo deploy/demo -n demo --to-revision=3  # quay về revision cụ thể
kubectl rollout status deploy/demo -n demo --timeout=120s
```

Mẹo thực tế: đặt annotation `kubernetes.io/change-cause` để `rollout history` có ý nghĩa:

```bash
kubectl annotate deploy/demo -n demo kubernetes.io/change-cause="rollout image 6.9.1"
```

`rollout undo` chỉ đổi spec của Deployment về revision cũ rồi để controller rollout lại; nó **không** khôi phục ConfigMap/Secret đã đổi (nếu bạn không gắn checksum), không sửa Service, không hoàn tác migration database. Nếu nguyên nhân sự cố là image không pull được hoặc config sai, `undo` có thể không giúp gì — nhiều khi phải sửa manifest và rollout tiếp (roll forward). Với StatefulSet, cách "rollback" là sửa manifest về bản cũ và apply lại, cẩn thận với thứ tự khởi động và dữ liệu.

### Helm rollback {#helm-rollback}

```bash
helm history demo -n demo
helm rollback demo 3 -n demo --wait --timeout 5m
helm status demo -n demo
```

Cơ chế cần nhớ: `helm rollback demo 3` **không** quay ngược thời gian về revision 3 rồi xóa 4, 5. Nó tạo **revision mới** (ví dụ revision 6) với nội dung của revision 3, và lịch sử vẫn còn đầy đủ. Vì vậy bạn có thể rollback "tiến" tiếp về revision 5 nếu bản 3 cũng không ổn.

Giới hạn của Helm rollback: CRD trong `crds/` không được cài lại và không được xóa (Helm không quản lý vòng đời CRD); hook resource không thuộc release nên không bị rollback; các resource tạo bởi `kubectl apply` tay hoặc bởi operator không nằm trong release; và mọi thay đổi dữ liệu do ứng dụng ghi (schema, nội dung) vẫn nguyên. Helm rollback khôi phục *manifest*, không khôi phục *state*.

### Rollback trong GitOps {#rollback-trong-gitops}

Trong GitOps, câu trả lời đúng nhất cho "rollback thế nào" là: **revert commit trên Git**. Với auto-sync bật, agent sẽ tự đưa cluster về trạng thái cũ; mọi thứ có audit, có review, và trạng thái Git khớp với cluster.

Điều này dẫn tới một cạm bẫy kinh điển: `argocd app rollback` (hoặc sửa trực tiếp trên cluster) chỉ là tạm thời. Vì application-controller vẫn đối chiếu với `targetRevision` (ví dụ nhánh `main` đang chứa commit lỗi), chỉ vài phút sau self-heal sẽ đưa bản lỗi trở lại — và bạn tưởng công cụ "không nghe lời". Hai lựa chọn đúng khi cần khôi phục tức thời:

1. **Tắt auto-sync tạm thời**, sửa trực tiếp để cắt sự cố, rồi revert Git và bật lại: `argocd app set demo -n argocd --sync-policy none`. Cách này nằm trong runbook break-glass và phải được ghi lại.
2. **Revert Git trước**, chấp nhận chờ một vòng sync (thường vài chục giây tới vài phút). Sạch sẽ nhất, nhưng không phù hợp nếu đang cháy.

Thứ tự ưu tiên khi sự cố: giảm tác động (có thể bằng thao tác tay) → khôi phục dịch vụ → đưa Git về đúng trạng thái → kiểm tra drift = 0 → viết postmortem. Một điểm tinh tế hay được hỏi: nếu manifest ghim **tag** thay vì digest, `git revert` có thể không khôi phục đúng artifact (tag có thể đã bị trỏ sang image khác). Đây là lý do production nên ghim digest — rollback bằng Git chỉ chính xác khi artifact là bất biến.

Với Helm trong GitOps: nếu ArgoCD render chart, không có release Helm để rollback — lịch sử nằm ở Git và `argocd app history`. Nếu Flux dùng `HelmRelease`, helm-controller tạo release thật và có `upgrade.remediation` (retry, rollback khi fail) — nhưng Git vẫn là nguồn chân lý, nên `helm rollback` tay sẽ sớm bị reconcile lại.

### Migration database an toàn khi rollback {#migration-database-an-toan}

Đây là phần khó nhất và cũng là phần phân biệt mid với senior. Quy tắc vàng: **schema thay đổi trước, code thay đổi sau, và không bao giờ xóa trong cùng release với thay đổi code** — mẫu expand/contract:

1. **Expand**: thêm cột/bảng/index mới (nullable, có default; index tạo `CONCURRENTLY` trên Postgres) — deploy schema, chưa ai dùng.
2. **Dual-write / dual-read**: code mới ghi cả chỗ cũ và chỗ mới, đọc ưu tiên chỗ mới với fallback.
3. **Backfill**: job nền chuyển dữ liệu, chạy được nhiều lần (idempotent), có checkpoint.
4. **Switch**: code mới chỉ đọc/ghi chỗ mới; deploy và quan sát.
5. **Contract**: ở release sau (khi chắc chắn không còn version cũ chạy), mới xóa cột/bảng cũ.

Vì sao phải vậy: trong rolling update hoặc canary, **hai version code cùng chạy**. Nếu release N xóa cột, pod của release N-1 vẫn đang chạy sẽ crash. Migration vì thế phải đảm bảo cả N-1 và N chạy được trên cùng schema. Với blue-green cũng không khác: lúc switch, green chạy schema mới, nhưng nếu cần rollback về blue thì schema mới phải tương thích ngược.

Thực hành:

- Chạy migration bằng Job gắn hook `pre-upgrade` (Helm) hoặc `PreSync` (ArgoCD), idempotent, có bảng `schema_migrations` để biết version hiện tại; không chạy migration tự động trong entrypoint của app (nhiều pod chạy đồng thời sẽ đua nhau).
- Migration phải **rollback được hoặc không cần rollback**: additive thì chỉ cần bỏ qua; destructive thì bắt buộc là bước riêng sau khi version cũ đã biến mất.
- Kịch bản không thể rollback (drop bảng, chuyển đổi dữ liệu một chiều): chấp nhận "roll forward", chuẩn bị backup/restore plan, và coi đó là thay đổi cần bảo vệ bằng feature flag + canary kỹ.
- Đo thời gian migration trên dữ liệu cỡ production, không phải trên DB dev vài nghìn dòng. Một `ALTER TABLE` khóa bảng 20 phút là sự cố lớn hơn cả lỗi code.

## Quản lý secret trong GitOps {#quan-ly-secret-trong-gitops}

Git không phải vault, và base64 không phải mã hóa. Nhưng GitOps lại đòi mọi thứ nằm trong Git — nên secret là bài toán trung tâm, và cũng là câu hỏi phỏng vấn rất hay gặp. Có hai hướng lớn:

- **Mã hóa để commit được**: ciphertext nằm trong Git, chỉ cluster đích (hoặc key được cấp) giải mã được — Sealed Secrets, SOPS + age/KMS.
- **Không đưa vào Git**: secret ở một secret manager, cluster đồng bộ hoặc mount về — External Secrets Operator, Secrets Store CSI, Vault Agent.

Chương 9 đã giới thiệu bức tranh tổng thể về secret trong Kubernetes; ở đây ta tập trung vào khía cạnh GitOps.

### Sealed Secrets {#sealed-secrets}

Sealed Secrets (Bitnami) gồm một controller trong cluster và CLI `kubeseal`. Controller sinh cặp khóa bất đối xứng và giữ private key trong Secret ở `kube-system`; bạn dùng public key để mã hóa **một chiều** secret thành CRD `SealedSecret`, commit file đó, controller giải mã thành `Secret` bình thường trong namespace đích.

```bash
# Tạo secret thường rồi seal (chưa apply gì lên cluster)
kubectl create secret generic demo-db --namespace demo --from-literal=password='S3cr3t!' --dry-run=client -o yaml > secret-plain.yaml
kubeseal --format yaml < secret-plain.yaml > sealed-db.yaml
rm secret-plain.yaml
kubectl apply -f sealed-db.yaml     # hoặc commit vào Git và để ArgoCD/Flux apply
```

Ba scope của SealedSecret cần nắm: mặc định (`strict`) gắn chặt với **cả tên và namespace** của Secret — đổi tên hoặc chuyển namespace là không giải mã được; `sealedsecrets.bitnami.com/namespace-wide: "true"` cho phép đổi tên trong cùng namespace; `sealedsecrets.bitnami.com/cluster-wide: "true"` cho phép dùng ở mọi namespace (tiện nhưng mở rộng phạm vi, chỉ nên dùng cho secret hạ tầng rất phổ biến). Điều này có nghĩa: muốn dùng cùng một secret ở cluster khác, bạn phải seal lại (hoặc re-encrypt) bằng public key của cluster đó.

Vận hành cần nhớ: controller tự rotate sealing key theo chu kỳ (mặc định 30 ngày) nhưng **vẫn giữ key cũ để giải mã** secret đã tạo; do đó **backup và bảo vệ private key** là nhiệm vụ sống còn — mất key nghĩa là toàn bộ SealedSecret trong Git vô dụng. Hãy backup ngay sau khi cài:

```bash
kubectl -n kube-system get secret -l sealedsecrets.bitnami.com/sealed-secrets-key -o yaml > sealed-secrets-key.yaml
```

rồi cất file này ở nơi an toàn (không commit lên Git). Ưu điểm của Sealed Secrets: không cần thêm hệ thống ngoài, thao tác đơn giản, hoạt động offline. Hạn chế: gắn với một cluster/key, không phù hợp khi cần dùng cùng secret ở nhiều cluster độc lập; secret dài (file lớn, certificate) cần chú ý giới hạn kích thước.

### SOPS + age/KMS {#sops-age-kms}

SOPS (Mozilla) mã hóa **giá trị** trong file YAML/JSON/env nhưng giữ nguyên key và cấu trúc, nên `git diff` vẫn đọc được cái gì thay đổi. Bạn chọn backend khóa: `age` (đơn giản, phù hợp on-prem/lab), GPG, hoặc KMS của cloud (AWS KMS, GCP KMS, Azure Key Vault). Quy tắc mã hóa khai báo trong `.sops.yaml`:

```yaml
creation_rules:
  - path_regex: secrets/.*\.yaml$
    encrypted_regex: "^(data|stringData)$"   # chỉ mã hóa phần value của secret
    age: age1qyqszqgpqyqszqgpqyqszqgpqyqszqgp...
```

```bash
sops -e -i secrets/demo-db.yaml         # mã hóa tại chỗ, file an toàn để commit
sops -d secrets/demo-db.yaml            # giải mã khi cần xem
sops updatekeys secrets/demo-db.yaml    # thêm/xoay người nhận
```

Khi đã có ciphertext trong Git, câu hỏi là **ai giải mã**. Với Flux, việc này native: private key (age) được cất trong một Secret của `flux-system`, và Kustomization khai báo:

```yaml
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: apps
  namespace: flux-system
spec:
  interval: 10m
  sourceRef:
    kind: GitRepository
    name: flux-system
  path: ./apps/prod
  prune: true
  decryption:
    provider: sops
    secretRef:
      name: sops-age
```

Với ArgoCD, repo-server không tự giải mã SOPS. Các cách thường dùng: cài plugin (ksops/`argocd-vault-plugin`) qua sidecar, hoặc dùng ESO để lấy secret từ manager, hoặc giải mã ở CI rồi apply (cách này làm mất tính "Git là nguồn chân lý" nên chỉ dùng như giải pháp tình thế). Với KMS, key không nằm trong cluster — cloud KMS thực hiện giải mã và mọi lần dùng đều có audit, đổi lại bạn phụ thuộc cloud và cần cấp quyền cho controller.

### External Secrets Operator {#external-secrets-operator}

ESO đi theo hướng ngược lại: **không có ciphertext trong Git**. Bạn khai báo *ý định* (lấy secret nào, từ đâu, refresh bao lâu), còn giá trị thật nằm ở Vault/AWS Secrets Manager/GCP Secret Manager/Azure Key Vault:

```yaml
apiVersion: external-secrets.io/v1
kind: SecretStore
metadata:
  name: vault-backend
  namespace: demo
spec:
  provider:
    vault:
      server: https://vault.vault.svc:8200
      path: kv
      auth:
        kubernetes:
          mountPath: kubernetes
          role: demo
---
apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: demo-db
  namespace: demo
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: vault-backend
    kind: SecretStore
  target:
    name: demo-db          # tên Secret được tạo trong Kubernetes
  data:
    - secretKey: password
      remoteRef:
        key: prod/demo/db
        property: password
```

Ưu điểm: một nguồn chân lý cho secret ở mọi môi trường, rotation tập trung (đổi ở Vault, ESO tự đồng bộ theo `refreshInterval`), audit đầy đủ ở secret manager, không cần quản lý key mã hóa trong Git. Nhược điểm: cluster phải truy cập được manager và xác thực được (Kubernetes auth, IRSA...), bootstrap cluster mới phụ thuộc hệ thống ngoài, và secret sau khi đồng bộ **vẫn nằm trong etcd** — vì vậy vẫn cần RBAC chặt, encryption at rest, và hạn chế quyền đọc của workload như đã bàn ở chương 9. ESO cũng hỗ trợ `PushSecret` cho chiều ngược lại (đẩy secret từ cluster lên manager) và `ClusterSecretStore` cho phạm vi toàn cluster.

### So sánh ba hướng tiếp cận {#so-sanh-ba-huong-tiep-can}

| Tiêu chí | Sealed Secrets | SOPS + age/KMS | External Secrets Operator |
|---|---|---|---|
| Secret nằm ở đâu | Ciphertext trong Git, plaintext trong etcd sau giải mã | Ciphertext trong Git, plaintext trong etcd sau giải mã | Nguồn thật ở manager; bản sao trong etcd |
| Ai giải mã | Controller trong cluster (private key) | Flux native; ArgoCD cần plugin/ESO/CI | Controller ESO gọi API manager |
| Rotation secret | Seal lại và commit | Sửa file, `sops -e`, commit | Đổi ở manager; ESO tự đồng bộ |
| Rotation/đổi key | Có, phải backup private key kỹ | `sops updatekeys`; KMS không cần giữ key | Không áp dụng (không có key trong Git) |
| Bootstrap cluster mới | Cần đúng cặp khóa của cluster đó | Cần private key (age) trong cluster | Cần truy cập manager + cấu hình auth |
| Hỗ trợ ArgoCD | Tốt (không cần plugin) | Qua ksops/AVP | Tốt (ESO sinh Secret) |
| Hỗ trợ Flux | Tốt | Native (`spec.decryption`) | Tốt |
| Độ phức tạp | Thấp | Trung bình | Cao (thêm hệ thống ngoài) |
| Phù hợp | Đội nhỏ, một vài cluster, muốn đơn giản | Nhiều môi trường, muốn diff được, cần KMS audit | Tổ chức lớn, đã có Vault/KMS, cần rotation tập trung |

Cách tôi thường khuyên: bắt đầu bằng **SOPS + age** nếu bạn cần kiểm soát hoàn toàn và làm việc với nhiều cluster (Flux rất mượt, ArgoCD cần thêm plugin); chọn **Sealed Secrets** nếu muốn setup nhanh, một cluster, không muốn thêm quy trình quản lý key phức tạp; chuyển sang **ESO/Vault** khi tổ chức đã có secret manager và yêu cầu compliance về rotation/audit. Điều không được phép chọn: để plaintext secret trong Git, dù chỉ một lần cho "tiện test".

## Câu hỏi phỏng vấn thường gặp {#interview-questions}

**1. GitOps là gì? Bốn nguyên lý của nó và vì sao pull model an toàn hơn push model?**

GitOps là cách vận hành hệ thống trong đó Git là nguồn chân lý duy nhất cho trạng thái mong muốn, và một agent chạy trong cluster liên tục đối soát để đưa trạng thái thực về đúng như trong Git. Bốn nguyên lý (OpenGitOps): khai báo (declarative), có version và bất biến, được kéo về tự động (pulled automatically), và được đối soát liên tục (continuously reconciled). Pull model an toàn hơn vì cluster không mở đường vào từ ngoài: CI không giữ kubeconfig của production, credential chỉ nằm trong cluster với quyền đọc Git; đồng thời agent phát hiện và sửa drift liên tục, trong khi push model chỉ tác động đúng lúc pipeline chạy.

**2. Kể tên các thành phần của ArgoCD và vai trò của từng thành phần?**

`argocd-server` phục vụ API/UI và session; `argocd-repo-server` clone repo, cache và render manifest (gọi `helm template`, `kustomize build`); `argocd-application-controller` so sánh desired state với live state, thực thi sync và đánh giá health; `argocd-applicationset-controller` sinh Application từ generator; `argocd-dex-server` làm SSO; `argocd-redis` chỉ là cache; `argocd-notifications-controller` gửi thông báo. Khi triển khai HA, repo-server và server scale ngang, còn application-controller dùng StatefulSet và có thể sharding theo cluster.

**3. Phân biệt auto-sync, selfHeal và prune. Khi nào cân nhắc tắt prune?**

Auto-sync nghĩa là tự sync khi phát hiện OutOfSync thay vì chờ người bấm nút. SelfHeal là tự đưa resource bị sửa ngoài Git về đúng giá trị trong Git. Prune là xóa resource trên cluster khi nó không còn trong Git. Nên cân nhắc tắt prune (hoặc đặt `Prune=false` cho từng resource) với dữ liệu/stateful workload, CRD, namespace dùng chung, và namespace nhạy cảm như `kube-system` — vì một thao tác xóa file trong Git có thể xóa tài nguyên thật ngoài ý muốn.

**4. App of apps và ApplicationSet khác nhau thế nào? Chọn cái nào cho 50 service × 3 môi trường?**

App of apps dùng một Application gốc trỏ tới thư mục chứa các Application con — dễ hiểu, không cần CRD mới nhưng khó debug khi lồng sâu và thứ tự sync không chặt. ApplicationSet dùng generator (list, git, cluster, matrix, merge, pullRequest) để sinh Application theo dữ liệu, hỗ trợ Go template và `rollingSync` để sync theo nhóm. Với 50 service × 3 môi trường, ApplicationSet với git directory generator (hoặc matrix của cluster × app) là lựa chọn đúng: viết một template, thêm service mới chỉ là thêm thư mục trong Git.

**5. `helm upgrade` hoạt động thế nào? Vì sao `helm rollback` không "quay ngược thời gian"?**

`helm upgrade` render manifest mới rồi tính patch theo cơ chế three-way merge giữa manifest cũ của release, manifest mới và trạng thái live — nhờ đó field do HPA hay controller khác quản lý không bị ghi đè. `helm rollback demo 3` không xóa hay tua lại lịch sử: nó tạo một revision mới với nội dung của revision 3, nên bạn vẫn rollback tiếp được về revision 5. Rollback của Helm không khôi phục CRD trong `crds/`, không dọn resource do hook tạo, không hoàn tác thứ đã `kubectl apply` tay, và không khôi phục dữ liệu — nó chỉ khôi phục manifest.

**6. Helm 4 có gì ảnh hưởng tới pipeline và GitOps?**

Helm 4 mặc định dùng server-side apply cho release mới; các release tạo bởi Helm 3 vẫn giữ client-side apply khi upgrade trừ khi truyền `--server-side`. Điều này quan trọng khi nhiều field manager cùng quản lý một resource (Helm, ArgoCD, operator) vì có thể phát sinh conflict field ownership. Ngoài ra `--atomic` đổi tên thành `--rollback-on-failure`, `--force` thành `--force-replace`; `--wait` dùng kstatus nên service account cần quyền `watch`; post-renderer phải là plugin; `helm registry login` chỉ nhận domain. Chart `apiVersion: v2` vẫn tương thích, nhưng Helm 3 đã ngừng phát triển và hết hỗ trợ bảo mật đầu năm 2027.

**7. Khi nào chọn Helm, khi nào chọn Kustomize?**

Helm phù hợp khi bạn cần phân phối package có version cho nhiều người dùng (chart nội bộ, third-party như ingress-nginx, kube-prometheus-stack), cần tham số hóa phức tạp, hook và vòng đời release. Kustomize phù hợp khi manifest do đội tự viết, khác biệt giữa các môi trường ít, muốn giữ YAML gốc dễ đọc và diff sát manifest cuối. Thực tế nhiều đội dùng cả hai: Helm cho thành phần third-party, Kustomize cho app nội bộ, có thể kết hợp bằng `helmCharts` generator hoặc đặt `HelmRelease` trong `Kustomization` của Flux.

**8. Ngoài `maxSurge`/`maxUnavailable`, cần gì để rolling update thực sự zero-downtime?**

Cần readiness probe phản ánh đúng khả năng phục vụ (không chỉ process còn sống), graceful shutdown với `preStop` và `terminationGracePeriodSeconds` đủ dài để rời endpoint và hoàn tất request đang bay, `minReadySeconds` để tránh promote quá sớm, PDB để bảo vệ khi node bị drain, và migration database tương thích ngược để hai version cùng chạy được. Thiếu bất kỳ mảnh nào, bạn vẫn có thể gặp 502 trong lúc rollout dù `maxUnavailable` bằng 0.

**9. Blue-green và canary — chọn theo tiêu chí nào?**

Blue-green phù hợp khi cần kiểm thử kỹ trước khi mở traffic, muốn rollback tức thời bằng cách đổi selector, và chấp nhận chi phí tài nguyên gấp đôi trong lúc chuyển. Canary phù hợp khi rủi ro cần giới hạn theo phần trăm người dùng, có metric đủ tin cậy để tự động quyết định promote/abort, và muốn giảm blast radius. Cả hai đều đòi hỏi schema database tương thích nhiều version; blue-green thêm khó khăn với kết nối dài, còn canary cần traffic routing và observability tốt.

**10. Sự cố lúc 2 giờ sáng, bản mới vừa deploy qua GitOps đang lỗi. Bạn rollback thế nào?**

Trước tiên đánh giá tác động và chọn cách nhanh nhất để giảm thiểu: nếu auto-sync đang bật và cần khôi phục ngay, có thể tắt auto-sync tạm thời rồi `git revert` hoặc thao tác tay có kiểm soát; nếu có thể chờ một vòng sync, `git revert` commit lỗi là cách sạch nhất. Trong lúc xử lý phải giữ nguyên tắc: mọi thao tác tay đều phải được đưa lại vào Git ngay sau đó, và kiểm tra drift về 0. Với Helm/ArgoCD, nhớ rằng `argocd app rollback` hay `helm rollback` chỉ là tạm thời nếu Git vẫn đang trỏ vào trạng thái lỗi. Sau sự cố, cập nhật runbook và bổ sung kiểm tra để lần sau rollback nhanh hơn.

**11. Làm sao deploy kèm migration database mà vẫn rollback được?**

Dùng mẫu expand/contract, chia migration thành nhiều release: thêm schema mới (additive) trước, dual-write/backfill, chuyển reads, và chỉ xóa cột/bảng cũ ở release sau khi không còn version cũ chạy. Migration chạy bằng Job gắn hook `pre-upgrade`/`PreSync`, idempotent, có bảng version. Nhờ đó cả version N-1 và N đều chạy được trên cùng schema, rollback code không cần rollback schema. Với thay đổi một chiều không thể rollback, phải chấp nhận roll forward, bảo vệ bằng feature flag và canary, và chuẩn bị backup/restore plan.

**12. So sánh Sealed Secrets, SOPS + age và External Secrets Operator. Khi nào dùng cái nào?**

Sealed Secrets mã hóa một chiều bằng public key của controller trong cluster; ciphertext commit được, giải mã tự động, setup nhanh nhưng gắn với một cluster/key và phải backup private key cẩn thận. SOPS + age mã hóa value trong file, giữ key/cấu trúc để `git diff` đọc được; Flux hỗ trợ native, ArgoCD cần plugin hoặc ESO; phù hợp khi nhiều cluster/môi trường và muốn kiểm soát hoàn toàn, có thể dùng KMS để có audit. ESO không đưa ciphertext vào Git mà đồng bộ từ Vault/KMS/secret manager theo `refreshInterval`, rotation tập trung; phù hợp tổ chức lớn đã có secret manager, nhưng secret vẫn nằm trong etcd nên vẫn cần RBAC và encryption at rest.

## Các điểm chính {#key-points}

- GitOps = Git là nguồn chân lý + agent pull + đối soát liên tục. Bốn nguyên lý: declarative, versioned/immutable, pulled automatically, continuously reconciled; "CI chạy `kubectl apply`" chưa phải GitOps.
- Pull model an toàn hơn push vì credential cluster không rời khỏi cluster và drift được phát hiện liên tục; trade-off là vòng lặp chậm hơn, repo thành critical path, và secret cần chiến lược riêng.
- ArgoCD gồm server (API/UI), repo-server (clone + render), application-controller (diff + sync + health), applicationset-controller, dex, redis, notifications; `install.yaml` cấp cluster-admin nên phải giới hạn bằng AppProject/RBAC.
- `syncPolicy.automated` có ba phần tách biệt: auto-sync, selfHeal, prune; prune là nguy hiểm nhất và nên cân nhắc theo từng resource/môi trường.
- ArgoCD map hook Helm (`pre-install`/`pre-upgrade` → PreSync, `post-*` → PostSync) nhưng không phân biệt install với upgrade, và không hỗ trợ `pre-rollback`/`post-rollback`/`test-*`; hook phải idempotent.
- ApplicationSet với generator (git, cluster, matrix, pullRequest) thay thế app of apps khi số app/môi trường tăng; `rollingSync` hỗ trợ rollout nhiều cluster theo nhóm.
- So với Flux: ArgoCD có UI, quản lý app tập trung; Flux là bộ controller tách rời, tạo release Helm thật, giải mã SOPS native, multi-tenancy bằng ServiceAccount impersonation. Cả hai đều là CNCF.
- Repo GitOps nên tách config khỏi source code, dùng directory-based promotion (tránh nhánh dài), overlay chỉ chứa phần khác biệt, ghim image bất biến (digest ở prod), validate manifest trong CI, và có quy trình break-glass viết sẵn.
- Helm: `version` là version chart, `appVersion` là version app; upgrade dùng three-way merge; `helm rollback` tạo revision mới chứ không xóa lịch sử; hook không thuộc release và không bị `helm uninstall` xóa; `--rollback-on-failure` (tên cũ `--atomic`) để tự rollback.
- Helm 4 dùng server-side apply mặc định cho install mới, đổi tên `--atomic`/`--force`, `--wait` dùng kstatus (cần quyền `watch`); chart v2 vẫn tương thích, Helm 3 hết hỗ trợ bảo mật trong 2027.
- Rolling update zero-downtime cần readiness probe, `preStop`/graceful shutdown, `minReadySeconds`, PDB và migration tương thích ngược; `maxUnavailable: 0` + `maxSurge: 1` là cấu hình an toàn cho production.
- Blue-green rollback cực nhanh nhưng tốn 2x tài nguyên; canary giới hạn rủi ro theo phần trăm và cần traffic routing + analysis (Argo Rollouts, Flagger); shadow traffic dùng để kiểm chứng, không thay thế canary.
- Trong GitOps, rollback = `git revert`; `argocd app rollback` chỉ tạm thời nếu Git vẫn trỏ vào commit lỗi; ghim digest để rollback bằng Git khôi phục đúng artifact.
- Migration database theo expand/contract để version N-1 và N cùng chạy được trên một schema; không xóa cột/bảng trong cùng release với thay đổi code.
- Secret trong GitOps: Sealed Secrets (một cluster/key, setup nhanh), SOPS + age/KMS (nhiều cluster, Flux native), ESO (không có ciphertext trong Git, rotation tập trung). Không bao giờ commit plaintext secret.

**1. Về mô hình GitOps, những phát biểu nào đúng? (Chọn tất cả đáp án đúng)**

**A)** Trong pull model, agent trong cluster chủ động kéo desired state từ Git; credential đọc repo nằm trong cluster nên pipeline CI không cần quyền ghi vào cluster.  
**B)** Mọi thay đổi trạng thái mong muốn đều đi qua commit/PR, nhờ đó có audit trail đầy đủ và có thể rollback bằng `git revert`.  
**C)** GitOps yêu cầu cluster truy cập được Git, nhưng việc đối soát liên tục giữa Git và cluster chỉ là tính năng tùy chọn của ArgoCD/Flux, không thuộc bốn nguyên lý của GitOps.  
**D)** Push model an toàn hơn pull model vì CI giữ credential ghi vào cluster nhưng có thể thu hồi ngay khi pipeline kết thúc.  




**2. Một Application được tạo với `syncPolicy.automated` gồm cả `selfHeal: true` và `prune: true`, đang ở trạng thái Synced/Healthy. Một operator chạy `kubectl edit deployment` để tăng replicas, đồng thời một dev khác xóa Deployment tương ứng khỏi Git. Sau vòng đối soát tiếp theo, hành vi nào đúng?**

**A)** ArgoCD giữ nguyên replicas mới vì thay đổi đó không đến từ Git; Deployment vẫn còn vì `prune` mặc định tắt.  
**B)** ArgoCD báo OutOfSync nhưng không tự làm gì cho tới khi có người bấm `argocd app sync`.  
**C)** ArgoCD đưa replicas về giá trị trong Git (self-heal) và xóa Deployment trên cluster vì resource không còn trong Git (prune).  
**D)** ArgoCD xóa Deployment trước rồi mới đối soát replicas trong cùng một vòng, nên kết quả phụ thuộc vào thứ tự xử lý.  




**3. Thành phần nào của ArgoCD chịu trách nhiệm clone repository và render manifest (gọi `helm template`, `kustomize build`) trước khi đối soát?**

**A)** `argocd-repo-server`.  
**B)** `argocd-application-controller`.  
**C)** `argocd-dex-server`.  
**D)** `argocd-server`.  




**4. Release `web` đang ở revision 5 và bạn chạy `helm rollback web 3`. Kết quả nào đúng?**

**A)** Helm xóa revision 4 và 5 khỏi history, đưa cluster về đúng trạng thái của revision 3.  
**B)** Helm chỉ đổi tag image trong values về bản cũ nhưng không re-apply manifest.  
**C)** Lệnh từ chối chạy vì release không được tạo bằng `--rollback-on-failure`; rollback chỉ hoạt động khi có flag này.  
**D)** Helm tạo revision 6 với nội dung của revision 3; history vẫn giữ 4 và 5, và bạn có thể rollback tiếp về revision 5.  




**5. Về hook của Helm, những phát biểu nào đúng? (Chọn tất cả đáp án đúng)**

**A)** Hook có thể điều khiển thứ tự bằng `helm.sh/hook-weight`; `hook-delete-policy` mặc định là `before-hook-creation`.  
**B)** Resource do hook tạo ra không được Helm quản lý như tài nguyên của release, nên `helm uninstall` không tự xóa chúng.  
**C)** Khi ArgoCD render chart, `pre-upgrade` được map thành hook `PreSync` và ArgoCD phân biệt được lần sync đầu tiên (install) với các lần upgrade nên `pre-install` không bao giờ chạy cùng `pre-upgrade`.  
**D)** Hook là một phần của release, được ghi vào cùng revision và tự động bị xóa khi release rollback về revision trước.  




**6. Về Helm và Kustomize, những phát biểu nào đúng? (Chọn tất cả đáp án đúng)**

**A)** Kustomize là template-free: dùng overlay và patch trên manifest YAML gốc; Helm dùng Go template với điều kiện, vòng lặp và hàm.  
**B)** Kustomize có sẵn trong kubectl (`kubectl kustomize`, `kubectl apply -k`) và render được offline, còn Helm cần `helm template` để render offline.  
**C)** Vì không đóng gói package có version, Kustomize không thể dùng cho môi trường production.  
**D)** Không thể kết hợp Helm và Kustomize trong cùng một luồng deploy: phải chọn một trong hai cho toàn bộ hệ thống.  




**7. Bạn cần deploy không downtime và yêu cầu mọi pod mới phải Ready trước khi pod cũ bị xóa, nhưng chấp nhận thêm tối đa một pod trong lúc rollout. Cấu hình nào đúng nhất?**

**A)** `strategy.type: RollingUpdate` với `maxUnavailable: 0`, `maxSurge: 1`, kèm readinessProbe đúng và `preStop`/graceful shutdown.  
**B)** `strategy.type: Recreate` vì đảm bảo không bao giờ có hai version chạy song song.  
**C)** `strategy.type: RollingUpdate` với `maxSurge: 0`, `maxUnavailable: 100%` để rollout nhanh nhất.  
**D)** `strategy.type: RollingUpdate` mặc định (25%/25%) và không cần readinessProbe vì Kubernetes tự biết pod đã sẵn sàng.  




**8. Bạn muốn kiểm chứng bản mới với 5% lưu lượng thật và để hệ thống tự rollback nếu tỉ lệ lỗi vượt ngưỡng, không chỉ dựa vào việc đổi Service selector. Giải pháp nào phù hợp nhất?**

**A)** Recreate kèm test kỹ trên staging trước khi deploy production.  
**B)** Blue-green: deploy green, chuyển 100% traffic, theo dõi rồi đổi selector lại nếu phát hiện lỗi.  
**C)** Argo Rollouts canary với `trafficRouting` (Istio/NGINX) và `AnalysisTemplate` truy vấn Prometheus để tự abort/rollback.  
**D)** StatefulSet với `partition` để chia lưu lượng theo thứ tự pod.  




**9. Application chạy với ArgoCD auto-sync + selfHeal. Trong sự cố, bạn dùng `argocd app rollback` về revision cũ nhưng vài phút sau trạng thái lỗi quay lại. Nguyên nhân và cách xử lý đúng nhất là gì?**

**A)** Vì application-controller vẫn đối chiếu với `targetRevision` trong Git (đang chứa commit lỗi), rollback thủ công chỉ là tạm thời; cách xử lý đúng là revert commit trên Git, hoặc tắt auto-sync trong lúc xử lý khẩn rồi bật lại.  
**B)** Vì cache của repo-server chưa được xóa; cần restart `argocd-repo-server` rồi rollback lại.  
**C)** Vì `prune` đang tắt; cần bật `prune: true` thì rollback mới giữ được.  
**D)** Vì Application thiếu `syncPolicy.automated.allowEmpty`; cần đặt thành `true`.  




**10. Về quản lý secret trong GitOps, những phát biểu nào đúng? (Chọn tất cả đáp án đúng)**

**A)** SealedSecret mã hóa một chiều bằng public key của controller; ciphertext commit được vào Git; mặc định secret gắn với cả tên và namespace nên đổi tên là không giải mã được.  
**B)** SOPS + age mã hóa value trong file YAML theo `creation_rules`; Flux giải mã native qua `spec.decryption`, còn ArgoCD cần plugin (ksops/AVP) hoặc ESO.  
**C)** Khi secret đã được mã hóa trong Git thì không cần bật encryption at rest cho etcd và không cần hạn chế RBAC đọc Secret, vì secret chỉ tồn tại ở dạng mã hóa.  
**D)** External Secrets Operator đồng bộ secret từ Vault/AWS Secrets Manager vào Secret của Kubernetes theo `refreshInterval`; secret vẫn nằm trong etcd nên vẫn cần RBAC và encryption at rest.
